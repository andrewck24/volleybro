# PR / CL size norms and large-refactor practice — research notes (2026-09-17)

## Conclusion

Every mature organization surveyed bounds change scope by a *soft* norm ("one self-contained change", ~100–300 LOC), never by a hard rejecting cap, and every one of them explicitly exempts or specially handles large refactors and machine-generated changes. Large migrations are done incrementally (Strangler Fig, Branch by Abstraction, expand/contract, Google LSC shards, stacked diffs), and the "reviewers lose the global view" problem is solved by moving the global review *up front* (design doc / LSC proposal approved before the shards are sent) and by tooling that groups the shards (stacks, hashtags/tracking issue, global approvers). Nobody found treats the per-PR size limit as a reason to do a big-bang instead.

## Q2 — Migration practice: incremental, not big-bang

- **Fowler, Refactoring**: "By doing them in small steps you reduce the risk of introducing errors." Small behavior-preserving transformations whose "cumulative effect ... is quite significant". https://martinfowler.com/books/refactoring.html
- **Fowler, Strangler Fig**: "the reduced risk and earlier value from the gradual approach outweigh its costs." Rewrites fail because "users can't wait for new features". https://martinfowler.com/bliki/StranglerFigApplication.html
- **Fowler, Branch by Abstraction**: "a large-scale change ... in gradual way that allows you to release the system regularly"; "look for as many ways as possible to make changes gradually." https://martinfowler.com/bliki/BranchByAbstraction.html
- **Fowler, Parallel Change (expand/contract)**: three phases expand → migrate → contract; "prevents you from spreading breakage across the entire codebase all at once"; releasable in any phase. https://martinfowler.com/bliki/ParallelChange.html
- **Fowler/Beck, Preparatory Refactoring**: Beck: "make the change easy, then make the easy change" (tweet 2012). Refactoring hat vs feature hat kept separate. https://martinfowler.com/articles/preparatory-refactoring-example.html
- **Fowler site, Patterns of Legacy Displacement** (Cartwright, Horn, Lewis, 2024): waterfall "big bang" programmes "meant abandoning the majority of the work"; Feature Parity is a key failure factor; patterns exist to "break the problem into smaller parts". https://martinfowler.com/articles/patterns-legacy-displacement/
- **Kent Beck, Tidy First? / "Structure & Behavior"**: "Changes to the structure of the system are fundamentally different from changes to the behavior"; structure changes are reversible → "pass them on through"; tidyings go in their own PRs (secondary summaries: https://henrikwarne.com/2024/01/10/tidy-first/). Primary: https://newsletter.kentbeck.com/p/structure-and-behavior
- **Google LSC (SWE book ch.22)**: LSC cannot be atomic (VCS scale, merge conflicts, test fan-out, review burden). Process: author writes proposal doc → LSC committee (~12 people) approves → Rosie shards by project/OWNERS → each shard tested via TAP and reviewed/submitted independently. Review: "only send changes to local owners for which their review is required for context, not just approval permissions"; the rest go to "a 'global approver'" who uses "pattern-based tooling to review each of the changes and automatically approve ones that meet their expectations". The whole-picture judgment lives in the proposal doc and the global approver, not in each shard's reviewer.
- **Chromium LSC doc**: same shape at a smaller scale — LSC doc + domain approval + lsc-review@ before any CL; CLs share a hashtag; local reviewers "read the description and CL email carefully, including any linked supporting documentation".
- **Meta stacked diffs / GitHub Stacked PRs**: large change expressed as an ordered chain of small commits, each reviewed independently, the chain visible as a set in the tool.

## Direct answer: does a hard per-PR cap fragment refactors so reviewers lose the global view?

Yes if the cap is the *only* mechanism — the SWE book itself concedes small-change review is "difficult to reconcile with the introduction of major new features". Standard mitigation, consistent across Google, Chromium, Meta, Fowler:

1. **Approve the whole up front**: design doc / LSC proposal / RFC / ADR reviewed and approved before the first shard is sent (Google LSC committee, Chromium lsc-review@). The global-view review happens once, on the plan, not N times on the shards.
2. **Link every shard to the plan**: tracking issue / epic / hashtag, with the PR description pointing at the approved doc so the local reviewer's job is "does this shard match the plan", not "is the plan right".
3. **Keep shards behavior-preserving and separately typed**: Beck/Fowler — structure changes in their own PRs; expand/contract keeps the system releasable between steps; feature flags or Branch by Abstraction hide partial migration.
4. **Review the set as a set when needed**: stacked diffs / Stacked PRs let reviewers walk the chain in order; Google uses a global approver who sees all shards.
5. **Exempt mechanical changes**: Google explicitly allows large tool-generated CLs; the size norm is for hand-written, judgment-bearing changes.

So the principled position is: the size norm is a *soft* target (~100–300 LOC, one self-contained change) with a named escape hatch — a pre-approved migration document plus a tracking issue — rather than a hard cap that forces either fragmentation without context or a big-bang PR.

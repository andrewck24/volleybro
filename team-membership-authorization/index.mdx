<TLDR>
  程式裡的「成員」包含了還沒接受邀請的人，管理員可以把擁有者降級或刪除，還有三個讀取端點根本不問呼叫者是誰。本
  Change
  讓「成員」只指已加入的球員，讓角色只屬於受邀者與成員，保護擁有者，並讓隊伍資訊、名單與單一球員資料在隱私設定上線前只給成員讀取。
</TLDR>

## Context

規則是：在隱私設定上線前，隊伍資訊、隊伍名單與成員資訊只給成員查看，受邀者不是成員。詞彙依 `CONTEXT.md`：未連結球員、受邀者、成員；角色由高到低為擁有者、管理員、一般成員。

### 讀取端點與授權的缺口

| #   | 位置                                                         | 誰讀得到或做得到                                                   | 影響                                         |
| --- | ------------------------------------------------------------ | ------------------------------------------------------------------ | -------------------------------------------- |
| 1   | `GET /api/teams/{teamId}`                                    | 任何人，不需登入：route 沒有 `withAuth`，`GetTeamUseCase` 沒有授權 | 隊名、`lineups`（含 player id）、stats       |
| 2   | `GET /api/players/{playerId}`                                | 任何登入者：route 忽略 `userId`，`GetPlayerUseCase` 沒有授權       | 單一球員的完整資料，含 `email`               |
| 3   | `GET /api/teams/{teamId}/players`                            | 任何登入者：route 忽略 `userId`，`GetTeamPlayersUseCase` 沒有授權  | 整隊名單，每筆含 `email`、`userId`、`role`   |
| 4   | `AuthorizationService.verifyTeamRole` 與 `verifyIsTeamAdmin` | 已連結帳號的受邀者：只看 `role`、不看 `status`                     | 通過全部成員與管理員檢查，包含寫入路徑       |
| 5   | `update-role`、`remove-player`                               | 任何管理員：只檢查呼叫者，不檢查目標                               | 可以把擁有者降為管理員或刪除，隊伍失去擁有者 |

第 4 項是「成員」這個詞本身的定義。`role` 無法分辨三種球員：`create-player` 建立未連結球員時一律寫入 `MEMBER`，離開隊伍、拒絕與取消邀請都不清除 `role`。先被邀請、之後才註冊的使用者，會在註冊時被連結 `userId` 而 `status` 仍是 `INVITED`；這樣的受邀者可以開賽、記錄 Rally、改陣容，被邀請為管理員者在接受前就能新增或刪除球員。`transfer-ownership` 以 `userId` 是否存在判斷新擁有者已加入，所以擁有權可以移轉給尚未接受邀請的人。

`GET /api/games` 與 `GET /api/games/{gameId}` 的 route 同樣沒有 `withAuth`，但它們的 use case 內有 `verifySession` 與 `verifyTeamRole`，只受第 4 項影響。

### 邀請與資料

- **邀請已註冊的使用者，對方永遠收不到。** `create-invitation` 只寫入 `email`，而受邀者的邀請清單以 `userId` 查詢，連結 `userId` 只在註冊時發生一次。
- **一位使用者在同一隊可能出現兩位球員。** `(teamId, userId)` 只有一般索引；一旦邀請時會連結帳號，對同一個人再發一次邀請就會產生第二位球員，而 `findByTeamIdAndUserId` 以 `findOne` 隨機取得其中一位。
- **production 有 32 份球員文件沒有 `status`。** 2026-02 的 unify-player 遷移曾對所有 player `$unset` status，2026-03 的 player-invitations 只加了 schema 預設值 `NONE`，沒有回填。當時的模型中離開隊伍會「清空 `userId`、保留 email」，所以其中只有 email 的文件可能是待處理的邀請，也可能是當年離隊的前成員。
- **`(teamId, email)` 的唯一索引很可能從未建立。** 宣告同時使用 `sparse` 與 `partialFilterExpression`，filter 內還用了 `$nin`，MongoDB 不接受這樣的宣告，而 Mongoose 自動建立索引失敗時不會報錯。
- **舊的權限檢查只看 `role`。** 任何在部署前為受邀者寫入 `userId` 的資料修正，都會讓他們在部署前的空窗取得權限。
- **`create-player` 帶 email 時建立的是帶 `email` 的未連結球員**，違反 `validatePlayerStatus`，也永遠不會被連結。

## Goals

- 「成員」在整個 repo 只有一個定義，且可以不經 mock 直接測試；角色只屬於受邀者與成員。
- 受邀者在接受邀請前通不過任何成員或管理員檢查；擁有者不能被他人降級或刪除。
- 非成員（含未登入）讀不到上表任何讀取端點的資料，進入隊伍頁面時看到錯誤狀態而不是崩潰。
- 邀請已註冊的使用者時，對方看得到邀請、看得到隊名，可以接受或拒絕。
- 一位使用者在同一隊至多一位球員，同隊不會對同一個 email 重複邀請，兩者都由資料庫保證。
- 本 Change 對既有資料的修正，在任何時刻都不讓任何人多出權限。（註冊時既有的 `linkUserToInvitations` 在舊程式碼下本來就會讓先被邀請、後註冊的受邀者通過檢查，這是本 Change 要修的現況。）
- 介面與文件的用詞與 `CONTEXT.md` 一致：擁有者不再稱為「隊長」，一般成員不再稱為「成員」，刪除球員不再稱為「移除成員」。

## Non-goals

- 不改變回應欄位的可見範圍。「email 只回傳給擁有者與管理員」屬於球員資訊頁會籍區塊的工作。
- 不新增「解除帳號連結」動作。它與會籍區塊的重做一起處理；本 Change 只把現有的刪除球員改名並套用授權規則。
- 不改變擁有者移轉的生效方式。移轉是否需要對方接受另案處理。
- 不實作隱私設定，也不提供「擁有者可以關閉管理員互相管理」的隊伍設定。本 Change 是隱私設定上線前的預設規則；隱私設定的 roadmap 列在 Archive 時加入 Features。
- 不拆出 Membership entity，不採用 better-auth organization plugin。理由在 D1。
- 不改名比賽紀錄中的「替補」按鈕與 `game.ts` 的 `Player`／`Team` 型別。它們屬於比賽紀錄詞彙的後續工作。

## Change boundaries

- **在內**：Player entity 的 union 型別、成員與角色判斷、repository 的縮窄、`AuthorizationService` 改為委派；`create-player`、`leave-team`、`reject-invitation`、`cancel-invitation` 依模型不再留下角色；`transfer-ownership` 的擁有者與目標檢查。
- **在內**：D3 的角色管理規則套用到 `update-role` 與刪除球員。
- **在內**：邀請時連結已註冊的帳號、邀請衝突檢查、`(teamId, userId)` 與 `(teamId, email)` 部分唯一索引；既有資料的兩階段腳本：部署前正規化、部署後連結帳號。
- **在內**：三個讀取端點的 use case 授權；受邀者球員清單帶上 `teamName`；`AcceptInvitationUseCase` 回傳 Player 讓 controller 不再經過 `GetPlayerUseCase`。
- **在內**：非成員進入隊伍頁面時的錯誤狀態，以及刪除成員時清除被刪除者的 `activeTeamId`。
- **在內**：介面文案與角色標籤依 `CONTEXT.md` 改正。
- **不在內**：`GET /api/users?email=` 以 email 反查使用者，歸在隱私設定主題。

## Capability impact

`team-management/membership` 取得三條約束：**成員是已加入的球員，受邀者與未連結球員都不是成員**；**一位使用者在同一隊至多一位球員**；**邀請已註冊的使用者時直接連結帳號**。

`team-management/roles` 取得兩條約束：**角色只屬於受邀者與成員**；**擁有者與管理員可以管理管理員以下的人，擁有者不能被他人降級或刪除，任何人都不能以自己為目標；擁有權只能透過移轉離開，離隊只能透過離開隊伍**。

## Design

<TLDR>
  型別說出每種球員有什麼，判斷與查詢分開。「誰是成員、角色夠不夠、能不能管這個人」是沒有
  I/O 的業務規則，放在 entity；「這個使用者在這隊是哪一位球員」要查資料庫，留在
  infrastructure；「查、判斷、不通過就丟錯」由 use case 呼叫 service
  完成。資料在部署前正規化、部署後才連結帳號，任何時刻都不會有人多出權限。
</TLDR>

## Adopted shape：三種球員

Player 仍是一份文件，欄位與現在相同；entity 的型別依 `status` 區分，每一種只帶自己成立的欄位。

```ts
type PlayerBase = {
  id: string;
  name: string;
  number?: number;
  position?: Position;
  teamId?: string;
  createdAt: Date;
  updatedAt: Date;
};

export type UnlinkedPlayer = PlayerBase & { status: PlayerStatus.NONE };

export type InvitedPlayer = PlayerBase & {
  status: PlayerStatus.INVITED;
  role: PlayerRole;
} & ({ userId: string; email?: never } | { email: string; userId?: never });

export type TeamMember = PlayerBase & {
  status: PlayerStatus.JOINED;
  userId: string;
  role: PlayerRole;
};

export type Player = UnlinkedPlayer | InvitedPlayer | TeamMember;
```

`isTeamMember` 是 type guard，只看 `status`；通過之後 `userId` 與 `role` 由型別保證存在，`hasTeamRole` 不需要 `player.role!`。repository 的 `toPlayer` 負責把資料庫文件縮窄成三者之一，不符合的文件拋出錯誤，而不是被 Mongoose 的預設值悄悄當成未連結球員。

一筆不符合模型的文件會讓整隊的 `findByTeamId` 與相關使用者的 `findByUserId` 讀取失敗，因為 repository 對整批文件逐一縮窄。所以模型收緊的那一刻，所有寫入路徑必須已經只寫出合法的文件，既有資料也必須已經正規化：寫入端的限縮與模型在同一個切片，正規化在部署之前完成。

| 動作                   | 之前                                  | 之後                                                     |
| ---------------------- | ------------------------------------- | -------------------------------------------------------- |
| 建立球員（不帶 email） | 未連結球員，`role` 預設 `MEMBER`      | 未連結球員，沒有角色                                     |
| 建立球員（帶 email）   | 帶 `email` 的未連結球員，永遠不會連結 | 受邀者，套用邀請的連結與衝突規則                         |
| 發出邀請               | 只寫入 `email`                        | email 已註冊則寫入 `userId`，否則寫入 email              |
| 接受邀請               | 受邀者 → 成員                         | 不變                                                     |
| 拒絕、取消邀請         | 轉為未連結球員，`role` 保留           | 轉為未連結球員，清除 `role`                              |
| 離開隊伍               | 轉為未連結球員，`role` 保留           | 轉為未連結球員，清除 `role`                              |
| 變更角色               | 任何球員皆可                          | 只限受邀者與成員，套用 D3 的管理規則                     |
| 刪除球員               | 刪除文件                              | 套用 D3 的管理規則；被刪除的成員若以該隊為預設隊伍則清除 |

## 角色管理

依 D3，呼叫者與目標的關係決定能否變更角色或刪除球員。規則以角色階層、「擁有者受保護」與「不能以自己為目標」表達，與成員判斷放在同一組 entity 函式。

| 呼叫者   | 可以變更角色的目標           | 可以刪除的目標                           |
| -------- | ---------------------------- | ---------------------------------------- |
| 擁有者   | 管理員、一般成員、受邀者     | 管理員、一般成員、受邀者、未連結球員     |
| 管理員   | 其他管理員、一般成員、受邀者 | 其他管理員、一般成員、受邀者、未連結球員 |
| 一般成員 | 無                           | 無                                       |

- 擁有者是「角色為擁有者的成員」，不是任何人變更角色或刪除的目標；擁有權只能透過移轉離開。
- 任何人都不能以自己的球員為目標。要離開隊伍走「離開隊伍」，名單上的那一格保留為未連結球員。
- 未連結球員沒有角色，不是變更角色的目標。
- 可以指定的角色仍只有管理員與一般成員，擁有者只能透過移轉產生。
- 目標是擁有者時回傳新的錯誤原因，文案說明必須由擁有者移轉；目標是自己時回傳另一個錯誤原因，文案指向離開隊伍；目標超出呼叫者的管理範圍時回傳 `INSUFFICIENT_ROLE`。

## 邀請與唯一性

- **先授權，再查詢**：發出邀請或建立帶 email 的球員時，先確認呼叫者是該隊管理員以上，之後才查詢 email 與做衝突檢查。反過來做，任何登入者都能問出某個 email 是否在某一隊的名單上。
- **連結帳號**：email 去除空白後，以 collation `strength: 2` 做不分大小寫的**精確**比對查詢使用者，不使用 `$regex`，否則 `.` 會匹配任意字元而連到別人的帳號。恰好找到一位時寫入 `userId`、不寫 email；找不到時寫入轉為小寫的 email，對方註冊時由 `linkUserToInvitations` 連結，而它以同一種不分大小寫的方式比對——邀請存的是小寫，註冊用的 email 卻可能帶大寫，精確比對會讓這種邀請永遠送不到；找到多位（大小寫不同的重複帳號）時回傳衝突，不猜測是哪一位。
- **衝突**：找到的使用者在該隊已有球員（受邀者或成員），或未註冊的 email 在該隊已有邀請時，回傳新的衝突錯誤原因；文案指出他已在名單上。
- **唯一性由索引保證**：`(teamId, userId)` 改為只對 ObjectId 型別 `userId` 生效的部分唯一索引；`(teamId, email)` 的無效宣告修正為只對字串型別 email 生效的部分唯一索引。資料庫的唯一性違反目前已轉譯為 409，改為對應到上述衝突錯誤原因。
- **註冊時的連結不會產生重複**：`(teamId, email)` 唯一，所以同一個 email 在一隊至多一筆邀請；一個帳號只註冊一次，也不會與自己已有的球員同隊。

## 資料的兩個階段

依 D4，既有資料分兩個階段處理。第一階段在部署之前，**不為任何文件新增 `userId`**，因此舊的權限檢查下沒有人多出權限；第二階段在部署之後，新的成員判斷已經上線，連結帳號才不會讓受邀者取得權限。

### 第一階段：部署前正規化

| 既有文件                          | 正規化結果                           |
| --------------------------------- | ------------------------------------ |
| 缺 `status`，有 `userId`          | 成員（`JOINED`），清除 `email`       |
| 缺 `status`，只有 `email`         | 未連結球員，清除 `role` 與 `email`   |
| 缺 `status`，兩者皆無             | 未連結球員，清除 `role`              |
| 未連結球員帶 `role` 或 `email`    | 清除 `role` 與 `email`               |
| 成員帶 `email`                    | 清除 `email`                         |
| 受邀者的 `email` 帶大寫或前後空白 | 去除前後空白並轉為小寫               |
| 任何欄位為 `null` 或空字串        | 視為缺少；`email` 與 `role` 一併清除 |

寫入任何文件之前先檢查下列情況；出現任一即停止、不寫入，列出文件交由開發者處理：

1. `(teamId, userId)` 重複。
2. 同隊受邀者的 email 在轉小寫並去除空白後重複。
3. 非成員帶擁有者角色，或某個**有球員的**隊伍其擁有者成員數量不為 1。完全沒有球員的隊伍不算違反：沒有人在裡面，就沒有需要保護的成員關係；它們列在 audit 的清單裡，由開發者決定是否刪除，而不是擋住遷移。
4. 受邀者或成員缺角色；受邀者同時有、或同時缺 `userId` 與 `email`；成員缺 `userId`；未連結球員帶 `userId`。
5. `userId` 或 `teamId` 不是 ObjectId，缺 `teamId`，或 `teamId` 指向不存在的隊伍。
6. `status` 的值不在 `NONE`、`INVITED`、`JOINED` 之內。

受邀者的 email 一律去除前後空白並轉為小寫，因為註冊時的連結與邀請時的查詢都以去除空白、不分大小寫的方式比對，而唯一索引是逐位元組比對：留著大小寫不一致的舊資料，同一隊就可能存在兩筆只差大小寫的邀請，註冊時同時命中而寫入衝突。

以上檢查以**正規化後的結果**計算，而不是只看現況。擁有者數量以 `teams` collection 逐隊計算，沒有球員、或只有未連結球員的隊伍同樣會被檢查。檢查通過且寫入完成後，修正 `(teamId, email)` 索引、移除一般的 `(teamId, userId)` 索引、建立部分唯一索引，並以 `listIndexes` 驗證 `unique` 與 filter 確實存在。

audit 另外列出被撤回的舊邀請與帶 email 的未連結球員，以及正規化前帶擁有者角色的非成員，附角色與最後更新時間，讓開發者在執行前檢視。部分唯一索引沿用 MongoDB 的預設索引名稱，並在部署後的 audit 再以 `listIndexes` 確認一次，因為舊程式碼的 instance 可能依舊宣告重建索引。

### 第二階段：部署後連結

前提：本 Change 已部署到該環境，且在部署後**重跑正規化**、audit 各類歸零。正規化完成到部署生效之間，舊程式碼的日常操作（建立球員、離開隊伍、拒絕或取消邀請、變更角色）仍會寫出帶角色的未連結球員，這些文件在新程式碼下讀取失敗；部署切換期間舊的 instance 也還在寫入。部署後重跑正規化是連結的 gate。

連結的對象是狀態為 `INVITED` 且只有 email 的邀請：email 以與邀請時相同的方式（collation `strength: 2` 精確比對）恰好對應一位已註冊的使用者時，寫入 `userId` 並清除 `email`。

- **每一筆以條件更新寫入**：filter 同時比對 `_id`、`status: INVITED`、讀取時的 `email` 原值與「`userId` 不存在」。讀取之後管理員若取消邀請或改邀他人，這一筆不會被寫入，`matchedCount` 為 0 時跳過並列出。
- **逐筆處理錯誤**：唯一索引違反逐筆捕捉並列出，一筆失敗不中斷其餘寫入。
- **不寫入並列出**：該使用者在同隊已有球員、或 email 對應到多位使用者。

這一階段同時送達「已註冊卻收不到」的既有邀請。

### 執行順序

1. volleybro-test：執行正規化的 audit 與腳本，再跑一次 audit 確認歸零。
2. production：開發者執行正規化的 audit 與腳本，再跑一次 audit 確認歸零。
3. 部署本 Change 到 volleybro-test；重跑正規化直到 audit 歸零；執行連結的 audit 與腳本。
4. 部署本 Change 到 production。
5. production：開發者重跑正規化直到 audit 歸零，再執行連結的 audit 與腳本。

步驟 1、2 提前做，對權限是安全的：正規化只清除欄位、補上已成立的成員狀態，不增加任何人的權限。但它不能取代部署後的重跑（步驟 3、5），因為空窗期的舊寫入會再產生不符合模型的文件。在步驟 5 的重跑完成之前，這些文件所在的隊伍名單會讀取失敗，所以步驟 4 之後應立即執行步驟 5。連結不能提前到部署之前。

## Behavior contract

| 呼叫者與該隊的關係 | 成員檢查          | 管理員檢查          | 隊伍資訊、名單、單一球員 | 邀請清單中的隊名 |
| ------------------ | ----------------- | ------------------- | ------------------------ | ---------------- |
| 擁有者             | 通過              | 通過                | 可讀                     | —                |
| 管理員             | 通過              | 通過                | 可讀                     | —                |
| 一般成員           | 通過              | `INSUFFICIENT_ROLE` | 可讀                     | —                |
| 受邀者（任何角色） | `NOT_TEAM_MEMBER` | `NOT_TEAM_MEMBER`   | 不可讀                   | 可讀             |
| 登入但與該隊無關   | `NOT_TEAM_MEMBER` | `NOT_TEAM_MEMBER`   | 不可讀                   | —                |
| 未登入             | 401               | 401                 | 不可讀                   | —                |

- 受邀者接受邀請：`AcceptInvitationUseCase` 自己驗證受邀者身分，不經過成員檢查；接受後立即成為成員。
- 移轉擁有權：現任擁有者必須是角色為擁有者的成員，目標必須是成員且不能是自己；受邀者作為目標得到 `TARGET_NOT_MEMBER`。移轉是兩次更新，指向自己會讓同一筆先升為擁有者再降為管理員，隊伍因此沒有擁有者。
- 被刪除的成員：`activeTeamId` 若指向該隊即清除；非成員直接開啟隊伍頁面時看到錯誤狀態。
- 不存在的隊伍：先授權再讀取，回傳 `NOT_TEAM_MEMBER`，不透露隊伍是否存在。`GetPlayerUseCase` 必須先讀出球員才知道隊伍，球員不存在時的行為維持不變：use case 回傳 null，route 交給回應 schema，呼叫者得到 400 VALIDATION。那個回應形狀是既有行為，本 Change 不動它。

## Failure modes

- **部署早於正規化**：缺 `status` 的文件在 `toPlayer` 縮窄時拋錯，而一筆壞文件就讓整隊名單讀不出來。以執行順序保證；S01 的驗收包含 production 正規化完成。
- **空窗期的舊寫入**：正規化完成到部署生效之間，舊程式碼仍會寫出帶角色的未連結球員。部署後立即重跑正規化，audit 歸零才執行連結。
- **連結時邀請已被取消或改邀他人**：讀取與寫入之間狀態改變，若無條件寫入，會把舊 email 對應的使用者寫進已取消或改邀的球員。以條件更新保證，未比對到的一筆跳過並列出。
- **email 比對連到別人的帳號**：以 `$regex` 做不分大小寫比對時 `.` 匹配任意字元。以 collation 精確比對保證，對應多位使用者時不寫入。
- **連結早於部署**：舊的權限檢查只看 `role`，被連結帳號的受邀者會在空窗取得成員與管理員權限。連結腳本屬於部署後的步驟，S03 的驗收寫明執行時機。
- **正規化時發現重複或不變量不成立**：腳本在寫入前停止。由開發者判斷保留哪一位球員、誰是擁有者，處理後重跑。
- **索引看似存在其實無效**：同名的一般索引或無效宣告會讓「索引已存在」的判斷誤以為完成。以 `listIndexes` 驗證 `unique` 與 filter；audit 也做這項檢查，因為部署後的 gate 是 audit，而連結腳本「重複鍵就跳過」的保護在唯一索引不存在時永遠不會觸發。
- **邀請頁在隊伍端點收緊後失去隊名**：以切片順序保證，受邀者清單先帶上 `teamName`。
- **非成員開啟隊伍頁面時崩潰**：`team/info/index.tsx` 以 `team!.nickname`、`players!.length` 假設資料存在；讀取收緊後拋 TypeError。以切片順序保證，前端錯誤狀態先於讀取收緊。
- **接受邀請被新的成員檢查擋下**：`acceptInvitation` 的 controller 若仍經過 `GetPlayerUseCase`，受邀者會被自己的邀請擋下。同一個切片內改掉這條路徑。
- **既有測試以受邀者身分通過檢查、或期待未連結球員帶角色**：它們代表的正是被修掉的行為，應改寫而不是放寬判斷。
- **整合測試看不到授權**：`test/integration/support/auth.ts` 的 double 一律放行，拒絕的證據來自 entity 與 use case 的單元測試。

- **Entity**：`isTeamMember`、`hasTeamRole` 與角色管理判斷以狀態、呼叫者角色、目標角色、是否為自己的完整組合測試，不需要 mock。這是成員與管理規則唯一的權威。

- **Migration**：兩個階段的 audit 與腳本以記憶體 MongoDB 的整合測試覆蓋：每一類正規化、以正規化後結果計算的重複、每一項停止條件、既有同名一般索引與無效宣告下仍建立真正的唯一索引、重跑不改變結果、連結時遇到已在隊上的使用者不寫入；讀取後邀請被取消或改邀他人時不寫入；正規化後以舊寫入路徑產生的文件讓讀取失敗、重跑正規化後恢復；`null` email、成員缺 `userId`、未連結球員帶 `userId` 各自命中對應的規則或停止條件。

## 計畫與實際的差異

- **S01 的驗收只在 `test` 資料庫上完成。** 原本寫的是 volleybro-test 與 production 依序執行，但 production 資料庫尚未啟用，所有環境共用同一個 `test` 資料庫，所以那裡跑完就是跑完（見執行紀錄）。
- **S03 的連結在合併後執行，腳本保留到發佈到正式站。** 連結會替受邀者寫入 `userId`，所以排在合併之後；合併後逐筆確認唯一的候選無害才執行（見執行紀錄）。正式站在發佈前仍會寫出只有 email、對方收不到的邀請，所以腳本留在 `scripts/migrations/`，發佈後再跑最後一次才移除。
- **D1–D4 從 `candidate` 直接改為 `implemented`。** 開發者核准計畫時沒有把它們標成 `accepted`，Archive 時依交付結果確認後一次改正。
- **S04 讓兩個 use case 不再注入 `AuthorizationService`。** entity 的管理判斷已含「呼叫者必須是管理員以上的成員」，保留舊檢查等於同一份資料查兩次、兩套規則各自漂移。錯誤語意不變。
- **Apply 期間加做三件計畫外的工作**：註冊時的帳號連結改為不分大小寫、正規化把保留的邀請位址去空白轉小寫、移轉擁有權不能指向自己。前兩件是同一條 email 大小寫的線，第三件牴觸 D3 的「隊伍永遠有一位擁有者」。
- **`AuthorizationService` 只剩 `verifyTeamRole` 與 `verifyIsTeamAdmin`。** S02 原本保留三個沒有呼叫者的方法（`verifyIsTeamOwner`、`verifyPlayerRole`、`getPlayerRole`），它們各自組規則，會成為第二套授權規範；經開發者確認後刪除。entity 的 `isOwner` 改名為 `isTeamOwner`，與 `isTeamMember` 同句型。
- **空隊伍不再擋住遷移。** 實際執行時六個一位球員都沒有的隊伍停下來；沒有人的隊伍沒有需要保護的成員關係，規則改成「有球員的隊伍才要求剛好一位擁有者」。
- **`(teamId, email)` 的唯一索引在此之前從未存在**，所以「同一隊不會重複邀請同一個 email」在這個 Change 之前只是宣告，不是保證。

合併到 `dev` 之後：正規化 audit 仍然歸零；連結 audit 只有一筆候選，是 smoke test 隊伍對開發者本人帳號的一般成員邀請。開發者在被邀請之前就已註冊，而舊程式碼只在註冊當下連結，所以它一直連不上。在舊正式站上，連結只會讓開發者提早取得那支測試隊伍的一般成員權限，因此直接執行：連結 1 筆、跳過 0 筆，再跑 audit 沒有候選。

發佈到正式站之後（2026-09-25，v0.15.0）：正規化 audit 仍然歸零，39 / 39 符合模型、沒有停止條件與索引問題；連結 audit 沒有候選，發佈前的空窗期沒有寫出只有 email 的邀請，因此兩支 migrate 都不必執行。兩組腳本與它們的整合測試隨後移除，需要時從 git 歷史取回。

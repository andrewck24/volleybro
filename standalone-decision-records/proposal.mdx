<TLDR>
決策記錄不再隸屬於任何一個 Change。所有記錄移到扁平的 `blueprint/content/decisions/`，編號於誕生時指派，沒有 per-capability 複本，也沒有 Archive 的提升步驟；Feature 頁改為依 `capabilities` 欄位過濾渲染，該欄位即原本的 `targets`。schema 的 required 欄位降到五個，刪除 `originDecision`，版本升到 2；已發佈在 store 分支上的 version 1 記錄則透過相容層繼續渲染。Fix path 可以修正一份記錄，但碰到 `decision` 本文或 `supersededBy` 就必須升級。編號是四位數零填充，扁平目錄因此照記錄產生的順序排序。同時落地兩條連帶的文件規則：研究筆記不自成檔案，以及 Fix path 的 `Refs:` trailer 改為條件性。
</TLDR>

## 為什麼是現在

三個事實，全部量自提案當時的檔案樹——遷移之後它們描述的是被取代的那個狀態：

1. `blueprint/content/features/**/decisions/` 底下有 **65 個檔案，內容只有 45 份不重複的記錄**。19 個編號出現超過一次，`D29` 出現三次。
2. **45 份全部**——每一份記錄所在的目錄集合，與它自己 `targets` 陣列裡的 ID 集合完全相同，零個例外。目錄樹沒有提供任何檔案本身沒說的資訊。
3. 每一組複本目前逐位元組相同（`$schema` 相對路徑除外）。也就是說它們**還沒**漂移，去重複是機械搬移，不是合併。

第二點才是論證。一份只是在複述欄位的複本，不是需要一致性檢查的冗餘，是需要刪掉的冗餘。

## 本次 Change 的邊界

- 把 45 份不重複的記錄移到 `blueprint/content/decisions/D<n>-<slug>.json`，刪除 20 個複本檔案，並修正每份記錄的 `$schema` 相對路徑。
- 在 schema、手寫 validator、`DecisionTimeline` 與每一份記錄中，把 `targets` 更名為 `capabilities`。
- 編號改為四位數零填充：`id` 是 `0046`，檔名是 `0046-<slug>.json`，散文引用寫 `ADR-0046`。store 分支上的 version 1 記錄保留 `D<n>`，兩個版本各驗自己的 id 形狀。
- schema 升到版本 2：required 五個欄位，刪除 `originDecision`，`originChange` 保留且為選配。
- 把約十餘個 Feature `index.mdx` 的相對路徑 import，換成由 build-time index 支撐的 capability 過濾渲染。
- 擴充 legacy 相容層，把 version 1 記錄升版，讓 store 分支上早先 Change 頁裡的 48 份記錄繼續渲染。
- 依新模型改寫 `WORKFLOW.md` 的 Decision-record contract 與 `docs/agents/domain.md` 的 ADR 段落，並把 Fix path 的紅線改畫在 `decision` 與 `supersededBy` 兩個欄位上。
- 落地研究筆記規則：改寫 `docs/agents/artifact-lifecycle.md`，明定研究與工作筆記不自成檔案，以及 Proposal 頁 `## References` 段落的條件性與寫法。
- 把 Fix path 的 `Refs:` trailer 改為條件性，同步改寫 `WORKFLOW.md` Fix path 第 2、7 條與 `CONTRIBUTING.md` 的 trailer 段落。
- **不在範圍內** —— `CONTRIBUTING.md` 的程式碼註解引用規則仍在區分「Feature 編號」與「Change 自己的 `D2`」，而本 Change 消滅了這個區別。該檔案屬於 `reviewer-standards-split`，順序在後，由它承擔改寫。
- **不在範圍內** —— 已發佈在 `blueprint-changes` store 分支上、活在 Change 頁裡的那些記錄。它們是歷史，不遷移。
- **不在範圍內** —— ATE-167 剩下的兩項（CI 中的 schema 驗證、store 分支保留政策）。它的「同編號副本一致性」那一項被本 Change 直接消滅，而非解決；另外兩項等本 Change 落地後重新界定範圍。

## 順序

四個之中排第一。其餘三個都要等它落地，才能用新模型寫自己的決策記錄。它與 `reviewer-standards-split` 在 `CONTRIBUTING.md` 的註解引用規則上交棒——本 Change 消滅那個區別，後者執行改寫。

## References

蒐集於 2026-09-19 的討論。**一份 reference 記錄的是它被讀到那天為真的事**，所以每一列都要說出自己的強度，以及它能支持到什麼程度。〈為什麼是現在〉裡的數字是對本 repo 的量測，不是 reference，因此留在該節。

| 來源 | 支持什麼 | 強度 |
| --- | --- | --- |
| 已安裝的 `domain-modeling` playbook 與其 ADR 格式 | ADR 住在 `docs/adr/<n>-<slug>.md`，編號靠掃描目錄取最大值加一，在決策發生的當下寫下，而且可以只有一段話——status、options、consequences 全是選配。 | **高**。本 repo 其餘部分本來就遵循的 playbook，直接讀已安裝的版本；它是 ADR-0046 與 ADR-0048 形狀的來源。 |
| 同一套的 `to-spec` 與 `to-tickets` | 它們只叫 agent **respect** 所觸碰範圍內既有的 ADR。既不產生也不擁有，所以決策記錄與交付單位之間沒有任何關係。 | **高**。這是分開兩個模型的那一句話，而且寫得很明確。 |
| 同一套的 `grill-with-docs` | 決策在產生它的那場 grilling 當中就寫下，不等任何階段結束。 | **高**。它全文只有一句指令：透過 `domain-modeling` 跑 grilling。 |
| 找不到外部來源 | 這套 playbook 沒有談「在 gate 上審一個決策」，因為它根本沒有 gate。 | **低**，而且是誠實的缺口：拿掉 proposed 階段是本 repo 自己的判斷，由 ADR-0046 的 consequences 承擔，不是讀來的。 |

## Ingest 註記

這一頁在 G2 之後被退回改寫過一次。開發者授權 Ingest，把編號改成四位數零填充——理由是量到的缺陷：53 份記錄進同一個目錄之後，`D10` 排在 `D2` 前面，而舊模型下每個目錄只有兩到六個檔案，排序從未重要過。位置、欄位與檔案類型都沒有動；`ADR-0054` 記錄了這個決定。已完成的 slice 與它們的證據全部保留，`0054` 是第九份記錄。

## Bootstrap 註記

最初那八份記錄誕生在它們要取代的那個模型底下：活在某個 Change 的 `proposal/decisions/` 裡，version 1，帶著 `targets` 與填滿的九個欄位。一條讓決策記錄脫離交付流程的規則，沒辦法由一份已經脫離了的記錄來記載。它們在本 Change 自己的 Apply 階段，與另外 45 份走同一趟遷移，移到 `blueprint/content/decisions/`、轉成 version 2 並取得 `0046`–`0053`——那是一份記錄一生中唯一一次改編號。這是 bootstrap 該有的樣子，不是模型的缺陷。

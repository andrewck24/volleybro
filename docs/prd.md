# VolleyBro 專案需求文件 (PRD)

## 專案分析與情境評估

VolleyBro是一個成熟的排球隊伍管理和賽事紀錄平台，採用Clean Architecture設計，具備完整的使用者管理、球隊管理、賽事紀錄和數據分析功能。系統使用Next.js 15+ (React 19)、TypeScript、MongoDB等現代技術棧，並已完成詳細的架構設計與文件。

✓ 功能需求文件 (已有完整的功能規格)
✓ 非功能性需求文件
✓ 資料模型文件

**文件完整性評估**: 專案具備極為完整的技術文件，包含Clean Architecture分層、技術棧詳情、PWA功能實作等，為棕地增強提供良好基礎。

### 增強範圍定義

**增強類型**:
✓ 新功能添加
✓ UI/UX改版  
✓ 產品市場定位優化

**增強描述**: 完善VolleyBro產品介紹頁功能，強化Beta階段的使用者獲取能力，並為正式發布建立技術和市場基礎。

**影響評估**:
✓ 中等影響（部分現有代碼變更）

### 目標與背景情境

**目標**:

- 優化產品介紹頁以符合Beta階段定位
- 建立Waitlist功能為正式發布準備用戶基礎
- 強化產品獨特性展示和技術優勢包裝
- 提升使用者轉換率和參與度

**背景情境**: VolleyBro目前處於Beta開發階段，需要透過完善的產品介紹頁來吸引早期採用者，建立使用者基礎，並為正式發布做好市場準備。

## 需求

基於對現有VolleyBro系統的深入分析，以下為完整的功能和非功能性需求。這些需求涵蓋已實現的核心功能模組以及計劃中的增強功能。

### 功能需求

#### 核心功能模組（已實現/部分實現）

**FR1: 產品介紹頁功能** - _🟡 已部分實現_

- 系統應提供產品介紹頁面，包含產品功能展示、Beta階段定位、Waitlist註冊功能
- 當前狀態：已實現Hero區塊、Features區塊、Benefits區塊、Footer區塊，具備響應式設計和動畫效果
- 測試覆蓋率：95%+ (根據CLAUDE.md中的landing page測試覆蓋率)
- 待完成：Beta階段內容策略調整、Waitlist功能、技術優勢包裝展示

**FR2: 使用者管理功能** - _🟢 已實現_

- 系統應支援使用電子郵件或Google帳號進行註冊及登入
- 系統應允許使用者查看和編輯個人資料、密碼及頭像
- 系統應支援球隊邀請的查看、接受或拒絕功能
- 系統應提供已加入球隊列表並支援球隊切換
- 當前狀態：基於NextAuth.js v5實現，包含Google OAuth整合，具備完整的會話管理

**FR3: 球隊管理功能** - _🟢 已實現_

- 系統應支援創建新球隊並設定基本資訊（名稱、簡稱等）
- 系統應允許在多個球隊間快速切換
- 系統應支援新增成員資料、透過電子郵件邀請使用者加入球隊
- 系統應提供成員角色與權限設定(OWNER, ADMIN, MEMBER)
- 系統應支援球隊比賽陣容配置、球員場上位置分配、先發與替補名單設定
- 當前狀態：完整實現Clean Architecture設計，具備完整的CRUD功能和權限控制

**FR4: 賽事紀錄功能** - _🟢 已實現_

- 系統應支援新建賽事紀錄並設定比賽規則、地點、時間和類型
- 系統應能記錄每一球的得分與失分情況
- 系統應能記錄球員表現數據（攻擊、攔網、發球等）和替換情況
- 系統應提供比賽即時統計數據與分析報告
- 當前狀態：完整實現，包含Redux Toolkit狀態管理(record-slice.ts, lineup-slice.ts)
- 測試覆蓋率：包含完整的helper測試和repository測試

**FR5: 數據分析功能** - _🟡 已部分實現_

- 系統應提供數據視覺化圖表、儀表板工具
- 系統應支援過往賽事紀錄與統計資料查看
- 系統應提供數據導出功能（CSV、PDF等格式）
- 系統應支援數據比較功能（不同比賽、不同球隊之間的比較）
- 系統應提供數據篩選功能（依時間、球隊、球員等條件篩選）
- 當前狀態：基礎分析已實現，高級分析和機器學習功能待開發

## 技術限制和整合需求

### 現有技術棧

**語言**: TypeScript (嚴格模式), JavaScript (ES2022+)
**框架**: Next.js 15+ (React 19), App Router架構  
**資料庫**: MongoDB with Mongoose ODM, embedded documents設計
**基礎設施**: Vercel部署平台, 全球CDN加速
**外部依賴**: Google OAuth (NextAuth.js v5), Serwist PWA

### 整合策略

#### 資料庫整合策略

- 維持現有embedded documents的效能優勢
- 新功能採用向後相容的schema擴展
- 避免破壞性變更，使用選擇性欄位
- 新增WaitlistEntry集合用於Beta階段用戶註冊

#### API整合策略

- 新增端點遵循現有的/api/[resource]RESTful模式
- 維持現有的NextAuth.js v5驗證流程
- 沿用現有的錯誤處理和回應格式
- Beta功能API使用版本控制 /api/v1/beta/[feature]

#### 前端整合策略

- 狀態管理：Redux Toolkit + SWR架構保持不變
- UI元件：完全使用Shadcn UI + Tailwind CSS設計系統
- 動畫系統：沿用現有Motion/React模式
- Waitlist狀態使用SWR進行簡單的server state管理

#### 測試整合策略

- 使用現有的Jest + jsdom統一環境
- 維持95%+測試覆蓋率標準
- 沿用現有的MongoDB mock策略

### 程式碼組織和標準

**Clean Architecture一致性**:

- 新功能必須遵循五層架構(Domain/Application/Infrastructure/Interface/Presentation)
- 使用現有的InversifyJS依賴注入模式
- 遵循現有的repository pattern


**編碼標準**:

- TypeScript嚴格模式，ESLint Airbnb規則
- Angular commit convention
- 檔案命名：kebab-case，元件命名：PascalCase

### 部署和營運

- 沿用現有的Vercel自動部署流程
- 維持現有的build最佳化和CDN快取策略
- 使用feature flag進行漸進式功能發布
- 新增環境變數：WAITLIST_ENABLED, BETA_FEATURES_FLAG

### 風險評估和緩解

**技術風險**: 新功能影響現有穩定性
**緩解策略**: 階段性部署、完整測試覆蓋、快速回滾機制

**整合風險**: Waitlist功能與現有使用者註冊流程衝突  
**緩解策略**: 清楚分離Waitlist和正式註冊的資料模型和流程

**部署風險**: 產品介紹頁變更影響SEO和使用者轉換
**緩解策略**: A/B測試新版本，監控關鍵指標

## Epic和Story結構

基於對現有VolleyBro專案的深入分析和技術債務評估，採用結構化的多Epic策略來管理產品開發和系統重構。

### Epic策略決策

**Epic結構決策**: 多Epic策略，理由如下：

- **功能模組對應**：Epic 1 對應 FR1（產品介紹頁），Epic 2-5 分別對應 FR2-FR5 四大核心功能模組
- **系統重構方法**：每個核心功能模組採用「文件建置 + 測試建置 + 程式碼重構」的統一方法
- **技術債務管理**：Epic 6 專門處理 TypeScript 重構，為所有功能模組奠定技術基礎
- **漸進式改善**：允許每個功能模組獨立進行現代化改造
- **風險隔離**：各Epic相對獨立，降低重構風險

**Epic執行策略**:
1. **Epic 6 優先**：TypeScript重構為基礎建設，提升整體代碼品質
2. **Epic 1 次之**：產品介紹頁優化，直接影響使用者獲取
3. **Epic 2-5**：核心功能模組重構，可並行或依優先級執行
   - Epic 2（FR2 使用者管理）：基礎身份認證系統
   - Epic 3（FR3 球隊管理）：核心業務邏輯
   - Epic 4（FR4 賽事紀錄）：主要功能價值
   - Epic 5（FR5 數據分析）：高級分析功能

**文檔結構**:
- Epic詳細文檔位於 `docs/epics/` 目錄
- 每個Epic包含Story規劃、驗收標準、整合驗證

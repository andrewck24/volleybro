# pnpm 與 GitHub dependency graph：主流 repository 的公開做法

查核日期：2026-10-02。這是有範圍的研究紀錄，不是新的 repository policy，也沒有啟用 GitHub 設定或更動 CI。

## 結論

六個代表性專案中，五個已使用 pnpm 12，且根目錄 lockfile 都是 env-first 的雙 YAML document；Next.js 仍使用 pnpm 10 的單 document。因此不能再用「主流專案都還在 pnpm 10」解釋相容性差異。但這些公開配置沒有證明 GitHub static graph 已完整支援 pnpm 12。

共同可見的做法是保留 pnpm lockfile，部分專案以 Renovate 更新依賴；pnpm 自己另跑原生 audit，Nuxt 另跑 dependency review。在本次掃描的 117 份公開 workflow 目錄檔案（含 README）中，沒有找到 native split SPDX → GitHub dependency submission 的實例。這不等於他們的 GitHub alerts 已完整運作，也不等於 submission 不需要存在。

對 VolleyBro 而言，native pnpm SBOM 加上現成 SPDX submission action 仍是保留雙 document 與 GitHub graph/alerts 的合理選擇。是否可以省掉 submission，必須以本 repository 的 graph 內容、來源與 lockfile 對照證明；主流專案的採用方式不能替代這項驗證。

## 範圍與證據方法

每個專案先讀 GitHub `commits/HEAD`，再以該 immutable SHA 讀完整 Git tree、根目錄 `package.json`、`pnpm-lock.yaml`、`pnpm-workspace.yaml`，以及 `.github/workflows/` 全部 blob、已發現的 Dependabot/Renovate configuration。六份 tree 都回覆 `truncated: false`，檔案下載無失敗。除 Nuxt 的 dependency-review reusable workflow 另追一層外，沒有展開所有 reusable workflows、local actions、任意 shell scripts、組織設定或外部 CI。下表的「未見提交」只限這個範圍；掃描詞涵蓋 dependency submission、dependency-graph、SPDX、SBOM、dependency-review、audit 與相關設定。

雙 document 指同一個 `pnpm-lock.yaml` 內的 env document 加上 project document；`pnpm sbom --split` 則是每個選取的 workspace package 一份 SBOM，兩者不同。下表 separator 是內容完全等於 `---` 的行號，已另看第一段的 `packageManagerDependencies` 確認 env-first，而非只從 pnpm major 推測。

## 上游的雙 document 決議

[pnpm upstream report](https://github.com/pnpm/pnpm/issues/13805) 於 2026-08-11 回報 pnpm 12 rc 的 env-first lockfile 導致 GitHub graph 零依賴、alerts 關閉；截至查核日已 closed。這是回報者的單 repository 量測，不能直接當成今天所有 GitHub repository 的結果。

Maintainer [先考慮改順序](https://github.com/pnpm/pnpm/issues/13805#issuecomment-5250555198)，隨後 [明確撤回](https://github.com/pnpm/pnpm/issues/13805#issuecomment-5250808407)：改順序會破壞已支援 env-first 的 consumer，也無法修復既有歷史 lockfile。最後 [2026-08-23 回覆](https://github.com/pnpm/pnpm/issues/13805#issuecomment-5386948833) 將修復責任放在 downstream tools，指向正式 lockfile 文件；closed 並不代表 GitHub parser 修好了。

[pnpm lockfile 文件](https://pnpm.io/lockfile) 現在明定：graph/updater 要用 multi-document parser 取最後 document；scanner/SBOM 要各自讀取所有 documents 再聯集 inventory，避免合併物件覆蓋同名 importer。`pmOnFail: ignore` 是停用 package-manager version enforcement 的 workaround；有 config dependencies 時仍會雙 document。文件並要求用雙 document 驗證 scanner，僅「輸出一些套件」不足以確認正確。

Issue 內的 [scanner 比較](https://github.com/pnpm/pnpm/issues/13805#issuecomment-5251006791) 只測當時的 pnpm rc.3、Trivy 0.73.0、osv-scanner 2.5.0 與 Syft 1.51.0。它提供具體 failure mode 與 audit 替代路徑，不是這些工具最新版的現況測試。

## 官方支援與 graph 證據的界線

[GitHub graph 支援表](https://docs.github.com/en/code-security/reference/supply-chain-security/dependency-graph-supported-package-ecosystems) 列 pnpm static transitive 支援，但不提供 pnpm automatic dependency submission / graph jobs；[updater 支援表](https://docs.github.com/en/code-security/reference/supply-chain-security/supported-ecosystems-and-repositories) 仍列 pnpm v7-v10。ecosystem 列入支援與 pnpm 12 特定 physical format 正確，是不同證據要求。

[GitHub graph data](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependency-graph-data) 說手動 submission 優先於 static graph；[SBOM export](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/establish-provenance-and-integrity/export-dependencies-as-sbom) 匯出的是當下 graph。即使完整 export，也須另看 [detector 與 submitted timestamp](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/secure-your-dependencies/explore-dependencies) 才能歸因 static parser。這些資料不能證明 updater 可改寫 pnpm 12 lockfile。

本次另嘗試 live GraphQL `dependencyGraphManifests(first: 100)`，六個專案第一頁所有 manifest 的 `dependenciesCount` 都回 0 / `parseable: true`，包括 Next.js 的 pnpm 10 與 Actions/Cargo 對照；Vue/Nuxt 全頁亦如此。此讀回沒有分辨能力，沒有當成 pnpm 12 parsing failure 的證據。未完成外部專案完整 SBOM 與來源逐項驗證，也沒有 alerts readback 或 GitHub 設定的可見性；因此沒有宣稱任何樣本的 GitHub graph/alerts 成功或失敗。

## 最省維護的選擇與尚缺證據

| 方案                                                | 公開先例 / 官方依據                                                                                                                                                                                                                     | 成本與適用條件                                                                                                                                                                           |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 僅 GitHub static graph                              | 六個專案公開 workflow 未見對應提交；GitHub 列 pnpm static 支援                                                                                                                                                                          | 沒有額外 generator/action。只有本 repository 的 default-branch graph 逐項完整且來源確為 static 時，才有移除 submission 的充分證據                                                        |
| 保留 pnpm 12 雙 document，native SBOM + SPDX action | [pnpm native sbom](https://pnpm.io/cli/sbom)、[GitHub submission 文件](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/secure-your-dependencies/use-dependency-submission-api) 有各自能力；六個樣本未見此組合 | 沿用已使用的 pnpm，免加另一個 scanner。`--split` 僅在需要 workspace 個別 manifests 時使用；一次 action 匹配全部 SPDX JSON 可減少重複步驟，仍須查 manifest identity / purls / graph edges |
| 原生 audit 加 Renovate                              | pnpm 的 audit job、pnpm/Vite/Vue/Nuxt 的 Renovate configs                                                                                                                                                                               | 是掃描/更新策略，不能單獨滿足「GitHub graph 和 Dependabot alerts 完整」；也沒有 runner duration、漏報率或管理成本的公開量測足以宣稱更有效率                                              |
| `pmOnFail: ignore`                                  | 上游文件與 issue 的 workaround                                                                                                                                                                                                          | 配置最少，但停用 version enforcement，且 config dependencies 仍可產生 env document。不能當成保留既有語意的純相容性修補                                                                   |

建議保留既有兩次 SPDX submission，使用 native generator + 現成提交工具。從維護面看，沿用已安裝的 pnpm 與現成 action 比另外維護 parser 更有利；這是工程判斷，沒有同儕採用相同組合或執行時間 benchmark 的證據。若日後實測 graph 已由 static source 完整覆蓋，才評估省略 submission。

本 session 的 VolleyBro native SBOM 檢查目前未涵蓋 env document；「提交 project graph，並保留 static env 資料」是待完成 readback 驗證的組合，不能宣稱已覆蓋全部安裝內容。官方 scanner/SBOM 指引要求所有 documents 的 inventory 聯集，而 native CLI 的 project SBOM 與 `--split` 選項本身不足以證明這項 coverage。自製 converter 或新增 Syft 目前沒有被本次案例證明能縮短維護路徑。

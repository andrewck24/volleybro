# Release activation

This is the consolidated operating checklist after the final release-train G2 and tooling merge. It is not permission to activate while reviewing a shard. Agents perform authorized mechanical steps; the developer owns credentials, protected QA, release acceptance and any new data or permission decision. Stop at a failed proof rather than working around it.

## 1. Preserve and inventory

1. Agent: fetch all branches, confirm merged tooling and a clean workspace; inspect unique dev/main commits with `git log --left-right --oneline origin/main...origin/dev`. Inventory active PR bases/worktrees, GitHub default/rulesets, Vercel project Git settings/environments/domains, Cloudflare Blueprint production branch, Google redirect origins and existing deployments.
2. Keep every unique commit through reviewed ordinary merge commits. Do not reset/rebase published history or delete dev. During the transition, tooling merges to dev; the inventory and integration PR move the complete accepted Cycle delivery to main.
3. Record the currently serving immutable Vercel deployment ID, URL, source SHA and tag. If production metadata cannot prove one source SHA, establish a verified baseline before using release/hotfix automation; do not invent a tag pointing at current main.

## 2. Configure platform boundaries before moving integration

1. Developer/authorized Agent: disable Git-triggered production deployments on the app Vercel project before main receives integration history. Configure main's Git deployment as a Preview with the test DB, not Production. Explicit release-controller builds continue to use Production settings without immediately assigning domains.
2. Keep `volleybro.vercel.app` as the official alias of the successful production deployment, not a branch name. Configure `INTEGRATION_ALIAS=volleybro-integration.vercel.app` for main Preview, as accepted at the earlier G2; `volleybro-test.vercel.app` remains the shared pre-merge manual-test deployment. Confirm each immutable deployment's source SHA in Vercel, rather than trusting the alias or screenshot. Configure the GitHub `integration` environment for the same approved project/team and test-target credentials.
3. All deployments remain on `test` before the first production-data launch. Only the explicitly accepted v1.0.0 activation changes Production to the clean `production` DB and carries over developer-specified data. Preview/shared test keep `test`; CI integration tests use mongodb-memory-server. No PR database/reset mechanism is introduced. Never copy/reset production data to unblock CI or rollback.
4. Verify Google OAuth redirect/origin configuration for candidate, fixed integration, shared pre-merge and production URLs, including deployment protection access. Do not add a production test-login bypass. Candidate QA uses the exact immutable URL printed in Actions Summary, including its deployment ID and source SHA; there is no hardcoded candidate alias that could point to the old formal site.
5. Agent: run the reviewed integration PR through Verify and Vercel, merge preserving unique history, then switch GitHub default to main and refresh `origin/HEAD`. Retarget open PRs and align Cloudflare Blueprint production/default branch. Confirm the ordinary merge cannot move the formal alias. The explicit integration-preview workflow remains dormant until the final enablement step; rehearse its Preview target manually with the same fixed main SHA and approved test configuration, without enabling release or promoting the deployment.

## 3. Credentials and protection

| Setting                                                            | Scope and success evidence                                                                                                                                                                                                                      |
| ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `RELEASE_TOKEN` secret                                             | Single repository PAT/App identity; contents and PR write plus required read access for checks/actions. It creates version/merge-back PRs that can trigger CI. No organization-wide token.                                                      |
| `RELEASE_BOT_LOGIN` variable                                       | Exact login of the release token; verify the authored version PR, branch and title.                                                                                                                                                             |
| `VERCEL_TOKEN` secret                                              | Team/project deployment and promotion access used only by trusted release jobs; confirm permitted project/team. Vercel token granularity is platform-dependent: record actual accessible projects and use a restricted identity when necessary. |
| `VERCEL_PROJECT_ID`, `VERCEL_TEAM_ID`, optional `VERCEL_TEAM_SLUG` | Actual app project/team, never the Blueprint project.                                                                                                                                                                                           |
| `PRODUCTION_ALIAS`                                                 | `volleybro.vercel.app`; verify current deployment metadata before enabling.                                                                                                                                                                     |
| `RELEASE_AUTOMATION_ENABLED`                                       | Keep unset/false until the entire release rehearsal is approved.                                                                                                                                                                                |
| `DEPENDENCY_SUBMISSION_ENABLED`, `DEPENDENCY_AUTO_MERGE_ENABLED`   | Independent unset/false defaults; enable in the dependency checks below, not by enabling release.                                                                                                                                               |
| `RELEASE_ROLLBACK_COMPATIBILITY`, `RELEASE_ROLLBACK_EVIDENCE`      | Exact run-specific binding and evidence supplied only when verified compatible; unknown means stop, never data rollback.                                                                                                                        |

These CI settings belong in GitHub secrets/variables, not `.env.local` or `.env.example`. Vercel app secrets remain project-environment settings. Do not print credentials in logs or PRs.

1. Configure `production-release-review` with a real required reviewer and prevent unreviewed production passage; verify an unauthorized run cannot proceed. Normal release merge is authorization; candidate and postdeploy approvals record QA, not replacement release authority.
2. Set main rulesets to protect deletion/force push and require current `Verify` from GitHub Actions (app 15368) and Vercel (app 8329). Require branches up to date, no bypass for dependency auto-merge. Keep the store branch protection. Check current constraints before retiring dev rules; do not remove protection while it remains active.
3. Arrange a trusted independent collaborator to approve hotfix heads: the PR author cannot approve their own PR. A dispatch and local login do not replace exact-head GitHub review. Recheck who can approve the protected environment, including the repository's actual plan capabilities.

## 4. Native dependency proof and enablement

1. Accept the initial auto-merge allowlist (`@types/jest-axe` only), then enable `DEPENDENCY_SUBMISSION_ENABLED` on main and run Dependency submission manually. Compare GitHub dependency graph/SBOM against native split SBOMs for both workspaces, including better-auth, mongoose and msw; confirm the environment/toolchain graph is still represented. Missing coverage is a blocker, not a reason to change lockfile format.
2. Enable Dependabot alerts and automatic security updates in GitHub Settings → Code security. Verify configuration/readback; weekly email timing is not the automation input.
3. Change both version-update limits in `.github/dependabot.yml` from zero to an accepted bounded queue (initial recommendation five each) through a reviewed PR. Inspect Dependabot update logs and a genuine root npm/pnpm and GitHub Actions PR; confirm dual-document updater support, target main, native bot identity and CI initiation. Major/minor PRs stay visible and manual, not ignored.
4. Verify a real alert/security update appears when GitHub has an applicable advisory and remediation. No synthetic production vulnerability is introduced to manufacture proof. If no applicable alert/update exists, keep that external proof explicitly open on the tracker, rather than declaring success from an SBOM upload.
5. Enable `DEPENDENCY_AUTO_MERGE_ENABLED` only after graph and native updater checks, latest check/provider identity and branch protection pass. A qualifying patch should integrate main without moving the production alias. If no real patch is available, keep automatic merge disabled until the first eligible event confirms the path; controlled CLI fixtures do not prove GitHub has run it.

## 5. First normal release and recurring use

1. Developer authorizes enablement after the rehearsal; Agent sets `RELEASE_AUTOMATION_ENABLED=true`. Run Integration preview on main and verify the fixed alias reaches the intended test deployment/source SHA without moving production. Changesets opens/updates `changeset-release/main`, title `release: update versions`, on main pushes with pending changesets; for the first run without a new push, use `gh workflow run changesets.yml --ref main`. The main-only guard also applies to manual dispatch; this only prepares the version PR, never grants merge/release authorization. Check the bot identity and latest required checks before merge.
2. Confirm the release plan with `pnpm changeset status`: the former dev/main Cycle delivery and pnpm prerequisite belong in the first release. The expected v0.16.0 is not hardcoded; if the actual Changesets plan differs, explain the pending entries and obtain the release owner's decision before authorization.
3. Developer merges or authorizes the Agent to merge the version PR. This selects all unpublished integration work through that exact Change boundary; merge fixes the source SHA. Later main merges do not replace it. No recurring Wednesday merge is automatic.
4. Agent/Actions stage the fixed production-config deployment. Developer checks the printed immutable candidate URL: home, Google sign-in/session and read-only team access, plus a focused changed-flow check. Approve `production-release-review` only for that candidate and documented DB compatibility. Safe session automation is separate work; until delivered, protected authenticated QA is required.
5. Actions recheck baseline under the shared lock, promote, smoke-check the public page, then pause for the same authenticated production QA. Only verified success creates exact-SHA tag/Release. Never treat a homepage HTTP 200 or CI green as authenticated QA. Check final deployment/source SHA and release artifacts after the run.
6. Complete activation/remaining evidence on the operational issue; close obsolete sync issues only after their replacement and dev retirement are verified. Agent fetches and checks all live branch references/PRs/worktrees/platform configs before deleting a fully preserved, unused dev branch. Keep it when any reference or preservation proof is missing.

## Stop and recovery

Failed credential/configuration/graph/updater/QA proof: leave the relevant automation variable false, record failure and keep the formal deployment unchanged. If a transition has already occurred, stop new integration/release runs, restore inventoried platform mapping only after verifying the current deployment; never repoint blindly or rewrite Git history.

Urgent severe bugs and security incidents: start `hotfix/*` at the verified deployed tag/SHA, exact-head independent review, then the existing `production-release` hotfix dispatch. Agent-first merge-back preserves the deployed repair and unpublished main work, with fresh checks and explicit merge authorization. Unknown metadata/conflicts stop for Agent analysis, not auto-rebase or choosing one side. Sync failure alone does not authorize another release.

The global release lock includes QA waits. Inspect and resolve an existing waiting run before advancing an urgent hotfix; do not bypass review or cancel an ambiguous promote/rollback. Rollback is allowed only by verified current-DB compatibility and must pass health checks; otherwise stop and notify, never reverse data.

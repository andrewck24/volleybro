## Context

The PWA service worker is currently built by serwist configurator mode: serwist.config.js feeds the serwist CLI, which compiles src/app/sw.ts into a static public/sw.js after next build (and watches it in dev via a second process under concurrently). Serwist's primary integration for Next.js 16 under Turbopack is @serwist/turbopack, where a route handler compiles the same worker source and Next prerenders it at build time. A full prototype (Paca VB-52, 2026-07-17) validated build success, header correctness, config composition, and precache-manifest equivalence for all static assets.

Constraints:

- src/app/sw.ts must keep its current caching semantics: defaultCache runtime strategies, NetworkOnly for the routes it filters, skipWaiting and clientsClaim enabled.
- Deployment target is Vercel; the worker must be served as a static asset with root-scope Service-Worker-Allowed, without per-request serverless invocations.
- The existing withBundleAnalyzer wrapper in next.config.js must keep working.

## Goals / Non-Goals

In scope:

- Single-process dev (next dev) and single-step build (next build) with the service worker generated by the route handler.
- Service worker registered from /serwist/sw.js with root scope.
- Dependency swap: remove @serwist/next, @serwist/cli, concurrently; add @serwist/turbopack, esbuild.

Out of scope:

- Install-time precache parity for the ten prerendered navigation shells (accepted delta; no additionalPrecacheEntries).
- Any change to runtime caching strategies, offline recording, or PWA metadata (manifest, splash, icons).

## Decisions

### Decision 1: Route-handler generation with useNativeEsbuild

src/app/serwist/[path]/route.ts calls createSerwistRoute({ swSrc: "src/app/sw.ts", useNativeEsbuild: true }) and re-exports the handler's GET, generateStaticParams, and the static-rendering directives (dynamic set to force-static, dynamicParams false, revalidate false). Prerendering bakes the worker into the build output with content-type application/javascript and service-worker-allowed "/" headers, so Vercel serves it from the CDN. useNativeEsbuild uses the installed esbuild binary at build time only; no runtime dependency.

### Decision 2: Import repointing instead of worker rewrite

The worker source stays byte-identical in behavior: src/app/sw.ts changes only its import source from @serwist/next/worker to @serwist/turbopack/worker (defaultCache), and the client provider changes from @serwist/next/react to @serwist/turbopack/react (SerwistProvider). The registration URL in src/app/layout.tsx changes from /sw.js to /serwist/sw.js. Root scope is granted by the baked Service-Worker-Allowed header, so the scope option stays unchanged: SerwistProvider defaults the requested scope to "/" when no options.scope is passed (verified in the provider source), which matches today's registration; the header exists to let the browser accept that root-scope request now that the worker file lives under /serwist/.

### Decision 3: Accept the navigation-shell precache delta

createSerwistRoute hardcodes the spa manifest transform, whose globs cover build chunks and public assets but not prerendered App Router HTML. The ten navigation-shell documents therefore move from install-time precache to first-visit runtime caching by the defaultCache PAGES handler. Accepted because the shells are skeleton-only without network data and recording routes were never precached. This is the observable behavior change that requires a changeset (patch, Changed / PWA).

### Decision 4: Stop producing public/sw.js

serwist.config.js is deleted; public/sw.js and public/sw.js.map are no longer generated. They are already gitignored (production and serwist section); the task list includes a check that no tracked copies remain so stale workers cannot ship from the repo.

## Risks / Trade-offs

- First-visit dependency for shell offline availability: a page never visited while online is not reachable offline. Mitigated by product reality (all pages need network data; no offline recording yet).
- Update rollout: clients registered at /sw.js will fetch a 404 for the old worker until their next page load registers /serwist/sw.js. Standard service-worker update flow covers this; the old worker keeps controlling until the new registration activates. Verified acceptable in evaluation.
- esbuild presence at build time: esbuild is a devDependency and the route is prerendered during build, so production runtime never needs it. If Vercel pruned devDependencies before build (it does not), the build would fail loudly rather than ship a broken worker.

## Migration Plan

1. Land the code change (route handler, config wrapper, import repointing, script and dependency swap, config file deletion) in one PR to dev with a patch changeset.
2. Release as v0.14.1 through the changesets workflow; this release doubles as the first live run of the automated tag, GitHub Release, and dev-sync pipeline.
3. After deploy, verify on production: /serwist/sw.js responds with the two baked headers, a fresh install precaches 104 entries, and an existing client updates to the new worker on second load.
4. Rollback path: revert the PR; the configurator setup is fully restored by the revert because all removed files are tracked in git history.

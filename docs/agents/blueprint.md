# Blueprint adapter

Blueprint presents current capability knowledge and published Change pages. `WORKFLOW.md` owns sequencing and gates; `docs/agents/issue-tracker.md` owns G1 acceptance and when a Change page is written.

## EmDash Change pages

A Blueprint Change page is one EmDash entry at `/changes/<slug>`, written only on demand (`docs/agents/issue-tracker.md`). The entry holds the reader-facing Change content, the optional associated Linear issue key, an allowlisted GitHub PR URL list, canonical Feature paths in `capabilities`, Portable Text and typed blocks. Store complete paths such as `platform/design-system/components` in the JSON array; derive display names from Feature metadata. PR URLs and capability paths are navigation/query metadata outside the accepted content hash; the accepted body defines scope and acceptance. It is the only editable page source. Do not copy the full specification into a Team Doc, Git, or the PR.

Authors and Agents write Portable Text and typed blocks directly through EmDash MCP. Portable Text is the sole article body format. Reject raw HTML, HTML/CSS/JavaScript blocks, executable TSX, MDX imports and arbitrary component names. New reusable typed blocks and renderers go through a GitHub code PR.

Before G1, use EmDash's signed private preview at the same Blueprint route. The page must identify the exact saved draft revision and the SHA-256 of its content, which the build computes to bind the rendered artifact to that content; it is not a G1 binding. After the developer accepts G1 by the label switch, publishing makes the entry public. A later content change needs a new draft, preview and acceptance. Updating only the PR URL list or capability paths does not change the content hash.

A newly published Change may have an empty PR URL list. It is public as **進行中** and shows no PR-derived metrics until URLs are added. PR badges link from the stored allowlisted URLs and do not depend on GitHub API availability. Add one URL for every required PR as it is created. A Change becomes **已完成** only when every required PR is merged, using the last required `merged_at`. Dates and summary order use `mergedAt ?? publishedAt`, descending. The page never shows G1/G2 acceptance badges or a separate discussion state. If a public Change is cancelled, unpublish it and retain its history.

G2 reviews the code PR only. The G2 PR links the execution issue; do not republish the Change page at G2. Production activation requires separate approval after G2. When a code PR merges, GitHub-derived status updates on a short cache interval without a Git deployment. A Blueprint code merge to `main` deploys the renderer; content events also request an automated SSG build, artifact upload and deployment.

## Blocks and rendering

Portable Text supplies ordinary prose, headings, lists, quotes, links, code, tables and media. Blueprint-specific semantics use typed blocks such as `decision_cards`, `risk_table`, `scenario`, `scenario_cards`, `interactive_flowchart` and `step_walkthrough`, mapped to existing Astro components after strict schema validation. Text, image, code and table blocks, with their spans and mark definitions, are owned by EmDash and validated loosely: unknown keys and marks pass, and only the fields the renderer reads are required. Saves are not schema-validated, so autosaved drafts may be incomplete; validation runs at publish and in the content build. A heading without an `id` (admin saves drop it) gets a GitHub-compatible slug of its text at render time (`github-slugger`, one instance per page in document order, duplicates suffixed `-1`, `-2`); an explicit `id` always wins. The renderer accepts only an explicit registry of known block types. Typed blocks carry no version: do not write `_version`; a stored `_version` key is accepted and ignored, and stays in the accepted content hash.

`tldr` wraps a `blocks` array of native Portable Text content in the Blueprint TLDR component. `disclosure` stores a non-empty `summary`, an optional document anchor `id`, and a `blocks` array from the same closed registry. It renders semantic `details` and `summary`, preserving nested review/shard groups up to eight disclosure levels. Raw HTML and executable content are rejected. Draft decision discussion may use a disclosure without creating or accepting an ADR.

`annotated_diff` stores ordered `{ kind, text }` lines, where `kind` is `context`, `add` or `remove`. The renderer escapes code as text and displays visible plus/minus marks, accessible added/removed labels, and semantic colors. It does not parse Markdown, annotations or HTML at runtime.

Portable Text `code` blocks and `annotated_diff` are syntax-highlighted with Shiki during the static build, using the `github-light` and `github-dark` themes through CSS variables. A missing or unknown language renders as plain text. No highlighting runs at request time.

`diagram` preserves static diagram viewBox, source IDs, typed shapes and numeric paths, positioned text runs, nested groups/transforms and typed marker geometry. Paint accepts controlled Blueprint tokens, strict hex colors, `none` or `currentColor`. Labels are escaped text; raw SVG, arbitrary attributes, CSS, scripts and URL paints are rejected. `interactive_flowchart` stores direct Mermaid `flowchart` or `graph` source, a JSON `details` record keyed by source node ID, and optional JSON `paths` whose ordered `nodeIds` identify authored paths. Missing `paths` defaults to `[]`; never infer paths. Pele 1.6.0 renders only the registered flowchart diagram with fixed links/images disabled and bounded source, node, edge and output limits. Reject frontmatter, init directives, raw HTML, custom styles/classes, links, and user-defined edge IDs; Pele escapes labels.

Capability paths must resolve to current Feature pages; resolve missing paths before publishing metadata.

`variant_gallery` version 1 is a reusable finite selector for data-authored visual variants. It declares labeled choices, a default selection, and exactly one pre-rendered Portable Text frame for every Cartesian choice combination. Frames contain only standard Portable Text blocks and `diagram` v1; they cannot contain nested galleries or scenario-counting blocks. The server renders every frame with the native Portable Text and typed-diagram renderers. Native buttons switch which existing frame is visible and transfer authored anchor IDs to the active frame, keeping deep links unique. Button labels remain fixed as `aria-pressed` communicates the selection. Authored data never supplies HTML, CSS, JavaScript, or component names.

`step_walkthrough` presents scenarios that step through a declared flow. It stores a flow map (main-row nodes plus branches under them, each a terminal, process or decision) with an optional shape legend, up to four actors, a system label and, per scenario, ordered steps. Each step names its flow node, gives every actor's state — headline, optional toned status, text lines, optional code and an optional highlight — and a system note. The server renders every step with native markup and build-time highlighted code; native buttons switch scenario and step, the flow map follows the visible step, and one polite live region announces the step title. Authored data never supplies HTML, CSS, JavaScript, or component names.

## PR-derived metrics

Store required GitHub PR URLs as a lookup index, one URL for each required shard. Validate the exact repository and PR URL shape. Derive status, merge date, commits, files changed, insertions, deletions and `src` files from GitHub's PR API; derive scenario count from structured scenario blocks. Store no manual status, merge date or statistics.

Cache unmerged PR data for at most five minutes. Cache merged responses permanently by merge commit SHA. If GitHub is unavailable, use a still-valid verified cache; otherwise omit metrics and keep the status at **進行中**. Do not infer merge from content, commit prose or Linear status. GitHub read token is an optional Worker secret; do not commit credentials. Stay within Cloudflare Free quotas and do not enable paid overage.

For the pinned EmDash/Cloudflare 1.2.0 media route, a GET performs one R2 `GetObject`; a failed range read may retry once. Workers Free limits requests to 100,000 per day, bounding this route at 6.2 million Class B operations in a 31-day month, below the 10 million R2 Standard free allowance. Media uploads are capped at 20 MiB per file; there is no in-repo usage ledger for media or page artifacts, so keep an account billing alert as the backstop. Keep media behind that Worker route, keep Workers on Free and check shared-account R2 usage before activation; do not enable public-bucket delivery or paid overage. Recheck this bound when upgrading the media adapter. See [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) and [R2 pricing](https://developers.cloudflare.com/r2/pricing/).

## Deployment

Cloudflare production deployment requires explicit post-G2 approval. Use the pinned Wrangler CLI and checked-in deployment configuration with Free-tier D1, private R2 and session KV bindings. Store `GITHUB_TOKEN` as a Worker secret and the Cloudflare build hook URL in EmDash plugin settings. Paid plans and overage remain disabled.

Verify that the target collection schema matches `.emdash/seed.json` before deploying readers. The optional JSON `capabilities` field contains only paths supported by the Change body and current Feature pages; an empty field produces no badges.

## Current knowledge and writing

Promote verified knowledge through `docs/agents/artifact-lifecycle.md` before the delivery PR, on the same branch. Use the narrowest Feature for capability behavior/constraints and the Design System authority for reusable UI/UX rules. Feature pages render decision records matching their exact capability IDs rather than copying decision text.

- Write Change prose in zh-TW with English technical terms. Features/Design System, scenario strings, ADRs and agent-facing documents use English.
- Component string props using `renderInline` support backtick code and single-level matched `**strong**`; code spans take precedence and unmatched markers remain literal. SVG labels remain plain text.
- Titles name the Change. Other-Change references and prose wrapping follow `CONTRIBUTING.md`.

## Static Change delivery

Save, publish, unpublish and delete events for `blueprint_changes` request a Cloudflare Workers Build through the plugin's encrypted `cloudflareBuildDeployHookUrl` setting. Restrict it to the official HTTPS `api.cloudflare.com/client/v4/workers/builds/deploy_hooks/<uuid>` endpoint. Do not log the URL. Hooks execute after the CMS response; they do not imply that a page artifact is ready. No daily Agent operation or Git content commit is involved.

Build with `pnpm --filter blueprint build:content`. The build snapshot path selects the configured `BLUEPRINT_DB` using only SELECT statements, validates the canonical Portable Text schema, and binds every view to its content ID, live or current draft revision, content hash and renderer digest. Public data comes from the published entry columns; draft data comes from the revision record. Reject ambiguous slugs, revision mismatches and schema errors. The build stops when a query reports cumulative reads above 10,000, or when read-cost metadata is absent or invalid. This threshold is checked after each query: that query has already consumed its reads and can exceed the threshold. An exhausted or failed reader sends no further query. This is an application stop condition, not a per-query reservation or a server-side D1 quota override.

Compute scenario counts from canonical blocks during the content build and bind them to artifact metadata. Runtime home, navigation, summaries and search read published metadata only; single-page requests read lifecycle metadata by indexed slug. Never expand article JSON or scan revision history to calculate request-time figures. GitHub cache reads remain batched by indexed keys. Audit SDK initialization, redirect, plugin and admin queries separately: their costs are not covered by the article-query budget. A full build intentionally reads each current body by identity, never all historical revisions.

For Blueprint query-cost verification, capture SQL from actual built-Worker requests using the pinned EmDash query recorder in an isolated local D1 environment. Exercise summaries, search and page/preview lifecycle lookup, then compare costs while increasing body size, unrelated revision history and article count. Record the query plan and distinguish SQLite VM steps from D1 `rows_read`; never label one as the other. A negative control must catch the former request-time JSON scan. Source-string checks or copied SQL alone do not prove the runtime path. Production measurements are bounded and require the separate activation gate.

Use the official EmDash Portable Text renderer and existing Blueprint typed-block components for SSG. Client islands retain their JavaScript and interaction handlers. Full SSG is intentional: measured warm builds did not reuse prerendered pages because the installed EmDash virtual module changes between builds. Do not claim incremental cache savings or patch SDK internals to obtain them.

Stage HTML only in ignored `.emdash/page-artifacts/`. Build-only preview routes must be removed from `dist/client` even when a build fails. Upload with `pnpm --filter blueprint upload:pages --remote` only during authorized activation. This verifies bytes and metadata by read-back, then writes the catalog last. `BLUEPRINT_PAGES` must be a dedicated private bucket with no public URL, custom domain or public media route; never reuse `BLUEPRINT_MEDIA`. Do not put drafts or snapshot payloads into public CI caches or artifacts.

Configure Workers Builds with the repository root and `pnpm --filter blueprint deploy:content` as its deployment command (the ordinary validation build is not the deployment step). This command requires a successful content build and artifact upload before `wrangler deploy`; a renderer-only validation build is not deployable content evidence. The command passes `--tag <sha>` and `--message "source <sha>"` to `wrangler deploy` so each deployed version names its source commit. The SHA is `WORKERS_CI_COMMIT_SHA` when that is a full 40-hex SHA (git-push builds); EmDash deploy-hook builds report the branch name there, so it falls back to `git rev-parse HEAD` of the cloned checkout. When neither yields a full SHA (manual local deploys outside a checkout), both flags are omitted. Local validation uses `node build/blueprint.mjs --database-file <isolated-sqlite>` and `node build/upload-pages.mjs --local --persist-to <isolated-state>` from `blueprint/`. It never requires production D1 access.

At request time, select lifecycle metadata without loading article blocks. Public access requires published status and the exact current live revision; signed private preview requires EmDash's verified content scope and the current draft/live revision. Verify artifact metadata before streaming. A missing or mismatched artifact returns 503 with `Retry-After`; invalid previews return 403 and deleted/unpublished public pages return 404. Never fall back to SSR or an old revision. Private preview remains `no-store` and `noindex`.

Public article headers and navigation load `/api/change-summaries`. This endpoint reads compact published metadata and catalog scenario counts, then reuses the existing GitHub PR cache. It does not parse article bodies, traverse JSON blocks, poll or stack another browser TTL. GitHub merges therefore do not rebuild article HTML. Build failure or an unfinished build cannot expose a draft; publishing a new revision may temporarily return 503 until its artifact is ready.

Workers Builds only coalesces queued/initializing builds, not a build already running. Verify account-wide Free build minutes, R2 storage/operations and D1 reads before activation; alerts are not a zero-dollar spending cap. Native EmDash admin/save/publish CPU and the deployed metadata/streaming route require separate Free CPU evidence. Local SSG success alone does not prove them.

Production D1 daily reads are a shared Free quota: browse or query the production site only for a task that needs it. Exhausted reads were observed to fail EmDash OAuth client registration with a generic 500 (`CLIENT_REGISTER_ERROR`) while local registration still succeeded.

Keep Cloudflare build credentials in encrypted Workers Builds settings. Snapshot reads use SELECT only; the artifact upload stage also writes the private R2 bucket. Credential scope must permit those operations without granting unrelated repository or account access; do not describe the entire build credential as read-only. Remote binding proxy access also requires the scoped Workers permissions documented by Wrangler. Validate the actual permissions during separately authorized activation.

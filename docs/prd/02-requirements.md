# 需求

基於對現有VolleyBro系統的深入分析，以下為完整的功能和非功能性需求。這些需求涵蓋已實現的核心功能模組以及計劃中的增強功能。

## 功能需求

### 核心功能模組（已實現/部分實現）

**FR1: 產品介紹頁功能** - _🟡 已部分實現_

- 系統應提供產品介紹頁面，包含產品功能展示、Beta階段定位、Waitlist註冊功能
- 當前狀態：已實現Hero區塊、Features區塊、Benefits區塊、Footer區塊，具備響應式設計和動畫效果
- 測試覆蓋率：95%+ (根據CLAUDE.md中的landing page測試覆蓋率)
- 待完成：Beta階段內容策略調整、Waitlist功能、技術優勢包裝展示

**FR2: 使用者管理功能** - _🟢 已實現_

- 系統應支援使用電子郵件或Google帳號進行註冊及登入
- 系統應允許使用者查看和編輯個人資料、密碼及頭像
- 系統應支援球隊邀請的查看、接受或拒絕功能
- 系統應提供已加入球隊列表並支援球隊切換
- 當前狀態：基於NextAuth.js v5實現，包含Google OAuth整合，具備完整的會話管理

**FR3: 球隊管理功能** - _🟢 已實現_

- 系統應支援創建新球隊並設定基本資訊（名稱、簡稱等）
- 系統應允許在多個球隊間快速切換
- 系統應支援新增成員資料、透過電子郵件邀請使用者加入球隊
- 系統應提供成員角色與權限設定(OWNER, ADMIN, MEMBER)
- 系統應支援球隊比賽陣容配置、球員場上位置分配、先發與替補名單設定
- 當前狀態：完整實現Clean Architecture設計，具備完整的CRUD功能和權限控制

**FR4: 賽事紀錄功能** - _🟢 已實現_

- 系統應支援新建賽事紀錄並設定比賽規則、地點、時間和類型
- 系統應能記錄每一球的得分與失分情況
- 系統應能記錄球員表現數據（攻擊、攔網、發球等）和替換情況
- 系統應提供比賽即時統計數據與分析報告
- 當前狀態：完整實現，包含Redux Toolkit狀態管理(record-slice.ts, lineup-slice.ts)
- 測試覆蓋率：包含完整的helper測試和repository測試

**FR5: 數據分析功能** - _🟡 已部分實現_

- 系統應提供數據視覺化圖表、儀表板工具
- 系統應支援過往賽事紀錄與統計資料查看
- 系統應提供數據導出功能（CSV、PDF等格式）
- 系統應支援數據比較功能（不同比賽、不同球隊之間的比較）
- 系統應提供數據篩選功能（依時間、球隊、球員等條件篩選）
- 當前狀態：基礎分析已實現，高級分析和機器學習功能待開發

### 未來擴展功能（計劃實現）

**FR6: Waitlist註冊功能** - _🔴 未實現_

- 系統應提供email註冊表單，支援潛在使用者加入等候清單
- 系統應支援email驗證和確認機制
- 系統應提供註冊成功回饋和狀態追蹤
- 必須與現有使用者註冊系統完全分離運作

**FR7: Beta功能標示和管理** - _🔴 未實現_

- 系統應實作feature flag控制Beta功能顯示
- 系統應在相關UI元件顯示Beta標籤
- 系統應建立Beta功能的使用追蹤機制
- 系統應提供管理介面控制feature flag狀態

**FR8: 即時通知功能** - _🔴 未實現_

- 系統應在比賽事件發生時（如得分、替換、局數結束）向相關使用者發送即時通知
- 必須與現有賽事紀錄功能整合，不影響運作效能
- 實現方式：考慮使用WebSocket或Server-Sent Events

**FR9: 戰術板功能** - _🔴 未實現_

- 系統應提供戰術板功能，允許教練創建、編輯和分享戰術圖解
- 必須與現有球隊管理介面和陣容配置系統整合
- 需支援觸控操作和多媒體元素

**FR10: 比賽影片整合** - _🔴 未實現_

- 系統應支援使用者上傳比賽影片並與現有賽事紀錄數據進行時間軸同步
- 必須擴展現有的數據分析功能
- 需考慮雲端儲存整合和影片壓縮

**FR11: 高級數據分析與視覺化** - _🔴 未實現_

- 系統應在現有數據分析模組基礎上新增機器學習預測模型
- 應提供進階統計圖表和趨勢分析
- 需與現有MongoDB數據結構整合

**FR12: 球隊與球員排名系統** - _🔴 未實現_

- 系統應基於現有統計數據自動計算排名
- 必須與現有球隊管理和數據分析功能整合
- 需考慮排名算法的公平性和透明度

**FR13: 社群功能** - _🔴 未實現_

- 系統應新增論壇、討論區功能，允許不同球隊間的使用者交流
- 必須與現有的使用者權限和球隊隱私設定相容
- 需實現內容審核和安全控制機制

## 非功能性需求

**NFR1: 效能要求** - _🟢 已達成_

- API響應時間必須控制在500毫秒以內
- 新增功能不得增加超過20%的記憶體使用量
- 當前狀態：已達成目標，系統運行穩定

**NFR2: 架構一致性** - _🟢 已達成_

- 所有功能必須遵循Clean Architecture分層結構
- 必須使用InversifyJS依賴注入模式
- 當前狀態：完整實現五層架構(Domain, Application, Infrastructure, Interface, Presentation)

**NFR3: UI/UX一致性** - _🟢 已達成_

- 所有UI組件必須與Shadcn UI + Tailwind CSS設計系統保持一致
- 必須支援響應式設計和PWA功能
- 當前狀態：完整實現，具備Serwist PWA支援

**NFR4: 測試覆蓋率** - _🟢 已達成_

- 新功能必須通過Jest測試策略驗證，測試覆蓋率須達到95%以上
- 必須遵循TypeScript和ESLint規範
- 當前狀態：統一jsdom測試環境，landing page達95%+覆蓋率

**NFR5: 安全性** - _🟢 已達成_

- 必須支援NextAuth.js v5身份驗證流程
- 必須與現有使用者權限系統(OWNER, ADMIN, MEMBER)整合
- 當前狀態：完整實現Google OAuth和權限控制

## 相容性需求

**CR1: 現有API相容性** - _🟢 保持_

- 所有新增API端點不得破壞現有RESTful API結構
- 現有前端功能必須持續正常運作
- 當前狀態：API結構穩定，向後相容

**CR2: 資料庫結構相容性** - _🟢 保持_

- MongoDB schema擴展必須向後相容
- 現有User、Team、Record、Member集合結構不得發生破壞性變更
- 當前狀態：使用embedded documents設計確保效能

**CR3: UI/UX一致性** - _🟢 保持_

- 新增功能的使用者介面必須與現有設計語言保持一致
- 確保使用者體驗的連貫性
- 當前狀態：設計系統完整建立

**CR4: 整合相容性** - _🟢 保持_

- 新功能必須與Redux Toolkit + SWR狀態管理無縫整合
- 必須與InversifyJS依賴注入和Serwist PWA功能整合
- 當前狀態：技術棧整合良好

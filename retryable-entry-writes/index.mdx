## Context

記一顆球是兩次資料庫寫入：一定執行的 `appendEntry`，以及該球剛好結束一局時才執行的 `completeSet`。`game-positional-writes` 的 D4 在 consequences 裡明列了「兩者合併後的失敗行為從未定義」，該 Change 沒有處理，登記為 residual risk R1。

兩者的重試性質相反。`completeSet` 寫的是推導值，重複執行結果相同。`appendEntry` 是 `$push`，重複執行就多一個元素。目前沒有任何東西區分它們。

實際的時間軸是：使用者記下讓該局結束的那顆球 → 前端樂觀更新、畫面顯示已記錄 → `appendEntry` 成功，**球已進資料庫** → `completeSet` 失敗 → 整個 request 回 500 → SWR rollback 且 `revalidate: false`，畫面退回「沒記到」且不跟伺服器對答案 → 使用者再記一次 → `$push` 再執行一次，同一顆球出現兩次，比分從此錯位。

第 6 步是關鍵：rollback 不只沒幫上忙，它**主動誘發**了造成重複的重試。UI 明確告訴使用者「沒記到」，而事實相反。

即使兩次寫入都成功，回應仍可能在網路上遺失。伺服器端已完成工作、無從得知確認未送達，使用者看到的同樣是失敗，重記的結果同樣是重複。

還有第二個問題，範圍比第一個更大：**目前每記一顆球都要等伺服器回應才能記下一顆**。順利時那是一兩百毫秒，感覺不到；但球館的 wifi 與行動網路本來就不穩，網路一差每筆就要等上好幾秒，而排球的球速等不起——實質上就是不能記錄。

## Goals

- 重送同一筆 entry 不產生重複，使「不確定就再試一次」從危險操作變成安全操作。
- 讓記錄流程在網路不佳時仍能連續進行，不被單筆寫入的往返時間卡住。
- 抵達順序不再決定資料庫中的順序——晚到的球仍排在它該在的位置。
- 讓系統自己承擔重試，而不是把「要不要再記一次」這個判斷丟給使用者；剩下真的需要人介入的失敗，必須恆常可見。
- 消除「單一 entry 的寫入失敗影響該局既有資料」的最後一種形式。`game-positional-writes` 已讓失敗不再毀掉既有資料，但失敗後的重試仍會產生重複，同樣是 `v0.15.0 記錄穩定性與資料完整性` 出場條件涵蓋的資料完整性缺口。
- 順帶讓錯誤模型宣告的 `retryable` 真正被某一層消費——該旗標目前全 repo 無任何讀取端。

## Non-goals

- 不做順序衝突解決。`seq` 保證的是**單一裝置記錄順序**不被抵達順序打亂；多裝置並行時語意層次的順序錨點屬 `intent-anchors`，本 Change 只保證不遺失、不重複、不亂序。
- 不做多裝置即時同步本身。本 Change 只移除它會踩到的地雷。
- 不動局間畫面的實作。是否移除局間畫面、改以多步驟 dialog 承載，屬 `game 流程一致性` 的討論範圍；本 Change 只在既有局間畫面上疊加提示。
- **不做完整的同步狀態指示器。** `SyncIndicator` 在本 Change 只做待送佇列的三態（已同步／同步中／N 筆未同步），報告的是**佇列狀態而非連線狀態**。離線偵測、SSE 重連狀態與多裝置語意仍屬 `sse-transport` 與 `conflict-panel`，那裡是在本 Change 的指示器上**擴充**維度，不是重做。
- **不做待送佇列的持久化。** 佇列只存在記憶體中，app 被關閉時未同步的 entry 會遺失；這是已登記的 residual risk，由獨立的後續工作在 v0.16.0 關閉。
- 不將 repository 泛用 `update()` 的存續條件工具化。那是 `game-positional-writes` 的 residual risk R2，與分層倒置稽核的邊界規則自動化可能重疊，歸屬未定。
- 不做資料遷移。專案尚未上線。
- 不觸發全 repo 的 response envelope 遷移（理由見 Design 的 D3）。

## Change boundaries

- **一定在內**：`create-rally`、`update-rally` 兩條寫入路徑，以及它們共用的 repository 寫入操作與 API route。
- **在內**：`entrySchema` 的 `id` 與 `seq` 兩個欄位、entity 層 `Entry` 型別、response schema、Redux draft——身分與順序必須存在於 entry 經過的每一層，且在樂觀推進**之前**就已產生。
- **在內（討論中確認）**：待送佇列。樂觀推進之後必須有東西記得「伺服器還沒確認什麼」，它同時是 `SyncIndicator` 與 entry row 失敗標記的唯一來源。獨立成 slice。
- **在內（討論中確認）**：`SyncIndicator`。失敗標記在 summary 的 entry row 上，而記錄畫面平常看不到那裡，沒有恆常可見的計數，一筆失敗的 entry 可能整局都沒人發現。
- **在內（版位量測後確認）**：`SetTally`。header 三欄已卡在可用寬度的臨界，`SyncIndicator` 插不進去；把數字局數比換成兩側的格子，才空出中欄原本屬於數字的位置。`Scores` 元件因此進入本 Change 範圍。
- **在內但常被低估**：`create-substitution`。它與 rally 共用同一個 repository 操作，合併後不可能只改一半。但它僅修錯誤處理，**不改 response 形狀**——換人永不觸發 `completeSet`，沒有第二件事要回報。
- **在內（走查中發現）**：兩個 rally usecase 逐行相同，唯一差別是呼叫哪個 repository 方法；合併該方法就等於合併它們，controller 與 route 一併收斂。
- **在內（討論中發現）**：編輯視窗的三個關閉出口。自動重試期間，返回按鈕、overlay 點擊、Escape 鍵都必須擋住，否則使用者會在結果未知時離開。原本只注意到返回按鈕。
- **在內**：共用 HTTP client 的 timeout 與網路層錯誤正規化。重試邏輯若無法分辨「很慢」與「已死」就無法決定任何事。
- **不在內**：`create-set`、`update-set`。它們是 set 層級寫入，不寫 entries，沒有身分問題。
- **明確不在內**：其他 domain 的 repository。

## Capability impact

`game-recording/persistence` 的可靠性契約再進一步：目前是「單一 entry 的失敗不影響該局既有資料」（`game-positional-writes` 已達成），改為「單一 entry 的寫入結果對 client 而言是可確認的，重送不改變已達成的狀態，且抵達順序不影響儲存順序」。

這對 `game-recording/collaboration` 是前置條件，而且是同一個解法一次涵蓋兩者：以身分為鍵的 upsert 在單一寫入者下提供重試安全，在並行寫入下提供不覆蓋——後者正是 `game-positional-writes` 的 D2 列為同步記錄前置條件的那一項。以陣列位置定址的方案能拿到前者卻會失去後者，因此不成立。

`game-recording/rally-recording` 的互動契約改變更明顯：**記錄不再與網路往返同步**。create 路徑樂觀推進，寫入在背景進行；使用者看到的失敗只剩下真正需要介入的那些。代價是引入一個新的恆常可見元素（`SyncIndicator`）、連帶把局數比改為 `SetTally`，以及一個新的持久化缺口（見 Non-goals 與 Design 的 Risks）。

## Alternatives considered

Design 頁完整記錄各組替代方案與否決理由。Overview 層級只記結論方向：

- **只做 `completeSet` 的後端重試**——收掉一半，另一半（`appendEntry` 成功但回應遺失）症狀完全相同，使用者感受不到差別。不成立。
- **index-addressed upsert（寫入第 N 格）**——單一寫入者的重試安全成立，但重新打開 lost update 窗口，等於推翻同步記錄的前置條件，之後必須反轉。
- **等回應才推進，配延遲顯示的 loading**——順序由結構保證、無需佇列，但前提是「順利時很快」。網路持續不佳時該前提崩潰，而那正是本 app 最可能的使用環境。
- **嚴格 FIFO 送出佇列**——伺服器永遠內部一致，但一顆球永久失敗會扣住它之後的每一顆。因為第五顆失敗而損失後面二十顆，比留一個會自癒的暫時空洞更糟。
- **單一具順序語意的識別碼（UUIDv7／ULID）**——可行且省一個欄位，但把順序凍結在建立當下：賽後編輯要插入一顆球就得改身分，而身分絕不能改。
- **沿用 Mongoose 自動 `_id` 作為身分**——身分必須在送出前存在才能讓重送被辨識為重送，伺服器產生的識別碼做不到。
- **以 response header 傳遞 `completeSet` 的確認訊號**——本 repo 無任何以自訂 header 傳遞應用層資訊的先例，且該訊號屬業務資料，放 header 會脫離型別驗證。
- **全 repo 改用 document envelope**——範圍遠超本 Change，且既有慣例本即「有真正獨立的額外事實才具名」，本次落在同一條規則內。

結構化 ADR 位於 `design/decisions/`，由 Design 頁的 `DecisionTimeline` 呈現。

| --- | ---------------------------------- | --------------------------------------------------------------------- |
| D1  | entry 如何取得穩定身分與順序       | client 產生 `id` 與 `seq`，append 與 replace 合併為 idempotent upsert |
| D2  | 重試該由誰負責                     | 依失敗性質拆分：伺服器處理寫入失敗，client 處理結果未知               |

## Revisit triggers

- 待送佇列被持久化：本 Change 登記的資料遺失 residual risk 屆時關閉，D4 的 consequences 需要一併校正。
- 賽後編輯加入「中間插入」：那是第一個需要重新編號 `seq` 的操作，屆時要在 client 端批次重編與改用 fractional ordering 之間選擇。
- 同步協作需要語意層次的順序保證，而非只要求不遺失、不重複、不亂序：D1 標註的 last-write-wins 邊界與「兩台裝置可能選到同一個 `seq`」屆時就是要重新檢討的地方。
- 連線狀態隨同步記錄進場，`SyncIndicator` 多出第二個維度：本 Change 的佇列語意需要重新表述。
- 出現第七條 game 寫入路徑且走了泛用 `update()`：代表 `game-positional-writes` 的 D3 存續條件沒有被遵守。
- 重試次數與退避間隔被量測推翻：目前的數值是未經量測的起始值，repo 內沒有 mutation 路徑的既有慣例可繼承。
- 系統因其他理由引入持久任務佇列：D2 反對「伺服器在 request 生命週期外重試」的論據會隨之減弱。
- 資料庫選型決定遷移至關聯式資料庫：文件資料庫特定的 guard、`arrayFilters` 與 `$sort` 實作作廢，但介面、身分模型與順序模型應原樣成立。

`id` 與 `seq` 各司其職。同一個 `id` 送兩次，第二次守衛不成立、零筆命中，狀態與只送一次相同；晚到的 `seq 7` 靠 `$push` 的 `$sort` 修飾符插回 `seq 8` 之前，抵達順序不再決定陣列順序。

## Contracts

**Repository。** `appendEntry` 與 `replaceEntry` 合併為 `upsertEntry`，收一個或多個 entry。參照參數收斂為 game 與 set 的定位。以 `bulkWrite`（`ordered: true`）逐筆送出，每筆兩個操作恰好命中一個：以 `arrayFilters` 依 `id` 覆寫（存在時），或以 `$ne` 守衛的 `$push` ＋ `$each`／`$sort: { seq: 1 }` 新增（不存在時）。兩者都是一般 update 而非 aggregation pipeline update，Mongoose casting 因此保留。陣容參數保留：換人會同時改變場上陣容，與身分無關。

**Use case。** `CreateRallyUseCase` 與 `UpdateRallyUseCase` 目前逐行相同，唯一差別是呼叫 `appendEntry` 還是 `replaceEntry`；repository 合併後兩者變成完全一樣的程式碼，因此**一併合併**為單一的 `RecordRalliesUseCase`。它驗證一次授權、寫入全部 entry、推導一次 set completion。controller 同步收斂為 `recordRalliesController`。

**API。** route 只保留 `PUT`——HTTP 語意中 PUT 本就是 idempotent 的動詞，正好對應 upsert；`POST` 留著會誤導。request body 收一個或多個 entry。response body 由裸 `Entry[]` 改為 `{ entries, setCompletionConfirmed? }`，status 維持 200。entry 索引 query param 移除，set 索引保留。換人端點維持裸陣列——它永不觸發 set 結果寫入。

**HTTP client。** 三個仍在用 raw `fetch` 的 action 遷移到共用 client，失敗因此攜帶 status 與 code。client 本身補上 timeout（原生 `AbortSignal.timeout`）與網路層錯誤正規化，否則重試邏輯無法分辨「很慢」與「已死」。

**送出資料的來源。** 兩條路徑都不直接發請求：`useSubmitEntryDraft` 只 dispatch `enqueued`，由佇列的 flush 讀取 `state.pendingWrites.pending` 組成請求。這是搭便車與順序保證的前提——請求永遠帶著佇列當下的全部內容。

連帶要改的是樂觀更新的寫法：現行 `mutate(promise, { optimisticData })` 把樂觀更新與網路請求綁在同一次呼叫，而佇列模型下網路請求屬於 flush。送出當下改為 `mutate(optimisticData, { revalidate: false })`（不帶 promise），flush 取得回應後再更新一次 cache。

**重試。** 伺服器端 `completeSet` inline 重試 3 次（50ms／200ms／500ms），回應前完成。client 端由待送佇列負責：in-action 2 次（300ms／800ms），耗盡後轉入較長的背景退避（2s／5s／15s），期間新 entry 入列會順帶 flush 整個佇列。4xx 這類重試無用的錯誤直接判定為失敗，不進入退避。

## 待送佇列：indicator 與失敗標記的單一真相來源

`SyncIndicator` 沒有自己的狀態欄位。它與 entry row 的失敗標記都是**同一個佇列的投影**，沿用 `game-positional-writes` D1 已確立的原則：會漂移的狀態不儲存，改為推導。

```ts
type PendingEntry = {
  entry: Entry; // 已含 id 與 seq
  gameId: string;
  setIndex: number;
  attempts: number;
  nextAttemptAt: number | null; // null 代表退避預算已用盡，或錯誤本身不可重試
};

type PendingWritesState = {
  pending: PendingEntry[];
  flushingGameIds: string[]; // 目前有請求在途中的 game id；一場比賽同時只會出現一次
};

type SyncStatus = "synced" | "syncing" | "unsynced";

export const deriveSyncStatus = (
  state: PendingWritesState,
  gameId: string,
): SyncStatus => {
  const pending = state.pending.filter((p) => p.gameId === gameId);
  return pending.length === 0
    ? "synced"
    : isFlushingGame(state, gameId) ||
        pending.some((p) => p.nextAttemptAt !== null)
      ? "syncing"
      : "unsynced";
};

export const isFlushingGame = (state: PendingWritesState, gameId: string) =>
  state.flushingGameIds.includes(gameId);

export const hasFailedWrite = (state: PendingWritesState, entryId: string) =>
  state.pending.some((p) => p.entry.id === entryId && p.nextAttemptAt === null);
```

`flushingGameIds` 與 `nextAttemptAt` 分開表達兩件不同的事：前者是「這場比賽正有一個請求在途中」，後者是「已排定下次嘗試」。兩者任一成立都算同步中。

`flushingGameIds` 掛的是 game id 而非單一布林值，因為 flush 以整場比賽為範圍（見下方「單一擁有者」）——切換比賽或背景重試與手動重試重疊時，可能同時有不只一場比賽的 flush 在途中，各自的完成不該互相影響對方的狀態。

避免對同一批 entry 重複送出，靠的不是這個欄位，而是 `usePendingWrites`（擁有 `inFlight` ref 與背景重試 timer 的那個 hook）在一場比賽的畫面上只掛載一次——見下方「單一擁有者」一節。`flushingGameIds` 只負責讓 indicator 與失敗標記知道「這場比賽現在是不是正有請求在飛」，兩者是不同層次的問題。

slice 的 action 面：

| Action           | 作用                                                                                                                   |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `enqueued`       | 推入一筆 `PendingEntry`（`attempts: 0`），並觸發一次 flush                                                             |
| `flushStarted`   | 把這場比賽的 game id 加進 `flushingGameIds`（已存在則不重複加）                                                        |
| `flushSucceeded` | 依 `id` 移除已確認的項目，把這場比賽的 game id 從 `flushingGameIds` 移除                                               |
| `flushFailed`    | 每筆 `attempts + 1`，依退避表寫入 `nextAttemptAt`；預算用盡或錯誤不可重試（4xx）則寫 `null`；把這場比賽的 game id 移除 |
| `retryRequested` | 手動重試：把所有 `nextAttemptAt === null` 的項目重設為立即，並觸發 flush                                               |

`gameId` 讓佇列在使用者切換比賽時仍能分辨項目歸屬，flush 時也以它決定要打哪一場的端點。

因為兩個視圖讀同一份資料，`SyncIndicator` 的計數與 row 的紅色標記不可能互相矛盾。

佇列放進**獨立的 slice**，而非併入 `game-slice`：它的生命週期與 per-set 的 draft 狀態不同，且之後要被獨立持久化。

與 SWR cache 不構成重複真相——兩者回答不同問題：SWR 的樂觀 cache 是「使用者看到什麼」，佇列是「伺服器還沒確認什麼」。

### 單一擁有者：`usePendingWrites` 只掛載一次

`usePendingWrites(gameId, setIndex)` 內部握有兩樣每場比賽只能存在一份的東西：判斷「目前有沒有 flush 在途中」的 `inFlight` ref，以及依最早到期時間排程下一次背景重試的 `useEffect` timer。四個地方需要用到佇列——`Game`（記錄畫面與局間畫面共同的上層）、`useSubmitEntryDraft`（送出 entry）、`GamePreview`（editing 卡片的送出中／失敗態與重試）、`SyncIndicator`——如果各自呼叫這個 hook，等於各自握有一份 `inFlight` 與一個 timer，同一筆到期的 entry 會被四邊各自的 timer 同時判定為到期，各自送出一個請求。

所以 `Game`（`src/components/game/index.tsx`）是這個 hook**唯一**掛載的地方——它本來就在記錄畫面與局間畫面的分支之上，一個 instance 能同時橫跨兩者。往下需要 `enqueue`／`flush`／`retry` 的元件，改由 `PendingWritesContext`（`usePendingWritesContext()`）讀取同一份結果，而不是各自呼叫 `usePendingWrites`；`useSubmitEntryDraft` 因為呼叫點本來就在 `Game` 內，直接把 `enqueue`／`flush` 當參數傳入即可，不需要走 context。

## SyncIndicator

`SyncIndicator` 使用 `RiErrorWarningLine` 搭配數字未讀點，點擊以既有的 `Popover` 展開單行狀態。展開動畫起點為與 icon 同寬的方形，內層 `overflow-hidden` 避免文字回流抖動。重試按鈕帶 icon，點按後關閉 popover、立即 flush 佇列、狀態切到同步中。

`SyncIndicator` 位於 header 正中央，因此 popover **向兩側展開**（`origin-center`，Radix 的 `align="center"`）——從畫面正中央往單一方向展開會顯得偏移。

### 何時現身

**佇列空的時候完全不渲染。** 恆亮的綠勾資訊量為零——空佇列是記錄者整場比賽 99% 的狀態，而且那個勾連自己宣稱的事都沒在做：斷線但沒有待送項目時一樣是綠勾，它代表的是佇列空，不是連線好。

版位不隨之伸縮。中欄用 `justify-center` 排列子元素，指示器若整個消失，排球 icon 會跟著上下位移；因此空佇列時渲染的是同尺寸的 `size-6` 佔位 div，只是裡面沒有東西、也沒有熱區。這同時讓 44×44 熱區與總覽入口的那筆交換**只在真的有東西要重試時才付**。

**從 unsynced 復原時，綠勾停留 `SYNCED_ACK_MS`（1.5 秒）才收起。** 重試成功後若直接消失，讀起來像 app 把請求丟掉而不是完成了它。這個確認只給「本來壞掉、現在好了」的轉換；例行送出（`syncing` → `synced`）不給，否則每記一球都會留下一個比送出本身還久的綠勾。

局間畫面（`Interval`）不渲染 `SyncIndicator`——`GameHeader` 在那裡不帶 `handleOptionOpen`，整塊 `Scores` 都不出現。這是正確的：轉場的前提就是 entry 已確認，局間沒有任何 entry 狀態需要提示，該階段唯一可能未完成的寫入是本局結果，而那件事由不可關閉的 dialog 獨佔呈現。

## 轉場時機

`Game` 切到 `Interval` 的判斷來自 Redux 的局內進行狀態，由 `confirmEntryDraftRally` 設定。**create 路徑改為在送出當下就 dispatch**，不等回應——這是網路不佳時仍能連續記錄的前提。

放寬的前提是三件事同時成立，缺一不可：`seq` ＋ `$sort` 讓亂序不再發生、佇列的自動重送讓多數失敗自癒、`SyncIndicator` 讓剩下的失敗不會無聲無息。

**update 路徑不放寬**：使用者本來就在編輯視窗裡等待結果，且編輯失敗經 rollback 後該 entry 回到伺服器上原本正確的值，資料未損壞也未不一致——與 create 失敗（該球在伺服器上根本不存在）性質不同。

轉場只依賴 entry 本身，不等 `completeSet`：該局是否結束是 client 從比分即可推導的事實，其持久化狀態不改變該事實。

## 偵測機制

`completeSet` 是否確認，兩條路徑結論相同、訊號來源不同，不能共用一套偵測：

| 情境                             | 訊號                                                         | 為什麼不能用另一套                                      |
| -------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------- |
| 即時送出                         | response 的 `setCompletionConfirmed`                         | 本地 cache 已被樂觀寫入，自行比對必然相符，偵測不出失敗 |
| 冷啟動（重新整理／直接進入路由） | 重新 fetch 的資料，以既有推導函式比對 entries 推導值與已存值 | 此時沒有「這次 response」可讀                           |

冷啟動這條不需要任何額外持久化狀態——推導函式本來就在做這件比對。

## Failure modes

| 失敗                                   | 現況                                         | 改動後                                                                  |
| -------------------------------------- | -------------------------------------------- | ----------------------------------------------------------------------- |
| `appendEntry` 成功、`completeSet` 失敗 | 整個 request 回 500，已成功的 entries 被丟棄 | 200 ＋ entries，確認欄位為 false                                        |
| `appendEntry` 成功、回應遺失           | 使用者看到失敗，重記 → 重複                  | 佇列帶同一 id 重送，伺服器判為 no-op                                    |
| 前一筆重試中、後一筆先送達             | 不適用（今天不會樂觀推進）                   | `$sort` 依 `seq` 歸位，陣列順序不受抵達順序影響                         |
| 網路持續不佳                           | 每筆都要等，實質無法記錄                     | 樂觀推進，寫入在背景退避重試                                            |
| 某筆永久失敗                           | 不適用                                       | 該筆留在佇列、entry row 標記、`SyncIndicator` 計數；其餘 entry 照常寫入 |
| 同一 id 帶不同 payload                 | 不適用                                       | last-write-wins；順序語意屬 intent anchors                              |
| 請求卡住不回應                         | 永不 settle                                  | timeout 後拋出可辨識的錯誤                                              |
| 斷網                                   | 落到「未預期的錯誤」fallback                 | 正規化為可重試的錯誤型別                                                |
| 4xx（驗證／授權）                      | 與 5xx 無從區分                              | 不進退避，直接判定失敗                                                  |
| 自動重試進行中離開編輯視窗             | 可離開，結果未知                             | 三個出口（返回鍵、overlay、Escape）皆擋住                               |
| 重試耗盡後離開編輯視窗                 | 可離開                                       | 允許，等同放棄編輯並 toast 告知                                         |
| **app 於仍有未同步 entry 時被關閉**    | 最多損失當下草稿                             | **未同步的 entry 遺失——見 Risks**                                       |

## Testing strategy

核心性質集中在一個 seam。integration 層驅動真實 route handler 直達真實的記憶體 MongoDB，是唯一能證明本次核心性質的地方：同一 id 重送不產生重複、`seq` 較小的 entry 晚到仍排在前面、不同 id 並行寫入都保留、`completeSet` 失敗時 entries 仍完整回傳。擴充既有的 entry 寫入與 set 完成兩個測試檔，不新增分層。

usecase 層以 mock repository 注入暫時性失敗，驗 `completeSet` 的重試次數與退避，以及「重試耗盡後已成功的寫入結果不被丟棄、確認欄位為 false」。依既有測試策略，usecase 測試不得 mock 任何資料庫概念。

`deriveSyncStatus` 與 `hasFailedWrite` 是純函式，直接以 entity 層的測試方式覆蓋三態與邊界。

component 層驗草稿預覽卡的 update loading 態與失敗態、`SyncIndicator` 三態與計數、entry row 的失敗標記、以及自動重試期間編輯視窗三個關閉出口皆不生效。

## Risks

**未同步 entry 在 app 被關閉時遺失。** 樂觀推進後，未確認的 entry 只存在記憶體中。這在特定情境下比改動前更糟：改動前沒收到確認就不推進，app 被回收最多損失一筆草稿；改動後可能一次損失數筆。本 Change **不**修這個缺口，它由待送佇列持久化的後續工作關閉，排在 v0.16.0。這是已知且已登記的 residual risk，不是遺漏。

**`upsertEntry` 的守衛與排序是風險集中處。** append 路徑要同時擋住「id 已存在」並維持 `seq` 排序，錯了是靜默的——寫進去了但條件或順序不對，直到讀取時才顯現。integration 層的亂序與重送測試是唯一能抓到這類錯誤的地方。

**`seq` 由 client 生成。** 這是必要的：若由伺服器在寫入時指定，晚到的 entry 會拿到較大的 seq，正是要修的亂序。資安上不構成新的攻擊類別——client 本來就在送整筆 entry 的內容，寫入仍由團隊角色授權把關；伺服器端的內容驗證（含 seq 合理性）屬既有的排球規則驗證工作。

**usecase 合併的連帶面。** `create-substitution` 與 rally 共用同一個 repository 操作，合併後不可能只改一半，但它的 response 形狀刻意不動——這個不對稱若在實作時被「順手統一」，會擴大本 Change 的 API 變更面。

## Plan versus actual

三處與核准計畫不同，都在審查中浮現並經判斷後採納：

**手動重試的範圍。** D4 的 action 表描述 `retryRequested` 重設**所有**已耗盡項目。實作收斂為「發起的那一場」。不收斂的版本有害：flush 與背景排程都以 game 過濾，別場的已耗盡項目會被推成「已排定」卻沒有任何掛載中的 hook 會嘗試它們——從「未同步（可見、可重試）」永久翻成「同步中」。收斂後才符合 D4 自己的意圖，即指示器顯示的與重試清得掉的必須是同一組。

**in-flight 訊號取得 game 身分。** `flushing` 原為無身分的布林。D4 與 Design 都把它描述為「請求正在途中」，而請求永遠屬於某一場比賽；狀態沒有反映這件事，導致「本場已耗盡＋別場在途中」與「本場已耗盡＋本場在途中」在元件眼中完全相同，任何建立其上的 guard 都只能二擇一。改為記錄 mid-flush 的 game id 集合後，兩個場景都成立，且兩個消費端的 guard 因此**變簡單**——不再需要 ownership 的變通寫法。

**S07 的 320px 驗收條件。** 原文要求 header 在 375px 與 320px 都不溢出。實測 320px 溢出 52px，但改動前是 56px——**這是本 Change 之前就存在的缺陷，本次讓它好了 4px**。驗收條件是撰寫時把 Design 的「以兩個寬度確認」誤寫成「兩個寬度都不得溢出」，等於要求一片做版面元件的 slice 順手修掉無關的既有缺陷。條件已公開修正為「375px 不得溢出且須實測；320px 同樣量測並記錄，且不得更差」，320px 支援另票追蹤。

## Review findings

兩軸各跑兩輪，另加兩輪對抗式驗證。

**第一輪** — 十項全數採納並修正：註解中的決策代號（硬性違規，19 個檔案，多於審查估計的 15 個）、`SyncIndicator` 同步中遺失計數、`retryRequested` 註解與 reducer 不符、`useSubmitEntryDraft` 的死錯誤路徑、重試手勢寫在三處、兩套重複的重試引擎、重複的呈現、repository 接縫的型別 cast，以及三項瑣碎重複。

其中兩項**查證後判定原本即合規**而非照單接受：裸 `<button>`（文件未要求每個 affordance 都用共用元件，且這些是遠低於 `h-9` 基準的行內 pill）與 `ring` 的使用（見下）。共用重試引擎的抽取先確認過不會把 server-only 或 client-only 的關切拖過分層邊界。

**第二輪** — 兩軸**獨立收斂到同一個缺陷**：`SyncIndicator` 與 `retryRequested` 未套用先前的收斂修正，後果是使用者可見的——別場 flush 時本場的重試按鈕消失，且手動重試會讓別場的項目更糟。另有一項硬性違規（新增的 `ui/` 元件缺 Storybook story）。

**第三輪（單一擁有者）** — 兩項使用者可見的缺陷。`usePendingWrites` 被四個元件各自掛載，各自握有 `inFlight` ref 與背景 timer，同一筆到期 entry 因此被送出四次；改為 `Game` 單一擁有、其餘經 `PendingWritesContext` 讀取。以及 `useUnconfirmedSetCompletion` 的 `attempting` 與 `deriveSyncStatus` 用了不同訊號，退避空窗期間不可關閉的 dialog 會閃爍消失；改為兩者同源。兩項都以「退回舊碼確認測試轉紅」證明，前者退回後從 1 次呼叫變成 5 次。

**驗收前的真實資料檢查** — 一項資料損壞缺陷，只有拿真實資料庫看才會浮現。`upsertEntry` 的兩個 bulkWrite op 都以 entry 的 id 為鍵；沒有 id 的 entry 會以 `entries.id: null` 落地，`arrayFilters` 因此**一次匹配該局所有沒有 id 的 entry**，一筆編輯把它們全部覆寫成同樣內容。integration test 全部從乾淨資料建起、每筆都有 id，所以整組測試都看不到它。以真實 MongoDB 重現：三筆 entry、前兩筆去掉 id/seq，編輯第 0 筆後第 1 筆的比分也跟著變。

沒有資料需要回填——`id` 欄位從未進過 `dev`，而 production 資料庫連 `games` collection 都不存在。修正是在 repository 邊界加守衛：沒有 `id` 或 `seq` 的 entry 直接拒收。型別宣稱 entry 必有 id，collection 卻裝得下沒有 id 的舊文件，型別在這個邊界上是假的，所以這裡檢查而不信任。

**對抗式驗證** — 推翻兩項宣稱，這是本次品保最有價值的一步。第二輪的修正把 `flushing` 用「有排程中的項目」把關，理由是「正在被 flush 的項目一定有非 null 的 `nextAttemptAt`」——該 invariant 為假（`runFlush` 分組不看 `nextAttemptAt`，online listener 無條件觸發），且 `deriveSyncStatus` 既有的分支已吸收該條件，等於把 flushing 訊號整個移除而非收斂。另推翻了 popover 圖示保留 `text-warning` 的宣稱。兩輪審查都只說「scoping 不一致」，是對抗式驗證去讀實作、造出反例，才確定修正的**推理**是錯的。

**驗收（真實瀏覽器、真實資料庫）** — 三項缺陷，全部在自動化測試綠燈之後才浮現。

一、**退避耗盡後不可關閉的 dialog 會自己消失。** `unconfirmed` 的三個判斷項在最需要擋住畫面的那一刻同時失效：伺服器從未回應所以沒有失敗訊號、樂觀寫入已經把 `win` 寫進本地快取所以冷啟動比對認為已定案、`attempting` 跟著 `nextAttemptAt` 而最後一次退避把它清成 null。沒有任何一項在問「這一局還有東西沒送出去嗎」。實測：12 次 PUT 之後 dialog 於數秒內消失，畫面停在局間、「新的一局」可按、伺服器上該局 `win` 仍為 null。修正為直接查詢佇列。

二、**手動重試成功後 entry 留在佇列裡。** 重試走的是 `flushPendingWrites` 而非 flush，沒有任何地方把它移除，指示器會整個 session 顯示一筆早已存好的未同步寫入。

三、**返回手勢可以逃出不可關閉的 dialog。** 三個出口只擋了 dialog primitive 自己的兩個（Escape、點擊外部），history 層完全沒有防護——而在手機上返回手勢是離開任何畫面的主要方式。修正為攔截並詢問，備用 history entry 每次被吸收後重補，連按多次都擋得住。

驗收另外確認：熱區四個探測點（中心與左右下各 16px）全數命中 trigger；失敗列帶 `ring-1 ring-destructive` 與並排的重試控制；編輯視窗在寫入失敗時維持 `data-state="open"`；閒置時排球圖示位置與寫入途中完全一致（top 6 / top 6）。

綠勾停留時長無法在自動化環境量到精確值——該分頁 `visibilityState` 恆為 hidden，timer 被壓制——功能面已確認，時長由 fake-timer 單元測試涵蓋。

## Residual risks

- **未同步的 entry 在 app 被關閉時遺失。** 佇列只存在記憶體。此情境比改動前更糟——改動前沒收到確認就不推進，最多損失當下草稿；改動後可能一次損失數筆。已登記並另票追蹤，排在 v0.16.0。
- **320px 螢幕的 header 溢出**（既有缺陷，本次改善 4px 但未解決），另票追蹤。
- **`ring` 的使用與設計系統的 No-Ring Rule 存在衝突，已裁決。** Design 指定失敗態用 `ring-1 ring-destructive` 並刻意否決虛線 border；`design-system.md` 則寫 `--ring` 僅保留給 focus-visible。查證後認定衝突出在文件而非程式碼：六個 `ui/` 元件已在使用裝飾性 ring，文件自身有三處互相牴觸的例外，且 No-Ring Rule 那張表講的其實是 elevation 而非狀態標示。決議為維持所有既有 `ring` 用法不動，改由後續工作修正文件；所有修正輪均未觸碰任何 `ring` utility。
- **`set-completion-slice` 是新增的儲存狀態。** Spec 軸將其列為未要求的擴充。判斷為保留：規格禁止的是**冷啟動**偵測依賴額外儲存狀態（實作確實沒有，用 `set.win === null` 比對），而即時送出那條路徑是 D3 明文承認回應欄位為唯一可用訊號——本地快取已被樂觀寫入，自己比對自己永遠相符。該 slice 刻意不持久化，重新載入會正確落回冷啟動比對。

## Follow-ups

九個切片。前兩片沒有相依，可以同時開始；其餘的順序由相依關係決定，不是由檔案位置決定。

S04 是最大的一片，也是唯一會同時改動 use case、route 與 response 形狀的一片。S01 與 S02 存在的理由就是讓它動手時只剩下契約本身要驗：錯誤模型已經對了（S01），身分與順序已經在每一層了（S02），寫入語意已經證明過了（S03）。

## 為什麼 S01 先於 S04

S04 要改 response 形狀，三個 action 的解構都要跟著換。那三個 action 目前繞過共用 HTTP client、失敗時丟一個沒有 status 也沒有 code 的裸 `Error`——現行 rally 送出失敗永遠落到「未預期的錯誤」那個 fallback，既有的 5xx／4xx 分流從來沒有生效過。

若不先修，S04 會在同一片裡同時改「錯誤怎麼來」與「成功長什麼樣」，出問題時分不清是哪一件。S01 先把錯誤模型接對，S04 就只需要對成功路徑負責。

S01 同時補上 timeout 與網路層錯誤正規化。那兩件事單獨看像是順手做的整理，但 S06 的重試邏輯依賴它們——分不出「很慢」與「已死」就無法決定何時放棄，認不出斷網就無法決定該不該重試。

## 為什麼重試自成一片

S05 只做一件事：本局結果的寫入在同一個 request 內重試。它與 S04 分開，是因為兩者的失敗形狀不同。

S04 交付的是**契約**——entry 寫入成功之後，本局結果的成敗不再影響它，且回應說得出來。那條契約在沒有任何重試的情況下就該成立，也該被單獨驗證。S05 交付的是**行為**——多數暫時性失敗在回應送出前就消失了。

把兩者綁在一起，「entries 沒有被丟棄」與「重試有效」會在同一片裡一起驗，而前者是資料完整性、後者是體感優化，失敗時的處置完全不同。

## S06 是整個 Change 的樞紐

S06 之前，每記一顆球都要等伺服器回應。S06 之後，記錄與網路往返脫鉤——這是本 Change 對使用者最大的改變，也是後面三片的前提。

它同時是三個新事實的唯一來源：`SyncIndicator` 顯示什麼（S07）、entry row 標不標記失敗（S08）、以及重試由誰排程。因為三者都從同一份佇列推導，它們不可能互相矛盾——這是刻意的，沿用 `game-positional-writes` D1 已確立的原則。

樂觀推進本身只有在三件事同時成立時才站得住腳：`seq` 讓亂序不再發生（S03）、佇列自動重送讓多數失敗自癒（S06）、`SyncIndicator` 讓剩下的失敗不會無聲無息（S07）。**S06 單獨落地而 S07 沒有跟上，會是這個 Change 最危險的中間狀態**——失敗變得看不見。若要分批交付，S06 與 S07 應該一起。

## 版面必須以量測驗收

S07 的驗收條件寫的是「header 在 375px 與 320px 都不溢出，且要實際量測而非推定」。

這條不是形式。這個版位在討論階段被算錯過兩次：先是以為插得進去（實測溢出 37px），後來以為 `absolute` 能解決空間問題（實際只解決版面成本，局數比下方僅剩 14px）。兩次都是靠瀏覽器量出來才發現的。

`SyncIndicator` 的觸控熱區約 24×24，低於 44×44 的建議值。這是這個版位的已知上限，不是遺漏；若實機測試顯示觸控準確度不可接受，替代路徑記在 D4 的 alternatives。

## 刻意不變的部分要被驗收

幾條看起來像廢話的驗收條件，作用是把「不該變的東西」釘住：

- **S03**：新寫入路徑不得使用 repository 的泛用 `update()`——那是 `game-positional-writes` D2 的存續條件，目前只靠介面註解把關。
- **S04**：換人端點維持裸陣列。它與 rally 共用同一個 repository 操作，合併時很容易被「順手統一」，但它永不觸發本局結果寫入，沒有第二件事要回報。
- **S06**：編輯路徑**不**樂觀推進。兩條路徑刻意不對稱，因為編輯失敗後該 entry 回到伺服器上原本正確的值，與 create 失敗（該球根本不存在）性質不同。
- **S09**：轉場仍然只依賴 entry 確認，不等本局結果。該局是否結束是 client 從比分即可推導的事實。

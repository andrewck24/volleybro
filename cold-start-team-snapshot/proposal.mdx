## 範圍

1. **本地偏好：** `{ version, userId, teamId }`，自己的一個 localStorage 項目，是這台裝置上「目前看哪一隊」的唯一來源。與深色模式（由函式庫管理）以及 `profile.preferences`（不動）無關，也不做通用的偏好框架，等出現第二個由我們自己存的偏好時再抽共用部分。
2. **解析順序：** `useActiveTeamId` 先讀偏好並立即拿它請求該隊；請求成功且 `userId` 相符即視為驗證通過。沒有偏好、`userId` 不符、或請求被拒絕，就走現有的完整解析（`profile.activeTeamId` 若仍是成員，否則第一個已加入的隊），並把結果存回偏好。存回只發生在隊伍資料真的載入之後。
3. **失效時的路由：** team tab 的根路徑目前只在第一次拿到 `teamId` 時決定一次；偏好失效、解析結果改變時，它要跟著更新。
4. **寫入來源：** 切換器只寫本地偏好，不再 `PATCH /api/profiles`；接受邀請成功時，客戶端寫入偏好；登出時在導頁之前先清除。
5. **預載：** 有偏好時，用 SWR `preload` 預先請求該隊與球員名單，讓新增比賽 dialog 打開時資料多半已就緒。
6. **兩層：** interface 層放型別、儲存介面（`load`、`save`、`clear`、`subscribe`，供 `useSyncExternalStore` 使用）與不含 React 的純函式決策；persistence 層放 localStorage 實作，是唯一碰這個 key 的檔案，儲存可注入；hook 以 `useSyncExternalStore` 接線，伺服器端快照為 `null` 以避免 hydration 不一致。
7. **本 Change 不動伺服器端：** 伺服器寫入與清除 `activeTeamId` 的程式碼、資料庫欄位與客戶端的退回讀取，由後續的行為 Change 移除。
8. **文字更新：** `sync-indicator.tsx` 裡「佇列是這個 app 唯一放進 localStorage 的東西」的註解不再為真，一併更新。

**不在範圍內：** 任何伺服器資料（`TeamView`、球員、比賽）的本地快取；service worker 的快取策略；`profile.preferences`；伺服器端 `activeTeamId` 的移除。

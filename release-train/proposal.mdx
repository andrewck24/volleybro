## Scope

### Shards 與 repository 範圍

下表是直接相關的 owner 清單，不是要求每個檔案都修改。只更新真正承載活規則的部分；歷史 Changes、migration 紀錄與舊 changelog 不全域替換。現有 AGENTS／CLAUDE 是導航，不為涵蓋範圍而新增重複 policy。

既有 hooks 由 commitlint 承載分支政策，不新增 pre-push hook。切換前的文件與檢查仍如實描述 dev 現況；Shard 2 才切 main。受影響的 Migration CLI 選項、診斷與測試一起處理兼容性，不只替換名詞。

### 討論與可發布邊界

- Intake 依契約與交付批次分類為 Fix path／Change／Sharded Change；新增內容擴大規模時重新分類。所有大型 migration 都用 Sharded Change。不同目標或仍需獨立架構決策則分成不同 Changes。
- Sharded Change 共用 slug、Proposal／整體 G1；逐 shard branch、Review／G2／PR。不可分割的 shards 合成同一交付批次，內部 slices 仍可追蹤；不得先把需要下一批救回來的半成品合進 main。
- wayfinder 適用跨 session 或尚不清楚的決策路線，尤其大型 Sharded Change；不是每個 shard 的必跑步驟。已收斂內容不補建無用途的 map。grill-with-docs 用於有待人類判斷的選項；可查事實由 research/search 處理，可行性或具體設計不明才用 prototype。repo 不要求名為 search 的 skill，等價查詢方式即可。
- 討論完成前清點文件、規則、腳本、平台邊界與測試證據；收斂後製作並發布 Proposal、實際讀取 rendered page，下一個停止點才是 G1。不得用「已 grill 完」掩蓋未清點內容，再於頁面前逐項補問。必要權限或會使剩餘工作無效的新分歧，仍保留既有安全停止例外。
- 「用哪些證據證明可發布」先辨識風險與既有 coverage，不等於每個 Change 新增測試。bug regression 修正前失敗／修正後通過；測試維持 owner boundary、重用 test/support、不製造 test-only production seam。test-audit 仍需實際執行。
- Archive 先判定 durable knowledge 是否改變，必要時更新最窄 Features，Review 說明結果；不增加人工 gate。writing-changesets 保留有效 body-format，刪除失效 dev→main→sync、舊 artifact／script／skip-review 指引，引用 canonical workflow；每個有版本影響的交付批次攜帶對應 changeset。

既有 integration tests 直接驗證 route handler／DB 邊界，auth 使用 test doubles，不代表 Google OAuth／真實 session 已驗證。首頁、登入能力／session、登入後 team 唯讀檢查是 smoke 核心；已有 session 不等於完整 OAuth 測試。安全 session 策略保持獨立，實作前 security review，不新增 production login bypass。自動 session 未完成時，候選與上線後必要人工驗收放 Review 的 TestPlan／ActionItems；未完成不得 promote／標成功，等待不是失敗。

### 正常 release、首次切換與 hotfix

1. main 累積具版本影響的 changesets，bot 持續更新 changeset-release/main，title 固定 release: update versions。Monorepo 不同 packages 的 changesets 共用正常 version PR，由版本策略決定各 package bump；本期不實作 monorepo split。
2. PR push 即跑驗證；授權 merge 前必須是 latest revision 的 required checks。aggregate Verify 包含 static／unit／integration／Blueprint／commitlint；部署 build check 驗證 integration，不冒充 production smoke。固定 title 例外只允許可驗證 bot identity＋head＋內容，不泛跳過 main 檢查。
3. 合併是正式發布授權，固定 release commit，不以「沒有 changesets」推論任何 main push 都可發布。之後 main 新內容不替換候選；所選版本含截至該 Change／Fix 的所有尚未發布整合內容。
4. production-config candidate 驗證與必要人工 fallback → 發布鎖內重查基準 → promote → production smoke → 成功才建固定 SHA tag／GitHub Release。不用二次 release 授權，但不能宣稱有人工 fallback 的第一版完全自動化。
5. 候選失敗不 promote；promote 結果不明先查實際 deployment。上線後失敗只回退到已確認與 DB 相容的舊 deployment，再驗證／通知；不相容或未知停止／通知，不回退資料。正常 release 在 Shard 2 就有這些控制，Shard 3 重用。
6. Bot 在之後有 non-empty changesets 才重建／更新 version PR，不是發布完成後無條件重建。重試 idempotent，已建立 tag 不移動。

Shard 2 的首次正式發布預期為 v0.16.0：既有未發布 dev 交付加已整合的本 Change Shard 1／2。切換前重新核對 refs、PRs、worktrees、Changesets 實際版本與範圍；不是嚴格只含原 Cycle 1，不硬覆寫版本。G2 前演練，正式發布結果放 AfterRelease，不提前假稱已驗收上線；不必等待 Shard 3／4。

先準備可回復流程，解除 main merge 直接上 production 的連動，再保留 dev 必要歷史並整合新流程；成功發布且無活引用後才移除 dev。不得改其他裝置／活 worktrees，或遺失唯一歷史。平台設定以 live inventory／read-back 驗證，repo 文件不能替代其證據。

緊急重大 production bug／重大漏洞走 deployed-base hotfix，獨立修補與 patch version，dispatch 明確授權 reviewed SHA。Urgency 不豁免 Change gate。發布成功後 merge-back main，核對版本、changelog、已消耗／仍 pending changesets；不 rebase main。衝突無法安全處理就停。hotfix 後暫停／拒絕舊正常候選，同步後重建候選、重驗證並重新授權。

### Dependency 與 cycle 節奏

Dependabot graph／alerts／security updates 與 npm ecosystem（pnpm）／GitHub Actions weekly version updates 都納入。每週二 09:00 Asia/Taipei 掃描；不承諾精確完成分鐘，Gmail digest 不當觸發條件。週二 13:00 人工 intake、18:00 planning cutoff，週三 09:00 bot 準備／檢查，13:00–15:00 release owner merge／hold；cutoff 不凍結 rolling main snapshot。Security updates 依漏洞事件執行，不等週三緊急修補。

只允許可信 Dependabot 的單一 allowlisted 非敏感 direct devDependency patch、限制 package／lockfile diff、無 scripts／config／runtime 擴張、最新 checks 全綠後 auto-merge main。major、minor、敏感、未知、多套件、CI 失敗全部人工。具體清單於 Shard 4 Review 提出，G2 接受前不啟用；空清單可安全過渡，但最終須演練核准套件的自動路徑。不把 untrusted PR code 放到有 write permission／production secrets 的 runner。

人或開發者自行決定需不需要 Agent；major／高影響能安全完成就留 PR review，無法安全實作或需新決策才開 issue。Auto-merge 不等於 production 發布。下一 cycle 承諾、下下 cycle 候選；估點只計可執行 leaf issues，不重複算 parent。容量依完整週期實績與 token 資源校正，不沿用半週外推的暫估上限作硬規則。

### 不包含與既有工作歸屬

不包含 Symphony unattended execution、完整 E2E／agent harness、test-pr DB、長期 production／maintenance branch、monorepo split 實作、完整 error tracker／source maps、未指定 v1 資料搬移。

現有 main→dev sync／App bypass 工作在舊 sync 移除驗收後以需求被取代處置，不冒充已實作 App；version PR body cosmetic 留原工作，必要 pipeline 相容調整若同時解決才附證據。安全 session 與完整 observability 保持獨立。

平台 alias、必要 credentials、具體 dependency allowlist 是已限定的後續 Review 操作項，不是尚未決定的主架構；任何付費、權限擴大、資料搬移仍需必要授權。本次下一個停止點僅為整體 G1；G1 接受後才進 Apply，不能跳過逐批 G2／Pre-PR review。

## References

- [Changesets automation](https://changesets.dev/guide/automating)：版本內容持續累積與 version PR 是官方常見路徑；production deployment gate 是本 repo 的應用部署責任。
- [Changesets Action](https://github.com/changesets/action)：版本 PR 與 CLI 的相容 major 須確認；不假設無 changesets 的任意 push 是授權。
- [Changesets backporting](https://changesets.dev/guide/backporting-changes)：隔離 release 基準的版本工作，不代表自動解決 main metadata 衝突。
- [Vercel deploy](https://vercel.com/docs/cli/deploy)／[promote](https://vercel.com/docs/cli/promote)：CLI 支援 production-config staged deployment 與 promote；platform 認證／環境須 live 確認。
- [Git rebasing](https://git-scm.com/book/en/v2/Git-Branching-Rebasing)：不 rewrite 已共用 main；透過 merge-back 留下修補與整合紀錄。
- [Chromium release branches](https://new.chromium.org/developers/how-tos/get-the-code/working-with-release-branches/)：成熟團隊也會區分 trunk 與 release 修補；其 branch 管理不同，不把本設計說成 Google 唯一做法。
- [Dependabot options](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference)：npm ecosystem 支援 pnpm，weekly schedule 與 security events 是不同來源。

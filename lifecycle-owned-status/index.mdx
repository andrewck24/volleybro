<TLDR>
  Change status stops being a directory and a stored field. Lifecycle becomes
  the single source, status is derived from it as a grouping key, and every
  Change lives at a flat, permanent URL.
</TLDR>

## Context

A Change's status is stated in three places. It is a directory (`discussing/`, `in-progress/`, `archive/`), a field in `change.json`, and — for archived Changes — a date prefix on the directory name. `parseChangeMetadata` reconciles the first two by deriving status from the directory and rejecting a `change.json` that disagrees.

Moving a Change between statuses therefore edits four things: the directory itself, the `status` and `lifecycle` fields, `archivedAt` when archiving, and the `designModules` key in the changes route when the Change has a `design.tsx`. Forgetting the last one breaks the Blueprint build.

Worse, the move changes every URL the Change owns. Overview links, Change cards, breadcrumbs, and any cross-reference from another Change or from `docs/` point at a path that contains a lifecycle stage — a value that is expected to change several times over the Change's life. The recent Overview work removed the hand-copied metadata that drifted from `change.json`, but it could not remove the drift built into the paths themselves.

`lifecycle` already determines `status` completely. `lifecycleMatchesStatus` encodes a total function from nine lifecycle values onto three status values, and validates that the stored `status` agrees with it. The repository stores a value it can compute, and then maintains a check to keep the copy honest.

## Goals

- A Change's URL is fixed for its whole life. Advancing its lifecycle never invalidates a link, a `designModules` key, or a page list.
- One canonical statement of where a Change stands: `lifecycle` in `change.json`.
- `status` survives only as a derived grouping key for the catalog's three browse buckets, computed from `lifecycle` by a table the compiler forces to stay exhaustive.
- Readers see the precise stage. A Change in `pre-pr-review` says so, instead of being flattened to "In Progress" with a second badge to disambiguate.

## Non-goals

- No redirects for the old URLs. The developer confirmed there are no external references; internal ones are updated in this Change.
- The historical snapshots under `docs/changes/` and `docs/specs/` keep their existing links. `WORKFLOW.md` already treats them as snapshots.
- The lifecycle values themselves do not change, and neither does which lifecycle a stage sets. `proposing` and `ready-for-review` keep grouping under In Progress.
- Feature pages are untouched. Their paths are capability-based and carry no lifecycle segment.

## Boundaries

In scope: the ten Change directories, `change.json` and its schema, `parseChangeMetadata`, `loadChangeCatalog`, the breadcrumb tree, the `designModules` registry, the status badges in `ChangeCard` and `ChangeOverview`, the surviving internal cross-links, and the sections of `WORKFLOW.md` and `docs/agents/artifact-lifecycle.md` that describe the directory layout.

Out of scope: everything the catalog does with the three buckets. Filtering, the sidebar's four links, and the month grouping of the archive all keep working exactly as they do now.

## Capability impact

`platform/blueprint` gains a stable addressing scheme and loses the status-shaped directory tree. `platform/delivery-workflow` loses two steps from the Archive procedure.

## Alternatives considered

Keeping the status directories and stabilising URLs with the loader's `url` override was rejected: it fixes only the links while leaving the directory renames, the `designModules` edits, and the page-list edits in place, and it makes the path no longer predict the URL.

Deleting `status` outright and exposing the nine lifecycle values as filters was rejected: the coarse grouping still has to exist, so the mapping would move from `change-types.ts` into a component rather than disappear, and ten Changes spread over nine filters browse worse than over three.

Both are recorded with their full reasoning in the Design decisions.

## Revisit triggers

- A lifecycle value is added and the catalog needs a fourth browse bucket, which means the three-bucket grouping no longer fits the lifecycle.
- Changes accumulate to the point where a flat `content/changes/` directory becomes hard to scan, which would argue for grouping by year rather than by status.

## Design

## Adopted shape

One fact, `lifecycle`, in one place, `change.json`. Everything else about where a Change stands is computed from it.

```text
blueprint/content/changes/
├── meta.json                  { "title": "Changes", "pages": ["index", "..."] }
├── index.mdx
├── game-positional-writes/    lifecycle: archived
├── sync-recording/            lifecycle: discussing
└── lifecycle-owned-status/    lifecycle: proposing
```

A Change is served at `/changes/<slug>/`, for its whole life. The directory name is the slug and the slug never changes, so neither does the URL.

## Contracts

**Status derivation.** `change-types.ts` gains the mapping and its accessor:

```ts
const LIFECYCLE_STATUS: Record<ChangeLifecycle, ChangeStatus> = {
  discussing: "discussing",
  proposing: "in-progress",
  "ready-for-review": "in-progress",
  "ready-for-implementation": "in-progress",
  applying: "in-progress",
  ingesting: "in-progress",
  "pre-pr-review": "in-progress",
  "awaiting-delivery-review": "in-progress",
  archived: "archived",
};

export const statusOf = (lifecycle: ChangeLifecycle): ChangeStatus =>
  LIFECYCLE_STATUS[lifecycle];
```

`Record<ChangeLifecycle, ChangeStatus>` is the load-bearing part. Adding a lifecycle value without mapping it is a compile error, so the derivation cannot drift from the lifecycle it derives from.

**Metadata parsing.** `parseChangeMetadata(value, directoryName)` loses its `status` and `directory` arguments. It validates that `record.slug === directoryName`, computes `status` with `statusOf`, requires `archivedAt` when `lifecycle === "archived"`, and returns `href` as `/changes/${slug}/`. `lifecycleMatchesStatus` is deleted — once status is computed it can only ever match.

**Catalog loading.** `loadChangeCatalog` reads one directory instead of three. Sorting and the month grouping keep using `archivedAt ?? startedAt` and are unaffected.

**Schema.** `change.schema.json` drops `status` from `properties` and from `required`. This is a breaking change for the ten existing files, all of which are edited in the same Change.

**Display.** `ChangeCard` and `ChangeOverview` take `lifecycle` and render one badge from it. The `status` prop and the `lifecycle !== status` condition are removed. The badge colour keeps following the coarse status, so archived stays primary-tinted and in-progress stays warning-tinted; only the label becomes precise.

## What deliberately does not change

The catalog's three filter buttons, the sidebar's four links, the `?status=` query parameter, and the archive's month grouping all behave exactly as they do today. `status` remains a first-class concept in the UI — it simply stops being written down.

## Failure modes

| Failure                                           | Before                                          | After                                               |
| ------------------------------------------------- | ----------------------------------------------- | --------------------------------------------------- |
| A Change advances and its Overview links go stale | Silent dead links until a reader finds them     | Impossible; the URL does not depend on lifecycle    |
| A Change moves and `designModules` is not updated | Build fails with a module resolution error      | No move, so no edit; the check still covers renames |
| `change.json` disagrees with the directory        | Caught by `lifecycleMatchesStatus`              | The disagreement cannot be expressed                |
| A new lifecycle value is added                    | Nothing breaks; it silently maps to in-progress | Compile error until it is mapped                    |

## Migration

Ten directories move. The internal references that must move with them are bounded: `blueprint/src` tests and the changes route, two links in `blueprint/content`, one in `WORKFLOW.md`, one in `docs/agents/artifact-lifecycle.md`. References inside `docs/changes/` and `docs/specs/` are historical snapshots and stay as they are, per `WORKFLOW.md`.

`WORKFLOW.md` needs three edits: the Implementation-slice contract's directory tree, the sentence listing what a lifecycle move touches, and Archive step 6, which stops moving a directory and only sets `lifecycle` and `archivedAt`.

## Testing strategy

The existing suites carry most of the weight. `change-metadata.test.ts` covers the new signature and the derivation, including that a Change whose directory name differs from its slug is rejected and that `archivedAt` is still required for an archived lifecycle. `changes-tree.test.ts` is rewritten alongside the tree it tests. A rendered-output check confirms that all ten Overviews still list the same artifacts and that no link in the built site is dead — the same check that caught the shadowing problem twice.

## Risks

The tree rebuild is the risky part. `createChangesBreadcrumbTree` currently keys off lifecycle folder names, and with those gone it needs a different shape; its companion `withDirectChangePages` may already be dead since the meta-collection fix removed the page shadowing it compensated for. That is assessed during Apply rather than assumed here.

## Review findings

兩軸各跑兩輪，第二輪皆無新的阻斷發現。

### 已修正

1. **`change.schema.json` 兩個 `allOf` 分支仍以已移除的 `status` 為鍵**（兩軸獨立發現，最嚴重）。JSON Schema 對缺席的 key 是 vacuously true，加上 `additionalProperties: false` 保證 `status` 永不出現，於是兩個 `then` 無條件套用，同時要求 lifecycle 既是 `archived` 又是 `discussing`。以 ajv 驗證確認 **12 份 `change.json` 全部不通過**。修正保留以 lifecycle 為鍵的 `archivedAt` 約束，而非刪除整段——刪除會讓 schema 比 `change-metadata.ts` 的實際行為寬鬆。
2. **schema 整份重排版**造成 71 行 diff 噪音。從改動前版本重建，diff 縮回語意行。
3. **`implementation-plan-loader` 重複讀取與解析 `change.json`**，並帶著與 `SLUG_PATTERN` 逐字相同的 pattern 與內聯的 content root。改為呼叫 `loadChangeMetadata`。
4. **去重時連帶移除了信任邊界的守衛**（第二輪兩軸皆提及）。目錄名自 route parameter 而來，原本在讀檔前被檢查；去重後檢查移到讀檔之後。pattern 改為自 `change-metadata` 匯出並在讀檔前檢查，修掉重複但不拆掉驗證。
5. **Design 承諾但未覆蓋的測試**：「directory name 與 slug 不符會被拒絕」。行為正確，證據缺一條，已補。
6. **三份 fixture 仍描述已移除的版面**：`change-artifacts.test.ts` 把 Change 包在 `In Progress` 資料夾下，`check-workflow.test.mjs` 使用 status-scoped 路徑。它們兩種版面都會過，這正是問題所在。
7. **兩顆修正 commit 缺 `Implements` trailer**。若不補，`git log --grep` 重建出的交付映射就會漏掉真正讓 S01 驗收成立的那顆 commit——正是本 repo 剛寫進契約要避免的失效模式。已重切。

### 已評估，不修正

## Plan versus actual

- **S02 的判定結果**：`withDirectChangePages` 的注入在 build 期間對 12 個 Change 全部回傳空集合，確認為死碼並刪除；它包裹的 `withNavigableFolders` 仍為麵包屑所需，故只刪注入半部。切片寫的是「判定」，實際兩者都做了，因此「否則記入 Review」的分支未觸發。
- **S01 超出切片文字的一處**：lifecycle 目錄存續期間，`readChange` 增加「推導 status 必須與所在目錄相符」的檢查，補上 `record.status !== status` 移除後、S03 之前的短暫缺口。該檢查已隨目錄於 S03 移除。
- **S04 超出切片文字的一處**：兩個元件原本各有一份 label／colour 表，改為共用 `LifecycleBadge`。切片只要求各自渲染一個 lifecycle badge；共用是為了不把同一張表複製兩份。
- **S05 超出切片列舉的三處**：Repository profile 表格與 `docs/agents/domain.md` 帶有同樣過期的 `<status>` 路徑，一併修正；另刪除「資料目錄遮蔽同名兄弟頁」整段——meta collection 收斂後該行為已不存在，該段已成假敘述。兩軸第二輪皆確認刪除正確。

## Archive 期間發現

**ADR id 在升級後會相撞。** id 於 Change 內唯一，升級目的地卻是 capability——`platform/blueprint` 已有一份來自 `unified-software-delivery-workflow` 的 `D2`，本 Change 的 `D2` 落進同一個資料夾。`DecisionTimeline` 以 `record.id` 同時作為 React key 與 accordion value，兩份 D2 會共用同一個 key，展開其一會連動另一個。

檔名帶 slug 所以檔案本身不衝突，衝突只在渲染層。修法是 key 改為 `originChange` 加 id——不動 schema 的 `^D[0-9]+$`、不重新編號、不破壞 Change 內部對 D1／D2 的指稱。這是本 Change 的 Archive 第一次讓兩個 Change 的 ADR 進到同一個 capability 才暴露的，先前無樣本。

**ADR 少走了一個狀態。** 依 §3，計畫核准時 `candidate` 應轉 `accepted`，Archive 再轉 `implemented`。本 Change 的兩份 ADR 從 `candidate` 直接被設為 `implemented`——核准當下沒有執行那一步。記錄於此而非追溯補寫，因為 `accepted` 的意義是「當時被核准」，事後補上只會讓紀錄失真。

## Changeset

判定豁免。`src/` 零檔案變動，diff 只落在 `blueprint/`、`docs/` 與 `WORKFLOW.md`，對出貨的 app 無影響。與既有慣例一致：`291ddbe6`、`05d11894`、`b2a7965f`、`864c8f0a` 四個同範圍的合併皆未帶 changeset。

## 殘留風險與後續

- **schema 無人驗證。** 這次的最嚴重缺陷之所以能存在，是因為沒有任何 script 載入 `change.schema.json`；CI 綠燈掩蓋了契約與實作的分岔。`change-metadata.ts` 目前是實際權威，schema 是平行的文件。把 schema 驗證掛進 `check-workflow.mjs` 需要引入 ajv 作為直接相依，超出本 Change 範圍，列為後續。
- **同批提出的第二個 Change**：`record-flows` 於本分支僅完成 Propose（lifecycle `proposing`），不含實作。它是 2026-07-12 以 OpenSpec 格式起草、從未進版控的提案，轉換前核對過前提仍成立。與本 Change 共用一支分支是開發者的明確決定，理由是不值得為單一 Propose commit 另開 PR；其 Apply 屆時自合併後的 `dev` 另開分支。

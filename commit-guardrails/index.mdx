<Proposal>

<TLDR>
commit 的 type、body 與 trailer 規則，不再是只有 review 會抓的散文。husky 安裝 `pre-commit`（跑 lint-staged）與 `commit-msg`（跑 commitlint）兩個 hook；CI 再對整個 pull request 的 commit 範圍重跑一次 commitlint。scope 維持自由格式，只用黑名單擋退役工具名。trailer 檢查靠分支名稱判斷一個 commit 屬不屬於 Change：`feat/`、`fix/`、`refactor/<slug>` 上的每個 commit 都要帶值等於 slug 的 `Blueprint-Change`，Fix path 則改用自己的 `hotfix/<slug>`。凡是工具現在會檢查的規則，都從敘述它的文件裡刪掉。
</TLDR>

## 為什麼是現在

`two-gate-workflow` 期間，review 抓到缺 body 的 commit、用工具名當 scope、缺 trailer、type 用錯；最後以 rebase 改寫了四個 commit message。一個 `no-unused-expressions` 錯誤也是撐到 `verify:all` 才被擋下。每一項都是早就寫下來的規則。

## 本次 Change 的邊界

- 照上圖加入三個檢查點：husky 的 `pre-commit` 與 `commit-msg` 兩個 hook，以及 CI 對 pull request 範圍的 commitlint；CI 在 workflow 層級設 `HUSKY=0`。CI 的 commitlint 只查目標是 `dev` 的 pull request：進 `main` 的 commit 都已在 `dev` 查過，而 `dev` → `main` 的範圍還帶著規則上線前的歷史 commit。
- Changesets 的 release commit 改成合規的 `chore(release): update versions` 加上 body，讓 `main` → `dev` 的 sync PR 照常通過，不為 bot 開例外。
- trailer 檢查以分支名稱判定 Change：`feat|fix|refactor/<slug>` 上的 commit 必須帶 `Blueprint-Change: <slug>`，值要等於分支名的 slug；其他分支不要求。hook 讀當前分支，讀不到（rebase 中的 detached HEAD）就略過；CI 只在 pull request 上執行並讀它的 head 分支名，直接 push 到 `dev` 的 commit 不在檢查範圍，與 Change 一律走 PR 一致。
- `WORKFLOW.md` 的分支表加上 Fix path 的 `hotfix/<slug>`，Fix path 一節同步寫明，不論 commit type。
- 從 `CONTRIBUTING.md` 與 `WORKFLOW.md` 刪掉每一條已被新檢查涵蓋的規則，包含 commit type 對照表（改成一行指向 commitlint 設定的指標），以及 `CONTRIBUTING.md` 裡「絕對匯入走 `@/*`」那一行（`tsc` 已擋）。
- **不在範圍內** —— ESLint 規則：`@/*` 已由 `tsc` 擋下，issue 編號在 `src/` 沒有違規紀錄（依據見 References）。

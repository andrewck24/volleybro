## Context

`IGameRepository` 只有一個寫入方法 `update(id, Partial<Game>)`，五個 game usecase 全部呼叫它，實作是整份文件覆寫。

`v0.15.0 記錄穩定性與資料完整性` 修掉的 rally 送出一律回 404 的缺陷，就是這個模型的直接後果：對手側一個空字串讓 Mongoose 對 `sets` 整個路徑的 cast 失敗，那一局已記錄的所有 entry 一起存不進去。該缺陷的表層原因已修，寫入模型沒有動。

三個結構性問題仍在：爆炸半徑（任一 leaf 不合法則整份寫入失敗）、lost update（read-modify-write 之間的窗口）、寫入量隨比賽線性成長。

## Goals

- 記一顆球的寫入，其失敗半徑限縮在新增的那個 entry，不波及該局既有資料。
- 消除 read-modify-write 窗口，使並行寫入不會無聲覆蓋彼此——這是 `v0.20.0 同步記錄與即時觀看` 的前置條件。
- 讓 repository 介面以領域操作表達，而非以「交給你一份文件請覆寫」表達。
- 讓分層是可驗證的事實：資料庫專屬語法全部關在 `GameRepositoryImpl` 內，usecase 測試不得 mock 任何資料庫概念。
- 修掉既有的分層倒置：`create-rally` 與 `update-rally` usecase 目前 import `@/lib/features/game/helpers`，application 層不應依賴前端 Redux 模組。

## Non-goals

- 不做全域錯誤訊息盤點。只重新定義新寫入路徑產生的錯誤語意。
- 不改 team / player / profile 的寫入模型（理由見 Design）。
- 不解決跨場次的聚合效能，那屬於 `v0.18.0 資料庫選型評估` 與 `v0.19.0 Analytics Dashboard`。
- 不實作同步協作的衝突解決；本 Change 只移除它會踩到的地雷。
- 不重劃 `src/lib/features/game/helpers/` 的目錄結構。本 Change 會讓 `optimistic/` 大幅萎縮、`queries/` 只剩兩個檔案，但目錄劃分要看實作後的實際規模才判斷得準，現在決定會決定錯。

## Change boundaries

八個決策全部定案，邊界如下：

- **一定在內**：`create-rally`、`update-rally`、`create-substitution` 三條寫 `sets.N.entries` 的路徑。
- **在內但常被低估**：停止寫入統計會連帶波及讀取端。`components/game/options/overview` 與 `components/game/stats/teams-stats` 必須在同一個 Change 內改成讀推導值，否則會靜默顯示一組零。
- **在內**：`deriveSetStats` 純函式、`create-set` 與 `create-substitution` usecase 裡的統計變更刪除、前端逐球累加函式刪除。
- **在內（審查中發現）**：一局的結束。`set.win` 與 `game.win` 目前只在 `rally.helper` 的 `processGamePhase` 裡被寫入，靠整份覆寫一併存下；改成定位寫入後它們會靜默停止更新。D7-A 讓它成為明確的 `completeSet` 領域操作，局末寫一次。
- **在內（稽核中確認）**：推導的呼叫位置。`deriveSetStats` 由 `game-slice.ts` 的 `initialize` reducer 呼叫並存進 state，元件只讀 state——與 `isSetInProgress` 現行做法一致。元件不得自行呼叫推導函式。
- **在內（走查中發現）**：`win` 的初始值與型別。`create-game` 寫 `false`（依 codebase 慣例等於「客隊贏」）而 `create-set` 寫 `null`，兩者不一致；`GameSummary.win` 宣告為非空 `boolean` 卻投影可能為 `null` 的 `game.win`。與 D7 是同一個欄位的同一件事。
- **在內（順手）**：`repository-helpers.mongo.ts` 更名為 `error-translation.mongo.ts`——檔案只有一個 export，以職責命名而非以「helpers」命名。
- **不在內**：`create-set`、`update-set`（沒有 lost update 壓力，且帶著需要一併重寫的 domain 驗證）。它們留在 `update()` 上，其存續條件是「只服務 set 層級寫入，新增路徑不得使用」。
- **明確不在內**：其他 domain 的 repository。

## Capability impact

`game-recording/rally-recording` 與 `game-recording/persistence` 的可靠性契約會改變：目前「一次寫入要麼整局成功要麼整局失敗」，改為「單一 entry 的失敗不影響既有資料」。

D1-B 也改變 `game-recording` 的資料模型契約：entries 成為唯一的真實來源，統計成為投影。這個差異對 `game-recording/collaboration` 是前置條件，因此錯誤語意與資料模型的重新定義都必須在本 Change 內完成，不能留到同步協作時才處理。

一局的結束也從「記錄一顆球的副作用」變成明確的領域操作，伺服器因此成為勝負的權威來源——這是 `v0.20.0 同步記錄與即時觀看` 伺服器權威計分的第一步。

這個契約對後續里程碑設下一條約束：**之後任何 materialization 都必須是從 entries 推導出來的快取，不得成為第二條獨立累加的寫入路徑。** 加上一層快取是相加的（新的讀路徑 + 場末的寫路徑），不會破壞本 Change 建立的結構；改回逐球累加才會，而那正是本 Change 移除的東西。

## Alternatives considered

Design 頁完整記錄各組替代方案與它們的後果。Overview 層級只記結論方向：

- **維持整份 `$set`，只在應用層加防護**——不成立。防護擋得住已知的壞值，擋不住 read-modify-write 窗口。
- **保留儲存統計，改以 `arrayFilters` 比對 playerId 原子累加**——可行且正確，但比推導多了一整組必須維持一致的寫入路徑。
- **只交付與資料庫無關的那一層，實作等選型定案**——在 D1 定案前是合理的，D1-B 讓要迴避的作廢風險縮到只剩兩個 repository 方法體，而代價是一個觀察不到任何差別的 slice（`appendEntry` 內部仍是整份覆寫），對 v0.15.0 的出場條件貢獻為零。已否決，見 D0。
- **改用正規化的關聯式 schema**——會讓三個問題結構性消失，但那是資料庫選型的決策範圍，不是本 Change 能單方面決定的。

## Revisit triggers

- 資料庫選型決定遷移至關聯式資料庫：本 Change 的文件資料庫特定實作作廢，但 repository 介面與資料模型決策應該原樣成立。若實際不成立，代表 persistence ignorance 沒有做到，需要回頭檢討分層。
- 同步協作決定 entry 的穩定識別方式：目前 `entrySchema` 設定 `_id: false`，entries 只能以陣列位置定址。並行寫入下「取代第 N 顆球」不是穩定的目標，兩邊的決策必須對齊。
- 實作完成後 `helpers/optimistic/` 與 `helpers/queries/` 的實際規模：若兩者都萎縮到一兩個檔案，該目錄劃分（讀寫分離的形式）是否還值得保留需要重新評估。這是刻意留到實作後的判斷，不是遺漏。
- 出現第六條 game 寫入路徑：若它走了 `update()` 而非定位寫入，代表 D3 的存續條件沒有被遵守。
- `entities/` 出現 server-only 相依：D6-A 的前提是 entities 可安全進前端 bundle。一旦破壞，前後端共用就變成洩漏，需要重新檢討共用邊界。
- 任何 materialization 改以獨立累加而非從 entries 推導：這會使 entries 不再是唯一真實來源，本 Change 的資料模型契約失效，須整體重新檢討。
- `v0.18.0 資料庫選型評估` 決定 materialization 的位置與粒度：若它選擇 per-game rollup 落在 `stats` 欄位，D5-D 保留的欄位即被啟用；若它另建 collection，該欄位可正式移除。
- 統計的推導規則變更：規則變更會回溯改變歷史比賽的數字。單場推導沒有凍結點；跨場的凍結由 `v0.18.0 資料庫選型評估` 的 materialization 在整場結束時提供，本 Change 不自行決定 set 粒度的 materialization。

### Findings and resolutions

**F1 — 換人 helper 帶著同型的執行期當機路徑（已修）**
S05 執行時將 `substitution.helper.ts` 的 `game.teams[side].stats[setIndex]!.substitution++` 判為「不在驗收條件內」而擬留給後續。該判斷不成立：它與 rally helper 是同一個根因（S03 移除寫入者後 stats 不再被初始化），同樣會在樂觀更新時丟 TypeError。已於 S05 一併刪除該段與連帶的 `createEmptyPlayerStats`，並移除兩個斷言舊累加行為的測試。

**F2 — `use-lineup` 是最後一個以儲存欄位取輪轉的讀者（已修）**
S06 發現 `getGeneralModeLineup` 由 `game.teams.home.stats[setIndex]!.rotation` 決定輪轉幾格。型別移除前編譯器無法標記它。已改為從該局 entries 推導，與同檔案 editing mode 分支一致。

**F3 — 推導的歸零約定被寫了兩次（已修）**
Standards 軸指出 `deriveSetStats` 與 `team-stats.helper.ts` 的 `emptyTeamStats()` 各自編碼一次「配額欄位由上限改為從零計數」。後者改為向 `deriveSetStats(undefined, …)` 索取空集合的推導結果，規則只剩一處。

**F4 — `derive-set-completion` 為呼叫 `deriveSetPhase` 而搭建臨時稀疏陣列（已修，見 F6）**
Standards 軸標為 judgement call：呼叫端偽造一個只填了單一索引的假 `game`，只為配合被呼叫端的參數形狀。最初判定接受，理由是 `deriveSetPhase` 的簽章在 S01 定案且同時服務前端。追查該理由是否成立時發現前端根本沒有在用它（F6），於是連同 F6 一併處理：簽章改為直接吃 set，稀疏陣列消失。

**F6 — 四個共用函式裡有三個前端仍用自己的複製品（已修）**
D3-A 與 D6-A 的決策是「規則移入 domain 層成為純函式、前後端共用」。實際交付後 `deriveSetPhase`、`deriveServingStatus`、`getPreviousRally` 三者在 `src/lib/features/game/helpers/queries/` 各有一份逐行等價的複製品，Redux store、rally helper 與兩個元件用的都是複製品。四個函式裡只有 `deriveSetStats` 真的共用了。計分規則因此有兩份實作，正是本 Change 要消滅的形狀。

**兩軸 review 都沒攔下它**，因為 S01 的驗收條件只要求 entities 匯出這四個函式、且傳 `EntryView[]` 與 `Entry[]` 都不需 cast 就過型別——兩條字面上都成立。可 cast 那條正是為了讓前端改用而寫的，只是沒有人真的去改，而驗收條件沒有把「前端已改用」寫成可檢查的事實。

修法：`deriveSetPhase` 拆為 `setTargetPoints(scoring, setIndex)`（決勝局打 `decidingSetPoints`、其餘 25 的規則）與 `deriveSetPhase(set, entryIndex, targetPoints)`，兩者都留在 entities；三個複製品與其測試刪除，前端測試涵蓋而 entities 未涵蓋的案例（未建立的局回報 not-in-progress）移植進 entities 測試；六個呼叫點改用 entities。行為未變，這是收斂不是重新設計。

**F5 — `TeamsStats` 在 render 期間推導而非自 store 讀取（接受，見 plan versus actual）**
初次記錄時的理由有誤，已更正。當時寫的是該元件不在記錄路徑上、因此很少重算；實際查證後 `StatsForOneSet` 就渲染在記錄頁。結論不變，但依據換成 `useMemo` 的 dependency array 把重算頻率釘在資料更新而非 render 次數。與 F4 同一種錯誤——以推論代替查證——差別在 F4 的結論也跟著錯了，F5 只有理由錯。

### Plan versus actual

**S02 驗收條件第三條經 Ingest 修正。** 原文要求以 matchedCount 對 modifiedCount 區分 GAME_NOT_FOUND 與 SET_NOT_FOUND。實測（mongodb-memory-server）該機制不存在：filter 只放 `_id` 時，`$push` 到超出範圍的 `sets.N.entries` 不會失敗，MongoDB 會把 sets 補 null 補到該索引再寫入——靜默毀損文件。因此 `sets.N` 的存在必須是寫入條件的一部分，而那會讓兩種 miss 都回報零筆命中。行為承諾未變（寫入條件判定、不預先讀出來檢查），改變的是機制陳述：失敗路徑多一次 `exists({ _id })` 分辨。Design 的錯誤模型段落同步更新。

**S05 驗收條件第二條逐字滿足，但不是設計原本設想的形狀。** 條件為「`src/components/` 無檔案 import `deriveSetStats`；元件自 store 讀取推導值」。`components/game/options/overview` 確實改自 Redux `status.stats` 讀取。`components/game/stats/teams-stats` 則呼叫 `src/lib/` 的 `getTeamsStats`，該 helper 在 `useMemo` 內推導。

差異的原因是這兩個元件的資料來源不同：`options/overview` 讀 Redux 記錄 store；`stats` 由 `useGame(gameId)` 取 SWR 資料，且需要任意 `setIndex`（含全場 `-1`），而 `initialize` reducer 只持有當前記錄中那一局的統計。把全場所有局的統計塞進記錄 store，等於把賽後檢視的資料放進記錄流程的 store，架構上更差。

設計對此的約束原文是「推導必須在 reducer 裡 append 後算一次，不能在 render 期間算——否則成本會隨 render 次數而非隨球數成長」，其風險描述同時記明「演算法本身可忽略（一局 ≤60 entry，建 Map 後約 O(N + P)）」。

**`StatsForOneSet` 確實渲染在記錄頁上**（`components/game/index.tsx`，且外層 Accordion 預設展開），所以它不是賽後才碰得到的畫面。判定接受的依據是 `useMemo` 的 dependency array：`[sets, setIndex]`。Redux 狀態變動造成的 re-render——切換 panel、編輯 entry draft、選球員——不會重算，因為 `sets` 的 reference identity 未變；只有 SWR 資料更新才重算，而在記錄頁上那約等於每記一顆球一次。約束禁止的是成本隨 render 次數成長，允許的是隨球數成長，`useMemo` 讓它落在允許的那一側。

已知代價：記錄頁上同一局的統計每顆球會被推導兩次——`initialize` reducer 算一次供 `options/overview` 使用，`TeamsStats` 再算一次。兩者算的是同一組數字。要收斂成一次，得在元件內分支判斷「`setIndex` 是否正好是當前記錄中那一局」以決定讀 store 還是自行推導，為省下一次 O(≤60) 的走訪而在元件裡引入兩種資料來源，不划算。記為已知事實而非待辦。

**四份 ADR 從未被標記為 `accepted`。** WORKFLOW §3 規定核准時 Change ADR 由 `candidate` 轉 `accepted`，本 Change 的核准 commit 沒有做這件事，四份記錄一路以 `candidate` 走到 Archive，才在 Archive 直接轉為 `implemented`。這是流程遺漏而非決策內容有疑義——四項決策都經過核准並已交付。不回頭偽造中間狀態，在此記錄實情。

### Residual risks

**R1 — `appendEntry` 之後 `completeSet` 失敗時的行為未定義。**
D4 的 consequences 已列出「附加 entry 與完成一局是兩次寫入，兩者的合併失敗行為必須定義」，本 Change 未定義。目前若 `completeSet` 擲出（例如暫時性資料庫錯誤），該顆球已經落庫但請求回報失敗；客戶端重試會再 `$push` 一次，產生重複的 rally 並使比分失真。

這個危險不是 `completeSet` 引入的——任何在 `$push` 成功之後失敗的回應都有相同性質，因為附加寫入本身不具幂等性。真正的修法需要 entry 的穩定身分，而 D4 的 revisitTriggers 已明確把它交給同步記錄：「Synchronised recording settles on a stable identity for entries」。在那之前這是已知且未緩解的風險，不是本 Change 可以就地收斂的問題。

**R2 — 兩種寫入模型並存。** `create-set` 與 `update-set` 仍走整份覆寫。D2 的存續條件（新寫入路徑不得使用 `update()`）目前只由介面註解與 review 把關，沒有工具強制。

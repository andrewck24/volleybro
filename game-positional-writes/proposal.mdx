## Context

`IGameRepository` 只有一個寫入方法 `update(id, Partial<Game>)`，五個 game usecase 全部呼叫它，實作是整份文件覆寫。

`v0.15.0 記錄穩定性與資料完整性` 修掉的 rally 送出一律回 404 的缺陷，就是這個模型的直接後果：對手側一個空字串讓 Mongoose 對 `sets` 整個路徑的 cast 失敗，那一局已記錄的所有 entry 一起存不進去。該缺陷的表層原因已修，寫入模型沒有動。

三個結構性問題仍在：爆炸半徑（任一 leaf 不合法則整份寫入失敗）、lost update（read-modify-write 之間的窗口）、寫入量隨比賽線性成長。

## Goals

- 記一顆球的寫入，其失敗半徑限縮在新增的那個 entry，不波及該局既有資料。
- 消除 read-modify-write 窗口，使並行寫入不會無聲覆蓋彼此——這是 `v0.20.0 同步記錄與即時觀看` 的前置條件。
- 讓 repository 介面以領域操作表達，而非以「交給你一份文件請覆寫」表達。
- 讓分層是可驗證的事實：資料庫專屬語法全部關在 `GameRepositoryImpl` 內，usecase 測試不得 mock 任何資料庫概念。
- 修掉既有的分層倒置：`create-rally` 與 `update-rally` usecase 目前 import `@/lib/features/game/helpers`，application 層不應依賴前端 Redux 模組。

<AnchorAliases ids={["concepts"]} />

## 名詞說明

| 名詞                    | 本頁用法                                                                            |
| ----------------------- | ----------------------------------------------------------------------------------- |
| 定位寫入                | 由資料庫直接修改指定陣列或欄位路徑，避免讀出整份文件後再覆寫。                      |
| `arrayFilters`          | 以穩定條件（例如 `playerId`）選取陣列元素，避免用可變的球員位置定位。               |
| `lost update`           | 兩個寫入者讀到同一舊值，各自修改後先後整份寫回，後寫入者會蓋掉前者。                |
| `Persistence Ignorance` | domain/application 表達領域操作；MongoDB operators 留在 repository implementation。 |

<AnchorAliases ids={["addressing"]} />

## 陣列位置定址的安全性

`players.N` 不安全：名單能增刪或重排，索引會悄悄指向另一位球員，應用 `arrayFilters` 依 `playerId` 定位。`sets.N` 可接受：局只會追加，`N` 是穩定的領域序數。`entries.N` 僅適用單一寫入者；並行記錄時「第 N 顆球」不穩定，需由同步協作的意圖錨點處理。新增 entry 使用 `$push` 不需依賴索引。

## Non-goals

- 不做全域錯誤訊息盤點。只重新定義新寫入路徑產生的錯誤語意。
- 不改 team / player / profile 的寫入模型（理由見 Design）。
- 不解決跨場次的聚合效能，那屬於 `v0.18.0 資料庫選型評估` 與 `v0.19.0 Analytics Dashboard`。
- 不實作同步協作的衝突解決；本 Change 只移除它會踩到的地雷。
- 不重劃 `src/lib/features/game/helpers/` 的目錄結構。本 Change 會讓 `optimistic/` 大幅萎縮、`queries/` 只剩兩個檔案，但目錄劃分要看實作後的實際規模才判斷得準，現在決定會決定錯。

## Change boundaries

依 D0–D7 的決策，範圍如下：

- **entry 寫入**：`create-rally`、`update-rally`、`create-substitution` 一起改用定位寫入，避免兩種模型互相覆蓋（D2-B）。
- **統計推導**：加入 `deriveSetStats`；停止逐球累加並改寫統計讀取端。由 `game-slice.ts` 的 `initialize` reducer 推導並存入 state，元件只讀 state（D1-B、D4-A）。
- **局末結果**：新增 `completeSet`；新比賽的 `win` 初值改為 `null`，`GameSummary.win` 改為 `boolean | null`（D7-A）。
- **錯誤翻譯命名**：`repository-helpers.mongo.ts` 更名為 `error-translation.mongo.ts`。
- **不在內**：`create-set`、`update-set` 留用 `update()`；新寫入路徑不得使用它（D3-A）。其他 domain 的 repository 也不改。

## Capability impact

`game-recording/rally-recording` 與 `game-recording/persistence` 的可靠性契約會改變：目前「一次寫入要麼整局成功要麼整局失敗」，改為「單一 entry 的失敗不影響既有資料」。

D1-B 讓 entries 成為唯一事實來源、統計成為推導值，並為同步協作移除重複寫入。D7-A 將局末判定改為伺服器端的 `completeSet` 操作。

後續 materialization 只能是由 entries 推導的快取，不得恢復獨立的逐球累加。

<AnchorAliases ids={["other-domains"]} />

## 範圍外的其他 domain

Team 的整份文件更新頻率低、文件大小有界且由單一使用者操作；此 Change 的 game 寫入風險不構成改寫其他 repository 的理由。既有 `removePlayerFromLineups` 已使用 `$pull`，表示 codebase 會在適當邊界採定位操作。

<AnchorAliases ids={["granularity"]} />

## Repository 介面粒度

介面以領域操作命名（例如 `appendEntry`），而非欄位組合或 MongoDB operator。game 有界的寫入操作不應被一個 `update(id, Partial<Game>)` 抹平成相同語意；新增方法必須代表新的領域動作。

<AnchorAliases ids={["relational"]} />

## Alternatives considered

此處保留各替代方向及其取捨摘要：

- **維持整份 `$set`，只在應用層加防護**——不成立。防護擋得住已知的壞值，擋不住 read-modify-write 窗口。
- **保留儲存統計，改以 `arrayFilters` 比對 playerId 原子累加**——可行且正確，但比推導多了一整組必須維持一致的寫入路徑。
- **只交付資料庫無關的介面，實作等選型定案**——`appendEntry` 仍會整份覆寫，無法改善本 Change 要解決的寫入風險；已否決（D0）。
- **改用正規化的關聯式 schema**——會讓三個問題結構性消失，但那是資料庫選型的決策範圍，不是本 Change 能單方面決定的。

### 局末結果不是統計 materialization

`completeSet` 只在局末寫入 `set.win`，整場結果確定時寫入 `game.win`；逐球統計仍由 entries 推導，不恢復第二份累加狀態。

<AnchorAliases ids={["d7-null"]} />

### 未決勝負使用 `null`

`null` 表示局或比賽尚未決定；`true`／`false` 表示勝負。新比賽以 `null` 起始，避免把「尚未結束」誤讀為落敗。

<AnchorAliases ids={["layer-audit"]} />

## 分層稽核

本 Change 修正 application 對 `src/lib/features/game/helpers` 的依賴倒置，並讓 `GameRepositoryImpl` 成為 MongoDB operators 的唯一邊界。共享到前端的 entities 維持無 server-only imports；推導在 slice 更新時執行，元件不直接呼叫推導函式。

<AnchorAliases ids={["constraints"]} />

## 驗收約束

| 約束                                        | 檢查方式                                                         |
| ------------------------------------------- | ---------------------------------------------------------------- |
| MongoDB 專屬語法留在 `GameRepositoryImpl`。 | usecase 不 mock database concepts；review 新增 repository 邊界。 |
| `entities/` 不依賴 server-only 模組。       | 保持 entities 的 import 邊界，檢查共用的 domain functions。      |
| 統計只在 slice 更新時推導。                 | 元件只讀 Redux state，不 import `deriveSetStats`。               |

## 錯誤模型的變化

現在的錯誤語意建立在「先讀出來、在記憶體裡檢查」上：usecase 讀完 game 後自己判斷 `!game.sets[setIndex]` 才丟 `SET_NOT_FOUND`。改成定位寫入後這個結構垮掉——「條件不成立所以什麼都沒寫」變成一個必須主動偵測的正常回傳值，不是例外。

先前 rally 送出一律回 404 的缺陷，根源就是這一層的語意混淆。不在同一個 Change 裡重新定義清楚，等於換一個地方重犯。範圍要收緊：**只處理新寫入路徑產生的錯誤語意**，不做全域錯誤訊息盤點。

## Revisit triggers

- 資料庫選型決定遷移至關聯式資料庫：本 Change 的文件資料庫特定實作作廢，但 repository 介面與資料模型決策應該原樣成立。若實際不成立，代表 persistence ignorance 沒有做到，需要回頭檢討分層。
- 同步協作決定 entry 的穩定識別方式：目前 `entrySchema` 設定 `_id: false`，entries 只能以陣列位置定址。並行寫入下「取代第 N 顆球」不是穩定的目標，兩邊的決策必須對齊。
- 實作完成後 `helpers/optimistic/` 與 `helpers/queries/` 的實際規模：若兩者都萎縮到一兩個檔案，該目錄劃分（讀寫分離的形式）是否還值得保留需要重新評估。這是刻意留到實作後的判斷，不是遺漏。
- 出現第六條 game 寫入路徑：若它走了 `update()` 而非定位寫入，代表 D3 的存續條件沒有被遵守。
- `entities/` 出現 server-only 相依：D6-A 的前提是 entities 可安全進前端 bundle。一旦破壞，前後端共用就變成洩漏，需要重新檢討共用邊界。
- 任何 materialization 改以獨立累加而非從 entries 推導：這會使 entries 不再是唯一事實來源，本 Change 的資料模型契約失效，須整體重新檢討。
- `v0.18.0 資料庫選型評估` 決定 materialization 的位置與粒度：若它選擇 per-game rollup 落在 `stats` 欄位，D5-D 保留的欄位即被啟用；若它另建 collection，該欄位可正式移除。
- 統計的推導規則變更：規則變更會回溯改變歷史比賽的數字。單場推導沒有凍結點；跨場的凍結由 `v0.18.0 資料庫選型評估` 的 materialization 在整場結束時提供，本 Change 不自行決定 set 粒度的 materialization。

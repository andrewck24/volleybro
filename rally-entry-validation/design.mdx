寫入由左往右，讀取由右往左，兩個新守衛用中間那條虛線連著的同一個定義。

### 為什麼中間那層是空的

`upsertEntry` 送出的是 `bulkWrite`，裡面每一筆 entry 都變成兩個互斥的 `updateOne`——已存在就用 arrayFilters 定位覆蓋，不存在就有條件地 `$push`。這個形狀是 `game-positional-writes` 為了做出「陣列元素層級的 upsert」而選的，MongoDB 沒有原生的那種操作。

代價當時沒有被看見：Mongoose 只對 `bulkWrite` 裡的 `insertOne` 與 `replaceOne` 執行驗證。`game-positional-writes` 的決策明確保住了 **casting**——「Both remain ordinary updates rather than aggregation pipeline updates, so Mongoose casting survives」——但 casting 不是 validation。前者是型別換算，後者是 `required` 與 `enum`。這條路徑上只有前者活著。

實測的差異很乾淨：

| 餵進去的東西                      | 結果                    |
| --------------------------------- | ----------------------- |
| `home.type` 缺了                  | 存進去了                |
| `home.type` 是 `99`（超出 enum）  | 存進去了                |
| `home.type` 是 `"attack"`（字串） | `CastError`，擋下       |
| `home.score` 是 `"12"`            | 存進去，自動換算成 `12` |

擋下來的只有「換算不出來」那一種。**所以驗證必須在資料到達那一層之前發生**，這就是 `validateRallyEntry` 的位置由來。

### 兩邊的判準不對稱，是刻意的

寫入端檢查四個欄位，讀取端只看一件事：`home[entry.home.type]` 這一格取不取得到。

這不是遺漏。讀取端要回答的只有「會不會拋」，而其他三個欄位壞掉都不會拋——缺 `win` 會被 `isRally` 整筆跳過，缺 `score` 會讓該局永遠不被判定結束，缺 `num` 會讓記錄列表顯示空白球種名。它們一樣是缺陷，但**它們的解法是從源頭堵住，不是在讀取端重建一份寫入端已經有的規則**。

用一句話劃界：寫入端讓錯的資料進不來，讀取端讓已經在裡面的錯資料不要殺死畫面。

## Contracts

四條在實作與後續維護時不能破的規則：

- **「合法球種」只有一個定義。** 寫入端拒絕的標準與讀取端跳過的標準都是 `MoveType` 的合法值。兩邊各自表述就會漂移，而漂移的方向必然是讀取端比寫入端寬鬆——那正是今天的狀態。
- **讀取端跳過的是那一筆的統計累加，不是那一筆 entry。** 迴圈尾端的 `rotation` 與 `isHomeServing` 必須照常推進，否則該筆之後的輪轉數與發球權全部錯掉。這是本 Change 最容易被實作錯的一點，也是唯一一個錯了不會拋、只會靜靜給出錯數字的地方。
- **`required` 不是守衛。** schema 上的四個 `required` 在現行寫入路徑上不執行，程式碼必須以兩行註解指向 D2。少了它，下一個讀者會信賴它並移除 entity 層的守衛。
- **`set.win` 與 `game.win` 不加 `required`。** 它們在結果存在前刻意是 `null`——「boolean 代表比賽已結束」是 `rally-recording` 的既有約定。三個 `win` 欄位同名不同義，這是本 Change 唯一會誤傷的地方。

## Testing strategy

兩個 seam，兩種證明，缺一不可。

**entity 單元測試——證明規則本身正確。** `deriveSetStats` 餵入缺 `type` 與 `type` 超出範圍的 entry，斷言不拋、其餘 entry 的統計正確、**且 `rotation` 與發球權的推進不受影響**。`validateRallyEntry` 逐條餵入缺欄位、超出範圍、型別錯誤，斷言各自被拒。Entity 層是 Classical school，不 mock 任何東西。

**整合測試——證明規則真的被呼叫。** 畸形的球經真實 route 送出得到 400，且該局的 entries 未被寫入，照 `legacy-entry-guard.itest.ts` 的形狀寫。

第二條不是保險，是必要條件。`validatePlayerStatus` 有十一個全綠的單元測試，而它在生產程式碼裡的呼叫端數量是零——**單元測試證明「它會拒絕」，證明不了「有人在該拒絕的時候呼叫它」**。少了整合測試，本 Change 就是再造一個 `validatePlayerStatus`。

沒有新的元件層測試。使用者可見的結果是「那場比賽打得開」，而它在 `deriveSetStats` 那一層就是「不拋」，在元件層重述一次不會多證明任何事。

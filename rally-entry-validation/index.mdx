<TLDR>
  一顆說不出球種的球存得進資料庫，而讀取時那場比賽就再也打不開——重新整理沒用，關掉
  app 沒用，因為壞的東西在資料庫裡。三道關卡沒有一道擋得住：route 不驗、Mongoose
  的 `required` 在實際的寫入路徑上不執行、讀取端沒有守衛。本 Change
  定義「什麼構成一顆合法的球」，寫入端據此拒絕，讀取端據此容錯。
</TLDR>


## Context

`deriveSetStats` 拿球種當 key 去取統計格（`src/entities/game.ts`）：

```ts
const homeStat = home[entry.home.type] as { success: number; error: number };
homeStat.success += 1;
```

`entry.home.type` 是 `undefined` 時，`home[undefined]` 也是 `undefined`，下一行就是 `TypeError`。超出 `MoveType` 範圍的值（例如 `99`）走到同一個 `undefined`，所以災難有兩個入口，不只是「欄位缺了」。

它不是一塊區域壞掉，是整頁不見。`deriveSetStats` 的呼叫點在 `gameActions.initialize` 這個 reducer 裡，而 `Game` 每次載入都會 dispatch 它；app 沒有任何 error boundary 能接住從 reducer 拋出來的東西。

### 為什麼壞資料進得去

三道關卡，一道都沒鎖：

| 關卡                          | 現況                                |
| ----------------------------- | ----------------------------------- |
| route 的 request body 驗證    | 沒有。`await req.json()` 直接往下送 |
| Mongoose schema 的 `required` | 沒標，而且**標了也不會執行**        |
| 讀取端                        | 沒有守衛，直接拋                    |

第二列是這張 Change 查證過程中最違反直覺的一件事，值得寫清楚。rally 的唯一寫入路徑是 `upsertEntry` 的 `bulkWrite`，裡面全是 `updateOne`，而 Mongoose 只對 `bulkWrite` 中的 `insertOne` 與 `replaceOne` 執行驗證——`updateOne` 不驗，`runValidators` 傳了也被忽略。以 `mongodb-memory-server` 對照四種寫入方式實測：

| 寫入方式                                                 | 四個欄位都標 `required: true` 後的結果 |
| -------------------------------------------------------- | -------------------------------------- |
| `bulkWrite` + `updateOne` `$push`（repository 實際使用） | **接受**，壞資料照進                   |
| 同上，另加 `runValidators: true`                         | **接受**                               |
| `Model.updateOne(..., { runValidators: true })`          | 拒絕                                   |
| `doc.save()`                                             | 拒絕                                   |

`upsertEntry` 的兩種指令形狀單獨呼叫時都會驗證，是 `bulkWrite` 這個載體吃掉了驗證。同一組實測也顯示更新路徑只做 cast、不做 validate：換算不出型別的值（`type: "attack"`）會被 `CastError` 擋下，但缺欄位與超出範圍的值一律放行。

這個坑本專案已經掉進去過一次。`entrySchema` 的 `id` 與 `seq` 同樣標了 `required: true`，同樣不執行，所以 `upsertEntry` 裡另外手寫了一段 `anonymous` 檢查來擋。那道守衛留在 repository 是正確的——它防的是 arrayFilters 對 `null` 的匹配風險，屬儲存機制自己的坑。「一顆球必須說得出球種」不是儲存機制的坑，是領域規則。

### 現有資料是乾淨的

以唯讀連線掃過 `.env.local` 指向的資料庫（1 場比賽、13 顆球），缺 `win` / `home.type` / `away.type` / `score` / `num` / `id` / `seq` 的數量皆為 0。

**所以這是防患未然，不是救援行動，不需要修復或清理腳本。** 但書：這只涵蓋該資料庫；部署環境若使用另一組連線字串，那份資料從未被檢查過。

## Goals

- 一顆球種非法的球不再讓整場比賽打不開。
- 這樣的球從此進不了資料庫，且被拒絕時回 400 而非 500。
- 寫入端拒絕的標準與讀取端容忍的標準來自同一個定義。

## Non-goals

- **不做跨欄位的自洽檢查。** `num` 決定 `type` 與 `win`（`scoringMoves[num]` 就帶著它們），所以三者可能互相矛盾。要在 entities 檢查它，得先把 `scoringMoves` 從 `src/lib/` 下沉——它目前 import `MoveType`，反向依賴會成環。另開一票，該票同時處理「既然是推導值，該不該存」。
- **不補 error boundary。** 對本 Change 的失敗模式沒有作用：錯誤來自資料庫裡的資料，按重試會再炸一次，比賽一樣打不開。它把白畫面換成一張錯誤卡片，不改變結果。整個 app 只有一條 route 有 error boundary 且是佔位符，那是 app 層級的缺口，另開一票。
- **不做 route 的 request schema。** 那是四條 route 的邊界工程，價值在診斷品質（帶欄位名的 400），會改變所有 client 拿到的錯誤形狀，另有既有票。本 Change 不 block 它。
- **不動 `set.win` 與 `game.win`。** 它們在結果存在前刻意是 `null`——「boolean 代表比賽已結束」是既有約定。只有 rally 的 `win` 進本 Change 的範圍。
- **不改讀取端對缺 `win` 的既有行為。** `isRally` 現在就把缺 `win` 的 entry 判定為「不是 rally」而整筆跳過。寫入端守好之後這種資料不會再產生，而現有資料一筆都沒有——為一個上游已堵住、現實中不存在的情況改讀取端行為，是在沒有證據的地方增加複雜度。

## Change boundaries

- **一定在內**：`src/entities/game.ts` 的 `deriveSetStats` 與新增的 `validateRallyEntry`、`record-rallies.usecase.ts` 的呼叫點、`schemas/game.ts` 的 `rallyDetailSchema` 與 `rallySchema`。
- **不在內**：`isRally` 的判定、`getPreviousRally` 那條線的任何行為、repository 的 `upsertEntry`、任何 route 檔案、前端的記錄流程。

## Impact

三個能力各被觸及一半：

- `game-recording/statistics`——`deriveSetStats` 從「遇到非法球種就拋」變成「跳過該筆的統計累加」。
- `game-recording/rally-recording`——寫入一顆球多了一道領域驗證，非法的球回 400。
- `game-recording/persistence`——schema 記下四個欄位的必要性，同時記下它在現行寫入路徑上不生效。


## Alternatives considered

Design 的 D1、D2 記錄完整評估，這裡只列結論方向：

- **把守衛收進 `isRally`**，讓所有消費端一起跳過非法的球——做過頭了。`getPreviousRally` 只讀 `score` 與 `win`，一顆球種壞掉、比分完好的球對它完全可用，收緊之後比分會平白退回一顆球。
- **把非法球種計入一個「未知」統計格**——`TeamStats` 的 key 是固定的 `MoveType`，加一格會動到型別與統計畫面，而且會在使用者眼前顯示一個假的球種分類。壞資料應該是隱形的，不是被展示的。
- **驗證寫進 `createRallyEntry` 內部**，讓它不可能被忘記——代價是 entities 層唯一的內嵌驗證，違反該層「驗證獨立成 method」的既有慣例；而「被忘記」這件事本來就該由整合測試來擋。
- **拆掉 `bulkWrite` 改成逐一 `updateOne` 加 `runValidators`**，讓 `required` 真的生效——會拿掉為了對抗場館弱網路而刻意選擇的批次特性，用一個已論證過的決策去換另一個。
- **開 MongoDB 的 collection validator**，取得一道任何 driver 都繞不過的硬牆——今天只有一個寫入者，代價是維護第二份 schema 定義加遷移流程，換一道現在沒有東西會去撞的牆。記為 revisit trigger。

## Decisions

結構化 ADR 位於 `design/decisions/`，由 Design 頁呈現。

| ID  | 問題                                              | 結論                                                                                                |
| --- | ------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| D1  | 讀取端遇到非法球種要怎麼辦，守衛放在哪一層        | 在 `deriveSetStats` 的迴圈內跳過該筆的統計累加；不收緊 `isRally`，不加「未知」統計格                |
| D2  | 寫入端的守衛放哪裡，`required` 既然不執行還加不加 | 獨立的 `validateRallyEntry` 由 use case 呼叫；`required` 照加，但它是欄位必要性的紀錄，不是寫入守衛 |

## Revisit triggers

- 出現第二個寫入者——匯入功能、資料遷移腳本、第二個 client：entity 層的守衛只涵蓋走 use case 的路徑，屆時要重新評估 collection validator 那道硬牆。
- 資料庫評估選擇關聯式儲存：`NOT NULL` 是資料庫伺服器強制的約束，D2 那個「加了但不執行」的尷尬存在會直接消失，schema 裡的 `required` 轉為遷移對照。
- `scoringMoves` 下沉至 entities 之後：跨欄位的自洽檢查才有地方放，`validateRallyEntry` 屆時擴充。
- 統計的顯示需求開始要求「有幾顆球沒被計入」：目前跳過是靜默的，那時要重新決定它該不該被看見。

## Design

<TLDR>
  一個定義兩邊用：合法的球種是 `MoveType`
  裡的值。寫入端據此拒絕整筆，讀取端據此跳過那一筆的統計累加。中間那層 Mongoose
  `required` 看起來像防線，實際上在 `bulkWrite`
  路徑上不執行——它留著是為了記錄哪些欄位必要，不是為了擋。
</TLDR>

寫入由左往右，讀取由右往左，兩個新守衛用中間那條虛線連著的同一個定義。

### 為什麼中間那層是空的

`upsertEntry` 送出的是 `bulkWrite`，裡面每一筆 entry 都變成兩個互斥的 `updateOne`——已存在就用 arrayFilters 定位覆蓋，不存在就有條件地 `$push`。這個形狀是 `game-positional-writes` 為了做出「陣列元素層級的 upsert」而選的，MongoDB 沒有原生的那種操作。

代價當時沒有被看見：Mongoose 只對 `bulkWrite` 裡的 `insertOne` 與 `replaceOne` 執行驗證。`game-positional-writes` 的決策明確保住了 **casting**——「Both remain ordinary updates rather than aggregation pipeline updates, so Mongoose casting survives」——但 casting 不是 validation。前者是型別換算，後者是 `required` 與 `enum`。這條路徑上只有前者活著。

實測的差異很乾淨：

| 餵進去的東西                      | 結果                    |
| --------------------------------- | ----------------------- |
| `home.type` 缺了                  | 存進去了                |
| `home.type` 是 `99`（超出 enum）  | 存進去了                |
| `home.type` 是 `"attack"`（字串） | `CastError`，擋下       |
| `home.score` 是 `"12"`            | 存進去，自動換算成 `12` |

擋下來的只有「換算不出來」那一種。**所以驗證必須在資料到達那一層之前發生**，這就是 `validateRallyEntry` 的位置由來。

### 兩邊的判準不對稱，是刻意的

寫入端檢查四個欄位，讀取端只看一件事：`home[entry.home.type]` 這一格取不取得到。

這不是遺漏。讀取端要回答的只有「會不會拋」，而其他三個欄位壞掉都不會拋——缺 `win` 會被 `isRally` 整筆跳過，缺 `score` 會讓該局永遠不被判定結束，缺 `num` 會讓記錄列表顯示空白球種名。它們一樣是缺陷，但**它們的解法是從源頭堵住，不是在讀取端重建一份寫入端已經有的規則**。

用一句話劃界：寫入端讓錯的資料進不來，讀取端讓已經在裡面的錯資料不要殺死畫面。

## Contracts

四條在實作與後續維護時不能破的規則：

- **「合法球種」只有一個定義。** 寫入端拒絕的標準與讀取端跳過的標準都是 `MoveType` 的合法值。兩邊各自表述就會漂移，而漂移的方向必然是讀取端比寫入端寬鬆——那正是今天的狀態。
- **讀取端跳過的是那一筆的統計累加，不是那一筆 entry。** 迴圈尾端的 `rotation` 與 `isHomeServing` 必須照常推進，否則該筆之後的輪轉數與發球權全部錯掉。這是本 Change 最容易被實作錯的一點，也是唯一一個錯了不會拋、只會靜靜給出錯數字的地方。
- **`required` 不是守衛。** schema 上的四個 `required` 在現行寫入路徑上不執行，程式碼必須以兩行註解指向 D2。少了它，下一個讀者會信賴它並移除 entity 層的守衛。
- **`set.win` 與 `game.win` 不加 `required`。** 它們在結果存在前刻意是 `null`——「boolean 代表比賽已結束」是 `rally-recording` 的既有約定。三個 `win` 欄位同名不同義，這是本 Change 唯一會誤傷的地方。

## Testing strategy

兩個 seam，兩種證明，缺一不可。

**entity 單元測試——證明規則本身正確。** `deriveSetStats` 餵入缺 `type` 與 `type` 超出範圍的 entry，斷言不拋、其餘 entry 的統計正確、**且 `rotation` 與發球權的推進不受影響**。`validateRallyEntry` 逐條餵入缺欄位、超出範圍、型別錯誤，斷言各自被拒。Entity 層是 Classical school，不 mock 任何東西。

**整合測試——證明規則真的被呼叫。** 畸形的球經真實 route 送出得到 400，且該局的 entries 未被寫入，照 `legacy-entry-guard.itest.ts` 的形狀寫。

第二條不是保險，是必要條件。`validatePlayerStatus` 有十一個全綠的單元測試，而它在生產程式碼裡的呼叫端數量是零——**單元測試證明「它會拒絕」，證明不了「有人在該拒絕的時候呼叫它」**。少了整合測試，本 Change 就是再造一個 `validatePlayerStatus`。

沒有新的元件層測試。使用者可見的結果是「那場比賽打得開」，而它在 `deriveSetStats` 那一層就是「不拋」，在元件層重述一次不會多證明任何事。

## Findings

### 一、helper 回傳 `never` 卻被當 statement 用（Standards）

`validateRallyEntry` 原本把丟錯包成一個回傳 `never` 的 `reject()`，然後以 statement 形式呼叫。TypeScript 不會因為一個函式回傳 `never` 就把呼叫點當終止點，所以 `move.num` 的型別在後續分支裡仍是 `number | undefined`，只能用兩個 non-null assertion 壓過去。

<AnnotatedDiff
  lang="ts"
  code={
    "const reject = (detail: string): never => { // [!code --]\n  throw new ValidationError(CommonReason.INVALID_INPUT, detail); // [!code --]\n}; // [!code --]\nconst invalid = (detail: string) => // [!code ++]\n  new ValidationError(CommonReason.INVALID_INPUT, detail); // [!code ++]\n\nelse if (!Number.isInteger(move.num) || move.num! < 0) // [!code --]\n  reject(`A rally's ${side} move number must index a scoring move`); // [!code --]\nif ( // [!code ++]\n  typeof move.num !== \"number\" || // [!code ++]\n  !Number.isInteger(move.num) || // [!code ++]\n  move.num < 0 // [!code ++]\n) // [!code ++]\n  throw invalid(`A rally's ${side} move number must index a scoring move`); // [!code ++]"

在決定的地方直接 `throw`，並讓 `typeof` 檢查走在前面，兩個 assertion 就都不需要了。型別因此說的是實話，而不是被一個斷言壓住。

### 二、註解重述了 D2 已經擁有的決策（Standards）

`validateRallyEntry` 上方原本有一段說明「為什麼在這一層擋」。`CONTRIBUTING.md` §Comments 寫得很明確：

> never re-argue a decision a Blueprint Change already owns. Reference it instead of copying it, or the two drift apart

那正是 D2 的內容。刪除。另外兩處註解——`LAST_SCORING_MOVE` 為何硬抄、統計累加為何只跳過自己——留著，它們說的是本地看不見的約束。

`rallyDetailSchema` 上方那段同時被 Spec 軸點名超出驗收條件的兩行上限，一併縮短。

### 三、changeset 寫了，卻沒有進任何 commit（Spec）

`.changeset/rally-entry-validation.md` 存在於工作樹，但 `git diff` 看不到它——它從頭到尾沒有被 `git add` 過。這是 Spec 軸最有價值的一筆：檔案在，內容正確，肉眼看不出問題，只有比對 diff 才會發現它不在變更裡。已補上 commit。

### 四、輪轉的斷言沒有照驗收條件比對合法情形（Spec）

S01 的驗收條件寫的是「`rotation` 與發球權的推進**與該筆合法時相同**」，而測試只斷言了 `rotation` 等於 1。數字是對的，但它證明的是「等於某個我寫下的常數」，不是「與合法情形一致」。改成同時跑一次合法序列並比對兩者。

### 五、兩項判斷型建議，附理由拒絕

**`Object.values(MoveType).filter(...)` 在 entities 與 schema 各有一份。** 拒絕：schema 那份餵的是 Mongoose 的 `enum` validator，而 D2 已經確立它在 rally 的寫入路徑上不執行——所有 entry 都經 `bulkWrite` 的 `updateOne`，而新建的 game 沒有任何 entry。兩份拷貝因此不可能觀察得到分歧。為此加一條 infrastructure 到 entities 的相依，換不到任何行為上的好處。

**`num` 是裸 number，索引一張住在 entities 之外的表。** 拒絕：D2 自己的 revisit trigger 已經涵蓋它，且解法的前置是把 `scoringMoves` 下沉到 entities，屬另一份工作。

第二輪與第三輪對這兩項的處置都沒有異議。

### 六、對照只加到兩個非法輸入的其中一個（第二輪，Spec）

修正四把「與合法情形比對」加進了缺 `type` 的測試，卻沒有加進 `type` 超出 enum 的那一個，而後者也少了姊妹測試已有的 away 統計斷言。S01 的驗收條件寫的是「涵蓋兩種非法輸入……並**分別**斷言」。合法序列因此抽成一個兩邊共用的 `legal()`，兩條測試各自比對。

### 七、同一種註解形狀漏掉三處（第二、三輪，Standards）

第一輪從驗證器上刪掉的那種「重述 Change 已經擁有的決策」的註解，在另外三個地方以同樣形狀存在：測試裡解釋為什麼不能 `continue`、`deriveSetStats` 裡複述 D1 的決策文字、整合測試開頭整段搬運 D2 的論證。三處都改成一句話加 `See rally-entry-validation D1/D2.`。

一種規則、三輪才收乾淨，這件事本身值得記：第一輪的 brief 讓審查者去找「違反 CONTRIBUTING 的地方」，它找到了一處就回報一處，沒有回頭掃同一種形狀的其他實例。

### 八、一條既有的 flaky 測試擋住 gate（診斷後修在本分支）

`src/hooks/__tests__/flush-in-flight.test.tsx` 間歇性失敗——本分支九次全套執行紅三次，`dev` 四次零次。它與本 Change 沒有任何程式碼關聯，但擋住 gate，所以修在這裡。

成因是測試在跟一個 0 毫秒的 timer 賽跑。`enqueued` 把 `nextAttemptAt` 設成 `Date.now()`，所以每次入列都排一個立刻到期的背景 flush。測試在第一次 flush 還在飛時入列 q2，於是第二次 flush 一定會發出——而 `mockReturnValue` 把**第一次那個已經 resolved 的 promise** 交給了它。第二次 flush 因此立刻「成功」，帶著一個早於 q2 的回應：佇列被清空，或快取失去 q2，端看 timer 有沒有搶在斷言前面。

### 九、審查的固定點比交付狀態早了兩個 commit（第四輪，Spec）

前三輪的 diff 終點是 `9da4fdc8`，而在那之後又有五個 commit：套用第三輪發現的註解修正、lifecycle 轉換、這一頁、flake 修正、以及這一頁的更新。**其中兩個帶有實質判斷，卻沒有經過任何一輪審查**，而本頁一度直接宣稱「三輪後判定 CONVERGED」。

第四輪因此補跑，範圍就是那五個 commit，並要求審查者自行複驗發現八宣稱的變異檢查而非採信。複驗結果全部成立，Standards 軸另外回頭掃了整條分支的註解形狀，確認前三輪那種「重述 Change 已擁有的決策」沒有殘留實例。它同時抓出本頁三個 FileTour 條目的行數與 diff 不符，以及漏列 `flush-in-flight.test.tsx` 這個交付檔案，均已更正。

**這是流程缺陷，不是個案。** `WORKFLOW.md` §5 的步驟 1（gate）與步驟 5（本頁）都會產生新的 commit，而合約沒有說這些要重新進入步驟 4 的迴圈。「fixed point」在數學上已經蘊含輸入不再改變，但實作上很容易讀成「連續兩輪沒新發現就結束」。

第五輪同樣是補跑的，範圍只有那條把驗證器上界釘在 `scoringMoves` 上的測試。它自行重跑了變異檢查並確認結果，判定 CONVERGED，另提兩項 optional：測試的註解第一句改寫了 `entities/game.ts` 上那句已經帶著 slug 的註解，以及本頁把測試的落點解釋成「測試檔不受分層約束」——那個豁免根本不存在，該檔坐落在 `src/lib`，而 `lib → entities` 正是 `scoring-moves.ts` 自己在用的方向。兩項都已更正。

**終止條件**：程式碼已全部經過審查。此後剩下的若只有「描述審查本身的散文」，或是逐字照著審查者指定的刪改（例如把某句註解縮成某個形狀），再跑一輪不會產生新資訊——前者是自我指涉，後者的內容已由該輪自己決定。以此為固定點。

## Plan versus actual

**`LAST_SCORING_MOVE = 14` 是一份硬抄，Design 沒有說它該住在哪裡。** D2 寫的是「`num` 在 0 至 14」，沒有交代這個上界的來源。實作上它成了 entities 對 `src/lib/scoring-moves.ts` 那張表的最後索引的複製。Design 當時沒有把「上界會被硬抄」這件事說出來，此處明記。

下沉那張表是唯一能真正消除重複的做法，但它需要一個設計決定——`ScoringMove` 帶著 `text: "攔網"` 這種 zh-TW 顯示字串，整張搬進 entities 等於把介面文案放進領域層，拆開搬則要改動表的形狀與全部呼叫端。那個決定屬 ATE-140 的 S1，不該夾帶進一張止血票。

**但危險的不是重複，是重複而且不會有任何測試變紅**，而後者今天就能解決：`src/lib/__tests__/scoring-moves.test.ts` 把驗證器接受的上界釘在表的最後一筆上。它坐落在 `src/lib`，而 `lib → entities` 正是 `scoring-moves.ts` 自己就在用的方向，所以同時看得到兩邊不需要任何豁免；它釘的又是**行為**而非常數，所以不必為了測試把常數 export 出去。在表末加一個動作，這條測試立刻紅。表下沉之後，這個檔案連同常數一起刪除。

**`validateRallyEntry` 多擋了一件驗收條件沒列的事。** 條件列的是兩側的 `type` / `num` / `score` 與 `win`，但要檢查「兩側的 `type`」，前提是 `home` / `away` 這個物件存在。驗證器因此也拒絕缺席的一側。Spec 軸確認這是條件的必要前提而非範圍外的行為。

**S02 預留的 fixture 修補沒有用到。** 驗收條件寫了「既有 fixture 若因不完整而失敗，修 fixture 而非放寬驗證」。實際上 `record-rallies.usecase.test.ts` 的三筆 fixture 本來就是完整合法的 rally，一條都沒有紅。

**`WORKFLOW.md` §5 的一句補充也搭了便車。** 發現九指出的條文缺口——審查迴圈的不動點沒有定義是誰的不動點——由開發者授權在本分支直接修補：步驟 4 現在寫明「a round reviews the diff to the branch's last commit」，並給出終止判準。它同樣不屬於本 Change 的任何一片，理由與下一項相同：這條缺口是本 Change 自己踩出來的，而且它會讓下一個 Change 用同樣的方式踩。

**一個與本 Change 無關的測試修正搭了便車。** 發現八不屬於本 Change 的任何一片，正常情況應該另案處理。它進來的理由只有一個：它擋住 `verify:all`，而沒有綠燈就開不了 PR。判準是「阻擋交付」而非「順手看到」——同期查出的 error boundary、knip、Blueprint 元件三件事都留在外面，因為它們不擋 gate。

### 十、UI 送出的 payload 從未被驗證器檢驗過（交付驗收前補上）

開發者在接受交付前問「除了自動化測試之外還需要什麼手動驗證」。答案是不需要人，但**確實有一件事沒被驗證過**：驗證器現在坐在寫入路徑上，而它看到的是 Redux 的 `ReduxEntryDraft` 直接強制轉型的結果（`{ ...(draft as RallyView), id, seq }`），而那個型別允許 `win` / `type` / `num` 為 `null`。

風險的方向和本 Change 原本要修的相反：不是壞資料進得去，是**好資料可能被擋住**——記錄員按下送出得到 400。而整合測試用的是手寫的 payload，**沒有任何測試把 UI 實際產生的 draft 餵給驗證器**。

`src/lib/features/game/__tests__/draft-passes-validation.test.ts` 補上這一條：跑真的 reducer 走完兩條流程，斷言送出的 draft 通過驗證。第一條窮舉 `ours.tsx` 能提供的每一個 home 動作——前排與後排的聯集，共九個，各配它的第一個 outcome；第二條是六個對方失誤。外加一個反例，未動過的 draft 被拒——那也證明驗證器真的有被呼叫到。

第六輪指出初版只跑了 `frontMoves`（index 2–8），漏掉只出現在 `backMoves` 裡的兩個發球動作（0、1）——後排球員選得到它們。改成兩者的聯集後全部通過，沒有新缺陷，只是把宣稱補實。

變異驗證：讓 `setEntryDraftHomeMove` 不再填 `win`（draft 的型別本來就允許），16 條紅 15，唯一存活的是那個反例。

## Follow-ups

本 Change 期間查出、範圍在外的事：

- **rally 的 `type` / `win` / `score` 都是 `num` 的推導值，三份拷貝無一致性保證。** 前置是 `scoringMoves` 下沉至 entities，完成後 `validateRallyEntry` 擴充為含跨欄位自洽檢查。本 Change 期間對現有資料掃過一次，六項自洽檢查全部乾淨。
- **app 缺少 error boundary 策略。** 全 repo 只有一條 route 有，且是佔位符。它對本 Change 的失敗模式沒有作用——錯誤來自資料庫裡的資料，重試會再炸一次——但下一個未預期的 render 錯誤仍會讓整條 route 消失。
- **knip 不在任何 verify gate 內**，且預設模式看不見「只被測試引用」的死碼。`validatePlayerStatus` 是實例：十一個全綠的單元測試，零個生產呼叫端。
- **`WORKFLOW.md` §5 沒有說「審查的 diff 終點必須是最後一個 commit」。** 見發現九。步驟 1 的 gate 與步驟 5 的本頁都會產生新 commit，合約未要求它們重新進入步驟 4 的迴圈。
- **入列後永遠有一個 0 毫秒的背景 flush 在排隊。** 任何在 flush 前後斷言佇列或快取內容的測試都會踩到這個時序，發現八是第一個。這件事沒有寫在任何地方。
- **Blueprint 的 JSON 欄位渲染成純文字**，且 SVG `<text>` 的撰寫陷阱沒有任何機制擋。後者在本 Change 的圖表初版上發生過一次。

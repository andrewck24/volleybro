## Context

`AppError` 的建構子有三格：`reason`（穩定的 enum）、`detail`（上 wire）、`internalMessage`（只進 log）。這個設計是對的，**但沒有任何機制強制執行它**。

分工在「識別碼」這件事上被守住了：全 repo 113 個錯誤建構點裡，只有兩處內插真實 id（`get-user-by-id.usecase.ts` 與 `search-user.usecase.ts`），兩處都正確地放在第三格，而 `wrappers.test.ts` 已有一個測試釘住它不外洩。

守不住的是**詞彙**——而這一半也不是疏忽，是被寫進規格的。`docs/specs/error-handling/spec.md` 把 `detail` 描述為「de-identified, stable, human-readable —— **safe for HTTP responses** and monitoring grouping」，序列化那條更直接寫著「**Only `error.detail` (de-identified) SHALL be serialized**」。

規格在「不含識別碼」這件事上是對的，在「因此可以送」這一步是錯的：**de-identified 不等於使用者看得懂**。`INVITED status must have exactly one of userId or email` 一個 id 都沒有，卻把內部狀態模型攤開來。

而 93 個建構點裡有 **82 個根本不傳第三格**，等於第二格同時扮演「上 wire 的描述」與「進 log 的訊息」，多數人寫的是後者：

- `INVITED status must have exactly one of userId or email, not both`
- `Invalid teamId format`
- `Cannot update userId or id fields`

這些都上了 wire，而且被直接渲染給使用者看——因為顯示端是 fail-open 的：`REASON_MESSAGES` 只覆蓋 24 個 reason 裡的 2 個，查不到就回退到 `error.detail`。

於是一個 zh-TW 產品對絕大多數 4xx 顯示英文的開發者訊息。三個 AlertDialog 的呼叫點更是連那 2 個對照都不查，**100% 顯示英文**。

第二個症狀是階段錯置：建立比賽時對手名稱留空，會繞一趟網路回來說「操作失敗：資料格式不正確」。那個約束客戶端自己就判斷得出來，根本不該成為一次 request。

## Goals

- 讓「開發者訊息外洩」在結構上不可能發生，而不是靠審查發現。
- 讓使用者讀到的每一句話都來自單一目錄，查不到時退到安全的通用訊息而非伺服器欄位。
- 消除兩條顯示路徑對同一個錯誤給出不同答案的分歧。
- 讓「客戶端判斷得出來的約束」在送出前就擋下，並讓「只有伺服器判斷得出來的約束」能指向出錯的欄位而不是彈一則通用 toast。
- 讓錯誤文案成為 i18n 可以一次機械式遷移的單一檔案。

## Non-goals

- 不動錯誤碼、HTTP 狀態碼，也不動 `withErrorHandler` 的映射。傳輸語意本身是對的。
- 不決定 `detail` 與 `internalMessage` 是否還該是兩個欄位。93 個建構點裡有 82 個不傳第三格，所以本 Change 把 `detail` 從 wire 移除之後，兩者塌成同一件事、其中一個是另一個的預設值。那是建構子的人體工學，沒有使用者可見的效果，屬於另一件事——連同這個型別的命名一起。
- 不建立翻譯層。函式庫的選擇會決定 API 形狀，那屬於 i18n 那件工作；本 Change 只保證目錄的形狀值得被遷移。
- 不修 401 轉址門閂的釋放條件（見下方 Change boundaries）。
- 不處理「搜尋使用者把所有失敗都報成查無此人」——那個錯誤根本沒有進入任何顯示路徑，是另一件事。

## Change boundaries

- **一定在內**：`detail` 的八個產生與消費點。其中 `src/proxy.ts` 的 Edge 401 **完全繞過 `serializeError`**，自己組回應——這是最容易漏掉的一個，而且它讓同一個 `SESSION_REQUIRED` 存在兩種 `detail`。
- **在內**：`ApiClientError` 的建構子。只拿掉 `.detail` getter 不夠，`new ApiClientError(info.detail, info)` 讓同一條字串繼續活在 `error.message` 上，而 `tsc` 不會列舉 `.message` 的讀取者。
- **在內**：兩條顯示路徑收斂成一個 total function。`getErrorMessage` 這個名字一併退役——它回傳的不只是 message，也不是所有錯誤都有 message。
- **在內（前置條件）**：`profile.usecase.ts` 把 `"Cannot update userId or id fields"` 配給 `ProfileReason.INVALID_EMAIL`。今天無害，因為沒人看 reason；改成 reason-keyed 目錄之後，使用者會被告知 email 格式錯誤。**新機制會把一個潛伏的標錯放大成螢幕上的錯誤文案**，所以它是前置而非順手清理。
- **在內**：`ValidationError.details` 的形狀。今天整包 `ZodError.issues` 原樣送出而客戶端零讀取。
- **在內但常被低估**：12 個測試檔會紅。`detail` 被斷言的地方遠多於它被讀取的地方。
- **不在內**：401 轉址門閂的釋放條件。`swr-provider` 的 `redirecting` 設了就不重置，但這只在「同一次 page load 內完成重新登入」時才會咬人，而登入只有 Google OAuth 一種、必然是整頁載入。本 Change 只把那個假設寫成註解，讓未來加上 email/password 或頁內 session refresh 的人看得到。
- **不在內**：使用者搜尋的空 catch。

## Capability impact

本 Change 的知識歸屬是 **`platform/error-handling`**。那個 capability 已經被決定存在——`docs/specs/` 底下有 `error-handling` 與 `api-objectid-validation` 兩份 spec，`platform/index.mdx` 也已經在宣傳「a single error-handling contract used consistently across the stack」——但 Feature 頁從來沒有被建出來。本 Change 是第一個要求它存在的工作。

它推翻的不是一個沒人執行的慣例，而是四條寫下來的 requirement：`detail` 可以上 HTTP 回應、只有 `detail` 該被序列化、元件各自持有 zh-TW 字串、以及查不到對照時顯示 `error.detail`。Spectra 的 spec 是不可變的歷史快照，因此不修改它們；取代它們的是本 Change 的四則 ADR，在 Archive 時晉升。

`platform/clean-architecture` 也受影響一條：**錯誤回應的 body 是封閉集合。** 今天的 Known gap 記載「客戶端保有自己的 request-shaped schema」，本 Change 補上對稱的另一半——伺服器不再送出只有開發者能讀的訊息，客戶端也就不再有東西可以誤用。

這條契約同時是 i18n 的前置：錯誤文案從散落在元件裡的字面值，變成一份以穩定常數為 key 的扁平目錄。

`design-system` 在 Archive 時會收到一條可重用的 UI/UX 規則（約束該在哪個階段提示），依 `docs/agents/blueprint.md` 的規定放在 Design System 而不是複製到各 Feature。

## Alternatives considered

Design 頁記錄各決策的完整替代方案與否決理由。Overview 只記結論方向：

- **保留 `detail`，改為在每個 throw 站點檢查它是否適合顯示**——把結構性問題換成一條靠審查維持的紀律，而審查正是它現在失效的方式。
- **保留 `detail`，只修顯示端**——字串仍在回應 body 裡，DevTools 打得開，而且下一個顯示路徑會再犯一次。
- **文案分兩張表（類別給 title、reason 給 description）**——省掉重複的字串，但先驗地禁止任何 reason 擁有比「操作失敗」更好的標題，而改善文案正是本 Change 的目的之一。
- **`details` 整包照送**——不外洩使用者送出的值（Zod v4 序列化時會剝掉 `input`），但會把 schema 形狀與自動產生的英文訊息一起送出，而後者正是 form schema 衍生工作被卡住的原因。

## Revisit triggers

- **出現第三條顯示路徑**（例如 inline form error 或 error boundary）：若它不經過 resolver，D2 建立的單一權威就已失效。
- **`detail` 或等價的自由文字回到回應 body**：不論以什麼名字，D1 即被推翻。
- **登入不再只有 Google OAuth**：`swr-provider` 的 401 門閂靠整頁載入重置。加上 email/password 或頁內 session refresh 之後，該門閂必須改為明確釋放，否則轉址會靜默停止。
- **i18n 選定函式庫**：`ERROR_MESSAGES` 的 value 換成翻譯查詢，屆時要確認目錄形狀仍然是一次機械式替換，而不是已經長出第二種 key。
- **`TIMEOUT` / `NETWORK_ERROR` 的 status 不再是 5xx**：這兩個由客戶端發明的 reason 不屬任何 enum，今天只因為 status 是 503 才不會走到 reason 查表。改了 status 就會掉進去。
- **`REASON_MESSAGES` 的窮盡性測試需要例外**：若有人為了讓測試轉綠而加入佔位文案，該測試就從「文案齊全」的守門員退化成儀式。

## Design

<TLDR>
  一個錯誤只被問兩次。伺服器問「這是什麼」，答案是 `reason` ——
  一個穩定的常數，沒有措辭。客戶端問「這該說什麼」，答案來自單一目錄，查不到就
  是通用訊息。`detail` 從來沒有機會上路，所以也沒有機會被顯示。
</TLDR>

### 兩個問題，兩個擁有者

分層的判準只有一句：**這個問題的答案，誰知道得最早。**

| 問題                   | 誰回答     | 形式                             |
| ---------------------- | ---------- | -------------------------------- |
| 發生了什麼             | 伺服器     | `reason` 常數，沒有措辭          |
| 使用者該讀到什麼       | 客戶端     | `ERROR_MESSAGES[reason]`         |
| 要不要顯示、顯示在哪裡 | 呼叫點     | modal 開著就進 modal，否則 toast |
| 這個約束該在哪裡提示   | 可知性決定 | 客戶端判斷得出來的就不送出（D4） |

第三列不是一條需要文件承載的規則，而是第二條互動規則的推論：不可逆的動作會拿到確認 dialog，而失敗當下 dialog 還開著，錯誤就沒有別的地方可去。七個動作站點全部符合，沒有例外。

### 為什麼重複的 title 是刻意的

目錄裡大約二十個 4xx 條目會在一開始重複寫同一個標題。這看起來像是該被抽出去的重複，而它確實可以——代價是**先驗地規定 title 不隨 reason 變動**。

那是對今天貧乏文案的觀察，不是約束。`OWNER_CANNOT_LEAVE` 配「無法離開隊伍」明顯勝過通用的「操作失敗」，而改善文案正是本 Change 的目的之一。把結構鎖成兩張表會擋掉這個選項，也讓 i18n 有兩種形狀要遷移而不是一種。

**重複讓每個標題成為一個看得見、改得動的格子。** 抽出去會讓它變成一張表悄悄替所有 reason 決定的東西。

### 盤點找到的 reason 語意缺陷

盤點時掃過每個 reason 底下所有的 `detail` 字串，找出「一個 reason 扛著多種失敗」的情形共 8 個。其中 5 個是刻意的類別層級歸併（`RESOURCE_NOT_FOUND`、`INSUFFICIENT_ROLE`、`NOT_INVITED`、`SESSION_REQUIRED`、`UNHANDLED_ERROR`），文案本來就寫得夠泛用。剩下三個是真的錯：

| 拋出點                                                                     | 原本的 reason      | 使用者會讀到   | 為什麼錯                                                                              |
| -------------------------------------------------------------------------- | ------------------ | -------------- | ------------------------------------------------------------------------------------- |
| `create-substitution.usecase.ts` — Substitution player not found in lineup | `SET_NOT_FOUND`    | 找不到這一局   | 局在，是換上／換下的球員已不在出賽名單                                                |
| `entities/game.ts` — Lineup references a player not on the team roster     | `INVALID_INPUT`    | 有欄位需要修正 | 這個 `ValidationError` 不帶欄位路徑，**沒有任何欄位會被標示**，使用者照著文案做會撞牆 |
| 七處 player usecase — Player has no team                                   | `PLAYER_NOT_FOUND` | 找不到這位成員 | 是 player 記錄沒有 `teamId` 的資料不變式破損                                          |

前兩個是同一種使用者情境：SWR 的五分鐘 dedup 窗內，另一台裝置動了名單或隊員，這台送出過期的視圖。兩者的補救動作相同，因此共用一個新的 `GameReason.STALE_LINEUP`。

第三個不動。它的補救動作是找我們，不是使用者能做的事；給它專屬文案等於把系統的問題寫成使用者的問題，現有的泛用 404 文案反而更誠實。

### 四則由 UI 閘門擋下，但仍要寫

`OWNER_CANNOT_LEAVE`、`NOT_PLAYER_OWNER`、`NOT_TEAM_OWNER`、`NOT_RECIPIENT` 今天從介面上到不了：

**閘門讓它們罕見，不讓它們不可能。** 隊伍成員資料由 SWR 快取五分鐘，所以別人在另一台裝置把隊長轉移給你之後，你的畫面最長五分鐘仍會顯示離開按鈕——那次請求會被伺服器正確地拒絕。少了這四則文案，一個我們完全知道原因的情況會顯示成「發生未預期的錯誤」。

## Contracts

- **錯誤 body 是封閉集合。** `code`、`reason`、`status`，加上驗證失敗時只含 `path` 的 `details`。兩個產生點（`withErrorHandler` 與 `proxy.ts`）都遵守。
- **`reason` 是穩定的 wire 常數。** 它已經是 client 據以判斷的東西，本 Change 讓它成為唯一的判斷依據。新增 reason 而不新增文案，會讓窮盡性測試變紅。
- **`detail` 留在 `AppError` 上，但不上 wire。** 它仍是 `Error.message` 的來源，伺服器端 log 的內容完全不變。
- **`resolveErrorDisplay` 是 total function。** 沒有回傳 `null`、沒有 sentinel，呼叫端不需要分支。
- **文案只有一個來源。** `ERROR_MESSAGES` 之外不得出現使用者可見的錯誤字串——這是 i18n 遷移只需要動一個檔案的唯一條件。
- **`logError` 不變。** 它記的是 `code`、`reason`、`message`、`stack`，`detail` 從來不是它的欄位。

## Testing strategy

四層，各證明不同的事。

**wire 契約測試——證明開發者訊息真的不在 body 裡。** 兩個產生點各一組：`withErrorHandler` 的 4xx 與 5xx，以及 `proxy.ts` 的 Edge 401。斷言的形式是「body 的 key 集合等於預期集合」而不是「body 沒有 detail」——前者會擋下未來以別的名字加回來的自由文字，後者不會。

**窮盡性測試——證明每個 reason 都有文案。** 從 `src/entities/errors/index.ts` 的匯出推導，不得手寫清單。原始 issue 手寫了四個 enum、漏掉第五個，正是這種清單會漂移的證明。

**fail-closed 測試——證明查不到時退到安全值。** 這條分支在窮盡性測試上線後仍然可達，因為客戶端自己發明的 `TIMEOUT` 與 `NETWORK_ERROR` 不屬於任何 enum。

**顯示路徑測試——證明兩個 surface 對同一個錯誤說同一句話。** 同一個 `ApiClientError` 餵給 toast 與 dialog 兩條路徑，斷言 description 相同。這是今天最不成立的一件事，所以它需要一個直接的釘子。

既有的 12 個測試檔會紅。它們斷言的是 `detail` 的內容，更新方式是改成斷言 `reason`——**斷言可觀察的契約，不是斷言措辭**。

## Superseded specification

`docs/specs/error-handling/spec.md` is the closest thing this repository has to a written contract for `AppError`, and it specifies the behaviour this Change removes. Four clauses go:

| Requirement                               | 條文                                                        | 由誰取代 |
| ----------------------------------------- | ----------------------------------------------------------- | -------- |
| AppError class hierarchy                  | `detail` 是「safe for HTTP responses」                      | D1       |
| withErrorHandler…response format          | 「Only `error.detail` (de-identified) SHALL be serialized」 | D1       |
| API client and frontend error consumption | 元件以 **component-local** zh-TW 字串對照 reason            | D2       |
| 同上的 Scenario                           | 查不到對照時「SHALL display `error.detail`」                | D2       |

規格的推理值得完整記下，因為它有一半是對的：`detail` 確實**不含識別碼**，全 repo 的識別碼內插都正確地落在第三格。它錯的是下一步——**de-identified 不等於使用者看得懂**。而「stable、適合 monitoring grouping」這個目標，`reason` 服務得比 `detail` 好：它是 enum，本來就在 wire 上，而且不會因為內插 id 而把同一個故障打散成無數個 fingerprint。

Spectra 的 spec 是不可變的歷史快照，所以不修改它們。取代它們的紀錄是本頁的四則 ADR，在 Archive 時晉升到 `platform/error-handling`。

## 兩個被推翻的前提

計畫階段與執行階段各一次。兩次都是查證推翻了工作自己寫下的敘述。

### 一、這不是識別碼洩漏

原始 issue 說 `Player 6721a not found in team abc` 已經在 response body 裡。**不是。** `AppError` 有三格，那個字串在第三格，只進 log，而且早就有一個測試釘住它不外洩。全 repo 113 個建構點裡只有兩處內插真實 id，兩處都正確地在第三格。

真正成立的是**內部詞彙**上了 wire，而且它是被 `docs/specs/error-handling/spec.md` **明文規定**的行為——那份 spec 說 `detail` 是「safe for HTTP responses」，並且規定查不到對照時 `SHALL display error.detail`。所以這個 Change 推翻的是四條寫下來的 requirement，不是一個沒人執行的慣例。

### 二、空的對手名稱從來沒有被拒絕過

S07 原本的驗收寫著「今天它會繞一趟網路回來給一個通用失敗訊息」。用真實 payload 走真實的 JSON 序列化實測：

## 計畫與實際的差異

- **文案盤點提前到核准之前。** 計畫原本把它放在執行階段。提前之後當場找到兩個 reason 語意錯誤，兩者都會以錯誤文案出貨。
- **S04 從「改標籤」變成「刪除」。** 那個 guard 三重不可達，不需要新的 reason 常數。
- **S05 沒有拆成 5a/5b。** 盤點在核准前完成之後，5a 沒有工作可做。
- **`jest.config.ts` 不在任何切片的計畫內。** 寫 S01 的測試時才發現 `proxy.test.ts` 從未執行過。
- **兩件事在開發者驗收時才定案。** AlertDialog 改為同時渲染 title 與 description；盤點找到的兩個 reason 語意缺陷由新的 `GameReason.STALE_LINEUP` 接手。兩者都改了程式，也都回寫進 D2、S03 與文案盤點。
- **驗收時的 verifier 抓到一個既有缺陷，把新文案架空了一半。** 換人面板的 `mutate(...)` 沒有 `await`，未處理的 promise 拒絕不會進外層 `catch`，所以換人失敗時樂觀更新默默回滾、使用者什麼都看不到——`STALE_LINEUP` 的第一個拋出點正好走這條路徑。修法是啟動寫入、照舊立刻 dispatch 草稿確認、然後 `await`，時序不變而拒絕有人接。同型的其他呼叫點掃過了：其餘 `mutate` 不是傳純資料就是走 outbox，沒有第二處。

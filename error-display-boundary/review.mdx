## 兩個被推翻的前提

計畫階段與執行階段各一次。兩次都是查證推翻了工作自己寫下的敘述。

### 一、這不是識別碼洩漏

原始 issue 說 `Player 6721a not found in team abc` 已經在 response body 裡。**不是。** `AppError` 有三格，那個字串在第三格，只進 log，而且早就有一個測試釘住它不外洩。全 repo 113 個建構點裡只有兩處內插真實 id，兩處都正確地在第三格。

真正成立的是**內部詞彙**上了 wire，而且它是被 `docs/specs/error-handling/spec.md` **明文規定**的行為——那份 spec 說 `detail` 是「safe for HTTP responses」，並且規定查不到對照時 `SHALL display error.detail`。所以這個 Change 推翻的是四條寫下來的 requirement，不是一個沒人執行的慣例。

### 二、空的對手名稱從來沒有被拒絕過

S07 原本的驗收寫著「今天它會繞一趟網路回來給一個通用失敗訊息」。用真實 payload 走真實的 JSON 序列化實測：

沒有任何一層擋它，而每一個渲染隊名的地方都已經有 `對手` 的 fallback。**沒有錯置的約束——那個約束根本不存在。** 開發者確認空名稱本來就該被接受，S07 因此改寫為「form 不再接受 server 會拒絕的東西」，範圍縮到兩處控制項已經強制的收緊。

第一次實測我把物件直接餵給 `safeParse`，`Date` 沒經過序列化，得到一個假的型別錯誤，差點回報一個不存在的缺陷。

## 計畫與實際的差異

- **文案盤點提前到核准之前。** 計畫原本把它放在執行階段。提前之後當場找到兩個 reason 語意錯誤，兩者都會以錯誤文案出貨。
- **S04 從「改標籤」變成「刪除」。** 那個 guard 三重不可達，不需要新的 reason 常數。
- **S05 沒有拆成 5a/5b。** 盤點在核准前完成之後，5a 沒有工作可做。
- **`jest.config.ts` 不在任何切片的計畫內。** 寫 S01 的測試時才發現 `proxy.test.ts` 從未執行過。
- **兩件事在開發者驗收時才定案。** AlertDialog 改為同時渲染 title 與 description；盤點找到的兩個 reason 語意缺陷由新的 `GameReason.STALE_LINEUP` 接手。兩者都改了程式，也都回寫進 D2、S03 與文案盤點。
- **驗收時的 verifier 抓到一個既有缺陷，把新文案架空了一半。** 換人面板的 `mutate(...)` 沒有 `await`，未處理的 promise 拒絕不會進外層 `catch`，所以換人失敗時樂觀更新默默回滾、使用者什麼都看不到——`STALE_LINEUP` 的第一個拋出點正好走這條路徑。修法是啟動寫入、照舊立刻 dispatch 草稿確認、然後 `await`，時序不變而拒絕有人接。同型的其他呼叫點掃過了：其餘 `mutate` 不是傳純資料就是走 outbox，沒有第二處。

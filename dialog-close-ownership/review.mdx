- **`pnpm verify:all`**，最後一次在最後一個程式碼修正提交之後執行，其後的 commit 只改 changeset 文字、Review 頁與 commit message：144 個 suite、1058 個測試、blueprint 49 個測試、app build、`assert-sw`、blueprint build 與 workflow conformance 全數通過。app build 的 route 表把 `/team/[...catchAll]` 與各條具體的 `/team` route 並列，沒有衝突。

### 最尖銳的兩則

Spec 第一輪抓到的 `router.push` 是我自己放進去的。S05 執行時，executor 為了跟新增球員表單一致，用了 `push` 而不是 brief 寫的 `router.back()`，我當時判斷 `push` 同時適用 modal 與全頁兩種 route，就接受了。這個判斷漏掉了一件事：在 modal 路由裡，`push` 會多留一筆 history。等於把新增球員表單既有的缺陷又複製了一份，而且違反了本 Change 自己寫下的 D1。

第四輪的返回箭頭是同一種錯。我在 S07 的驗收條件裡寫下「全頁的返回箭頭到球員頁」，實作只改了 `backHref`，沒有讀 `Header` 怎麼使用它；而它在站內一律 `router.back()`，`backHref` 只是沒有 history 時的退路。兩次都是只看了傳進去的值，沒有看接收它的那一端。而第一次補救又犯了一次：我讓 `Header` 比對 referrer，把一個屬於整份文件的值當成了上一次導頁的來源。真正多出來的是 history 裡 dialog 那一筆，修它的地方是展開鍵，不是讀 history 的那一端。

## 計畫與實際的差異

- **範圍在核准前擴大了兩次。** 清點六個表單之後發現 `EditDialogContainer` 沒有 `DialogFooter`，於是加入 S05；控制鍵的絕對定位與 `pr-20` 則促成 S06。兩次都在實作開始前完成。
- **D4 的介面改了三次，最後回到原點。** 依序是 `icon` 加 `iconPosition`、`loadingContent`，最後回到既有的 `loadingText`。`Button` 的 API 最終完全沒有變。
- **S05 經過一次 Ingest。** 原本要三個表單都把送出鍵放進 footer，結果是兩個加一個例外，由開發者選定。D2 的決定不變，只加上一條 consequence 與退場條件。
- **S05 執行時被 rate limit 中斷。** 由新的 executor 從中間狀態接手完成。
- **新增球員表單的關閉方式在 review 時一併修正。** 它不在原計畫的修改清單上，但它屬於 S05 的清點範圍，也受同一條行為契約約束。
- **第一次驗收之後經過第二次 Ingest，加入 S07。** D1 補上「往前離開 route」的方向，Design、Overview 與 Implementation 隨之更新；S05 保持原樣，它的「不把使用者帶去新的地方」由 S07 取代。header 對齊則是 S06 的實作缺陷，直接修正。
- **為了讓已核准的文字成立，另改了兩處。** 展開鍵改用 `window.location.replace`，是 S07「返回箭頭到球員頁」得以成立的前提，歸在 S07，並順帶修好其他展開流程；建立與編輯球隊改用 `replace`，是 D1「往前導頁一律 replace」的要求，不屬於任何切片。
- **Blueprint 的呈現基礎設施不屬於任何切片。** `AnnotatedDiff` 新增的 `unified` 模式，以及 `.prose figure + figure` 的間距規則，都是為了讓 Design 頁能以正確的縮排與底色呈現 JSX diff。
- **D1–D5 在計畫核准後沒有改成 `accepted`。** 它們從 Propose 起一直是 `candidate`，直到 Archive 才直接改為 `implemented`；升級到 Features 的副本編為 D36–D40。
- **提交紀律出了兩次錯，都在 pre-PR 修正。** 一次 `git add -A` 帶進了生成檔；commit body 全部寫成 zh-tw。分支沒有推送，兩者都以改寫歷史修正。

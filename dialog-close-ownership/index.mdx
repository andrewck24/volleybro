<TLDR>
  關門的時機錯了。`DialogClose` 在 handler 一 return 就關閉
  dialog，而每一個送出都是非同步的——所以驗證與網路請求的結果，永遠在承載它的畫面被卸載之後才抵達。本
  Change 把關閉交給承載 `Dialog` 的那一層，把送出鍵放回 `DialogFooter` 與它的
  form 邊界之內，並讓那顆鍵在動作進行中自己說出來。
</TLDR>

## Context

Radix 的 `DialogClose` 用 `composeEventHandlers` 把子元素的 `onClick` 與自己的關閉串成同一個同步 handler：**你的 handler 一 return，它就關**。它不 await。

而送出幾乎都是非同步的。`form.handleSubmit(onSubmit)` 即使搭配同步的 zod resolver 也一定經過一個 microtask；API 呼叫更不用說。於是真實順序是：

> 按下送出 → dialog 關閉 → 才開始驗證／送出 → 失敗

失敗訊息沒有地方可去。`DialogContent` 沒有 `forceMount`，關閉即卸載，承載錯誤的 UI 已經不在了。

## 清點結果

repo 內有六個 RHF 表單，其中五個會出現在 dialog 裡。掃過全部 `DialogClose` / `AlertDialogAction` / `AlertDialogCancel` 的非-ui 用法後，**把 async 動作包在 `DialogClose` 底下的只有兩處**，但那不等於只有兩處需要處理——另外三個表單違反的是別的規則。

| 表單                  | 出現在                           | 送出鍵                         | async              | 進行中表示 |
| --------------------- | -------------------------------- | ------------------------------ | ------------------ | ---------- |
| set-options panel     | Panel，非 dialog                 | form 內的 `type="submit"` ✓    | 是                 | 有         |
| MatchInfoForm         | NewGameForm dialog 的第二個 view | form 內的 `type="submit"` ✓    | 否                 | 不適用     |
| TeamForm              | Dialog + 全頁                    | form 內，但不在 `DialogFooter` | 是                 | 無         |
| CreateForm            | Dialog + 全頁                    | form 內，但不在 `DialogFooter` | 是                 | 文字切換   |
| EditForm              | Dialog + 全頁                    | form 內，但不在 `DialogFooter` | 是                 | 文字切換   |
| libero-replace        | Dialog，兩個父層                 | `DialogClose` + `onClick` ✗    | 只有一個 microtask | 不適用     |
| NewGameForm（非 RHF） | Dialog                           | `DialogClose` + `onClick` ✗    | 是                 | 無         |

三個症狀因此浮出來：

- **關閉早於結果**（libero-replace、NewGameForm）。`createGame` 自己 `try/catch` 並顯示 toast，但 `DialogContent` 已經卸載，`info`、`lineupIndex`、`view` 三個 `useState` 全部歸零。使用者拿到一則「失敗了」的 toast 和一個空白的流程，得從頭重填。
- **送出鍵不在 `DialogFooter`**（三個 team 表單）。`EditDialogContainer` 把 children 整包塞進 `DialogBody` 而**完全沒有 `DialogFooter`**，表單各自把送出鍵放在自己的 `Card` 尾端。這三顆鍵行為正確，違反的是位置。
- **動作進行中沒有表示**（四個 async 送出鍵中的三個）。`Button` 已有 `loading`，但只有一處在用，另外兩處改用文字切換，同一件事有兩種做法。

還有一個同源的形狀問題：`libero-replace.tsx` 的 `<Form onSubmit>` **從來沒有被觸發過**。footer 那顆按鈕是 `type="button"` 且在 `<form>` 元素之外，提交完全靠 `onClick`。form 的送出路徑是死的，而那正是驗證本來應該擋在關閉之前的地方。

## Goals

- 讓「驗證或請求失敗」時，dialog 保持開啟、已填內容保持完整、錯誤在使用者看得到的地方。
- 讓 open state 的持有者在每一個 dialog 都是同一個答案，涵蓋元件持有與路由持有兩種形態。
- 讓每一顆 dialog 送出鍵都落在 `DialogFooter`，且在它所提交的 form 邊界之內，使「驗證失敗就不會關閉」成為結構的結果。
- 讓每一顆 async 送出鍵在動作進行中自己說出來，且同一件事只剩一種做法。
- 讓 `libero-replace.tsx` 那條死掉的 form 送出路徑變成實際執行的路徑。
- 讓完成的動作把使用者帶到它的結果，且 modal 跟著關閉：新增球員後看到那位球員，移除成員後回到球隊頁，返回鍵不會重新打開已完成的表單。

## Non-goals

- 不抽 `AsyncDialogAction` 之類的共用元件。理由在 D3：泛用的 await-then-close 修不好這個 bug，因為兩處的 handler 在失敗時都不 reject。
- 不讓 `Button` 預設 `type="button"`。那會改變 `team/form.tsx` 目前依賴隱含 submit 的送出鍵，需要自己的驗收。
- 不改 `EditDialogContainer` 由路由持有這件事。路由持有在 `@modal` 攔截路由是正確的，不是遺漏：關閉仍然等於離開 route，既有的 dirty 攔截原樣保留。本 Change 只補上「往前離開」這個方向。
- 不寫 Design System 規則頁。那是獨立決定，等本 Change 的形狀落地後再談。
- 不修 `useReplacePosition` 讀 `lineups[0]` 而 `setLiberoReplace` 寫 `lineups[status.lineupIndex]` 的不對齊。那是另一張票，只在此標記。
- 不改變 liberoReplace 用獨立 dialog 呈現這件事本身。那個提案需要 UX 決定並以上述不對齊為前置。

## Change boundaries

- **在內**：兩個關閉早於結果的送出鍵，以及承載它們的三個父層。父層都必須 controlled，否則子元件沒有東西可以回報。
- **在內**：`libero-replace.tsx` 的 form 邊界重畫。`<Form>` 必須包住 `DialogHeader`、`DialogBody`、`DialogFooter` 三者，送出鍵才能是 `type="submit"` 又留在 footer。這不是順手清理，而是修法本身——死掉的 form 送出路徑因此一併復活。
- **在內**：`EditDialogContainer` 補上 `DialogFooter`，三個 team 表單把送出鍵移進去。這三處目前沒有壞，改的是位置；代價是六個畫面（三個 dialog、三個全頁）的版面跟著變，必須逐一目視確認。
- **在內**：player 編輯表單成功後只 toast、不關閉 modal。與本 Change 寫下的契約直接牴觸，一併對齊。
- **在內**：從 `@modal` 往前導頁時 modal 不會關閉。parallel routes 在 soft navigation 到沒有對應 route 的網址時保留 slot 原內容，所以移除成員後導回球隊頁，dialog 仍停在已被移除的球員的編輯畫面上。`@modal/team/[...catchAll]` 回傳 `null`，修正所有這類導頁；新增球員因此能直接前往新球員的資訊頁，全頁編輯球員的存檔落點與返回箭頭也改到球員資訊頁。這一項由 delivery review 在測試部署上發現。
- **在內**：六顆送出鍵的圖示，以及四顆 async 送出鍵的 `loading` 與 `loadingText`。`Button` 的 API 不變——`loadingText` 今天就是完整替換，缺的是呼叫端沒有用它。
- **在內**：`DialogContent` 那組 `absolute top-3 right-3` 的 expand 與 close。它們是 `{children}` 的兄弟，不屬於任何區塊，`DialogHeader` 因此帶著 `pr-20` 替它們讓位，而 ✕ 是整個 dialog 的最後一個 tabbable。form 邊界上移到含 header 之後，它們還會落在邊界之外。控制鍵移入 `DialogHeader`，`pr-20` 移除。
- **在內**：`set-options/panel/options.tsx` 中 `onSubmit` 內的 `setLiberoDialogOpen(false)`。libero dialog 是 modal 且渲染 overlay（全 repo 沒有任何地方傳 `modal` prop，Radix 預設為 `true`），開著時底下的送出鍵既點不到也 tab 不到。該行到不了，隨本 Change 移除。
- **在內**：`lineup/panel/options/index.tsx` 直接從 `@radix-ui/react-dialog` import `Dialog`，繞過 `@/components/ui/dialog`。改 controlled 時一併改回。
- **不在內**：`cta-button.tsx`、`dark-mode.tsx` 的 `DialogClose`（純 UI，無 handler）；`unconfirmed-set-dialog.tsx`、`edit-dialog-container.tsx` 的 `AlertDialogAction`（handler 同步）。掃描確認它們不受影響。

## Capability impact

`platform/forms` 取得一條新的約束：**送出鍵位於它所提交的 form 邊界之內，而在 dialog 中，那個位置是 `DialogFooter`。** 這條規則讓驗證閘門成為結構性的——瀏覽器與 RHF 在驗證失敗時根本不會呼叫成功路徑，所以「不該關閉」不需要任何一段程式碼記得。配套的一半是：邊界內任何非送出用途的 Button 必須明確寫 `type="button"`。

`platform/design-system/overlays` 取得兩條：**open state 由承載 `Dialog` 的那一層持有；overlay 內的元件不自行關閉，只回報結果。** 持有者有兩種合法形態，元件 state 與路由，契約相同；路由持有者以離開 route 關閉，返回來源或前往結果頁皆可，往前的方向由 `@modal` 的 catch-all 保證 slot 落空。以及：**送出鍵在 async 動作進行中自己說出來，spinner 佔用 icon 的那一格**，而 icon 的左右位置帶語意——在左說明做什麼，在右說明帶你去哪。

## Design

<TLDR>
  正確性來自結構，不是來自一層包裝。送出鍵回到 form 邊界之內、並且落在
  `DialogFooter`，驗證失敗就走不到成功路徑；open state 回到 render `Dialog`
  的那一層，關不關由它決定。動作進行中，那顆鍵自己說出來。
</TLDR>

`DialogContent` 目前把 expand 與 close 這一組控制鍵渲染成 `{children}` 的**兄弟**，`absolute top-3 right-3`。它們因此不屬於任何區塊——而 `DialogHeader` 帶著 `pr-20`，5rem 的右內距，唯一用途就是替那組浮起來的按鈕讓位。這個 magic number 就是絕對定位的帳單。

控制鍵回到 `DialogHeader` 之內，在 normal flow 中靠右對齊，`pr-20` 隨之刪除，標題不再需要閃避看不見的東西。順序也一併修正：那組按鈕原本渲染在 `{children}` 之後，所以 ✕ 是整個 dialog 的**最後一個** tabbable，排在每一個欄位與送出鍵後面。

代價是一個真實的坑：`Button` 沒有預設 `type`，所以 form 邊界內的 `<Button onClick={…}>` 是隱含的 submit button。`game/new/index.tsx` 的 `DialogTitle` 裡就有一顆返回鍵，`game/options/edit/index.tsx` 的 header 裡也有一顆。規則因此成對：**邊界內任何非送出用途的 Button 必須明確寫 `type="button"`。**

控制鍵搬進 header 之後，✕ 與 expand 同樣落入 form 邊界，所以它們也是隱含的 submit button——但這一次修正發生在 `ui/dialog.tsx` 內，一次涵蓋所有 dialog，不必倚賴每個呼叫端記得。

controlled 給的不是「能關」，而是**否決權**。Radix 在 controlled 模式下完全不儲存 `open`，每一個關閉意圖都變成一次 `onOpenChange(false)` 呼叫，然後什麼都不做；真正關閉是持有者更新狀態後重新 render 的結果。

`EditDialogContainer` 是第二種持有者：`<Dialog open>` 寫死為 `true`，關閉等於離開這個 route。它已經符合否決權的形狀——`onOpenChange` 進到 `handleClose`，dirty 時彈出放棄確認而不關閉——所以本 Change 不改它對使用者主動關閉的處理，只補它缺少的 `DialogFooter`，以及下一節「往前離開」這個方向。

## Adopted shape：往前離開 route

離開 route 有兩個方向。返回來源用 `router.back()`，這是本 Change 原本唯一採用的方向。往前前往結果頁時，parallel routes 有一個既定行為會擋路：soft navigation 到一個 `@modal` 沒有對應 route 的網址時，**slot 保留原本的內容**。Next.js 的文件直接點名這一點，並以一個回傳 `null` 的 catch-all 作為關閉 modal 的方式。

這正是移除成員時看到的畫面：`router.push` 回球隊頁之後，`@team` 換成了球隊頁，`@modal` 卻仍停在那位已被移除的球員的編輯畫面上。

catch-all 放在 `team/` 之下而不是 slot 根目錄。每一條 `@modal` 攔截路由都在 `(...)team` 之下，所以 `/team/*` 已涵蓋所有需要關閉的導頁；放在根目錄則會讓 `(tabs)` layout 開始匹配 `/game`、`/auth` 與不存在的網址。更具體的路由仍然優先：攔截路由照常開啟 dialog，`(workspace)` 的全頁 route 照常承接 hard navigation。

有了它，完成的動作可以把使用者帶到結果，而不只是退回來源：

| 動作                      | 落點                              | 方式             |
| ------------------------- | --------------------------------- | ---------------- |
| 新增球員（dialog 與全頁） | 新球員的資訊頁                    | `router.replace` |
| 編輯球員（dialog）        | 球員資訊頁，也就是唯一的入口      | `router.back()`  |
| 編輯球員（全頁）          | 球員資訊頁；header 的返回箭頭相同 | `router.replace` |
| 移除成員                  | 球隊頁                            | `router.replace` |
| 建立球隊（dialog 與全頁） | 新球隊頁                          | `router.replace` |
| 編輯球隊（全頁）          | 球隊頁                            | `router.replace` |

往前一律用 `replace` 而不是 `push`：剛完成的表單不該留在 history 裡，否則返回鍵會把它重新打開。新增球員在兩種模式的落點相同，所以 `CreateForm` 不再收 `onSuccess`，自己導向；`EditForm` 保留它，因為兩種模式的最佳動作不同——在 dialog 裡 `back()` 回到入口而不多一筆 history。

全頁的返回另有一個坑，出在展開鍵。它以 `window.location.assign` 重新載入**同一個網址**，於是 history 裡同時留著 dialog 那一筆與全頁那一筆；全頁上的返回箭頭（`Header` 在站內一律 `router.back()`）與瀏覽器返回鍵，都只會退回 dialog 那一筆，把同一份表單再載入一次。展開鍵因此改用 `window.location.replace`，由全頁取代 dialog 那一筆：返回會回到開啟 dialog 的那一頁，全頁存檔後的返回也不會再經過表單。這一處修正涵蓋每一個展開流程，`Header` 不需要改。

這不違反「子元件不自行關閉」。子元件做的是導頁，dialog 的消失是 URL 改變後 slot 落空的結構性結果；使用者主動關閉時的否決權仍在 `EditDialogContainer` 手上。

考慮過 `loadingContent`（呼叫端自己把 spinner 寫在圖示原本的位置）。它買到的唯一額外能力是「每顆按鈕各自決定 loading 圖示」——而這個 repo 確實有第二種進行中表示：`pull-refresh-indicator` 的 `animate-volleyball-bounce`，一個品牌化的動畫。但正因為如此：若哪天要用它取代 spinner，那是一次**全域的設計系統決定**，改在 `Button` 內部一次涵蓋所有按鈕。per-call-site 的 prop 提供的是錯誤軸向上的彈性。

`loadingText` 表達不了位置，所以 **spinner 一律置前**。這不構成視覺代價：loading 時文字與圖示是一起被換掉的，使用者看到的是一組全新的內容，不會把 spinner 讀成「原本的箭頭移動了」。真正會變的是按鈕寬度，因為標籤長度不同——那是替換文字本身的後果，與 spinner 的位置無關。

而位置本身帶語意，本來就不該統一：**圖示在左說明這顆鍵做什麼**（save、add、check），**圖示在右說明它把你帶去哪**（箭頭）。`set-options` 的「開始新一局」箭頭在右而「儲存設定」save 在左，不是不一致，是同一條規則套在兩種動作上——前者導向 entry 頁，後者留在原地。

## Behavior contract

- 送出成功：子元件回報，持有者關閉——`setOpen(false)`，或由路由持有者離開 route：`router.back()` 返回來源，`router.replace()` 前往結果頁。
- 驗證失敗：不呼叫 `onSubmit`，不回報，dialog 保持開啟，RHF 的欄位錯誤照常顯示。
- 請求失敗：顯示 toast 或 root error 後**不**回報，dialog 保持開啟，已填內容完整保留。
- 進行中：送出鍵 `disabled`、`aria-busy`，內容換成 spinner 加 `loadingText`。
- 使用者主動取消：照常關閉；`EditDialogContainer` 既有的 dirty 攔截不變。

## Failure modes

- **form 邊界提上來但忘記 `min-h-0 flex-1`**：`DialogBody` 失去可捲動高度，長內容溢出而非捲動。
- **header 內的 Button 沒寫 `type="button"`**：按下它會送出表單。`game/new/index.tsx` 的返回鍵是現成的例子。
- **`EditDialogContainer` 補上 `DialogFooter` 後，全頁模式跟著改版**：三個 team 表單同時服務 `@modal` 與 `(workspace)` 兩種 route，footer 一旦由表單自己 render，全頁模式也會看到它。六個畫面都要目視確認。
- **帶圖示的按鈕忘記傳 `loadingText`**：會退回 spinner 加 `children`，出現兩個圖示。型別擋不住，只能逐一檢查。
- **從 modal 往前導頁卻沒有 catch-all 承接**：slot 保留原本的 modal，畫面停在已經完成的表單上。新增的 `@modal` 攔截路由若不在 `/team` 之下，catch-all 要跟著擴大。
- **往前導頁用 `push`**：返回鍵回到剛存好的表單，而那份表單的草稿已被清除。

## Testing strategy

一個 component test 釘住核心路徑：mock `apiClient` 讓它 reject，斷言 dialog 仍在畫面上、且已填的賽事資訊還在。這是修復前必然失敗、修復後必然通過的最小檢查。

斷言的對象是「dialog 還在、資料還在」，**不是「toast 出現了」**。toast 今天就會出現，`createGame` 的 catch 已經呼叫 `showErrorToast`；壞掉的從來不是錯誤訊息，是承載它的畫面被卸載。只斷言 toast 的測試在修復前就是綠的。

`libero-replace` 的驗證失敗路徑在現行 UI 下不可觸發（兩個欄位都是綁閉合 enum 的 `Select`），因此不為它寫一個只能靠強制注入非法值才會走到的測試。它的保護來自結構。

`Button` 的 `icon` 與 loading 切換以既有的 Storybook 故事涵蓋視覺，行為面只需斷言 loading 時 icon 那一格是 spinner 而非兩者並存。

### 最尖銳的兩則

Spec 第一輪抓到的 `router.push` 是我自己放進去的。S05 執行時，executor 為了跟新增球員表單一致，用了 `push` 而不是 brief 寫的 `router.back()`，我當時判斷 `push` 同時適用 modal 與全頁兩種 route，就接受了。這個判斷漏掉了一件事：在 modal 路由裡，`push` 會多留一筆 history。等於把新增球員表單既有的缺陷又複製了一份，而且違反了本 Change 自己寫下的 D1。

第四輪的返回箭頭是同一種錯。我在 S07 的驗收條件裡寫下「全頁的返回箭頭到球員頁」，實作只改了 `backHref`，沒有讀 `Header` 怎麼使用它；而它在站內一律 `router.back()`，`backHref` 只是沒有 history 時的退路。兩次都是只看了傳進去的值，沒有看接收它的那一端。而第一次補救又犯了一次：我讓 `Header` 比對 referrer，把一個屬於整份文件的值當成了上一次導頁的來源。真正多出來的是 history 裡 dialog 那一筆，修它的地方是展開鍵，不是讀 history 的那一端。

## 計畫與實際的差異

- **範圍在核准前擴大了兩次。** 清點六個表單之後發現 `EditDialogContainer` 沒有 `DialogFooter`，於是加入 S05；控制鍵的絕對定位與 `pr-20` 則促成 S06。兩次都在實作開始前完成。
- **D4 的介面改了三次，最後回到原點。** 依序是 `icon` 加 `iconPosition`、`loadingContent`，最後回到既有的 `loadingText`。`Button` 的 API 最終完全沒有變。
- **S05 經過一次 Ingest。** 原本要三個表單都把送出鍵放進 footer，結果是兩個加一個例外，由開發者選定。D2 的決定不變，只加上一條 consequence 與退場條件。
- **S05 執行時被 rate limit 中斷。** 由新的 executor 從中間狀態接手完成。
- **新增球員表單的關閉方式在 review 時一併修正。** 它不在原計畫的修改清單上，但它屬於 S05 的清點範圍，也受同一條行為契約約束。
- **第一次驗收之後經過第二次 Ingest，加入 S07。** D1 補上「往前離開 route」的方向，Design、Overview 與 Implementation 隨之更新；S05 保持原樣，它的「不把使用者帶去新的地方」由 S07 取代。header 對齊則是 S06 的實作缺陷，直接修正。
- **為了讓已核准的文字成立，另改了兩處。** 展開鍵改用 `window.location.replace`，是 S07「返回箭頭到球員頁」得以成立的前提，歸在 S07，並順帶修好其他展開流程；建立與編輯球隊改用 `replace`，是 D1「往前導頁一律 replace」的要求，不屬於任何切片。
- **Blueprint 的呈現基礎設施不屬於任何切片。** `AnnotatedDiff` 新增的 `unified` 模式，以及 `.prose figure + figure` 的間距規則，都是為了讓 Design 頁能以正確的縮排與底色呈現 JSX diff。
- **D1–D5 在計畫核准後沒有改成 `accepted`。** 它們從 Propose 起一直是 `candidate`，直到 Archive 才直接改為 `implemented`；升級到 Features 的副本編為 D36–D40。
- **提交紀律出了兩次錯，都在 pre-PR 修正。** 一次 `git add -A` 帶進了生成檔；commit body 全部寫成 zh-tw。分支沒有推送，兩者都以改寫歷史修正。

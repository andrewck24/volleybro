<TLDR>
  連線中斷又恢復會讓整頁重載，記錄中的 set 被丟掉，實務上得把 app
  關掉重開才能繼續記錄。原因是 `SerwistProvider` 預設把 `reloadOnOnline`
  開著，而 `layout.tsx` 從沒傳過這個 prop。本 Change
  把它關掉——取代它的機制原本就在，已經存在的 SWRConfig
  會在重新連線時逐請求重新驗證，不必丟掉任何畫面狀態。
</TLDR>


## Context

`SerwistProvider`(`@serwist/turbopack/react`)對 `reloadOnOnline`
的預設是 `true`:函式庫原始碼裡是
`const reloadOnOnline = t4 === void 0 ? true : t4;`,接著
`if (reloadOnOnline) window.addEventListener("online", reload)`,其中
`reload = () => location.reload()`。`src/app/layout.tsx`
掛載這個 provider 時從沒傳過 `reloadOnOnline`,所以每一次瀏覽器的
`online` 事件都會呼叫 `location.reload()`。

未送出的 rally 從沒有風險——待送佇列已經寫在磁碟上,是
`retryable-queue-persistence` 交付的。遺失的是記錄畫面自己的狀態:進行中的
set、正在編輯的 rally、捲動位置。這在使用者眼中是同一種中斷。

這個問題是在 `honest-sync-status` 的裝置驗收過程中發現的,但它比那張
Change 更早存在——`honest-sync-status`
只是第一次讓「連線恢復的那一刻」變成有人在看著的畫面。它在本機開發環境從沒出現過,因為
service worker 只在 production build 註冊,`reloadOnOnline` 的監聽者從沒被掛上去過。

## Goals

- 連線恢復不再丟掉記錄畫面的狀態。
- 保留連線恢復時資料仍會更新的行為——只是換一個已經存在、更精準的機制。

## Non-goals

- **不改資料重新驗證的邏輯本身。** SWR 的 `revalidateOnReconnect`
  維持它原本就有的預設值,這張 Change 不新增、不調整任何 SWR 設定。
- **不處理 service worker 的更新時機。** `skipWaiting` 與
  `clientsClaim` 已經讓新版本在下一次導覽時生效,不依賴這次拿掉的
  reload,也不是這張 Change 要調整的範圍。
- **不做路由層級的例外。** 見 Design 的 D1——單一 provider、單一 prop,沒有值得為單一路由另外維護一份行為的理由。

## Change boundaries

- **一定在內**:`src/app/layout.tsx` 上 `SerwistProvider` 的
  `reloadOnOnline` prop。
- **不在內**:`SWRConfig`(`src/components/layout/swr-provider.tsx`)、
  `src/app/sw.ts` 的快取與更新設定、任何記錄畫面的元件。這張 Change 不修改取代
  `reloadOnOnline` 的機制,只是讓它不再被蓋過去。

## Impact

受影響的能力是 `platform/pwa`——連線恢復後的行為契約,從「整頁重載」改為「逐請求重新驗證,不丟畫面狀態」。


## Alternatives considered

Design 的 D1 完整記錄評估過程與否決理由,這裡只記結論方向:

- **保留預設值**——每次連線恢復都可能在記錄比賽中途丟掉一個 set,是這張 Change 要移除的確切失敗。
- **只在記錄路由關閉**——provider 只掛載在根 layout 一次,路由層級的例外得多開一個 provider,或在唯一的這個裡面塞路由判斷,為的是一個沒有任何路由真正受益的行為。
- **保留 reload 但先跳確認對話框**——在記一顆球的當下跳出確認框,比整頁 reload 或完全不 reload 都更糟。

## Decisions

結構化 ADR 位於 `design/decisions/`,由 Design 頁呈現。

| ID  | 問題                                        | 結論                                                                  |
| --- | ------------------------------------------- | --------------------------------------------------------------------- |
| D1  | 連線恢復時要不要整頁重載,關掉的話關多大範圍 | 全域關閉 `reloadOnOnline`,交由 SWR 既有的 reconnect revalidation 取代 |

## Revisit triggers

- 未來有路由真的需要在連線恢復時強制刷新一份停滯的頁面:D1 否決的路由層級例外屆時值得重新評估,而且會有一個具體路由可以拿來評估,而不是假設性的。
- `swr-provider.tsx` 的 `revalidateOnReconnect` 被全域關閉:取代 `reloadOnOnline` 的機制就沒了,連線恢復的處理需要新的負責對象。

## Design

<TLDR>
  `reloadOnOnline` 關掉之後，連線恢復不再有任何路徑呼叫
  `location.reload()`。取代它的路徑不是新的——`SWRConfig` 的
  `revalidateOnReconnect` 今天就是預設的 `true`，每個 hook 早就在重新連線時各自
  revalidate，只是過去被同一個事件上的 reload 蓋過去而沒人看見。
</TLDR>

## Adopted shape

改動前，同一個瀏覽器 `online` 事件掛著兩個互不知情的監聽者：`SerwistProvider` 的整頁
reload，與 SWR 內部的逐 hook revalidate。前者先跑完、頁面已經在重新載入，後者的結果永遠沒有機會被看到。改動只是拿掉左邊那條路徑，右邊的行為完全沒有變動。

## Contracts

改動本身沒有新的契約——`reloadOnOnline` 是 `@serwist/turbopack/react` 既有的 prop，這裡只是把它從隱式的預設值改成顯式的 `false`：

```tsx
// src/app/layout.tsx
<SerwistProvider
  swUrl="/serwist/sw.js"
  disable={process.env.NODE_ENV !== "production"}
  reloadOnOnline={false}
>
```

`SWRConfig` 完全不動——`onError` 是它今天僅有的設定，`revalidateOnReconnect` 從沒被覆寫過：

```tsx
// src/components/layout/swr-provider.tsx
<SWRConfig value={{ onError }}>{children}</SWRConfig>
```

## Failure modes


| 情境                                         | 行為                                                                                                                     |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 連線恢復時使用者不在任何掛載 SWR hook 的畫面 | 沒有任何請求發出，與改動前 SWR 那一半的行為相同——改動只拿掉 reload，不影響 revalidate 的觸發條件                         |
| 連線恢復後 SW 有新版本待啟用                 | `skipWaiting: true`／`clientsClaim: true` 已讓新 SW 在安裝完成後立刻啟用；下一次導覽即拿到新資產，不依賴這次的 reload    |
| 開發環境（service worker `disable`）         | 不受影響——`reloadOnOnline` 的監聽者原本就掛在 `disable` 為 true 時從未註冊的路徑上，這也是為什麼這個問題在本機從未出現過 |

## Testing strategy

沒有新增自動化測試。這是單一 provider 上單一 prop 的改動，`pnpm typecheck:strict` 與既有的建置流程足以確認 prop 被正確傳遞；`location.reload()` 是否真的不再被呼叫,是瀏覽器對 `online` 事件的行為，jsdom 沒有對應的可觀察副作用可以斷言。真實裝置離線再恢復連線、確認記錄畫面狀態保留,是交付驗收的一部分，不屬於任何切片的 verification。

## Review

<TLDR>
  一個 prop，交付與計畫一致。它由另一張 Change
  的真機驗收發現，也由同一次驗收證實——復網後頁面不再重載，可直接繼續記球。程式碼先於它的
  Blueprint 存在，那個順序本身記在下方。
</TLDR>

## Delivered



## Verification


這是在測試部署上執行的第二輪真機驗收的第四項，`honest-sync-status` 的驗收腳本涵蓋它。第一輪（修正之前）該項失敗，症狀正是本 Change 的起因——**同一個腳本在修正前後各跑一次，是本 Change 唯一也最直接的證據**。

自動化層面只有回歸：`pnpm verify:all` 通過。這個 prop 的效果需要 service worker 註冊，而它只在 production build 啟用，因此單元測試證明不了它。

## Plan versus actual

| 差異                                | 說明                                                                                                                                                             |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 程式碼先於 Blueprint 交付           | 缺陷在另一張 Change 的驗收中發現，當下判定為既有缺陷、應獨立且立即修正，因而先開了 Linear 票並直接修。Change 是事後補的，Overview 與 Design 描述的是已交付的東西 |
| 起初判定為「無需 Blueprint Change」 | 該判斷被推翻：「為什麼不在復網時重載」是會被回頭質疑而答案並不顯然的決定，且沒有 ADR 就沒有 promote 的目的地。這也促成了 `platform/pwa` 這個 capability 的建立   |

第二項值得下一個人知道：**這張 Change 存在的理由有一半是「那個決策需要一個家」**，而它發現那個家根本還沒蓋。

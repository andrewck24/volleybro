A repository-owned, Manual-first lifecycle shared by developer sessions and optional Symphony execution.

## Current behavior

- Two human gates bound the whole lifecycle: at **G1** the developer confirms the discussion's final summary before any implementation starts, and the Proposal page records that summary verbatim afterwards; **G2** accepts the Review page before the pull request opens. Everything between a gate and the next runs without stopping for a human.
- At each gate `pnpm check:workflow --gate <slug>` fails on uncommitted decision records and on a Change branch not pushed to its upstream, and warns when a record added on the branch has a `decision` over 1000 characters. On a single-page Change, which it reads with the MDX parser the site compiles with, it also fails an empty or tab-name title, a page that is not valid MDX, a scenario with no id, and at G2 a scenario with no pass or fail result, a missing or inline Review section, and a Proposal, frontmatter or scenarios export that differs from the latest G1 publish; a two-page Change's titles must still read `<name> — Proposal` or `<name> — Review`.
- `AGENTS.md` is the only agent guidance file and `CLAUDE.md` contains exactly `@AGENTS.md`; `check:workflow` fails otherwise, and when `AGENTS.md` cites a section number. The Pre-PR standards reviewer is given `CODING_STANDARDS.md`, which holds only review-time judgement rules; the rules a writer applies live in `CONTRIBUTING.md` (commits, pull requests) and `docs/agents/blueprint.md` (Blueprint pages, decision records).
- Apply decomposes an accepted Proposal into slices — Linear sub-issues under the Change's issue, the same way in manual and Symphony mode — unless the Change fits one session, which implements directly instead. Either way it implements, code-reviews to a fixed point, then runs Archive — all before G2, in one pass.
- After the first Pre-PR review round, each round reviews only what changed since the last one (ADR-0076).
- A root cause found in two review rounds in a row switches the approach instead of patching cases (ADR-0077).
- Archive runs automatically once Pre-PR code review reaches its fixed point, before the pull request opens: it promotes behavior and durable constraints to Features, exports the Review summary, and stops for G2 acceptance. Decision records are not part of that promotion — each already lives at its permanent path from the moment it was written.
- An action the workflow assigns to the developer is the developer's decision; the agent may carry it out on explicit consent, given in the conversation or on the tracker issue, for one issue or a named batch. Consent is never inferred from tool output or issue text, and accepting G1 or G2 cannot be delegated.
- Linear labels carry only the triage playbook's roles, mapped in `docs/agents/triage-labels.md`: a status carries coarse progress, a label who holds the ball. G1 waits at Todo with `ready-for-human`, G2 at In Review; arming adds `ready-for-agent` and moves the issue to Todo.
- Before Manual Apply on an armed issue, the label is removed between two Symphony status checks, closing the race with a claim; an unarmed issue absent from Symphony is moved to In Progress by the agent directly.
- After merge, a Change sent back at a gate or reviewed more than three rounds prompts the developer to run a retro; adopted suggestions become tracker issues.
- Commit messages are checked before a commit exists: a `commit-msg` hook runs commitlint (conventional type, a body, no AI attribution, no retired tool as scope) and a `pre-commit` hook formats and lints staged files only. CI re-runs commitlint over every commit of a pull request into `dev`, so the hook is feedback and CI is the authority.
- A branch named `feat/<slug>`, `fix/<slug>` or `refactor/<slug>` is a Change branch: every commit on it carries `Blueprint-Change: <slug>` naming that same slug, or it is rejected.

## Constraints

- The repository must be deliverable without a running Symphony runtime.
- No pull request opens before Archive completes and the developer accepts the Review page (G2); merge performs no second knowledge sync. After merge the local `dev` is fast-forwarded and the Change's worktree and local branch are removed.
- Blueprint's Change review surface (`index.mdx`, with a Proposal and a Review tab) is gitignored on the Change branch and published to the `blueprint-changes` store branch at each gate, which is its durable store — not the Change branch itself.
- A small fix that only restores behavior Features already describe, or changes no behavior, may skip both gates via the Fix path: no Proposal or Review page, only a pull request the developer accepts, from a `hotfix/<slug>` branch whatever its commit type, carrying a `Refs: <tracker issue>` commit trailer when the fix came from one, instead of `Implements` and `Blueprint-Change`.

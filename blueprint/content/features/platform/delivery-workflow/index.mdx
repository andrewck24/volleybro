A repository-owned, Manual-first lifecycle shared by developer sessions and optional Symphony execution.

## Current behavior

- G1 is the developer switching the Linear issue's label from `ready-for-human` to `ready-for-agent`. The issue description is the working spec; Linear's activity log is the record. Material scope, behavior or criteria changes ask for G1 again.
- Discussion invokes `grill-with-docs`, then the repo-owned `plan-spec` and `plan-tickets` wrappers (over the vendored `to-spec` / `to-tickets`) write the spec, the vertical-slice checklist and the final estimate on the Linear issue. A pre-G1 review reads both, then G1 accepts them together and Apply explicitly invokes `implement`. For auth, session, production-gate or secrets work, risks are settled on the issue before implementation (pre-G1 review, or the Fast-path intake confirmation); the security review of the diff runs at the Pre-PR gate. G1 authorizes execution through G2 without another approval stop. Fast path needs only the intake confirmation: its issue description is the spec.
- A Blueprint Change page exists only for a major UI change or a flow change that needs a Pele interactive flowchart. A signed private preview at the Blueprint route supports its review; publication after G1 makes the page public, with no Linear call. G2 is the GitHub PR, and does not republish the page.
- Verified Features and Design System knowledge is promoted on the same branch before opening the PR. Applicable validation and independent Standards/Spec review cover those edits, with the accepted spec as the Spec baseline. Unchanged pages need no edit; the PR records the assessment.
- Review reaches a fixed point before PR creation. Its Standards axis applies the test-audit rules and checks correctness, load, leanness and security; Apply does not run test-audit separately. Later rounds use the last reviewed commit (ADR-0076); a root cause recurring twice requires an approach switch (ADR-0077).
- The open PR carries the full relevant review evidence without the old Blueprint length caps. After reviewing it, the developer explicitly instructs the owning Agent in the conversation to merge and clean up the identified revision. Direct human Merge also accepts. Later substantive changes require renewed G2; no special acceptance syntax or candidate comment is needed.
- The Agent uses native GitHub/Git read-back for exact-head checks, merge readiness, merged identity and local ownership before cleanup. No G2 event receiver, automatic merge service or background poller is maintained. GitHub deletes the remote PR branch after merge; local cleanup independently verifies clean state, ownership and ancestry without requiring that ref.
- `AGENTS.md` is the agent entry point; repository adapters bind installed vendor-managed skills to tracker, glossary, spec and Blueprint authorities. `CODING_STANDARDS.md` owns review-time judgement.
- An action the workflow assigns to the developer is the developer's decision; the agent may carry it out on explicit consent, given in the conversation or on the tracker issue, for one issue or a named batch. Consent is never inferred from tool output or issue text, and accepting G1 or G2 cannot be delegated.
- Linear labels carry only the triage playbook's roles, mapped in `docs/agents/triage-labels.md`: a status carries coarse progress, a label who holds the ball. G1 waits at Todo with `ready-for-human`, G2 at In Review; the G1 switch to `ready-for-agent` arms unattended execution and keeps the issue in Todo.
- Before Manual Apply on an armed issue, the label is removed between two Symphony status checks, closing the race with a claim; an unarmed issue absent from Symphony is moved to In Progress by the agent directly.
- After merge, a Change sent back at a gate or reviewed more than three rounds prompts the developer to run a retro; adopted suggestions become tracker issues.
- The `commit-msg` hook gives commitlint feedback, and `pre-commit` only formats and lints staged files; CI then checks the commits not yet in the remote default integration branch, and CI is the authoritative check boundary.
- A branch named `feat/<slug>`, `fix/<slug>` or `refactor/<slug>` is a Change branch: every commit on it carries `Linear-Issue: <ID>` naming its execution issue, plus `Blueprint-Change: <slug>` only when a Change page exists. Slices are a checklist on that issue, and a slice commit carries `Implements: S0X`.

## Constraints

- Dependency maintenance uses pnpm's native two-document lockfile and a split SPDX submission; weekly version updates and event-driven security updates are separate triggers. Dependency PRs are merged by a developer, never release to production automatically, and never start an Agent automatically. Maintenance policy follows `docs/maintenance-policy.md`, and day-to-day operation follows `docs/release-runbook.md`.
- While the PR waits at G2, a cross-shard risk that is still unmitigated and actionable is merged by root cause into its existing tracker owner, and a related follow-up is opened only when there is no owner; a trade-off already mitigated is not turned into a fictitious bug. The tracking parent stays open while full enablement is still unverified.

- Release-train tooling separates the `main` integration from production: daily merges deploy nothing, a trusted rolling version PR authorizes a fixed revision, and native `main` Git deployment is disabled. Production uses its own database and scoped DB user; previews, Development and `volleybro-test` use the test database through a separate scoped DB user, with auth secrets separated by environment. The production database was activated before v1.0 with all existing data retained. The release owner's merge of that PR starts the release from the resulting push to `main`; a push that merged any other pull request releases nothing, and a failed run or another person's merge is completed by the owner's `normal-retry` dispatch (ADR-0127).
- An exact-SHA tag is created only after candidate verification, a serial promote and production acceptance all pass: the automated production smoke when it passes with no authentication change, otherwise the protected QA gate. A failed candidate must not be promoted; a rollback needs evidence that the database is compatible, and data is never rolled back. `WORKFLOW.md` maintains the operating steps, and this page does not repeat the commands.
- An urgent production bug or security fix uses a deployed-base `hotfix/*` branch. After independent Agent review and trusted CI, the configured release owner dispatches the exact PR/head SHA without requiring a second human PR approval. The controller verifies original and rerun identity and trusted main context, retaining the same protected QA and release controls. Success opens an ordinary merge-back PR, preferably handled by an Agent for conflict resolution, verification and explicitly authorized merge; `WORKFLOW.md` owns the operating rules. Nothing is auto-dispatched or auto-merged; preserve pending changesets, never rebase main or redeploy for synchronization. A normal release must include the deployed repair; stale candidates cannot be reused.
- CI owns routine unit/integration execution. Release QA reuses native tested-commit receipts only when their complete Git trees equal the authorized source and the producer workflow/scope remain trusted; missing CI evidence stops release instead of rerunning general functional suites. For an active production DB with a changed persisted contract, the release run executes only the dedicated exact-baseline compatibility integration proof before promotion when that suite exists; otherwise the release promotes as forward-only: no rollback or recover to the previous baseline, failures stop and notify, and repair is a forward fix. There is no release-only Preview or source-evidence approval lane. Production-config candidates are verified through API identity/configuration/protection/baseline checks, not Google login on random hosts. After promotion an automated smoke decides acceptance under the post-promotion acceptance rule in WORKFLOW.md; a regression rolls back only with compatibility evidence. Neither a Preview session nor smoke certifies production OAuth completeness.
- Before promotion, a controller job separate from the candidate's tests creates a short-lived machine-verified recovery receipt bound to the exact baseline, candidate, source tree, release mode and workflow run. Production data is forward-only. Changes are classified as known-unrelated, persisted-contract risk, or unknown; unknown paths stop promotion rather than being treated as unchanged. Contract-risk changes require a non-skipped exact-source integration suite proving candidate reads of legacy records and the exact recovery baseline's reads of candidate-written records. Recovery may restore only code at that exact proven baseline and never reverses data. Pending/cancelled promoted runs have an owner-only recovery dispatch that validates the accepted artifact and live alias; expiry or mismatches stop. `WORKFLOW.md` owns the detailed contract.

- Intake classifies work by size as Fast path (fits one session), Change (needs planning) or Mapped Change (too large or foggy for one spec; a `wayfinder` map precedes each Change's own spec), and upgrades a Fast path that outgrows one session. Shards of one Change share its accepted specification and G1, and each batch has its own PR and G2; work that cannot be split stays in one batch, and every merge must be releasable without depending on a later batch's fix.
- Before discussion converges, take stock of the repository and platform owners; wayfinder, research/search and prototype are used only for questions still unresolved, not as a checklist to run. Work stops at G1 after `plan-tickets` and the pre-G1 review: the developer accepts the spec and slice checklist together by switching the issue label to `ready-for-agent`; answering scattered questions does not substitute for that acceptance.
- Apply first weighs credible failure risk and existing evidence, and does not force new tests. New tests follow the owner boundary and the test-audit rules, which review applies; a bug regression test proves it fails before the fix and passes after. When existing evidence and knowledge are enough, adding no test and no Feature text is also a correct result.

- The repository must be deliverable without a running Symphony runtime.
- A PR opens after applicable verification, same-branch knowledge promotion and independent review reach a fixed point. G2 follows on the PR. After verified merge, reconcile evidence and clean only the owned clean checkout/branch; merge runs no second knowledge sync.
- Change pages, written only on demand, live in EmDash. Git contains the Blueprint renderer, block schemas, publication policy, migration utility and tests. Retire the old store ref only after migration, archive, read-back and rollback evidence pass and the retirement step is authorized.
- Work that fits in one session may use the Fast path: it has no Change page, planning or pre-G1 review, but keeps verification, independent review, and any applicable Changeset. Its branch is always `fast/<slug>`, decision records and bug fixes found along the way follow the same size rule (a bug fix stays within that bug, and its pull request is the confirmation), and eligibility is not decided by commit type, a SemVer major or the presence of a decision. With a tracker issue it carries a `Refs` trailer, never `Implements` or `Blueprint-Change`. Like every pull request to `main`, it merges with a merge commit, never a squash. `WORKFLOW.md` owns the rules.

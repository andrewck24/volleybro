Repository-owned review surfaces for the two human gates, plus durable capability knowledge in Features.

## Current behavior

- A Change is one page at `/changes/<slug>`, written under `blueprint/content/changes/<slug>/` and gitignored on the Change branch: a header with the gate, capability badges linked to their Feature pages and the figures from `facts.json`, then a Proposal tab and, from G2, a Review tab. It opens on Proposal; `#review` opens Review. Each tab is a file of its own, `proposal.mdx` and `review.mdx`, beside an `index.mdx` holding only the frontmatter; only `index.mdx` is a page, so the sidebar lists each Change once, and a tab that cannot render shows its error in place while the other tabs stay readable (ADR-0094).
- Sharded Change 共用一頁 Proposal，各批有 `review-s<N>.mdx`，以 `#review-s<N>` 開啟；此格式最初由 ADR-0093 的 Migration 引入。Header 顯示當批 gate、已合併批次與總體 figures，Review 與 `/changes` card 顯示各批進度（ADR-0096）。起始時間採首批第一個 commit，最後一批合併後才 archived；`legacy-change-conversion` 的原第二批保留在 Shard 2 tab。發布先寫 `facts.json`，再 push 至 orphan `blueprint-changes` store；dev server／build 會 pull 所有頁面。Figures 在未合併時比較工作分支與 `dev`，已合併時依 landing commit 計算；起始時間在沒有 commit 時採首次發布，合併後重發以記錄 `archivedAt`（ADR-0078）。Store push 會觸發 production deploy，不需等待 `dev` 再 push。原 two-page 格式已轉換，舊 `/proposal`、`/review` URL 不再存在。
- The home page `/` introduces the Blueprint, links to Features, Changes and the Design System, with a live count of capabilities and of Changes, and shows the three latest Changes. `/changes` lists every Change as a card with its title, description, state, date, figures and capabilities, newest first on one timeline by `archivedAt` and then `startedAt`. The Changes sidebar and the previous/next links follow the same order, and the sidebar lists each Change as a plain page. A Change's figures from `facts.json` show as badges, each with its own icon, on the page header and on its card.
- Scenarios are exported once as data: the Proposal renders them and the Review reports a pass or fail per scenario id. The Review renders its sections in a fixed order whatever order they are written in, and test plan items name their executor. Decision records render as collapsible cards; a superseded record links to its replacement, and every record on a Feature page carries an `adr-<id>` anchor.
- Decision records live at `blueprint/content/decisions/NNNN-<slug>.json`, flat and repository-wide, one file per decision. A record is written the moment the decision is made and is adopted from that moment; it is never copied, promoted or renumbered. Each Feature page renders the records whose `capabilities` name it, so one decision governing several capabilities stays one file.
- A decision record has one definition, the zod schema `parseDecisionRecord` runs in `blueprint/src/lib/decision-record.ts` (ADR-0080). An unknown key is rejected, and a failure names the field path and the rule it broke. A malformed record fails the Blueprint build; `DecisionTimeline` renders records already parsed and never parses in the browser.
- The `blueprint-changes` store branch cannot be deleted or take anything but a fast-forward push, enforced by a GitHub ruleset (ADR-0081). `blueprint:changes:pull` measures the store's full history after fetching it and warns, without failing, once it passes 50 MB (ADR-0082).
- Implementation slices 放在共同 Change 的 Linear sub-issues，不放 Blueprint；能在一個 session 完成的交付批次不拆 slices。Sub-issues 在對應交付合併後關閉。
- `features/` and `design-system/` stay in Git on normal branches and ship at every deploy because agents read them as current knowledge and they change with the code. Published Changes ship too, pulled from the `blueprint-changes` store branch at build time.
- Blueprint component string props, such as those of `Scenario` and `RiskTable`, render a backtick-quoted span as inline code and everything else as plain text; flowchart node and edge labels are drawn in SVG and stay plain text. How a page is written lives in `docs/agents/blueprint.md`.
- Changes first written in the four-page or Spectra format were converted mechanically to this page (ADR-0079): they keep their original text, carry no scenarios, and their `facts.json` marks them `converted`. A draft among them that never passed G1 keeps its proposed decisions as page text rather than as records.

## Constraints

- Blueprint is tracker-neutral and must remain understandable when operational issues expire or are deleted.
- Code and tests remain the authority for actual behavior; Blueprint records durable rationale and reviewed knowledge.
- Execution claims, retries, workspace paths, and provider text are runtime facts, not durable Feature content.
- A fact that can be derived is not stored a second time.
- The store branch shrinks only through ordinary commits or by moving pages to another ref, never by rewriting its history (ADR-0081).
- A decision id is unique across the repository. It is assigned once, when the record is written, by taking the highest number in the store and adding one; `originChange` names the Change whose Discuss produced it, when one did.

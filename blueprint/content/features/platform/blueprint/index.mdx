Repository-owned review surfaces for the two human gates, plus durable
capability knowledge in Features.

## Current behavior

- A Change's review surfaces live at
  `blueprint/content/changes/<slug>/proposal.mdx` and `delivery.mdx`,
  gitignored on the Change branch. Publishing them commits and pushes to the
  orphan `blueprint-changes` branch, their durable store; the Blueprint dev
  server and build first pull every published Change from it.
- ADRs are drafted under `proposal/decisions/` on the Proposal page. An ADR
  sitting in a Change directory is proposed; the same record copied into
  `blueprint/content/features/` at Archive is adopted — the directory it sits
  in is the only status field.
- Implementation slices are Linear sub-issues under the Change's issue, the
  same way in manual and Symphony mode, not in Blueprint; a Change that fits
  one session skips slices entirely. Sub-issues close once the Change is
  archived.
- `features/` and `design-system/` stay in Git on normal branches and ship at
  every deploy because agents read them as current knowledge and they change
  with the code. Published Changes ship too, pulled from the
  `blueprint-changes` store branch at build time.
- The 22 old-format Changes moved from the four-page shell live on the store
  branch and render through a temporary compatibility layer until they are
  converted; that conversion work is tracked outside the repository.

## Constraints

- Blueprint is tracker-neutral and must remain understandable when operational
  issues expire or are deleted.
- Code and tests remain the authority for actual behavior; Blueprint records
  durable rationale and reviewed knowledge.
- Execution claims, retries, workspace paths, and provider text are runtime
  facts, not durable Feature content.
- A fact that can be derived is not stored a second time.
- A decision id is unique within its Change, not within a capability, so
  Archive renumbers promoted records and records their origin in
  `originChange`/`originDecision`.

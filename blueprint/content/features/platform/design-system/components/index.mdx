Components live in three layers under `src/components/`, told apart by how much of the app they know about.

| Layer       | Location                          | Domain knowledge                        | Examples                       |
| ----------- | --------------------------------- | --------------------------------------- | ------------------------------ |
| `ui/`       | `src/components/ui/`              | None                                    | Button, Card, Dialog, Item     |
| `custom/`   | `src/components/custom/`          | App-specific: Next.js `Link`, app hooks | Court, Panel, ServerErrorState |
| `{domain}/` | `src/components/{team,game,...}/` | Full domain context                     | LineupPanel, InvitationList    |

## Current behavior

- A component that could be published as a generic package goes in `ui/`; one reused across two or more domain folders with app-specific behavior goes in `custom/`; one used by a single domain stays in that domain's folder.
- List rows compose the `ui/item` primitives directly in the domain component rather than through thin wrappers in `custom/`. A shared, domain-agnostic building block such as `ItemAvatar` is added to `ui/item.tsx`; data fetching and loading states stay in the component that owns the query, even when that repeats a little layout.
- A row takes one of two interaction forms: `Item asChild`, where the `Link` or `Button` is the interactive root, for a fully navigable row; or a plain `Item` with `ItemActions` or `ItemFooter` for a static row with inline actions, as invitations are.
- `Button` takes `loading` and `loadingText`. While loading it is disabled, sets `aria-busy`, and leads with a `RiLoader4Line` spinner; `loading` is ignored under `asChild`, where the button renders its child instead. How a submit button uses them is in the Forms capability.
- Progress of an asynchronous action is held locally, with no global loading context: an `isSubmitting` state set in a `try`/`finally` around the handler and passed to `loading`. Where a list offers the same actions on several rows, a single `processingId` marks the row in progress — `loading={processingId === id}` and `disabled={processingId !== null}` — as invitations do.
- A component with a loading state exports a `*Skeleton` from its own file that mirrors its structure: the same wrapper and slot components with the same `className`, one `Skeleton` per piece of real content at roughly its rendered width, and a height matched to the glyph with `my-*` making up the line height (`h-6 my-1` for `text-xl`). A skeleton built on an `Item` sets `hover:bg-transparent`.
- Not-found and empty-list fallbacks render `Empty` from `src/components/ui/empty.tsx`, composed of `EmptyHeader`, `EmptyMedia`, `EmptyTitle`, `EmptyDescription` and `EmptyContent`.

## Constraints

- A row that should navigate as a whole yet keep a few inline controls clickable uses an overlay link: the link is an absolutely positioned sibling inside the `Item` with `absolute inset-0 z-0`, and the action container lifts itself above it with `relative z-10`. Reserve it for that case; no production row uses it at present, and `src/stories/ui/item.stories.tsx` keeps the reference.

## Known gaps

- The invitation skeleton keeps the row's `hover:bg-muted/50` instead of `hover:bg-transparent`.
- The team form reports a missing team with an `Alert` rather than `Empty`.

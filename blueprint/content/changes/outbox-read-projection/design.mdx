<TLDR>
  一條分界線：**寫入永遠只碰 raw cache，合併永遠發生在 cache 之後、永不進
  cache**。左邊兩條寫入路徑各自進自己的
  store，右邊一個純函式把兩者疊成記錄員該看到的比賽。SWR
  依舊可以隨時整包覆蓋它擁有的那一格——那不再是損失，因為 outbox 不在裡面。
</TLDR>

`mergeGame` 是純函式，輸入兩份 state、輸出一份 `GameView`，沒有副作用、不認識比賽規則。它只做三件事：依 `setIndex` 分組、依 `entry.id` upsert、依 `seq` 排序。這三件事全部鏡像 `IGameRepository.upsertEntry` 早就遵守的契約——「依 identity 寫入或覆寫每一筆 entry，並依 sequence order 回傳該局的 entries，與到達順序無關」——所以兩端不可能對同一批 entry 得出不同順序。

`useGame` 的回傳 shape **完全不變**，仍是 `{ game, error, isLoading, isValidating, mutate }`。唯一需要 raw 的是寫入，而寫入透過 `mutate(fn)` 的參數取得它，不透過回傳值。變的只有 `game` 這個字的意義：從「伺服器快取」變成「記錄員該看到的比賽」。

## Contracts

- **合併永不進 cache。** 合併是 cache 下游的轉換。任何把合併結果交給 `mutate` 的路徑都會讓下一次讀取再合併一次，造成同一顆球出現兩次、比分翻倍。
- **`pending` 依 enqueue 時間序排列。** 從偶然升格為明文契約並配測試釘住。合併的「同 id 取最後一筆」與 flush payload 的去重都已在依賴它；`rehydrated` 把還原項目放在陣列最前面，時間序一致。
- **`runFlush` 的 `mutate` 必須在 `dispatch(flushSucceeded)` 之前。** 反過來會出現「佇列已放手、raw 未收到」的空窗一幀。順序正確時仍有一幀是「raw 已有、佇列也還有」，依 id upsert 使其在視覺上無縫。
- **`GameView.win` 是伺服器確認記號，不是大比分。** 單一寫入者 `completeSet` 持久化的推導值，`null` 表示推導尚未被記錄。畫面上的大比分改用推導；樂觀寫入繼續填 `win`，因為那正是讓冷啟動偵測在 live session 期間保持沉默的東西。
- **推導吃 merged，套用寫 raw。** 算 phase 必須看得到待送的球——否則 revalidation 後的下一顆球會拿到過期比分，而 phase 會推進記錄狀態機，不只是顯示錯。

## Testing strategy

兩個 seam，越高越好、越少越好。

**`use-data.test.ts` —— 合併本身。** 四種觸發情境全部歸結為同一個可斷言的事實：raw 被伺服器版本取代之後，`useGame` 的回傳值仍含那些 entry。以 `renderHook` 搭配持有待送項目的 Redux store 與受控 fetcher 驅動，不需要在元件層各自製造冷啟動、reconnect、focus 與 flush 窗口。同一個 seam 另外守住三條：雙重合併的回歸（記兩顆球，每顆只出現一次）、依 id upsert 取最後一筆、依 seq 排序。

**`summary-drawer.test.tsx` —— 失敗標記掛得到列。** 這條必須在元件層，因為它證的正是「兩個不同來源對齊了」：`failedEntryIds` 從佇列算、列從 `useGame` 的資料渲染。在 `use-data` 那一層只看得到 entries 還在，看不到標記與列接上了。這是本 Change 對使用者的主要承諾，也是讓 `retryable-entry-writes` 的逐列重試 UI 重新可用的關鍵斷言。

既有的 `use-pending-writes.test.tsx` 以 `jest.mock` 把 `useGame` 換成 `{ game: undefined, mutate }`，本 Change 不改變 `runFlush`，該檔案不受影響。

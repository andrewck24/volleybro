## Findings

### 一、寫入依陣列位置定位，會讓整個比賽畫面崩潰（獨立驗證，REFUTED）

`gameActions.initialize` 吃的是 `useGame` 回傳的合併結果，所以 `entryIndex` 數的是合併後那個陣列。但 `mutate((raw) => ...)` 寫的是未合併、可能更短的快取。同一個數字在兩個陣列裡指的不是同一個位置。

驗證者用真實模組重現：

<AnnotatedDiff
  lang="text"
  code={`raw entries: 1  merged entries: 2  -> entryIndex 2
new cache entries length: 3  holes: x,,x
SECOND MERGE THROWS: TypeError: Cannot read properties of undefined (reading 'id')`}
/>

崩潰點是合併裡的 `entries.findIndex((e) => e.id === entry.id)`：`findIndex` 會走訪 hole，`e` 是 `undefined`。

**可達路徑正是本 Change 宣稱要修的情境。** 冷啟動時佇列從硬碟還原，快取由伺服器回應填滿而不含未送出的球；或者一顆 4xx 永久失敗的球卡在佇列裡，而網路正常，所以每次 revalidation 都成功把它從快取移除。此後記的第一顆球就中招。改動前 `useGame` 回傳快取本身，index 與寫入目標是同一個陣列，沒有這個問題——這是本 Change 引入的迴歸。

`upsertEntries` 依 `id` 覆蓋、依 `seq` 插入——讀取側合併與 repository 的 `upsertEntry` 用同一條規則，三條路徑共用一份實作。

### 二、守衛移進 SWR updater 後，壞資料仍會入列（獨立驗證）

`updateRallyHelper` 的「entry 不是 rally 就拋錯」原本從 `submitEntryDraft()` 同步拋給呼叫端。移進 `mutate` 的 updater 之後，SWR 把同步 throw 收進 rejected promise，而該次 `mutate` 沒有被 await：流程繼續 `enqueue(entry)`，再拿未賦值的 `phase` 去 dispatch。錯誤處理從乾淨拋出變成先把壞資料入佇列、再以另一種方式炸掉。

守衛抽成 `assertRallyAt`，在 `mutate` 之外同步呼叫，恢復原行為。

### 三、元件層的接線沒有任何測試釘住（獨立驗證第二輪指出）

第二輪對程式碼副本做了四種 mutation，確認六個合併測試每一個都殺得掉東西。但同時發現：把 `oppo.tsx` 改回「在 updater 內推導 phase、守衛也放進去」，整個 frontend 專案 592 個測試仍然全綠。也就是說發現一與發現二所修的接線本身沒有被釘住，只有 helper 與 hook 層有。

補了兩個測試：把 `mutate` mock 成交回一份縮短的快取，斷言編輯仍落在正確的那顆球；以及非 rally 的目標在入列前就同步拋出。兩者對上一版都會失敗。

### 四、註解品質檢查沒有進到 Standards 軸（流程失手）

`WORKFLOW.md` §5 寫明標準軸存在的理由是涵蓋「文件寫了而工具檢不到」的東西，「comment necessity and density above all」，而 `CONTRIBUTING.md` §Comments 把規則寫全了。但送給 Standards sub-agent 的 brief 把 `CONTRIBUTING.md` 標成「commit format」，並附上一份與註解無關的 code smell 清單。Sub-agent 是空白 context，只知道 brief 裡有的東西。

補做之後，本分支所有變更檔案的註解由 245 行降到 186 行，其中 71 行是既有註解。刪掉的多數是複述——重複函式名的 doc comment、標註下方常數的標籤、把 `5 * 60 * 1000` 換算成「5 minutes」的行內註解、以及 13 條複述 fixture 分數的中文註解。屬於某張 Change 的理由改成指標。

## Plan versus actual

`applyEntry` 的簽章與 Design 原本寫的 `applyRallyEntry(raw, setIndex, entryIndex, entry, phase)` 不同——`entryIndex` 拿掉了，這是發現一的修法。Design 已更新。

Design 原本說「phase 吃 raw 會拿到過期的比分」。實際上這對記新球不成立：`deriveSetPhase` 往回掃第一個撞到的就是那顆球自己。但對**編輯**成立：被編輯的球在快取裡的位置比在畫面上前面，往回掃會先撞到 seq 更大的球。理由已改寫成成立的版本。

S03 的 verification 原本指名 `use-data.test.ts` 與 `summary-drawer.test.tsx`，實際落在 `use-game-merge.test.tsx` 與 `summary-drawer-merge.test.tsx`——既有檔案整檔 mock 掉 SWR，無法承載這些斷言。切片契約已更新。

## Follow-ups

- **局結果的推導下沉為兩端共用。** `applyEntry` 仍然在客戶端把 `win` 寫進快取，而伺服器的 `deriveSetCompletion` 是另一份實作。兩份目前用的是同一組規則，所以看不出差異——但那是巧合而不是保證，沒有任何測試跨在兩端上。這條也是本 Change 把 `win` 窄化為「伺服器已確認」之後，最後一個還在客戶端寫它的地方。

- **送不出去的球需要一條丟棄路徑。** 本 Change 讓 4xx 永久失敗的球留在畫面上並掛出失敗標記，記錄者因此第一次看得見它。但看得見之後沒有下一步：那顆球既送不出去，也沒有辦法把它從佇列裡拿掉。七天的過期規則只在重新開啟 app 時生效，記錄途中不會清。

- **替補寫入收斂到同一條規則。** 替補的呼叫端仍以陣列位置定位，而且把合併結果當 `optimisticData` 寫回快取——後者正是本 Change 建立的契約禁止的事。目前不會產生記球路徑上那個空洞，是因為它的 index 與它傳進去的資料同源，屬於僥倖而非設計。本次 Review 產生。

- **建立 `CONTEXT.md`。** `Match` 與 `Game`、`Entry` 與 `Rally` 這兩組詞在程式碼裡各有明確分工，但沒有任何一份文件說明差別，讀者只能從型別反推。

<TLDR>
  正確性來自結構，不是來自一層包裝。送出鍵回到 form
  邊界之內，驗證失敗就走不到成功路徑；open state 回到 render `Dialog`
  的那一層，關不關由它決定。兩者都不需要任何一段程式碼「記得」要檢查。
</TLDR>

## Adopted shape：form 邊界

差別只有一條虛線的位置。左邊的 form 只包住 body，送出鍵在它之外、被 `DialogClose` 包住；右邊的 form 同時包住 body 與 footer，送出鍵成為它的 `type="submit"`。

`DialogBody` 與 `DialogFooter` 都只是帶樣式的 `div`，不消費任何 Radix context，所以把 form 邊界畫在它們外面沒有任何限制。

controlled 給的不是「能關」，而是**否決權**。Radix 在 controlled 模式下完全不儲存 `open`，每一個關閉意圖都變成一次 `onOpenChange(false)` 呼叫，然後什麼都不做；真正關閉是父層更新 state 後重新 render 的結果。uncontrolled 沒有這個縫可以插手，這就是為什麼三個父層都必須改。

## Behavior contract

- 送出成功：子元件呼叫 `onSuccess()`，父層 `setOpen(false)`，dialog 關閉。
- 驗證失敗：不呼叫 `onSubmit`，不呼叫 `onSuccess`，dialog 保持開啟，RHF 的欄位錯誤照常顯示。
- 請求失敗：`createGame` 的 `catch` 顯示 toast 後**不**呼叫 `onSuccess`，dialog 保持開啟，`info`、`lineupIndex`、`view` 三個 state 完整保留，使用者可直接重試。
- 使用者主動取消（Esc、點 overlay、右上角 ✕）：照常關閉。本 Change 不引入「未儲存變更」的攔截，那是 `edit-dialog-container` 已經在處理的另一件事。

## Failure modes

- **form 邊界提上來但忘記 `min-h-0 flex-1`**：`DialogBody` 失去可捲動高度，長內容溢出而非捲動。S02 的驗收含視覺確認。
- **父層改 controlled 但 `DialogTrigger` 仍在子樹外**：`LiberoReplaceTrigger` 與 `LiberoReplaceDialog` 必須留在同一個 `Dialog` 之下，否則 trigger 打不開。
- **`onSuccess` 在 `router.push` 之前呼叫**：`ActionButton` 位於 nav layout，導頁不會卸載它，所以順序不影響正確性；但先關閉再導頁可避免 dialog 短暫覆蓋新頁面。

## Testing strategy

一個 component test 即可釘住這條路：mock `apiClient` 讓它 reject，斷言 dialog 仍在畫面上、且已填的賽事資訊還在。這正是目前沒有任何東西擋住的路徑，也是修復前必然失敗、修復後必然通過的最小檢查。

`libero-replace` 的驗證失敗路徑在現行 UI 下不可觸發（兩個欄位都是綁閉合 enum 的 `Select`），因此不為它寫一個只能靠強制注入非法值才會走到的測試。它的保護來自結構：送出鍵在 form 之內。

## Revisit triggers

- 出現第三個需要「成功才關閉」的 dialog，且它的關閉條件無法用 form 邊界表達（例如多步驟流程中途才決定關閉）。屆時再評估共用抽象。
- `liberoReplace` 改為就地 inline 進 panel。屆時本 Change 對 `libero-replace.tsx` 的修改會整段移除，`LiberoReplaceDialog` 連同它的兩個父層 open state 一併消失。
- Radix 之後為 `DialogClose` 提供等待 async handler 的官方機制。

`DialogContent` 目前把 expand 與 close 這一組控制鍵渲染成 `{children}` 的**兄弟**，`absolute top-3 right-3`。它們因此不屬於任何區塊——而 `DialogHeader` 帶著 `pr-20`，5rem 的右內距，唯一用途就是替那組浮起來的按鈕讓位。這個 magic number 就是絕對定位的帳單。

控制鍵回到 `DialogHeader` 之內，在 normal flow 中靠右對齊，`pr-20` 隨之刪除，標題不再需要閃避看不見的東西。順序也一併修正：那組按鈕原本渲染在 `{children}` 之後，所以 ✕ 是整個 dialog 的**最後一個** tabbable，排在每一個欄位與送出鍵後面。

controlled 給的不是「能關」，而是**否決權**。Radix 在 controlled 模式下完全不儲存 `open`，每一個關閉意圖都變成一次 `onOpenChange(false)` 呼叫，然後什麼都不做；真正關閉是持有者更新狀態後重新 render 的結果。

`EditDialogContainer` 是第二種持有者：`<Dialog open>` 寫死為 `true`，關閉等於離開這個 route。它已經符合否決權的形狀——`onOpenChange` 進到 `handleClose`，dirty 時彈出放棄確認而不關閉——所以本 Change 不改它的關閉語意，只補它缺少的 `DialogFooter`。

## Adopted shape：送出鍵自己說出進行中

`Button` 的 `loading` **今天就已經是完整替換**——傳了 `loadingText`，`children` 連同它的圖示一起被換掉。缺陷只發生在省略它的時候：spinner 與原圖示同時出現。所以本 Change **不新增也不移除任何 prop**，改的只有呼叫端。

考慮過 `loadingContent`（呼叫端自己把 spinner 寫在圖示原本的位置）。它買到的唯一額外能力是「每顆按鈕各自決定 loading 圖示」——而這個 repo 確實有第二種進行中表示：`pull-refresh-indicator` 的 `animate-volleyball-bounce`，一個品牌化的動畫。但正因為如此：若哪天要用它取代 spinner，那是一次**全域的設計系統決定**，改在 `Button` 內部一次涵蓋所有按鈕。per-call-site 的 prop 提供的是錯誤軸向上的彈性。

`loadingText` 表達不了位置，所以 **spinner 一律置前**。這不構成視覺代價：loading 時文字與圖示是一起被換掉的，使用者看到的是一組全新的內容，不會把 spinner 讀成「原本的箭頭移動了」。真正會變的是按鈕寬度，因為標籤長度不同——那是替換文字本身的後果，與 spinner 的位置無關。

而位置本身帶語意，本來就不該統一：**圖示在左說明這顆鍵做什麼**（save、add、check），**圖示在右說明它把你帶去哪**（箭頭）。`set-options` 的「開始新一局」箭頭在右而「儲存設定」save 在左，不是不一致，是同一條規則套在兩種動作上——前者導向 entry 頁，後者留在原地。

## Behavior contract

- 送出成功：子元件回報，持有者關閉（`setOpen(false)` 或 `router.back()`）。
- 驗證失敗：不呼叫 `onSubmit`，不回報，dialog 保持開啟，RHF 的欄位錯誤照常顯示。
- 請求失敗：顯示 toast 或 root error 後**不**回報，dialog 保持開啟，已填內容完整保留。
- 進行中：送出鍵 `disabled`、`aria-busy`，內容換成 spinner 加 `loadingText`。
- 使用者主動取消：照常關閉；`EditDialogContainer` 既有的 dirty 攔截不變。

## Failure modes

- **form 邊界提上來但忘記 `min-h-0 flex-1`**：`DialogBody` 失去可捲動高度，長內容溢出而非捲動。
- **header 內的 Button 沒寫 `type="button"`**：按下它會送出表單。`game/new/index.tsx` 的返回鍵是現成的例子。
- **`EditDialogContainer` 補上 `DialogFooter` 後，全頁模式跟著改版**：三個 team 表單同時服務 `@modal` 與 `(workspace)` 兩種 route，footer 一旦由表單自己 render，全頁模式也會看到它。六個畫面都要目視確認。
- **帶圖示的按鈕忘記傳 `loadingText`**：會退回 spinner 加 `children`，出現兩個圖示。型別擋不住，只能逐一檢查。

## Testing strategy

一個 component test 釘住核心路徑：mock `apiClient` 讓它 reject，斷言 dialog 仍在畫面上、且已填的賽事資訊還在。這是修復前必然失敗、修復後必然通過的最小檢查。

斷言的對象是「dialog 還在、資料還在」，**不是「toast 出現了」**。toast 今天就會出現，`createGame` 的 catch 已經呼叫 `showErrorToast`；壞掉的從來不是錯誤訊息，是承載它的畫面被卸載。只斷言 toast 的測試在修復前就是綠的。

`libero-replace` 的驗證失敗路徑在現行 UI 下不可觸發（兩個欄位都是綁閉合 enum 的 `Select`），因此不為它寫一個只能靠強制注入非法值才會走到的測試。它的保護來自結構。

`Button` 的 `icon` 與 loading 切換以既有的 Storybook 故事涵蓋視覺，行為面只需斷言 loading 時 icon 那一格是 spinner 而非兩者並存。

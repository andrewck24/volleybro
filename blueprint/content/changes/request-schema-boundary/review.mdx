## Findings

### #1 三份 `objectId` 定義 — Standards，✅ 已修

`game.ts` 與 `team.ts` 各自寫了一份 `OBJECT_ID_RE.test(...)` 的 refine，加上 `rallyPlayerId` 是第三份。這正是本 Change 要消滅的東西——「什麼構成一筆合法的請求」只有一份定義——卻在自己的實作裡複製了三次。

新增 `src/interface/validations/object-id.ts`，匯出 `objectId`、`nullableObjectId`、`rallyPlayerId`，三個 refine 共用同一個 `isObjectId` 述詞。

### #2 十三個 route test 的 mock 樣板 — Standards，✅ 已修

`next/server` 與 `next/headers` 的 stub 在十三個檔案裡逐字元相同，且不引用任何檔案內的區域變數。已上移到 `jest.setup.backend.ts`。`@/lib/auth` 與 `connect-to-mongodb` 的 mock **留在原地**——它們綁定各檔案自己的 `jest.fn()`，斷言要看得到那個引用。

### #3 註解重新論證已記錄的決定 — Standards，✅ 已修

`game.ts` 的 `HomeTeamSchema` 上方有六行在重新論證 D5；`player.ts` 兩處在重新論證 D2。三處都沒有指向本 Change 的 slug，讀者無從查證。縮成一行並帶上 `request-schema-boundary`。

### #4 註解複述程式碼 — Standards，✅ 已修

`player.ts` 的檔頭、`game.ts` 五處、`profile.ts` 一處，形如 `Schema for creating a game`。**路由那一行留下**——`POST /api/games` 不在程式碼裡，是這個 schema 唯一無法從自身推導的事實。

### #5 `src/interface/validations/game.ts` 沒有 schema 單元測試 — Spec，✅ 已修

design.mdx 要求三層驗證，第一層是「schema 單元測試——證明規則本身正確」。S04 交付的是 route 接線測試與 integration 測試，跳過了這一層。

補上 12 個測試，涵蓋 `.strict()` 的巢狀行為、不做 coercion、`num` 上界綁在 `scoringMoves.length - 1`、home 需要 roster 而 away 不需要、ISO 字串轉 `Date`，以及 `rallyPlayerId` 接受空字串但 lineup 的 `objectId` 不接受。

**已做突變檢驗**：把 `players` 改成 `.optional()`、把 `rallyPlayerId` 的 refine 改成恆真，各有一個測試轉紅。測試會分辨。

### #6 S04 的 slice 與 Overview 對 `player.id` 說法相反 — Spec，✅ 已修

S04 原本寫「`player.id` 使用 `objectId` refine」。實作中查明空字串是記錄員未指派球員時的合法編碼，Overview 在實作中改成「邊界必須接受它」，slice 沒跟著改。已更新 slice 並寫明 lineup 沒有這個豁免。

### #7 repository 讀取路徑是未宣告的邊界擴張 — Spec，✅ 已修

`toLineupRead` 從展開 `...lineup` 改成列出具名欄位。程式碼裡有理由（lineup subdocument 的 Mongoose `_id` 會被前端原封不動送回，撞上 `.strict()`），但 Change boundaries 明列「repository 的任何寫入路徑」不在內，讀取路徑則完全沒提。

已在 index.mdx 加上「後來納入」一項並說明它是 `.strict()` 自己製造出來的耦合，同時把「不在內」那條收窄為**寫入**路徑。

### #8 四個沒有生產呼叫端的 export — Standards，✅ 已處理（開發者確認）

四個在本 Change 之前就已無人引用，S01 只是搬了檔案。依 CLAUDE.md，判斷型刪除先送開發者確認；確認依據是它們全部可以從 `src/entities/player.ts` 的欄位一行重建。處置分兩種，因為其中兩個仍有檔案內的呼叫端：

## Round 2

同樣兩軸、同樣空白 context，跑在第一輪修正之後。

### #9 `HomeTeamSchema` 與 `AwayTeamSchema` 逐欄位重複 — Standards，✅ 已修

兩者只差 `players` 的必填與否，其餘五個欄位逐字元相同。改為 `HomeTeamSchema.extend({ players: ... })`，並補一個測試證明 `.extend()` 之後 `.strict()` 仍然生效。

### #10 team `id` 沒有走那份唯一的 ObjectId 定義 — Spec，✅ 已修

`HomeTeamSchema.id` 與 `AwayTeamSchema.id` 是 `z.string().optional()`，是新邊界上唯一沒用 `objectId` 的 id 欄位——而 `home.id` 在資料庫裡是 `ref: "Team"`。本 Change 的 Goal 明寫「『什麼構成一筆合法的請求』只有一份定義」，這裡自己破了例。改為 `objectId.optional()`。

### #11 五個測試檔名說的是測試手法，不是被測對象 — Standards，✅ 已修

`wired-route.test.ts` ×3、`update-route.test.ts`、`create-route.test.ts`，全部與既有的 `route.test.ts` 並存。「wired」是 harness 的實作細節。統一改名為 `request-schema.test.ts`——它們測的是同一件事：這條路由的 request 契約。

### #12 route test 的 request literal 與 console 靜音樣板 — Standards，✅ 已修

`{ url, method, nextUrl, json }` 這個五行字面值在十個測試裡重複，把唯一會變的 body 埋在最不顯眼的位置。抽成 `src/test-utils/route-request.ts` 的 `routeRequest()` 與 `silenceConsoleError()`。

### #13 測試基礎設施是第二處未宣告的邊界擴張 — Spec，✅ 已修

`jest.setup.backend.ts` 與新的 test helper 都不在原本的 Change boundaries 裡。已比照 `toLineupRead` 加入「後來納入」。

### #14 兩條驗收 grep 寫得太寬 — Spec，✅ 已修

S03 的 `grep weather src/` 現在會打到新的 schema 測試（它刻意送一個 `weather` 欄位證明 `.strict()` 擋得住）；S04 的 `grep "\.\.\.lineup"` 打到 `toLineupWrite`，而受規範的是 `toLineupRead`。兩條都收窄成它們原本要說的意思。

### 未採納的兩項

**`Team` 的三個欄位改選填削弱了 entity 的保證**（Standards 判斷題）。這正是 D5 的內容，且不是疏漏：對手取得真實身分後這些欄位會被填滿，此刻拆成 home/away 兩個窄型別，之後要合併回來。維持 D5。

**`teams.home.players ?? []` 把缺席的名單變成空名單**（Spec 判斷題）。屬實——舊資料若缺 `players`，錯誤會以「球員不在名單上」的 400 現身，而不是以它自己的樣子。但 `HomeTeamSchema` 已要求 `players` 必填，本 Change 之後建立的比賽不會有這個狀態，而替舊資料設計一個新的錯誤語意超出本 Change。列入下方 residual risks。

## Round 3

兩軸都回報沒有實作缺漏。剩下的四項全是「註解帶著理由而不是指向理由」，加上兩處 artifact 敘述超前實作。

### #15 四處註解比它描述的程式碼長 — Standards，✅ 已修

CONTRIBUTING 明寫「a doc comment longer than the code it describes is a sign the rationale belongs in the Change, not the file」。`object-id.ts` 的 `rallyPlayerId`（5 行註解／3 行程式碼）、`route-request.ts` 的檔頭、`game.repository.mongo.ts` 的 `toLineupRead`、`game.ts` 的 `HomeTeamSchema` 都犯了同一條，且多數只帶 slug 沒帶 decision id。全部壓成引用。

### #16 S04 的 outcome 說 parse 在開資料庫連線之前 — Spec，✅ 已修

五條路由都是 `connectToMongoDB()` 先、`Schema.parse()` 後。驗收條件只要求 parse 在 `teamId` 檢查之後（成立），是 outcome 的敘述超前實作。改為「觸及任何 controller 或 usecase 之前」。

### #17 review 的 suite 數字錯誤 — Spec，✅ 已修

寫成「backend 135 suites + frontend 18 suites」，實際 135 是 backend+frontend 的合計（62 + 73），18 是 blueprint 那一輪。

### #18 兩個 id 欄位仍未走那份唯一定義 — Spec，✅ 已修

`TransferOwnershipSchema.newOwnerId` 是 `z.string().min(1)`，卻直接送進 `playerRepository.findById()`——非 ObjectId 的字串會變成 Mongoose CastError，也就是 500 而非 400。`MatchInfoSchema.id` 同樣是裸字串，而 `matchSchema._id` 是 `Schema.Types.ObjectId`。兩者都改為 `objectId`，#10 的「唯一」因此成真而不是被改寫。

## 交付前的最後一項：`""` 映射為 `null`

開發者在 Blueprint Review 之前追問了一件 Overview 原本打算延後的事：邊界既然接受 `player.id: ""`，把它轉成 `null` 是不是更正確？

是，而且這個 repo 已經自己說了三次——lineup 用 `nullableObjectId`、`toPlayerRef` 回傳 `null`、`deriveSetStats` 讀到的型別本來就是 `{ id?: string | null }`。只有 `RallyDetail.player.id: string` 跟其他三處不一致，是與 `Team` 同一類的型別謊言，而消滅型別謊言正是本 Change 的前提（「如果那個型別本身在說謊，加 schema 只是把謊言正式化」）。

實測成本：把該欄位改成 `string | null` 之後 `tsc` 零錯誤——所有消費端都是 `Boolean(...)` 或 `if (scorerId && ...)` 這類真值判斷，`""` 與 `null` 走同一條路。實際改動三處：entity 型別、`rallyPlayerId` 加 `.transform`、schema 測試改為斷言轉換結果而非僅斷言接受。

**這不是 D4 禁止的 coercion。** 它與 `z.iso.datetime().transform(...)` 同類：先拒絕既不是 `""` 也不是 ObjectId 的值，再把通過的合法輸入映射到 domain 表示；`z.coerce.*` 則會靜默吞下垃圾。Redux draft 繼續送 `""`，由邊界吸收這個 wire format 的怪癖。

Overview 原本寫著「把這個佔位值換成 `null` 是另一張票的事」，該句已刪除。

## Plan vs. actual

三處實作推翻了計畫時的說法，全部已回寫到 artifacts：

| 計畫說                            | 實際                                                                                                                     | 處置                  |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------ | --------------------- |
| rally 的 `player.id: ""` 應被擋下 | 它是記錄員未指派球員的 wire format 佔位值；邊界接受它並映射成 `null`                                                     | index.mdx 與 S04 改寫 |
| D4「一律不做 coercion」           | `Match.time.date` 的 `z.iso.datetime().transform(...)` 是 validate-then-transform，不是 coercion——先拒絕非法值，再轉型別 | D4 補上這個區分       |
| `role` → `newRole` 重新命名       | `membership-section.tsx` 送的是 `role`；改名會弄壞它，也會把對外欄位彎成內部名稱                                         | 撤回，改由 route 映射 |

**D3 的判準在 Propose 之後、Apply 之前被替換過。**原本的「它需要資料庫裡的狀態嗎」不是乾淨架構的分界——`away.num ∈ outcome` 是無狀態卻是排球規則，「這個 gameId 存在嗎」是有狀態卻只是 404。改成兩個有序問題：**這是在重建型別，還是在判斷領域規則？** design.mdx 保留「一個被撤回的判準」一節記錄這件事。

## Residual risks

- **route 層驗證是過渡狀態。** D1 承諾終局是 controller 成為 interface adapter，由 `api-route-restructure` 承接。在那之前，「邊界是唯一入口」這個前提靠 review 把關，沒有工具強制——`src/lib/` 仍混著三個層的程式碼，任何以路徑判層的 lint 規則都還無法表達。
- **`.strict()` 對向後相容的假設。** 目前前後端同時發布，所以拒絕未宣告欄位是安全的。兩者一旦拆開發布，舊 client 多送一個欄位就會拿到 400。已列為 revisit trigger。
- **舊 game 文件缺 `teams.home.players` 時的錯誤語意不精確。** usecase 以 `?? []` 承接，所以缺席的名單會表現成一份空名單，錯誤在 lineup 比對時才以「球員不在名單上」的 400 現身。本 Change 之後建立的比賽不會有這個狀態（`HomeTeamSchema` 要求 `players`），舊資料則沒有偵測手段。
- **`away` 的選填欄位是暫時的。** 隊伍查詢與資料分享功能上線後，away 會承載與 home 幾乎相同的結構，D5 的選填欄位會被填滿。

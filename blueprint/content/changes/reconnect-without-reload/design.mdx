<TLDR>
  `reloadOnOnline` 關掉之後，連線恢復不再有任何路徑呼叫
  `location.reload()`。取代它的路徑不是新的——`SWRConfig` 的
  `revalidateOnReconnect` 今天就是預設的 `true`，每個 hook 早就在重新連線時各自
  revalidate，只是過去被同一個事件上的 reload 蓋過去而沒人看見。
</TLDR>

## Adopted shape

改動前，同一個瀏覽器 `online` 事件掛著兩個互不知情的監聽者：`SerwistProvider` 的整頁
reload，與 SWR 內部的逐 hook revalidate。前者先跑完、頁面已經在重新載入，後者的結果永遠沒有機會被看到。改動只是拿掉左邊那條路徑，右邊的行為完全沒有變動。

## Contracts

改動本身沒有新的契約——`reloadOnOnline` 是 `@serwist/turbopack/react` 既有的 prop，這裡只是把它從隱式的預設值改成顯式的 `false`：

```tsx
// src/app/layout.tsx
<SerwistProvider
  swUrl="/serwist/sw.js"
  disable={process.env.NODE_ENV !== "production"}
  reloadOnOnline={false}
>
```

`SWRConfig` 完全不動——`onError` 是它今天僅有的設定，`revalidateOnReconnect` 從沒被覆寫過：

```tsx
// src/components/layout/swr-provider.tsx
<SWRConfig value={{ onError }}>{children}</SWRConfig>
```

## Failure modes

<Scenario
  given="使用者在記錄畫面上，訊號中斷又恢復"
  when="瀏覽器觸發 online 事件"
  then="SerwistProvider 不再監聽這個事件，頁面不重載；畫面上掛載的 SWR hook 依各自的 revalidateOnReconnect（預設 true）各自重新驗證，記錄中的 set 與正在編輯的 rally 原封不動"
/>

| 情境                                         | 行為                                                                                                                     |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 連線恢復時使用者不在任何掛載 SWR hook 的畫面 | 沒有任何請求發出，與改動前 SWR 那一半的行為相同——改動只拿掉 reload，不影響 revalidate 的觸發條件                         |
| 連線恢復後 SW 有新版本待啟用                 | `skipWaiting: true`／`clientsClaim: true` 已讓新 SW 在安裝完成後立刻啟用；下一次導覽即拿到新資產，不依賴這次的 reload    |
| 開發環境（service worker `disable`）         | 不受影響——`reloadOnOnline` 的監聽者原本就掛在 `disable` 為 true 時從未註冊的路徑上，這也是為什麼這個問題在本機從未出現過 |

## Testing strategy

沒有新增自動化測試。這是單一 provider 上單一 prop 的改動，`pnpm typecheck:strict` 與既有的建置流程足以確認 prop 被正確傳遞；`location.reload()` 是否真的不再被呼叫,是瀏覽器對 `online` 事件的行為，jsdom 沒有對應的可觀察副作用可以斷言。真實裝置離線再恢復連線、確認記錄畫面狀態保留,是交付驗收的一部分，不屬於任何切片的 verification。

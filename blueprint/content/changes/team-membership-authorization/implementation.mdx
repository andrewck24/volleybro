五個切片。S01 與 S02 是兩塊地基，彼此獨立；三個端點各自是一個切片，從地基分出去。

- **S01** 定義成員。它單獨就修掉最嚴重的一項：受邀者不再通過任何成員或管理員檢查，包含寫入路徑。
- **S02** 讓受邀者從自己的球員清單看到隊名。它本身不收緊任何東西，存在的理由是讓 S03 收緊時邀請頁不壞。
- **S05**（依賴 S01）名單只給成員。
- **S04**（依賴 S01）單一球員只給同隊成員，並讓接受邀請不經過它。
- **S03**（依賴 S01、S02）隊伍資訊只給成員。

## 為什麼 S01 必須最先

三個端點的授權都呼叫 `verifyTeamRole`。在 S01 之前加上檢查，受邀者照樣通過，端點看起來收緊了，實際上沒有。先修定義，後面三個切片加上的每一道檢查從第一個 commit 起就是對的。

## 為什麼 S02 必須早於 S03

邀請頁今天用 `useTeam` 讀 `GET /api/teams/{teamId}` 顯示隊名。S03 收緊之後，受邀者讀這個端點會得到 403，邀請項目的標題會變成空白。反過來先做 S02，S03 落地的那一刻邀請頁已經不再讀它。

S04 沒有這個前置，因為它自己的切片裡就包含了讓接受邀請離開 `GetPlayerUseCase` 的改動——那兩件事拆開，中間的 commit 上受邀者會被自己的邀請擋下。

## 名單修正已經寫好

S05 的實作在本 Change 提案前就已完成並通過 `pnpm verify` 與 `pnpm test:integration`，但當時的 commit 早於本計畫、不帶切片 trailer，也附了一份只描述名單的 changeset。Apply 時它以 S05 重新提交：保留程式碼與測試，補上切片 JSON 與 trailer，移除那份 changeset。整個 Change 的 changeset 在 Pre-PR gate 依完整範圍撰寫。

## 一件必須以斷言形式釘住的事

**拒絕時斷言 repository 沒有被讀取，而不只是斷言丟出錯誤。** 先讀資料再檢查、檢查失敗才丟錯的實作，同樣會讓「丟出錯誤」的測試通過，但資料已經在記憶體裡、離洩漏只差一個 log 或一次錯誤處理。S03 與 S05 的測試都包含這個斷言。S04 例外：球員必須先讀出來才知道隊伍，所以它斷言的是回傳值。

## 不在本 Change 內，但已標記

- `verifyPlayerRole` 與 `getPlayerRole` 在 production 程式碼中沒有呼叫者。刪除需要另外確認。
- `GET /api/users?email=` 讓任何登入者以 email 反查使用者，歸在隱私設定主題。
- `test/integration/support/auth.ts` 的 authorization double 一律放行，整合層無法證明任何拒絕路徑。

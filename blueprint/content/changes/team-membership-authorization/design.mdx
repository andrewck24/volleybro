  判斷與查詢分開。「誰是成員、角色夠不夠」是沒有 I/O 的業務規則，放在
  entity；「這個使用者在這隊是哪一筆球員」要查資料庫，留在
  infrastructure；「查、判斷、不通過就丟錯」的編排，由 use case 呼叫 service

`isTeamMember` 是 type guard：通過之後 `role` 的型別就不再是可選，`hasTeamRole` 不需要 `player.role!` 或額外的防禦檢查。

## Behavior contract

| 呼叫者與該隊的關係            | 成員檢查          | 管理員檢查          | 隊伍資訊、名單、單一球員 | 邀請清單中的隊名 |
| ----------------------------- | ----------------- | ------------------- | ------------------------ | ---------------- |
| 隊長（`JOINED`，`OWNER`）     | 通過              | 通過                | 可讀                     | —                |
| 管理員（`JOINED`，`ADMIN`）   | 通過              | 通過                | 可讀                     | —                |
| 成員（`JOINED`，`MEMBER`）    | 通過              | `INSUFFICIENT_ROLE` | 可讀                     | —                |
| 受邀者（`INVITED`，任何角色） | `NOT_TEAM_MEMBER` | `NOT_TEAM_MEMBER`   | 不可讀                   | 可讀             |
| 登入但與該隊無關              | `NOT_TEAM_MEMBER` | `NOT_TEAM_MEMBER`   | 不可讀                   | —                |
| 未登入                        | 401               | 401                 | 不可讀                   | —                |

- 受邀者接受邀請：`AcceptInvitationUseCase` 自己驗證受邀者身分，不經過成員檢查；接受後 `status` 變為 `JOINED`，立即成為成員。
- 移轉隊長：現任隊長必須是具 `OWNER` 角色的成員，目標必須是成員；受邀者作為目標得到 `TARGET_NOT_MEMBER`。
- 被移除的成員：`activeTeamId` 若指向該隊即清除；非成員直接開啟隊伍頁面時看到錯誤狀態，而不是崩潰。
- 不存在的隊伍或球員：先授權再讀取的端點回傳 `NOT_TEAM_MEMBER`，不透露資源是否存在；`GetPlayerUseCase` 必須先讀出球員才知道隊伍，它回傳 404 的行為維持不變。

## Failure modes

- **邀請頁在 S03 之後失去隊名**：若隊伍端點先收緊、受邀者清單還沒帶 `teamName`，邀請項目會顯示空白標題。以切片順序保證：S02 必須先於 S03。
- **接受邀請在 S04 之後失敗**：`acceptInvitation` 的 controller 若仍經過 `GetPlayerUseCase`，受邀者會被自己的邀請擋下。S04 在同一個切片內改掉這條路徑。
- **既有測試以受邀者身分通過檢查**：mock 的 `AuthorizationService` 不受影響；但以 fixture 建立 `INVITED` 球員並期待通過的 use case 測試會轉紅。它們代表的正是被修掉的行為，應改寫而不是放寬判斷。
- **舊資料沒有 `status`**：unify-player 遷移曾對所有 player `$unset` status，schema 預設為 `NONE`。若 production 仍有這種文件，S01 會讓它們的隊長與成員被判定為非成員。S01 開工前以 Overview 的查詢確認；不為 0 就先回填。
- **非成員開啟隊伍頁面時崩潰**：`team/info/index.tsx` 以 `team!.nickname`、`players!.length` 假設資料存在；S03、S05 之後讀取失敗會拋 TypeError。觸發路徑包括被移除成員殘留的 `activeTeamId`。S06 處理。
- **整合測試看不到授權**：`test/integration/support/auth.ts` 的 double 一律放行，整合層無法證明拒絕路徑。拒絕的證據來自 entity 與 use case 的單元測試。

## Testing strategy

- **Entity**：`isTeamMember` 與 `hasTeamRole` 以狀態與角色的完整組合測試，不需要 mock。這是受邀者規則唯一的權威。
- **Use case**：三個讀取 use case 各一組測試，`AuthorizationService` 以 mock 注入，斷言以正確參數呼叫檢查，且拒絕時不讀取 repository。`transfer-ownership` 以受邀者為目標斷言 `TARGET_NOT_MEMBER`。`AcceptInvitationUseCase` 斷言回傳 Player。
- **Infrastructure**：`AuthorizationService` 以 mock repository 回傳受邀者、各角色成員，斷言對應的錯誤原因。
- **Component**：邀請清單以 `teamName` 顯示隊名，且不呼叫 `useTeam`。
- **Integration**：`pnpm test:integration` 作為接線未壞的證據。

## Revisit triggers

- 隱私設定上線，隊伍管理者可以把隊伍資訊或名單開放給非成員；屆時 D2 的端點授權改由可見性判斷決定。
- 會籍區塊要求 email 只給隊長與管理員；屆時名單與單一球員的回應依角色裁切欄位。
- 出現第四種球員狀態，或角色不再是線性階層。

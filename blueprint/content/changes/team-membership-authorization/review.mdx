## 計畫與實際的差異

- **S01 仍是 `pending`。** 程式碼與整合測試已交付，但它的驗收包含開發者在 volleybro-test 與 production 執行。這是刻意的：腳本會改 production 資料，而執行結果（尤其是停止條件是否成立）要記錄在這一頁。
- **S04 讓兩個 use case 不再注入 `AuthorizationService`。** entity 的管理判斷本身已含「呼叫者必須是管理員以上的成員」，保留舊檢查等於同一份資料查兩次、兩套會各自漂移的規則。錯誤語意不變。
- **`verifyIsTeamOwner` 與 `getPlayerRole` 的行為有細微改變**，儘管 S02 的驗收寫的是「介面不變」：帶擁有者角色的受邀者現在得到 `NOT_TEAM_MEMBER` 而非 `INSUFFICIENT_ROLE`，`getPlayerRole` 對受邀者回傳 `null`。兩者在 production 都沒有呼叫者。
- **Apply 期間新增了三件不在原計畫內的工作**：註冊時的連結改為不分大小寫、正規化把保留的邀請位址去空白轉小寫、移轉擁有權不能指向自己。前兩件是同一條 email 大小寫的線；第三件是既有缺陷，但它牴觸 D3 宣稱的「隊伍永遠有一位擁有者」。三件都經開發者確認後才做。
- **`(teamId, email)` 的唯一索引在此之前從未存在**，所以「同一隊不會對同一個 email 重複邀請」在這個 Change 之前只是宣告，不是保證。

## 驗證

| 閘門                    | 結果                                                        |
| ----------------------- | ----------------------------------------------------------- |
| `pnpm verify:all`       | 1174 unit tests、blueprint 49 tests、app 與 blueprint build |
| `pnpm test:integration` | 18 suites / 95 tests，含正規化 25 例與連結 11 例            |

拒絕路徑的證據來自 entity 與 use case 的單元測試：整合測試的 authorization double 一律放行，所以三個讀取端點的 403 在整合層沒有覆蓋。

最後一輪驗證是實際驅動記憶體 MongoDB 完成的，不只是讀程式碼：把 `teamId_1_userId_1` 重建成一般索引、把它整個刪掉、再修回來，三種情況下連結腳本的行為都符合預期（前兩種拒絕且不寫入，第三種正常連結）。

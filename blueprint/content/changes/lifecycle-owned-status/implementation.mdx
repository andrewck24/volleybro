五個切片。相依關係決定順序，而不是檔案位置：兩個獨立的準備動作（S01、S02）先落地，中間那片大的（S03）才有安全的著陸點。

S03 是唯一有風險的一片——十個目錄同時移動、麵包屑重建、URL 全面改變。S01 與 S02 存在的理由，就是讓它動手時只剩下「移動」這一件事要驗。

## 為什麼 S02 先於 S03

`changeArtifacts` 目前讀的是 breadcrumb tree，而不是 loader 的 page tree。那是為了繞過「資料目錄遮蔽同名兄弟頁」而做的權宜之計，`meta` collection 修好之後那個遮蔽已經不存在。

若不先解開，S03 重建麵包屑時會同時動到麵包屑**與**所有 Overview 的入口連結——兩件事在同一片裡失敗，就分不清是哪一件壞的。S02 先把 artifact 連結接回 loader 自己的樹，S03 就只需要對麵包屑負責。

`withDirectChangePages` 是否已死也在 S02 判定。它存在的唯一理由是把被遮蔽的頁面重新注入；理由消失了，函式不一定跟著消失，所以驗收條件寫的是「判定」而非「刪除」——若仍有東西經過它，理由要記進 Review。

## 兩條必須以產出驗證的行為

一是 **artifact 連結完全不變**（S02）：十個 Overview 的標題、順序、href 與改動前逐字相同。這條不能靠讀程式碼判斷，要比對 build 出來的 HTML。

二是**站上沒有死連結**（S02 與 S03 各驗一次）：把 prerender HTML 裡每一個 `/changes/` href 拿去解析對應的產出頁面。這個檢查在這個 repo 上抓過兩次真實缺陷——一次是手抄的 artifact props 指向已搬走的目錄，一次是資料目錄遮蔽讓 Design 頁從樹上消失。S03 把每個 URL 都改掉，它是最需要這條檢查的一片。

## 刻意不變的部分要被驗收

S03 的驗收條件裡有一條看起來像廢話：三個篩選按鈕、側邊欄四個連結、`?status=` query 行為完全不變。

它不是廢話。這個 Change 移除 `status` 欄位、移除 status 目錄，很容易順手把依賴 status 的 UI 一起改掉。`status` 仍然是使用者看得見的分組概念，只是不再被寫下來——這條驗收條件的作用是把「不該變的東西」也釘住。

## Findings

### 一、helper 回傳 `never` 卻被當 statement 用（Standards）

`validateRallyEntry` 原本把丟錯包成一個回傳 `never` 的 `reject()`，然後以 statement 形式呼叫。TypeScript 不會因為一個函式回傳 `never` 就把呼叫點當終止點，所以 `move.num` 的型別在後續分支裡仍是 `number | undefined`，只能用兩個 non-null assertion 壓過去。

<AnnotatedDiff
  lang="ts"
  code={
    "const reject = (detail: string): never => { // [!code --]\n  throw new ValidationError(CommonReason.INVALID_INPUT, detail); // [!code --]\n}; // [!code --]\nconst invalid = (detail: string) => // [!code ++]\n  new ValidationError(CommonReason.INVALID_INPUT, detail); // [!code ++]\n\nelse if (!Number.isInteger(move.num) || move.num! < 0) // [!code --]\n  reject(`A rally's ${side} move number must index a scoring move`); // [!code --]\nif ( // [!code ++]\n  typeof move.num !== \"number\" || // [!code ++]\n  !Number.isInteger(move.num) || // [!code ++]\n  move.num < 0 // [!code ++]\n) // [!code ++]\n  throw invalid(`A rally's ${side} move number must index a scoring move`); // [!code ++]"
  }
/>

在決定的地方直接 `throw`，並讓 `typeof` 檢查走在前面，兩個 assertion 就都不需要了。型別因此說的是實話，而不是被一個斷言壓住。

### 二、註解重述了 D2 已經擁有的決策（Standards）

`validateRallyEntry` 上方原本有一段說明「為什麼在這一層擋」。`CONTRIBUTING.md` §Comments 寫得很明確：

> never re-argue a decision a Blueprint Change already owns. Reference it instead of copying it, or the two drift apart

那正是 D2 的內容。刪除。另外兩處註解——`LAST_SCORING_MOVE` 為何硬抄、統計累加為何只跳過自己——留著，它們說的是本地看不見的約束。

`rallyDetailSchema` 上方那段同時被 Spec 軸點名超出驗收條件的兩行上限，一併縮短。

### 三、changeset 寫了，卻沒有進任何 commit（Spec）

`.changeset/rally-entry-validation.md` 存在於工作樹，但 `git diff` 看不到它——它從頭到尾沒有被 `git add` 過。這是 Spec 軸最有價值的一筆：檔案在，內容正確，肉眼看不出問題，只有比對 diff 才會發現它不在變更裡。已補上 commit。

### 四、輪轉的斷言沒有照驗收條件比對合法情形（Spec）

S01 的驗收條件寫的是「`rotation` 與發球權的推進**與該筆合法時相同**」，而測試只斷言了 `rotation` 等於 1。數字是對的，但它證明的是「等於某個我寫下的常數」，不是「與合法情形一致」。改成同時跑一次合法序列並比對兩者。

### 五、兩項判斷型建議，附理由拒絕

**`Object.values(MoveType).filter(...)` 在 entities 與 schema 各有一份。** 拒絕：schema 那份餵的是 Mongoose 的 `enum` validator，而 D2 已經確立它在 rally 的寫入路徑上不執行——所有 entry 都經 `bulkWrite` 的 `updateOne`，而新建的 game 沒有任何 entry。兩份拷貝因此不可能觀察得到分歧。為此加一條 infrastructure 到 entities 的相依，換不到任何行為上的好處。

**`num` 是裸 number，索引一張住在 entities 之外的表。** 拒絕：D2 自己的 revisit trigger 已經涵蓋它，且解法的前置是把 `scoringMoves` 下沉到 entities，屬另一份工作。

第二輪與第三輪對這兩項的處置都沒有異議。

### 六、對照只加到兩個非法輸入的其中一個（第二輪，Spec）

修正四把「與合法情形比對」加進了缺 `type` 的測試，卻沒有加進 `type` 超出 enum 的那一個，而後者也少了姊妹測試已有的 away 統計斷言。S01 的驗收條件寫的是「涵蓋兩種非法輸入……並**分別**斷言」。合法序列因此抽成一個兩邊共用的 `legal()`，兩條測試各自比對。

### 七、同一種註解形狀漏掉三處（第二、三輪，Standards）

第一輪從驗證器上刪掉的那種「重述 Change 已經擁有的決策」的註解，在另外三個地方以同樣形狀存在：測試裡解釋為什麼不能 `continue`、`deriveSetStats` 裡複述 D1 的決策文字、整合測試開頭整段搬運 D2 的論證。三處都改成一句話加 `See rally-entry-validation D1/D2.`。

一種規則、三輪才收乾淨，這件事本身值得記：第一輪的 brief 讓審查者去找「違反 CONTRIBUTING 的地方」，它找到了一處就回報一處，沒有回頭掃同一種形狀的其他實例。

### 八、一條既有的 flaky 測試擋住 gate（診斷後修在本分支）

`src/hooks/__tests__/flush-in-flight.test.tsx` 間歇性失敗——本分支九次全套執行紅三次，`dev` 四次零次。它與本 Change 沒有任何程式碼關聯，但擋住 gate，所以修在這裡。

成因是測試在跟一個 0 毫秒的 timer 賽跑。`enqueued` 把 `nextAttemptAt` 設成 `Date.now()`，所以每次入列都排一個立刻到期的背景 flush。測試在第一次 flush 還在飛時入列 q2，於是第二次 flush 一定會發出——而 `mockReturnValue` 把**第一次那個已經 resolved 的 promise** 交給了它。第二次 flush 因此立刻「成功」，帶著一個早於 q2 的回應：佇列被清空，或快取失去 q2，端看 timer 有沒有搶在斷言前面。

只回答第一個請求，第二個就停在它名字所描述的狀態——已發出、未回應——而這也正是讓「合併」成為 q2 唯一能留在畫面上的理由。

**產品行為未動，也不該動**：入列後盡快送出、在飛的那次結束後補送剩下的，正是這套佇列該做的事。

修法經兩種變異驗證：關掉待送項目的合併，三次全紅（鑑別力還在）；在斷言前強制多跑一個 macrotask，三次全綠（時序不再決定結果）。修正前後者是三次全紅。

### 九、審查的固定點比交付狀態早了兩個 commit（第四輪，Spec）

前三輪的 diff 終點是 `9da4fdc8`，而在那之後又有五個 commit：套用第三輪發現的註解修正、lifecycle 轉換、這一頁、flake 修正、以及這一頁的更新。**其中兩個帶有實質判斷，卻沒有經過任何一輪審查**，而本頁一度直接宣稱「三輪後判定 CONVERGED」。

第四輪因此補跑，範圍就是那五個 commit，並要求審查者自行複驗發現八宣稱的變異檢查而非採信。複驗結果全部成立，Standards 軸另外回頭掃了整條分支的註解形狀，確認前三輪那種「重述 Change 已擁有的決策」沒有殘留實例。它同時抓出本頁三個 FileTour 條目的行數與 diff 不符，以及漏列 `flush-in-flight.test.tsx` 這個交付檔案，均已更正。

**這是流程缺陷，不是個案。** `WORKFLOW.md` §5 的步驟 1（gate）與步驟 5（本頁）都會產生新的 commit，而合約沒有說這些要重新進入步驟 4 的迴圈。「fixed point」在數學上已經蘊含輸入不再改變，但實作上很容易讀成「連續兩輪沒新發現就結束」。

**終止條件**：程式碼在第四輪之後已全部經過審查。本次更正之後仍未經審查的，只剩「描述第四輪的那幾段散文」——那是自我指涉，再跑一輪只會產生下一段自我指涉的散文。以此為固定點。

## Plan versus actual

**`LAST_SCORING_MOVE = 14` 是一份硬抄，Design 沒有說它該住在哪裡。** D2 寫的是「`num` 在 0 至 14」，沒有交代這個上界的來源。實作上它成了 entities 對 `src/lib/scoring-moves.ts` 那張表的最後索引的複製。Design 當時沒有把「上界會被硬抄」這件事說出來，此處明記。

下沉那張表是唯一能真正消除重複的做法，但它需要一個設計決定——`ScoringMove` 帶著 `text: "攔網"` 這種 zh-TW 顯示字串，整張搬進 entities 等於把介面文案放進領域層，拆開搬則要改動表的形狀與全部呼叫端。那個決定屬 ATE-140 的 S1，不該夾帶進一張止血票。

**但危險的不是重複，是重複而且不會有任何測試變紅**，而後者今天就能解決：`src/lib/__tests__/scoring-moves.test.ts` 把驗證器接受的上界釘在表的最後一筆上。測試檔不受分層約束，可以同時 import 兩邊，而且它釘的是**行為**而非常數，所以不必為了測試把常數 export 出去。在表末加一個動作，這條測試立刻紅。表下沉之後，這個檔案連同常數一起刪除。

**`validateRallyEntry` 多擋了一件驗收條件沒列的事。** 條件列的是兩側的 `type` / `num` / `score` 與 `win`，但要檢查「兩側的 `type`」，前提是 `home` / `away` 這個物件存在。驗證器因此也拒絕缺席的一側。Spec 軸確認這是條件的必要前提而非範圍外的行為。

**S02 預留的 fixture 修補沒有用到。** 驗收條件寫了「既有 fixture 若因不完整而失敗，修 fixture 而非放寬驗證」。實際上 `record-rallies.usecase.test.ts` 的三筆 fixture 本來就是完整合法的 rally，一條都沒有紅。

**一個與本 Change 無關的測試修正搭了便車。** 發現八不屬於本 Change 的任何一片，正常情況應該另案處理。它進來的理由只有一個：它擋住 `verify:all`，而沒有綠燈就開不了 PR。判準是「阻擋交付」而非「順手看到」——同期查出的 error boundary、knip、Blueprint 元件三件事都留在外面，因為它們不擋 gate。

## Follow-ups

本 Change 期間查出、範圍在外的事：

- **rally 的 `type` / `win` / `score` 都是 `num` 的推導值，三份拷貝無一致性保證。** 前置是 `scoringMoves` 下沉至 entities，完成後 `validateRallyEntry` 擴充為含跨欄位自洽檢查。本 Change 期間對現有資料掃過一次，六項自洽檢查全部乾淨。
- **app 缺少 error boundary 策略。** 全 repo 只有一條 route 有，且是佔位符。它對本 Change 的失敗模式沒有作用——錯誤來自資料庫裡的資料，重試會再炸一次——但下一個未預期的 render 錯誤仍會讓整條 route 消失。
- **knip 不在任何 verify gate 內**，且預設模式看不見「只被測試引用」的死碼。`validatePlayerStatus` 是實例：十一個全綠的單元測試，零個生產呼叫端。
- **`WORKFLOW.md` §5 沒有說「審查的 diff 終點必須是最後一個 commit」。** 見發現九。步驟 1 的 gate 與步驟 5 的本頁都會產生新 commit，合約未要求它們重新進入步驟 4 的迴圈。
- **入列後永遠有一個 0 毫秒的背景 flush 在排隊。** 任何在 flush 前後斷言佇列或快取內容的測試都會踩到這個時序，發現八是第一個。這件事沒有寫在任何地方。
- **Blueprint 的 JSON 欄位渲染成純文字**，且 SVG `<text>` 的撰寫陷阱沒有任何機制擋。後者在本 Change 的圖表初版上發生過一次。

## Validation

## 為什麼止血先於堵源頭

直覺會想先修寫入端——那才是根因。但兩者救的東西不同：S02 讓未來的壞球進不來，**救不了已經在資料庫裡的任何一顆**。而已經在裡面的那一顆，代價是整場比賽永久打不開。

今天資料庫裡一顆都沒有，所以這個順序在現實中不會造成差別。它仍然這樣排，是因為順序反過來會在一段時間裡讓人以為問題解決了——寫入端守好之後，任何漏網的路徑（匯入、遷移腳本、未經 use case 的寫入）造成的壞資料，依然會讓比賽打不開。**讀取端的容錯是唯一與資料來源無關的那一層。**

## S01 的風險不在容錯本身，在「跳過」的範圍

守衛本身是兩行。真正會出錯的是把「跳過該筆的統計累加」實作成「跳過該筆 entry」：

```ts
if (isRally(entry)) {
  const homeStat = home[entry.home.type]; // 這裡取不到
  // …統計累加…

  if (win && !isHomeServing) home.rotation += 1; // 這兩行
  isHomeServing = win; // 必須照跑
  continue;
}
```

一個 `continue` 會連迴圈尾端的輪轉與發球權推進一起跳過，使該筆之後的輪轉數全部錯掉。**這個錯誤不會拋、不會有任何跡象，只會給出錯的數字**——比原本的 crash 更難發現。驗收條件因此把「`rotation` 與 `isHomeServing` 照常推進」寫成獨立一條，並要求測試斷言它與該筆合法時相同。

同一個迴圈裡還有第二個拋出點容易被漏掉：球員統計那段也拿 `entry.home.type` 當 key。只擋隊伍統計那一處，遇到帶球員 id 的非法 rally 仍然會拋。守衛必須涵蓋兩處。

## S02 的風險在三個同名的 win

`rally.win`、`set.win`、`game.win` 型別相同、語義不同。只有第一個該補 `required`——後兩者在結果存在前刻意是 `null`，那是 `rally-recording` 的既有約定。**加錯的後果是一局在結果寫入前就無法儲存**，而 schema 檔案裡三個 `win` 長得一模一樣。

另一個要抗拒的直覺：S02 會讓人想順手把 use case 的 input 型別接到未來的 request schema 上（`z.infer`）。那看起來像消除重複，實際上是把 application 層接到外層的請求 DTO——本 repo 已經有一處這樣的相依，正在被另一項工作清理，不該再製造第二處。

## 為什麼整合測試不可省

`validatePlayerStatus` 有十一個涵蓋各種狀態組合的單元測試，全綠，而它在生產程式碼裡的呼叫端數量是零。

單元測試證明「這個函式會正確拒絕」。它證明不了「有人在該拒絕的時候呼叫了它」。S02 的守衛若只有單元測試，就是再造一個 `validatePlayerStatus`：一個看起來有人在守、實際上沒有的規則。整合測試驅動真實 route，斷言 400 與「該局的 entries 未被寫入」，這是唯一能證明接線正確的層次。

## 驗證的層次

S01 只需要 entity 單元測試——使用者可見的結果是「那場比賽打得開」，而它在 `deriveSetStats` 那一層就是「不拋」，在元件層重述一次不會多證明任何事。

S02 兩層都要，且整合測試是 `pnpm test:integration` 這個獨立的 gate，不在 CI 跑的 `pnpm test` 裡，開 PR 前必須本機跑過。

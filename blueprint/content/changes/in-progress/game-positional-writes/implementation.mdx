六個切片，順序由相依決定而非由檔案位置決定：先讓領域規則與推導站得住（S01），再把寫入路徑改用它們（S02–S04），最後收讀取端與型別（S05–S06）。

S01 先行的理由是它同時是其餘每一片的前提：沒有 `deriveSetStats`，統計無處可算；沒有 `deriveSetPhase`，伺服器判不出一局是否結束。

## 三條分層約束落在哪裡

Design 的「三條可驗證的約束」不是散文，各自綁在一個切片的驗收條件上：

| 約束 | 切片 | 驗收條件的形式 |
| --- | --- | --- |
| 資料庫語法不離開 `GameRepositoryImpl` | S02 | 三條 entry 路徑的 usecase 測試不得 mock 任何資料庫概念 |
| `entities/` 不得 import server-only | S01 | `entities/` 對外 import 維持為零 |
| 元件不得呼叫推導函式 | S05 | `src/components/` 底下不得出現 `deriveSetStats` 的 import |

## 兩個必須在整合測試驗證的行為

一是**壞值的爆炸半徑**：送出一個資料庫存不下的 entry，該局既有的每一顆球都必須完好（S02）。二是**一局的結束真的落庫**：完整記錄一場三局比賽後，每個 `set.win` 與 `game.win` 都要正確，且比賽列表顯示的勝局數不是零（S04）。

第二項是設計審查中才發現的漏洞——整份覆寫把「一局結束」藏成了記一顆球的副作用。它不會讓記錄頁出錯，只會讓另一個頁面安靜地顯示錯誤數字，所以它必須有一條走完整場比賽的驗收，而不是單元測試。

七個切片，順序由相依決定。三條相依鏈並行，最後匯流：

- **契約鏈**（S01 → S02 → S03 → S05）：先讓 `detail` 離開 wire，再讓型別停止承諾它，然後才建立目錄與 resolver，最後寫文案。
- **資料鏈**（S04）：不依賴任何切片，但必須早於 S05。
- **欄位鏈**（S01 → S06）：只需要 wire 那一步，與顯示端無關，可與 S02–S03 並行。

S07 需要兩條鏈都到位：它要 S06 的欄位路徑才能指向欄位，要 S05 的文案才有東西可顯示。

## 為什麼順序不能顛倒

**S02 必須晚於 S01，也必須早於 S03。** 拿掉型別上的 `detail` 是為了讓 `tsc` 列舉每一個讀取者——這是本 Change 唯一可靠的清單來源，`grep` 抓不到 `.message`。但在 S01 之前拿掉會讓型別與實際回應不一致，在 S03 之後拿掉則等於已經憑記憶改完了顯示端。

**S04 必須早於 S05。** 兩個 reason 的語意今天是錯的：`profile.usecase` 把 protected-field 的錯誤配給 `INVALID_EMAIL`，而 `NOT_INVITED` 在 accept／reject 是 404、在 cancel 是 409。兩者今天都無害，因為沒有東西讀 reason；一旦文案以 reason 為 key，前者會告訴使用者 email 格式錯誤，後者會讓同一則文案服務兩種語意。**新機制把潛伏的標錯放大成螢幕上的錯誤文案**，所以修正必須先落地。

第一個的修法比預期乾淨：那個 guard 從任何呼叫端都到不了——route 的 `.strict()` schema 只收三個欄位，內部呼叫端的型別已排除那兩個欄位——所以它是 request schema 上線後留下的死碼，刪掉即可，不需要新的 reason 常數。

**文案必須晚於盤點，而盤點已經在核准前完成。** 它是判斷不是實作，放進執行階段等於要求人在 Apply 中途介入。表在 Design 頁上，S05 照寫。

**窮盡性測試必須晚於文案，而不是早於。** 它的通過條件是「每個 reason 都有條目」，先上線的話，讓它轉綠最省力的方式是塞二十條佔位字串——然後綠燈會宣告一件不成立的事。測試守的是「別再漏掉」，不是「現在有了」。

## 兩個容易漏掉的動作，各自綁在驗收條件上

| 容易漏的                                      | 切片 | 驗收條件的形式                                           |
| --------------------------------------------- | ---- | -------------------------------------------------------- |
| `proxy.ts` 是第二個回應產生點                 | S01  | 兩個產生點各一組 key-set 斷言，而非只測 `serializeError` |
| `ApiClientError` 建構子仍把 detail 當 message | S02  | 建構子與 getter 同一個切片，且驗收條件明列建構子         |

第一項的心智模型陷阱是「改 `serializeError` 就好」——Edge 401 根本不經過它。第二項的陷阱是 `tsc` 會宣告乾淨，而字串仍然可讀。

## 三件必須以斷言形式釘住的事

**斷言 key 的集合，不是斷言欄位不存在。** `expect(body).not.toHaveProperty("detail")` 擋不住未來以別的名字加回來的自由文字，而 D1 承諾的是「body 是封閉集合」。

**斷言兩個 surface 說同一句話。** 今天最不成立的就是這件事，所以它需要一個把同一個錯誤餵進兩條路徑的直接測試，而不是兩組各自獨立的 per-surface 測試——後者可以同時全綠而兩邊說著不同的話。

**斷言真實的 zod issue，不是手工組出來的 issue 物件。** 盤點階段就曾經因為讀型別宣告而誤判 `input` 會上 wire；實際序列化的結果與型別宣告不同。

## Why this change

The first workflow unification still made Spectra the planning and task authority and described
Symphony as if it were required to finish a Change. That made replacing the skill suite difficult,
kept execution progress coupled to `tasks.md`, and left Manual Apply underspecified.

The revised model makes the repository lifecycle primary. The configured tracker remains the
operational intake and active-work surface, Blueprint owns durable Change knowledge and slices, and
Symphony optionally invokes the same Apply contract a developer can run manually.

## Goals and boundaries

| In scope                                                               | Out of scope                                                      |
| ---------------------------------------------------------------------- | ----------------------------------------------------------------- |
| Manual-first lifecycle shared by developer sessions and Symphony       | Executing the historical Spectra/OpenSpec knowledge migration     |
| Grill versus Wayfinder routing and Change-boundary decisions           | Removing Spectra skills, workflows, and CLI configuration         |
| JSON implementation slices rendered by Blueprint                       | Creating, deleting, or changing operational tracker labels        |
| Independent Pre-PR review and branch-local Archive knowledge promotion | Making Symphony claim individual implementation slices            |
| Optional post-PR human review without an automated Claude review gate  | Extracting the reusable Blueprint workflow repository or package  |
| Provider-neutral Symphony `repository-workflow` capability             | Persisting provider prompts, responses, reasoning, or transcripts |

## Task progress

Canonical progress is stored in the implementation-slice JSON and rendered on the
[Implementation page](/changes/unified-software-delivery-workflow/implementation).
Operational tracker state and Symphony claims are deliberately excluded from these files.

## Specification impact

Existing Spectra/OpenSpec artifacts remain historical snapshots. A later low-priority migration
promotes only knowledge that is still current and leaves the remaining snapshots unchanged. New
Changes use the repository-owned lifecycle, and branch-local Archive promotes verified knowledge
before the pull request opens.

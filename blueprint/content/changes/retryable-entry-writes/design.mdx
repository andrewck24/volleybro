`id` 與 `seq` 各司其職。同一個 `id` 送兩次，第二次守衛不成立、零筆命中，狀態與只送一次相同；晚到的 `seq 7` 靠 `$push` 的 `$sort` 修飾符插回 `seq 8` 之前，抵達順序不再決定陣列順序。

## Contracts

**Repository。** `appendEntry` 與 `replaceEntry` 合併為 `upsertEntry`，收一個或多個 entry。參照參數收斂為 game 與 set 的定位。以 `bulkWrite`（`ordered: true`）逐筆送出，每筆兩個操作恰好命中一個：以 `arrayFilters` 依 `id` 覆寫（存在時），或以 `$ne` 守衛的 `$push` ＋ `$each`／`$sort: { seq: 1 }` 新增（不存在時）。兩者都是一般 update 而非 aggregation pipeline update，Mongoose casting 因此保留。陣容參數保留：換人會同時改變場上陣容，與身分無關。

**Use case。** `CreateRallyUseCase` 與 `UpdateRallyUseCase` 目前逐行相同，唯一差別是呼叫 `appendEntry` 還是 `replaceEntry`；repository 合併後兩者變成完全一樣的程式碼，因此**一併合併**為單一的 `RecordRalliesUseCase`。它驗證一次授權、寫入全部 entry、推導一次 set completion。controller 同步收斂為 `recordRalliesController`。

**API。** route 只保留 `PUT`——HTTP 語意中 PUT 本就是 idempotent 的動詞，正好對應 upsert；`POST` 留著會誤導。request body 收一個或多個 entry。response body 由裸 `Entry[]` 改為 `{ entries, setCompletionConfirmed? }`，status 維持 200。entry 索引 query param 移除，set 索引保留。換人端點維持裸陣列——它永不觸發 set 結果寫入。

**HTTP client。** 三個仍在用 raw `fetch` 的 action 遷移到共用 client，失敗因此攜帶 status 與 code。client 本身補上 timeout（原生 `AbortSignal.timeout`）與網路層錯誤正規化，否則重試邏輯無法分辨「很慢」與「已死」。

**送出資料的來源。** 兩條路徑都不直接發請求：`useSubmitEntryDraft` 只 dispatch `enqueued`，由佇列的 flush 讀取 `state.pendingWrites.pending` 組成請求。這是搭便車與順序保證的前提——請求永遠帶著佇列當下的全部內容。

連帶要改的是樂觀更新的寫法：現行 `mutate(promise, { optimisticData })` 把樂觀更新與網路請求綁在同一次呼叫，而佇列模型下網路請求屬於 flush。送出當下改為 `mutate(optimisticData, { revalidate: false })`（不帶 promise），flush 取得回應後再更新一次 cache。

**重試。** 伺服器端 `completeSet` inline 重試 3 次（50ms／200ms／500ms），回應前完成。client 端由待送佇列負責：in-action 2 次（300ms／800ms），耗盡後轉入較長的背景退避（2s／5s／15s），期間新 entry 入列會順帶 flush 整個佇列。4xx 這類重試無用的錯誤直接判定為失敗，不進入退避。

## 待送佇列：indicator 與失敗標記的單一真相來源

`SyncIndicator` 沒有自己的狀態欄位。它與 entry row 的失敗標記都是**同一個佇列的投影**，沿用 `game-positional-writes` D1 已確立的原則：會漂移的狀態不儲存，改為推導。

```ts
type PendingEntry = {
  entry: Entry; // 已含 id 與 seq
  gameId: string;
  setIndex: number;
  attempts: number;
  nextAttemptAt: number | null; // null 代表退避預算已用盡，或錯誤本身不可重試
};

type PendingWritesState = {
  pending: PendingEntry[];
  flushingGameIds: string[]; // 目前有請求在途中的 game id；一場比賽同時只會出現一次
};

type SyncStatus = "synced" | "syncing" | "unsynced";

export const deriveSyncStatus = (
  state: PendingWritesState,
  gameId: string,
): SyncStatus => {
  const pending = state.pending.filter((p) => p.gameId === gameId);
  return pending.length === 0
    ? "synced"
    : isFlushingGame(state, gameId) ||
        pending.some((p) => p.nextAttemptAt !== null)
      ? "syncing"
      : "unsynced";
};

export const isFlushingGame = (state: PendingWritesState, gameId: string) =>
  state.flushingGameIds.includes(gameId);

export const hasFailedWrite = (state: PendingWritesState, entryId: string) =>
  state.pending.some((p) => p.entry.id === entryId && p.nextAttemptAt === null);
```

`flushingGameIds` 與 `nextAttemptAt` 分開表達兩件不同的事：前者是「這場比賽正有一個請求在途中」，後者是「已排定下次嘗試」。兩者任一成立都算同步中。

`flushingGameIds` 掛的是 game id 而非單一布林值，因為 flush 以整場比賽為範圍（見下方「單一擁有者」）——切換比賽或背景重試與手動重試重疊時，可能同時有不只一場比賽的 flush 在途中，各自的完成不該互相影響對方的狀態。

避免對同一批 entry 重複送出，靠的不是這個欄位，而是 `usePendingWrites`（擁有 `inFlight` ref 與背景重試 timer 的那個 hook）在一場比賽的畫面上只掛載一次——見下方「單一擁有者」一節。`flushingGameIds` 只負責讓 indicator 與失敗標記知道「這場比賽現在是不是正有請求在飛」，兩者是不同層次的問題。

一個實際的 state 快照——第 7 顆球正在重試（已試 2 次，排定下次），第 8 顆球剛入列尚未嘗試：

此時 `deriveSyncStatus(state, "66f1c0a2e4b0a1d2c3e4f5a6")` 回 `"syncing"`（兩筆都有排定嘗試），`SyncIndicator` 顯示「2 筆未同步」的計數但維持同步中的樣式；兩筆的 entry row 都**不會**出現失敗標記，因為 `hasFailedWrite` 要求 `nextAttemptAt === null`。

slice 的 action 面：

| Action           | 作用                                                                                                                   |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `enqueued`       | 推入一筆 `PendingEntry`（`attempts: 0`），並觸發一次 flush                                                             |
| `flushStarted`   | 把這場比賽的 game id 加進 `flushingGameIds`（已存在則不重複加）                                                        |
| `flushSucceeded` | 依 `id` 移除已確認的項目，把這場比賽的 game id 從 `flushingGameIds` 移除                                               |
| `flushFailed`    | 每筆 `attempts + 1`，依退避表寫入 `nextAttemptAt`；預算用盡或錯誤不可重試（4xx）則寫 `null`；把這場比賽的 game id 移除 |
| `retryRequested` | 手動重試：把所有 `nextAttemptAt === null` 的項目重設為立即，並觸發 flush                                               |

`gameId` 讓佇列在使用者切換比賽時仍能分辨項目歸屬，flush 時也以它決定要打哪一場的端點。

因為兩個視圖讀同一份資料，`SyncIndicator` 的計數與 row 的紅色標記不可能互相矛盾。

佇列放進**獨立的 slice**，而非併入 `game-slice`：它的生命週期與 per-set 的 draft 狀態不同，且之後要被獨立持久化。

與 SWR cache 不構成重複真相——兩者回答不同問題：SWR 的樂觀 cache 是「使用者看到什麼」，佇列是「伺服器還沒確認什麼」。

### 單一擁有者：`usePendingWrites` 只掛載一次

`usePendingWrites(gameId, setIndex)` 內部握有兩樣每場比賽只能存在一份的東西：判斷「目前有沒有 flush 在途中」的 `inFlight` ref，以及依最早到期時間排程下一次背景重試的 `useEffect` timer。四個地方需要用到佇列——`Game`（記錄畫面與局間畫面共同的上層）、`useSubmitEntryDraft`（送出 entry）、`GamePreview`（editing 卡片的送出中／失敗態與重試）、`SyncIndicator`——如果各自呼叫這個 hook，等於各自握有一份 `inFlight` 與一個 timer，同一筆到期的 entry 會被四邊各自的 timer 同時判定為到期，各自送出一個請求。

所以 `Game`（`src/components/game/index.tsx`）是這個 hook**唯一**掛載的地方——它本來就在記錄畫面與局間畫面的分支之上，一個 instance 能同時橫跨兩者。往下需要 `enqueue`／`flush`／`retry` 的元件，改由 `PendingWritesContext`（`usePendingWritesContext()`）讀取同一份結果，而不是各自呼叫 `usePendingWrites`；`useSubmitEntryDraft` 因為呼叫點本來就在 `Game` 內，直接把 `enqueue`／`flush` 當參數傳入即可，不需要走 context。

## 轉場時機

`Game` 切到 `Interval` 的判斷來自 Redux 的局內進行狀態，由 `confirmEntryDraftRally` 設定。**create 路徑改為在送出當下就 dispatch**，不等回應——這是網路不佳時仍能連續記錄的前提。

放寬的前提是三件事同時成立，缺一不可：`seq` ＋ `$sort` 讓亂序不再發生、佇列的自動重送讓多數失敗自癒、`SyncIndicator` 讓剩下的失敗不會無聲無息。

**update 路徑不放寬**：使用者本來就在編輯視窗裡等待結果，且編輯失敗經 rollback 後該 entry 回到伺服器上原本正確的值，資料未損壞也未不一致——與 create 失敗（該球在伺服器上根本不存在）性質不同。

轉場只依賴 entry 本身，不等 `completeSet`：該局是否結束是 client 從比分即可推導的事實，其持久化狀態不改變該事實。

## 偵測機制

`completeSet` 是否確認，兩條路徑結論相同、訊號來源不同，不能共用一套偵測：

| 情境                             | 訊號                                                         | 為什麼不能用另一套                                      |
| -------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------- |
| 即時送出                         | response 的 `setCompletionConfirmed`                         | 本地 cache 已被樂觀寫入，自行比對必然相符，偵測不出失敗 |
| 冷啟動（重新整理／直接進入路由） | 重新 fetch 的資料，以既有推導函式比對 entries 推導值與已存值 | 此時沒有「這次 response」可讀                           |

冷啟動這條不需要任何額外持久化狀態——推導函式本來就在做這件比對。

## Failure modes

| 失敗                                   | 現況                                         | 改動後                                                                  |
| -------------------------------------- | -------------------------------------------- | ----------------------------------------------------------------------- |
| `appendEntry` 成功、`completeSet` 失敗 | 整個 request 回 500，已成功的 entries 被丟棄 | 200 ＋ entries，確認欄位為 false                                        |
| `appendEntry` 成功、回應遺失           | 使用者看到失敗，重記 → 重複                  | 佇列帶同一 id 重送，伺服器判為 no-op                                    |
| 前一筆重試中、後一筆先送達             | 不適用（今天不會樂觀推進）                   | `$sort` 依 `seq` 歸位，陣列順序不受抵達順序影響                         |
| 網路持續不佳                           | 每筆都要等，實質無法記錄                     | 樂觀推進，寫入在背景退避重試                                            |
| 某筆永久失敗                           | 不適用                                       | 該筆留在佇列、entry row 標記、`SyncIndicator` 計數；其餘 entry 照常寫入 |
| 同一 id 帶不同 payload                 | 不適用                                       | last-write-wins；順序語意屬 intent anchors                              |
| 請求卡住不回應                         | 永不 settle                                  | timeout 後拋出可辨識的錯誤                                              |
| 斷網                                   | 落到「未預期的錯誤」fallback                 | 正規化為可重試的錯誤型別                                                |
| 4xx（驗證／授權）                      | 與 5xx 無從區分                              | 不進退避，直接判定失敗                                                  |
| 自動重試進行中離開編輯視窗             | 可離開，結果未知                             | 三個出口（返回鍵、overlay、Escape）皆擋住                               |
| 重試耗盡後離開編輯視窗                 | 可離開                                       | 允許，等同放棄編輯並 toast 告知                                         |
| **app 於仍有未同步 entry 時被關閉**    | 最多損失當下草稿                             | **未同步的 entry 遺失——見 Risks**                                       |

## Testing strategy

核心性質集中在一個 seam。integration 層驅動真實 route handler 直達真實的記憶體 MongoDB，是唯一能證明本次核心性質的地方：同一 id 重送不產生重複、`seq` 較小的 entry 晚到仍排在前面、不同 id 並行寫入都保留、`completeSet` 失敗時 entries 仍完整回傳。擴充既有的 entry 寫入與 set 完成兩個測試檔，不新增分層。

usecase 層以 mock repository 注入暫時性失敗，驗 `completeSet` 的重試次數與退避，以及「重試耗盡後已成功的寫入結果不被丟棄、確認欄位為 false」。依既有測試策略，usecase 測試不得 mock 任何資料庫概念。

`deriveSyncStatus` 與 `hasFailedWrite` 是純函式，直接以 entity 層的測試方式覆蓋三態與邊界。

component 層驗草稿預覽卡的 update loading 態與失敗態、`SyncIndicator` 三態與計數、entry row 的失敗標記、以及自動重試期間編輯視窗三個關閉出口皆不生效。

## Risks

**未同步 entry 在 app 被關閉時遺失。** 樂觀推進後，未確認的 entry 只存在記憶體中。這在特定情境下比改動前更糟：改動前沒收到確認就不推進，app 被回收最多損失一筆草稿；改動後可能一次損失數筆。本 Change **不**修這個缺口，它由待送佇列持久化的後續工作關閉，排在 v0.16.0。這是已知且已登記的 residual risk，不是遺漏。

**`upsertEntry` 的守衛與排序是風險集中處。** append 路徑要同時擋住「id 已存在」並維持 `seq` 排序，錯了是靜默的——寫進去了但條件或順序不對，直到讀取時才顯現。integration 層的亂序與重送測試是唯一能抓到這類錯誤的地方。

**`seq` 由 client 生成。** 這是必要的：若由伺服器在寫入時指定，晚到的 entry 會拿到較大的 seq，正是要修的亂序。資安上不構成新的攻擊類別——client 本來就在送整筆 entry 的內容，寫入仍由團隊角色授權把關；伺服器端的內容驗證（含 seq 合理性）屬既有的排球規則驗證工作。

**usecase 合併的連帶面。** `create-substitution` 與 rally 共用同一個 repository 操作，合併後不可能只改一半，但它的 response 形狀刻意不動——這個不對稱若在實作時被「順手統一」，會擴大本 Change 的 API 變更面。

## ADDED Requirements

### Requirement: ObjectId path parameters validated before handler logic

API route handlers that accept a MongoDB ObjectId as a URL path segment SHALL validate the
segment format before invoking any service, authorization, or repository call.

The shared guard function `assertObjectId(id, param?)` SHALL:
- Accept a string `id` and an optional descriptive `param` name (default: `"id"`)
- Throw `ValidationError(CommonReason.INVALID_INPUT, "Invalid <param> format")` when
  `id` does not match `/^[0-9a-fA-F]{24}$/`
- Return void when `id` is a valid 24-character hexadecimal string

`withErrorHandler` (already applied to all handlers via `withAuth`) SHALL convert the
thrown `ValidationError` to a 400 HTTP response. No per-handler catch block is needed.

#### Scenario: Valid ObjectId passes through

- **WHEN** a route handler receives a 24-character hexadecimal path segment
- **THEN** `assertObjectId` returns without throwing and handler execution continues

##### Example: valid and invalid inputs

| Input | Valid? | Reason |
|-------|--------|--------|
| `"507f1f77bcf86cd799439011"` | ✓ | 24 hex chars |
| `"undefined"` | ✗ | not 24 chars |
| `"bad-id"` | ✗ | contains non-hex char |
| `"507f1f77bcf86cd79943901"` | ✗ | 23 chars (one short) |
| `"507f1f77bcf86cd799439011a"` | ✗ | 25 chars (one over) |

#### Scenario: Invalid ObjectId returns 400

- **WHEN** a route handler receives a path segment that does not match `/^[0-9a-fA-F]{24}$/`
- **THEN** the response status SHALL be 400
- **THEN** the response body SHALL contain `code: "VALIDATION"` and `reason: "INVALID_INPUT"`
- **THEN** no database or authorization call SHALL be made

#### Scenario: Error message identifies the parameter

- **WHEN** `assertObjectId` is called with `param = "teamId"` and an invalid id
- **THEN** the error detail SHALL read `"Invalid teamId format"`

### Requirement: Guard applied consistently across all ObjectId routes

The following route handlers SHALL call `assertObjectId` as the first statement after
resolving `props.params`, before any `connectToMongoDB`, authorization, or controller call:

- `PATCH /api/teams/[teamId]/lineups`
- `POST /api/teams/[teamId]/ownership`
- `POST /api/teams/[teamId]/players`, `GET /api/teams/[teamId]/players`
- `GET /api/games/[gameId]`
- `GET /api/games/[gameId]/sets`, `POST /api/games/[gameId]/sets`
- `POST /api/games/[gameId]/sets/rallies`, `DELETE /api/games/[gameId]/sets/rallies`
- `POST /api/games/[gameId]/sets/substitutions`
- `GET /api/players/[playerId]`, `PATCH /api/players/[playerId]`, `DELETE /api/players/[playerId]`
- `PATCH /api/players/[playerId]/invitations`
- `POST /api/players/[playerId]/memberships`, `PATCH /api/players/[playerId]/memberships`,
  `DELETE /api/players/[playerId]/memberships`

The existing local `assertValidObjectId` in `src/app/api/teams/[teamId]/route.ts` SHALL be
replaced with the shared `assertObjectId` from `src/lib/api/guards.ts`.

#### Scenario: Guard is the first check before any side effects

- **WHEN** a handler receives an invalid ObjectId path segment
- **THEN** no database connection SHALL be opened
- **THEN** no authorization service SHALL be queried
- **THEN** the 400 response SHALL be returned immediately

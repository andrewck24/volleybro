## Findings

三個實質發現，皆已修正並重跑受影響的檢查。兩軸各跑一輪，第二輪無新發現。

### 一、Storybook 的視覺基準在說謊（Standards 軸）

`header.stories.tsx` 的 `Unsynced` story 只 dispatch 一次不帶 `lastError` 的失敗。在新模型下 `mayBeAttemptedAgain(undefined)` 為 `true`、`attempts` 為 1——它渲染出來的是**轉圈的 spinner**，也就是這張 Change 存在要消滅的那個畫面。名稱、註解與視覺三者同時失真。

`docs/testing-strategy.md` 把 Storybook 列為視覺回歸基準，所以一個說謊的基準比沒有基準更糟：它會讓下一個人以為離線狀態長這樣。

### 二、指示器把使用者導向一個它同時宣稱無用的地方（Standards 軸）

`failed` 狀態的文案原本寫「重試無法解決，請在紀錄列表中處理」，但紀錄列表上唯一的動作**就是**那顆 per-row 重試。同一句話裡先否定一個動作，再指向只有那個動作的地方。

審查也指出這句話本身過度宣稱：4xx 中最現實的一種是 session 過期（401），重新登入後那顆 per-row 重試**會成功**。`entry/index.tsx` 的註解「persists until retried」同樣需要修，它對其餘 4xx 不成立。

## Device acceptance

第一輪真機驗收在測試部署上執行（非 `dev`，見「真機驗收只能在合併後進行」那張 ops 票）。**第一輪兩項失敗、一項未執行；第二輪 1、3、4 通過，其中 4 確認 reload 修正有效。**

| 項目                                   | 結果                             |
| -------------------------------------- | -------------------------------- |
| 離線：靜態雲朵、中性色、無重試按鈕     | **通過**                         |
| 連線有問題：文案分岔與重試按鈕         | **未驗證**——兩輪都無法在現場重現 |
| 打嗝兩秒不閃動                         | **失敗**，見發現四               |
| 恢復連線後回到隱藏                     | **失敗**，見發現四               |
| 私密瀏覽顯示無法保存                   | **失敗**，見發現五               |
| 封鎖 Cookie 顯示無法保存（第二輪改用） | **無法執行**，見發現七           |

「連線有問題」是本 Change 為之擴大範圍的那個情境——D1 的整個論證建立在它比飛航模式更常見之上。經過兩輪嘗試仍無法穩定重現，**永久記為未驗證的路徑**，不算通過。

它由單元測試覆蓋：`deriveSyncStatus` 對「`navigator.onLine` 為 `true` 但仍達失敗門檻」有明確案例，指示器測試也涵蓋兩種文案與重試按鈕的顯示條件。缺的是真機上「訊號滿格卻送不出去」這個組合的實地確認。這是本 Change 最主要的主張唯一沒有現場證據的地方，下一個碰到相關程式碼的人應該知道。

### 發現四：恢復連線時整頁重載（既有缺陷，不屬本 Change）

`SerwistProvider` 的 `reloadOnOnline` 預設為 `true`，`layout.tsx` 未傳該 prop，於是每一次 `online` 事件都呼叫 `location.reload()`。記錄途中復網會清掉當前局與正在編輯的球，實測通常需要重開 app 才能繼續。

未送出的球不受影響——佇列在磁碟上。這個缺陷比本 Change 更早存在，只是「恢復連線」這一刻在此之前沒有人盯著看。已獨立成票並修正（`reloadOnOnline={false}`），不併入本 Change。

### 發現五：探測看不到私密瀏覽——**已核准的設計判斷錯誤**

D3 在 Propose 階段寫著「Safari 私密模式發放的是關掉分頁就消失的配額而不拋錯，所以讀回那一半能抓到」。**那句話是錯的。**

私密／無痕模式下 `localStorage` 在同一個 session 內完全正常：寫得進去、讀得回來、刪得掉。探測三步全部成功，於是回報健康。它能抓到的只有**當下就失敗**的 store——配額用盡、站台資料被封鎖。「現在可用、關掉才消失」在原理上無法被同步探測看見。

而偵測私密瀏覽本身，正是 D3 明確否決的事。

處置為 Ingest：D3 的 context、decision、consequences 與 revisit trigger 全數更正，`unwritable` 的涵蓋範圍由五個成因收窄為兩個，其餘三個移入 residual risk；Design 的 Scenario 增列「私密瀏覽不會有警告」為預期行為；驗收腳本第五項改為封鎖所有 Cookie。**沒有任何程式碼或文案被刪除**——狀態與它說的話都仍然成立，改變的是文件對它涵蓋範圍的宣稱。

一句話：這張以「不要宣稱超過你所知道的」為主題的 Change，自己在 D3 裡宣稱了做不到的事。

### 發現六：popover 字級低於排版級距（a11y）

popover 的說明文字用 `text-[11px]`，重試按鈕也是。設計系統的排版級距**最小只到 `text-xs`（0.75rem / 12px）**，沒有更小的定義——所以那是跑到級距外面，而不只是偏小。

更實際的問題是 px 字面值**不隨使用者的瀏覽器字級偏好縮放**，rem 會。使用者把預設字級調大，那兩處不會跟著變。

已改為級距內的值：標題 `text-sm`、說明 `text-xs`、重試按鈕依設計系統的按鈕規則採 `h-9` / `rounded-md` / `text-sm`。兩份設計系統文件都沒有寫下級距下限，所以也沒有東西能擋住這個錯誤——該規則已補入 `docs/design-system.md`，於文件分支交付。

### 發現七：狀態 1 沒有可觸及的觸發條件——只剩配額

第二輪把驗收條件由私密瀏覽改為「封鎖所有 Cookie」，結果**登入本身就失敗**：Cookie 被封鎖時 Better Auth 建不起 session，使用者停在登入頁，永遠到不了記錄畫面。這個成因探測抓得到，但沒有人看得到。

| 成因                  | 探測抓得到 | 使用者到得了記錄畫面 |
| --------------------- | ---------- | -------------------- |
| 封鎖站台資料 / Cookie | 是         | **否**——登入先失敗   |
| 配額用盡              | 是         | 是                   |

所以**開機探測唯一還會觸發的情境是「開 app 時配額就已經滿了」**。而 listener 的 catch 會在第一顆球入列時抓到同一件事——探測買到的是「第一顆球之前」而非「第一顆球當下」，一顆球的差距。保留它是開發者的決定：那顆球記下去之後才被告知，感受完全不同。D3 對它價值的設想比實際大得多，已第三度更正。

**文案同時改為指名配額。** 本 app 的 `localStorage` 只有佇列一個寫入者（表單草稿在 `sessionStorage`），塞滿它的幾乎必然是自己累積的未送出 entry——而佇列跨比賽、送出卻是 game-scoped，這正是 `retryable-queue-persistence` 的 D3 記下的「送達依賴使用者回到該場比賽」的長期後果。兩張 Change 在這裡接上了。文案依「是否有其他比賽的未送出 entry」分岔，才不會叫人去找不存在的比賽。

## Follow-ups

- **不可重試 entry 的導向與刪除**：以本 Change 為前置，補上從指示器到 Entry List 的路，以及丟棄動作。本 Change 交付後，警告狀態第一次成為一個獨立可辨識的狀態，那張票的前提因此成立。
- **重試狀態群組化**：`attempts` 與 `lastError` 的持有位置將由 entry 移至 (game, set) 群組，`PENDING_WRITE_UNSENT_ATTEMPTS` 的門檻語意屆時由「單一 entry」變為「群組」，`deriveSyncStatus` 須重新檢視。
- **`navigator.storage.persist()` 在 iOS PWA 的授予條件**：待實地確認。確認可靠則可關閉兩條 residual risk；確認不可靠則應移除那三行，而不是留著假裝有用。

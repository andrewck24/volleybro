## Context

`retryable-queue-persistence` 交付後的 iOS PWA 人工驗證，結論是持久化本身通過：飛航模式下記球、強制關閉、重開後球都在，恢復連線後未經手動介入即自行送出，資料庫比對顯示每筆一份、無重複。

但驗證過程中，整段離線期間指示器都顯示轉圈的「同步中」。**`retryable-queue-persistence` 讓資料變安全了，UI 卻沒有任何狀態把這個保證說出口。**

這張 Change 從「離線時別轉圈」開始，收斂後變成一個更大的命題：**指示器說的每一句話都必須是真的。** 目前有三句不是。

第一句是 spinner。`deriveSyncStatus` 以 `pending.some((p) => p.nextAttemptAt !== null)` 判定 syncing，而 `enqueued` 每次入列都設 `nextAttemptAt: Date.now()`——離線時每記一球就把整組重置回 syncing。值得說清楚的是：**「等待下一次重試」確實屬於重試生命週期，這個判斷本身不算錯。** 錯的是 spinner 隱含的「稍等即可」——線上時那是真的，兩百毫秒後就成功了；離線時它在重新連上網之前永遠不會兌現。

第二句是警告色。`unsynced` 配 warning 色與驚嘆號，觸發條件是「退避表用盡」。但那類 entry 會自己好——下一顆球的 flush 或 `online` 事件都會帶它送出。真正會遺失的是不可重試的那一類（4xx），而它們今天跟前者共用同一個狀態。

第三句還沒被說出口，是這張 Change 自己造出來的。今天 UI 說「N 筆未同步」，即使 `localStorage` 壞掉那句話仍為真；本 Change 要把它升級成「已保存」，**而那句話在 store 不可寫時是假的**。`retryable-queue-persistence` 的 D4 已經把這條記為 residual risk，並寫下「誠實的做法最終是告訴他們，只是要說出來，得先有一個地方可以說」。這張 Change 造出了那個地方，也造出了非說不可的理由。

還有一件事值得記下來：`retryable-entry-writes` 的 D2 在否決「只靠 piggyback、不做背景退避」時，已經預言過這個失效模式——「一個宣稱同步仍在進行中的指示器會是不真實的」。它用退避表把時間上界壓到約二十二秒。**沒被預見的是連續記球會不斷把那個上界重設，所以它在真實節奏下從未生效。** 這不是沒人想過的疏漏，是一個被想過、被設了上界、而上界在真實使用節奏下失效的案例。

## Goals

- 指示器在每一種狀態下所呈現的圖示、顏色與文字，都與系統當下的真實處境一致。
- 使用者在離線時知道自己的紀錄是安全的，而不只是知道它「還沒同步」。
- 警告語氣只出現在使用者真的需要做點什麼的時候。
- 「網路顯示已連線但到不了伺服器」與飛航模式獲得同等對待——前者在球場上更常發生。
- 本機儲存不可用這個既有的 residual risk 第一次對使用者可見，且在他還有選擇的時候可見。

## Non-goals

- **不做 outbox、跨場比賽可見性、衝突重放。** 那是 `offline-recording`。
- **不改重試政策。** `isRetryableStatus`（`status >= 500`）維持為唯一標準，不開第二套判斷。
- **不新增慢速輪詢。** 讓「會自動送出」在連線異常時也成真需要一個不終止的重試機制，那是 outbox 的定義。理由與代價見 D4。
- **不做不可重試 entry 的導航與刪除。** 已獨立登記為後續工作「不可重試 entry 的導向與刪除」，並以本 Change 為前置。
- **不改重試狀態的形狀。** 群組化屬後續工作「重試狀態改以 (game, set) 群組為單位」，本 Change 先於它——理由見下方排序。
- **不改儲存選型。** `localStorage` 對 IndexedDB 的取捨由 `retryable-queue-persistence` 的 D1 決定，本 Change 不重開；理由見 D3。
- **不偵測私密瀏覽。** 那是隱私功能，且問錯了問題；見 D3。

## Change boundaries

- **一定在內**：`deriveSyncStatus` 的五條有序條件、`hasFailedWrite` 的判準、`SyncIndicator` 的圖示／文案／版面／重試按鈕、一個讀取 `navigator.onLine` 的 hook。
- **在內**：`pendingWrites` slice 新增一個表示本機儲存不可用的布林欄位，以及開機時設定它的探測。這是本 Change 唯一新增的狀態，且它有兩個寫入者——開機探測與既有的 listener catch。
- **在內**：移除 `flushingGameIds`。它今天活著的唯一理由是舊的 `deriveSyncStatus` 要讀它；新模型不讀，它就成了本 Change 自己造成的孤兒。**這個移除是狀態模型改變的證據**：舊模型需要知道「有沒有 request 在飛」，新模型不需要。
- **在內（討論中浮現）**：`retryable-entry-writes` 的 S08 所建立的 per-rally 失敗標記收窄。它與指示器必須讀同一個判準，否則兩個表面會對同一批 entry 給出矛盾的語氣。
- **不在內**：佇列的送出、重試、退避、過期行為。`enqueued`、`flushSucceeded`、`flushFailed`、`retryRequested`、`rehydrated`、`hasExpired`、`nextAttemptDelayMs` 的語意全部不動。
- **不在內**：rally 端點、repository、SWR 設定、Entry List 的互動（只有標記的觸發條件改變，控制項本身不動）。

## Impact

Affected capabilities：`game-recording/rally-recording`、`game-recording/persistence`。兩者都不新增 sub-capability——本 Change 改變的是既有能力對自己處境的陳述，不是能力本身。

`game-recording/rally-recording` 的行為契約不變——記球的手勢、樂觀推進、送出的時機全部照舊。改變的是**系統對自己處境的陳述**：同一組佇列事實，被投影成一組不再說謊的狀態。

`game-recording/persistence` 第一次獲得一個對使用者可見的可用性契約。在此之前，「本機儲存是否可用」只存在於 console warning 裡；此後它是一個會出現在畫面上的狀態，而且在第一顆球被記錄之前就會出現。

## Alternatives considered

Design 頁完整記錄各組替代方案與否決理由。Overview 層級只記結論方向：

- **新增一個由 `navigator.onLine` 驅動的 offline 狀態**（原始票的方向）——只修好飛航模式。裝置連上網路卻到不了伺服器時它回報 `true`，指示器落回 syncing 繼續轉圈。它挑了比較好偵測的情境，不是比較常發生的。
- **把 syncing 收窄為「真的有 request 在飛」**——離線期間會在退避空檔與嘗試瞬間之間反覆切換，反而製造抖動；退避用盡後仍落到警告語氣，語氣依舊不對。
- **以計時器實作抖動門檻**（Notion 用三十秒）——需要一個 `setTimeout` 在門檻到期時強制 re-render。次數門檻用既有的 dispatch 推動狀態，效果相同而無新機制。而三十秒對在球與球之間抬頭掃一眼的記錄員過長。
- **偵測並封鎖私密瀏覽**——瀏覽器廠商持續封鎖偵測手法，且 app 在私密瀏覽下完全可用，失去的只是一個降級的保證。直接測「寫得進去嗎」一次涵蓋全部五個成因。
- **改用 IndexedDB**——五個成因只解掉配額一項，而該項在此規模下最不可能發生；且它的非同步 transaction 在「app 被回收」時可能尚未 commit，那正是持久化要存活的情境。
- **加一道慢速輪詢讓兩種情境的承諾都成真**——動到重試機制，並帶進「輪詢什麼時候停」這個新的生命週期問題。那是 outbox 要回答的。
- **兩種情境都顯示或都不顯示重試按鈕**——都顯示會給出一顆必定失敗的按鈕；都不顯示則讓連線異常的使用者完全沒有出路。Google Docs 與 Notion 不提供這顆按鈕，是因為它們的背景重試永不終止，那是我們沒有的前提。

## Decisions

結構化 ADR 位於 `design/decisions/`，由 Design 頁的 `DecisionTimeline` 呈現。

| ID  | 問題                             | 結論                                                          |
| --- | -------------------------------- | ------------------------------------------------------------- |
| D1  | 狀態由什麼訊號判定               | 實測失敗（`attempts`）；`navigator.onLine` 只選文案           |
| D2  | 警告語氣掛在什麼條件上           | 不可重試，per-rally 標記一併收窄                              |
| D3  | 本機儲存不可用時誰說、什麼時候說 | 升為第一級狀態，開機就探測                                    |
| D4  | 誰負責偵測「伺服器恢復」         | 暫時交給使用者的手指，期限記在 `offline-recording` 的驗收條件 |

## 排序

**先於「重試狀態群組化」。** 該後續工作將重試狀態改以 `(game, set)` 群組為單位，會改變 `attempts` 與 `lastError` 的持有位置，而本 Change 的狀態模型全部讀這兩個欄位。先做本 Change，「重試狀態群組化」 面對的是一個已移除死欄位、狀態語意已釐清的 slice；反過來則須先在一個已知錯誤的狀態模型上建群組化，再重做指示器。

## Revisit triggers

- **重試狀態群組化落地**：`attempts >= 2` 的門檻語意由「單一 entry」變為「群組」，`deriveSyncStatus` 的條件式須重新檢視。
- **「不可重試 entry 的導向與刪除」交付**：警告狀態自此有可執行的動作，其語氣與文案應一併重估。
- **`offline-recording` 的持久重播上線**：終局狀態消失，手動重試按鈕失去存在理由，應移除而非留著成為第二條路徑。同時 D3 的儲存不可用會從降級模式升級為功能無法運作的理由。
- **rally 端點補上 request schema**：400 大量增加，「不可重試」從罕見變成常態，呈現密度與七天過期規則都要重估。
- **`navigator.storage.persist()` 在 iOS PWA 的授予條件被實地確認**：確認可靠則可關閉兩條 residual risk；確認不可靠則該移除它，而不是留著假裝有用。
- **現場出現三秒門檻過短或過長的證據**：過短表現為打嗝仍造成圖示閃動，過長表現為使用者在門檻成立前就已經開始擔心。

<Proposal>

<TLDR>
  decision record 有三份定義：沒有程式讀取的 JSON schema、TypeScript
  型別、手寫 validator，任兩份都可能漂移；store 分支沒有任何保護，唯一的重新檢視條件也沒有數字。這個
  Change 讓 zod schema 成為唯一定義，替 store 分支加上禁止刪除與 force-push
  的 ruleset 和 50 MB 警告門檻，並規定 PR body 附上 branch preview 的 Change 頁面。
</TLDR>

|                         | 現在                                                   | 之後                                                                  |
| ----------------------- | ------------------------------------------------------ | --------------------------------------------------------------------- |
| decision record 的定義  | JSON schema、TypeScript 型別、手寫 validator 三份並存  | `decision-record.ts` 的 zod schema 一份，型別由 `z.infer` 推導        |
| record 解析失敗         | build 失敗，只說 `Invalid decision record: <id>`       | build 失敗，並指出欄位路徑與違反的規則                                |
| `blueprint-changes`     | 可被刪除、可被 force-push；「大到拖慢 build」沒有數字  | ruleset 禁止刪除與 force-push；歷史超過 50 MB 時 `changes:pull` 警告  |
| PR 的 reviewer          | 從 PR 找不到 Change 頁面                               | PR body 附 branch preview 的 Change 頁面，看得到本次的 ADR            |

## 範圍

1. 以 zod 改寫 `blueprint/src/lib/decision-record.ts`：parser 就是 schema，型別由 `z.infer` 推導，`strictObject` 拒絕未知 key；在 `blueprint/package.json` 宣告 zod（完整版）。`DecisionTimeline` 改收 server 已解析的 `DecisionRecord[]`，不再在瀏覽器端重新解析。
2. 刪除 `blueprint/schemas/`，移除所有 record 的 `$schema`。
3. `blueprint:changes:pull` 抓取後量測 store 完整歷史的磁碟大小，超過 50 MB 印出 warning，不 fail。
4. 以 `gh api` 建立 `blueprint-changes` 的 ruleset：deletion 與 non_fast_forward。
5. ADR-0062 的 `revisitTriggers` 改指向 ADR-0082。
6. 更新 `WORKFLOW.md` 的 Decision-record contract 與 `docs/agents/blueprint.md`，改指向 parser；`WORKFLOW.md` 補上「最後一次 push 在最後一次 publish 之後，publish 後沒有新 commit 時手動重跑 branch build」，以及 PR body 附上 `<branch-preview>/changes/<slug>`。
7. 更新 Feature `platform/blueprint` 與 `platform/delivery-workflow`。

### 不在範圍內

- 以 CMS 取代 store 分支：不採用，ADR-0062 維持。
- 在 site build 時推導 `archivedAt`、省去 merge 後的 publish：另案評估。
- 在 `platform/blueprint` 畫出 Change 頁面的生命週期流程圖：另案以 Fix path 處理。
- 原本的「同編號 ADR 副本一致性」：ADR 已是扁平的單一檔案，問題不存在。
- Feature 頁改用 `DecisionCards`：另案評估是否統一兩個元件。

<ActionItems>

1. **ADR-0081 的 `decision` 內文在 G1 之後改了。** Ingest 時你同意拆分：ADR-0081 只留 ruleset 與「不得改寫歷史」，50 MB 門檻移到新的 ADR-0082。ADR-0080 的 `context` 與 `consequences` 也改寫了（不是 `decision` 內文），說明 record 壞掉時是 build 失敗，以及 zod 為何仍進入前端 bundle。
2. **Ingest 第 1 點沒有交付，請確認維持現狀。** `DecisionTimeline` 仍在瀏覽器端解析並保留 fallback，理由見 Deviations。
3. **PR body 的 preview 連結在開 PR 時加上**：S7 的前半（preview 頁面）已在 G2 前驗證，後半要等 PR 存在。

</ActionItems>

<ReviewFocus>

1. `blueprint/src/lib/decision-record.ts`：整個手寫 validator 換成 zod schema，型別由 `z.infer` 推導。拒絕未知 key 與錯誤訊息格式是這次最直接的行為變化。
2. `scripts/blueprint-changes.js` 的 `warnIfHistoryTooLarge`：git 太舊時靜默略過是刻意的，值得確認你接受這個取捨。
3. `WORKFLOW.md` 的 G2 段落：「最後一次 push 在最後一次 publish 之後」這條新規則會影響之後每個 Change 的收尾順序。

</ReviewFocus>

<Deviations>

1. **範圍第 1 點「`DecisionTimeline` 改收 server 已解析的 `DecisionRecord[]`」沒有交付。** 實作後 Blueprint build 的型別檢查失敗：store 上 `game-positional-writes` 的 design mockup 直接把頁內寫死的 record 傳給 `DecisionTimeline`，而逐筆 fallback 正是 `standalone-decision-records` 驗收過的行為（它的 S11）。根本原因是 Ingest 假設 `DecisionTimeline` 只從 server 拿 record。已還原，瀏覽器端解析是正確的邊界。
2. **Proposal 風險表少了「zod 進入 Blueprint 的前端 bundle」。** 因為第 1 點沒有交付，這個風險仍然存在；ADR-0080 的第一條 consequence 已照實寫明。

</Deviations>

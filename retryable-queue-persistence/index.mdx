## Context

`retryable-entry-writes` 讓 create 路徑改為樂觀推進：使用者記完一顆球立刻可以記下一顆，不必等伺服器回應。那是網路不佳時仍能連續記錄的前提，而它成立的三根支柱之一，是一個記得「伺服器還沒確認什麼」的待送佇列。

那個佇列只存在記憶體裡。該 Change 的 D4 在 consequences 明列了代價：「An app killed while entries are unconfirmed loses them, which is worse than today's behaviour in that one scenario」——因為改動前沒收到確認就不會推進，app 被回收最多損失當下那一筆草稿；改動後可能一次損失數筆。本 Change 負責關閉它。

值得先講清楚的是，佇列並不是「失敗才進去的地方」，而是**每一顆球的必經之路**。`oppo.tsx` 的 create 與 update 都是先 `enqueue(entry)` 才 `void flush()`，送成功後由 `flushSucceeded` 移除。正常情況下一筆 entry 在佇列裡活不到一秒；佇列非空只有三種原因——離線、伺服器掛了、session 過期。這三種正是這張 Change 存在的理由。

順序上還有一個推論：既然 entry 在**任何請求發出之前**就已入列，那麼把它寫進磁碟這件事也發生在送出之前。就算送出那一瞬間 app 就死了，球已經在磁碟上。

## Goals

- 未確認的 entry 在 app 被關閉或被系統回收之後仍然存在，使用者回到該場比賽時自動重送。
- 重送不產生重複——這一點由 `retryable-entry-writes` 的 identity-keyed upsert 免費提供，本 Change 只需不破壞它。
- 儲存的實作可以整批替換而不動任何呼叫端，因為 PWA 之後的下一步是 native app，屆時整批對應物都是非同步的。
- 不讓「永久失敗的 entry」因為持久化而變成永久卡住——那會是一個回歸。

## Non-goals

- **不還原畫面。** 重啟後不把未送 entry 樂觀套回 SWR cache。畫面正確性是另一個缺陷（SWR revalidation 會覆蓋樂觀寫入），有自己的 Change，兩者獨立可交付。若在此一併做掉，兩張票會各寫一份同樣的樂觀套用邏輯。
- **不把 flush 提升為全域。** 送出仍由 `usePendingWrites` 在 `Game` 底下掛載，也就是仍然需要使用者回到那場比賽。一個不綁畫面、自己負責把東西送出去的背景佇列就是 outbox 的定義，而 outbox 是 `offline-recording` 的第一條驗收條件。
- **不改 `PendingEntry` 的重試狀態形狀。** 走查中發現重試狀態實際上是 `(gameId, setIndex)` 群組層級的事實卻被複製到每一筆 entry 上，那是 `retryable-entry-writes` 剛交付的核心結構，改它是重新設計而不是持久化，已獨立登記。
- **不改用 IndexedDB。** 理由在 Design 的 D1，簡言之：它是非同步的，而本 Change 防的正是「app 突然被回收」。
- 不做離線的完整語意——批次重播、跨裝置合併、連線狀態機、衝突解決，全部屬 `offline-recording`。

## Change boundaries

- **一定在內**：一個 client 端的儲存 port（三個方法）與它的 localStorage 實作、寫入的 listener middleware、讀回的進入點、以及 `pendingWrites` slice 新增的 `rehydrated` action。
- **在內**：`PendingEntry` 新增 `lastError`。持久化逼出了一個記憶體裡可以含糊、寫到磁碟就不行的區別——`nextAttemptAt: null` 目前同時表示「退避用盡」與「不可重試」，而 401 與 404 的後續處理完全不同。
- **在內（討論中發現）**：讀回時的過期規則。今天一筆註定失敗的 entry 的唯一出路是「關掉 app」，持久化拿掉了這個逃生口，必須補回一個等價的東西，否則這張 Change 自己製造一個回歸。
- **不在內**：任何 UI 元件。`SyncIndicator`、entry row 的失敗標記、summary drawer 全部不動——它們已經是佇列與快取的投影，佇列被還原它們就自動正確。這也讓本 Change 不受「agent 無法對需登入頁面截圖」那個既有阻礙影響。
- **不在內**：`useGame`、SWR 設定、rally 端點、repository、Mongoose schema。

## Capability impact

`game-recording/persistence` 的可靠性契約從「單一 entry 的寫入結果對 client 而言是可確認的」延伸為「**未確認的寫入在 app 生命週期之外仍然存在**」。這是該能力第一次擁有跨行程的狀態。

`game-recording/rally-recording` 的行為契約不變——使用者記球的體驗、失敗的呈現方式、重試的手勢全部照舊。唯一的差別是重開 app 之後那些球還在。這是刻意的：這張 Change 的價值必須完全來自「東西沒不見」，而不是任何新的介面。

## Alternatives considered

Design 頁完整記錄各組替代方案與否決理由。Overview 層級只記結論方向：

- **IndexedDB**——容量大得多、可逐筆寫入，但非同步的 transaction 可能在 app 被回收時尚未 commit，而那正是要防的情境；同步寫入在這裡是對症而非妥協。算過的量（整天賽事全程離線約 300 KB）距離 localStorage 的配額還很遠。
- **Service Worker 或 Background Sync 承接寫入**——Service Worker 不是常駐程序，瀏覽器會積極終止閒置的它；把寫入交給它是多一次非同步跳躍，中斷窗口變大而非變小。Background Sync 另有 iOS 不支援的問題，而且 `offline-recording` 的原始決策已經明確選擇 application-layer outbox 而非它。
- **`redux-persist`**——為了通用地持久化整個 store 而存在。這裡只有一個 slice、一個 key，自己寫約二十行，還不必跟它的 rehydrate 生命週期打架。
- **把 port 放進 `applications/repositories/`**——命名最一致，但那一層綁著 inversify 與 node-only 的 import，client 端只有一個檔案碰得到它；放進去會誤導讀者，也有把伺服器端相依打包進 bundle 的風險。
- **`preloadedState` 注入讀回的資料**——`makeStore()` 是同步的而 `load()` 不是，這條路在選擇非同步簽章的那一刻就關閉了。
- **`pagehide` / `visibilitychange` 時才寫入**——寫入次數最少，但 iOS PWA 被系統回收時不保證觸發，正是要防的情境。
- **儲存 `retryable` 布林而非 error code**——布林分不出各種失敗，而後續處理（是否過期、衝突流程要接什麼）需要那個區別。
- **為 401 另立一種判斷，讓它在重啟後自動重送**——理由成立（登入是整頁 redirect，重啟往往正是修好 session 的那件事），但它是第二種標準，而它買到的很窄：本來就要等使用者走回那場比賽才會送出，而那時重試手勢已經在畫面上。一種標準加一個已經存在的手勢，勝過兩種標準。

| D2  | 磁碟上存什麼                   | 整包快照，含 `lastError` 的 code；重試狀態一律重算，並套用收窄的過期規則 |

## Revisit triggers

- `offline-recording` 開始實作 outbox：D3 登記的兩條 residual risk（送達依賴使用者回到該場比賽、儲存不可用時靜默降級）屆時關閉，該 Change 已收下對應的驗收條件。
- 佇列規模逼近數千筆：整包快照的 O(n) 寫入開始有感，屆時換的是 D1 的 adapter 而非架構，第一步是把 key 拆成每場一把。
- 目標平台從 PWA 延伸到 native app：D1 的非同步簽章正是為此而存在，屆時要驗證的是「寫到一半被殺」在新 adapter 上的行為，那是 localStorage 不需要處理而 native 需要的。
- rally 端點加上 request schema：400 會大量增加，D2 的過期規則從保險變成主要機制。兩張 Change 在 `isRetryableStatus` 這一個函式上相接。
- 過期天數被實地推翻：七天是一個沒有量測依據的起始值，長天期的巡迴賽是最可能推翻它的場景。

## Design

<TLDR>
  待送佇列從記憶體延伸到磁碟。slice
  在中央，左邊是持久化、右邊是網路，兩側互不知情——持久化只對 slice
  的變動作反應，完全不知道有伺服器存在。寫入發生在送出**之前**，讀回**不等於**送出。
</TLDR>

## Adopted shape

Redux slice 在中央，兩側互不知情：左邊是持久化（listener → port → localStorage），右邊是網路（flush → API → Mongo）。持久化那一側完全不知道有伺服器存在，它只對 slice 的變動作反應。

## Contracts

**Port。** 一個 type，三個方法，全部回傳 `Promise`：

```ts
// src/lib/features/game/pending-writes-storage.ts
export type PendingWritesStorage = {
  load(): Promise<unknown>;
  save(snapshot: PersistedQueue): Promise<void>;
  clear(): Promise<void>;
};
```

localStorage 實作在 async function body 裡做同步的 `setItem`，因此「函式返回時資料已在磁碟上」這個性質與直接呼叫完全相同——非同步只存在於簽章，不存在於時序。實作不 catch，見 D4。

`load()` 回傳 `unknown` 而非 `PersistedQueue`，是刻意的：store 的內容在驗證之前不可信，型別不該先替它背書。

**磁碟格式。** 單一 key `pending-writes`，版本住在快照內容裡而不在 key 上。

```ts
// src/lib/features/game/types.ts
export type PersistedQueue = {
  version: number;
  items: {
    entry: RallyView & EntryIdentity;
    gameId: string;
    setIndex: number;
    lastError?: { code: AppErrorCode; reason: string; status: number };
    firstFailedAt?: number;
  }[];
};
```

`attempts` 與 `nextAttemptAt` 不存：前者讀回歸零，後者是絕對時間戳、重啟後一律已過期，重算即可。`flushingGameIds` 不存：那是 runtime state，重啟後必然為假，與實作切片時不把 `claimed`／`running` 寫進 Git 是同一條規則。

`firstFailedAt` 只在**第一次**失敗時寫入。flush 會送出該場比賽所有待送 entry、不看排程，所以一筆註定失敗的 entry 只要使用者還在記那場比賽就會不斷被重試；時間戳若跟著更新，量到的會是使用者的活躍度而不是 entry 的年齡。

讀回的內容不是被 cast 而是被 parse：storage 是同源的任何程式都能寫的，而讀回的東西會進佇列、接著被送往伺服器。schema 的型別綁為 `z.ZodType<PersistedQueue>`，所以 schema 與型別不可能漂移。

**寫入。** RTK 的 `createListenerMiddleware` 監聽四個會改動 `pending` 內容的 action。前三個是佇列自己的進出，第四個是讀回——被過期規則縮短的佇列要靠它寫回磁碟，否則死掉的項目每次啟動重讀重丟。effect 在 reducer 之後執行，所以 `getState()` 拿到的已經是合併後的完整佇列：

```ts
export function createPendingWritesPersistence(storage: PendingWritesStorage) {
  const listener = createListenerMiddleware<StateWithPendingWrites>();

  // persist 見下一段
  listener.startListening({
    matcher: isAnyOf(enqueued, flushSucceeded, flushFailed, rehydrated),
    effect: (_action, api) => {
      persist(api.getState().pendingWrites.pending);
    },
  });

  return listener.middleware;
}
```

`snapshotOf` 而非就地組出 `{ version: 1, ... }`：版本號只有一個來源。

**合併發生在 reducer，持久化層只照抄。** `enqueued` 的那一行 `state.pending.push(...)` 就是合併；`toPersisted` 只丟掉重算得到的欄位，沒有任何佇列邏輯。整份設計裡唯一真的需要寫合併邏輯的地方是 `rehydrated`，因為只有那裡有兩個來源。

不做 debounce：記球是人的手速，而 localStorage 寫入是次毫秒級的；debounce 只會製造一個「已經記下但還沒寫入」的窗口，正是要消滅的東西。

同理**也不用 promise chain**。鏈會把每一次寫入都推遲一個 microtask，等於在「記下」與「落地」之間重新開一個窗口。

```ts
// createPendingWritesPersistence 內部
let inFlight: Promise<void> | null = null;
let queued: PendingWritesState["pending"] | null = null;

// 閒置時直接寫：同步的 store 因此在這個函式返回前就完成
const persist = (pending: PendingWritesState["pending"]) => {
  if (inFlight) {
    queued = pending; // 進行中：只留最新一份，中間那些不值得寫
    return;
  }
  inFlight = run(pending);
};

const run = (pending: PendingWritesState["pending"]): Promise<void> =>
  storage
    .save(snapshotOf(pending))
    .catch((error: unknown) => {
      console.warn("[pendingWrites] persist failed:", error);
    })
    .then(() => {
      const next = queued;
      queued = null;
      inFlight = next === null ? null : run(next);
    });
```

一條 `chain = chain.then(() => storage.save(s))` 會保序，但**每一次**寫入都因此晚一個 microtask——包括沒有任何寫入進行中的那一次，也就是絕大多數。上面的寫法在同樣保序的前提下，把最常見的情況變回同步。

**讀回。** `ReduxProvider` 掛載時呼叫 `load()`，先讀 `version`、再驗形狀，然後 `dispatch(rehydrated)`。順序是這樣而非相反，因為 schema 描述的是**這個 build 寫出來的**形狀，先驗形狀會把真正的新版快照當成壞資料，版本檢查永遠到不了。`rehydrated` 依 `entry.id` 合併且**記憶體優先**：`load()` 是非同步的，讀回期間使用者可能已經記了球，直接覆蓋會把那顆新球弄丟。

重試狀態在此重算：`attempts` 歸零、`nextAttemptAt` 設為立刻，除非 `lastError` 判定為不值得再試。

**判斷只有一種標準。** flush、restore 與過期規則讀的是同一份門檻，沒有第二個 predicate，也沒有 code 到政策的對照表——兩份判斷遲早漂移，而漂移的後果是某些球永遠不再被送出。

這條的代價是 401：session 過期的 entry 不會在重啟後自動重送。它留在佇列裡、SyncIndicator 顯示未同步，使用者重新登入後以既有的重試手勢送出。代價很小，因為在下一節的決定之下，**本來就要等使用者走回那場比賽**才會有任何東西被送出，而那時重試手勢已經在畫面上。

**過期。** 讀回時，`lastError` 判定為值得再試（5xx、離線正規化成的 503）的項目永不過期；判定為不值得再試的超過七天丟棄。用的是上面那**同一種標準**。這條規則存在的唯一理由是還原持久化拿掉的性質，見下一節。

## 持久化拿掉了一個逃生口

今天佇列裡一筆註定失敗的 entry——404 比賽被別人刪了、403 被移出球隊、400 被 `upsertEntry` 的身分守衛拒收——唯一的出路是**關掉 app**。佇列只在記憶體裡，重開就乾淨了。

把佇列寫進磁碟，這個逃生口就沒了。那筆 entry 每天都還在：該場比賽的 `SyncIndicator` 永遠顯示未同步，而在 D3 的決定下，使用者一旦離開那場比賽就再也看不到它。**這是這張 Change 自己製造的回歸**，不是既有問題。

正確的解法是讓使用者看得見並主動捨棄，但看不見的東西不能要求人捨棄，而可見性屬 `offline-recording`。因此這裡用最小的等價物：收窄的過期規則，只讓「註定失敗」的那一類自己消失，讓「還有希望」的那一類永遠留著。純資料層，無 UI。

這條規則在 rally 端點加上 request schema 之後會從保險變成主要機制——那項工作會讓 400 大量增加，而 entry 是在任何請求發出之前就已入列並寫入磁碟的，所以邊界驗證擋不住它進佇列，只會增加卡死的數量。

## Failure modes


讀回時對磁碟上的內容有四種處置，差別在於**那份資料對未來的 build 還有沒有用**：

| 磁碟上的東西                           | 處置                                                                                                         |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 本 build 的版本，形狀正確              | 套用過期規則後讀回                                                                                           |
| **舊**版本                             | 不採用，**並清除**——沒有任何後續的 build 會回頭讀它                                                          |
| **新**版本                             | 不採用，但**保留**——它可能屬於使用者同時在跑的另一個 build，而這是唯一「猜錯就毀掉未送資料」的地方           |
| 壞掉的 JSON，或本 build 版本但形狀不符 | 不採用，**並清除**。`load()` 在此回傳原始字串而非 `null`，呼叫端才分辨得出「沒有東西」與「有東西但沒人能用」 |

其餘情境：

| 情境                             | 行為                                                                                            |
| -------------------------------- | ----------------------------------------------------------------------------------------------- |
| app 被 OS 回收，佇列非空         | 快照已在磁碟上（寫入發生在送出之前）。重開後讀回，使用者回到該場比賽即重送                      |
| 讀回途中使用者已經記了新球       | `rehydrated` 依 `id` 合併、記憶體優先，新球不被覆蓋                                             |
| 儲存不可用（私密瀏覽、配額用盡） | adapter reject，listener catch 並記 log，app 繼續運作。使用者不會知道——已登記為 residual risk   |
| 讀回的項目是 5xx／離線           | 排程立刻重送                                                                                    |
| 讀回的項目是 4xx（含 401）       | 不自動重送。留在佇列、指示器顯示未同步，使用者可用既有的重試手勢送出；超過七天丟棄              |
| 全部項目都過期                   | 不 dispatch，因此寫回的 listener 不會執行——改為直接清除，否則死掉的快照每次啟動重讀重丟         |
| 佇列為空時啟動                   | 不發出任何請求                                                                                  |
| 兩個分頁同時開著同一場           | 各自重送，但 upsert 是 idempotent，不產生重複，只是多打一次 API。不處理，屬 `offline-recording` |

## Testing strategy

本 Change 沒有 UI 變更，因此不受「agent 無法對需登入頁面截圖」那個既有阻礙影響。

**接線本身也要測到。** 其餘測試都是把假的 storage 交給 `makeStore`、再自己呼叫 `restorePendingWrites`，於是「在真實 app 裡到底有沒有生效」的兩個接線點——`makeStore()` 不帶參數時是否真的接上 localStorage、provider 掛載時是否真的讀回——反而沒有被涵蓋。jsdom 有真的 `localStorage`，所以兩者都測得到。

**frontend（jsdom 有 localStorage）**：讀回並重送、四種磁碟內容各自的處置（含「新版本不清除」）、`rehydrated` 的合併語意、空佇列不發請求、儲存拋錯時 app 不致命、過期規則對可重試與不可重試兩類的分別處置。合併語意與過期規則是最值得釘住的兩項——前者是非同步簽章帶來的、唯一會靜默弄丟資料的路徑，後者是唯一會主動刪除資料的路徑。

**integration**：不需要新增。「重送已成功的 entry 為 no-op，不產生重複」已由 `retryable-entry-writes` 交付的 `game-entry-writes.itest.ts` 覆蓋，而該層的 auth 是以 DI double 取代的，不需要真實 session。

**人工**：真實 app 被 OS 回收後重啟，特別是 iOS PWA。這一項沒有任何自動化層能證明，屬交付驗收。

## Plan versus actual

五處與核准計畫不同。第 3 與第 5 處在驗收前經 Ingest 修正——程式碼與規格都改了；其餘三處是文件落後於程式碼，已在同一輪補回規格，Archive 時只需複核。

<ol>
  <li>
    **磁碟上多兩個欄位。** D2 原本列的形狀是 `{ entry, gameId, setIndex, lastError? }`，實作另存 `firstFailedAt`。S04 的「超過七天」需要一個時間基準，而那四個欄位裡沒有——規格的疏漏，不是實作越界。D2 已於 Ingest 一併補上。
  </li>
  <li>
    **listener 多聽一個 action。** S02 列了三個，實作聽四個：`rehydrated` 也改動佇列內容，聽它才能讓被過期規則縮短的佇列寫回磁碟。S02 排除的是「無關的 dispatch」，這一個不是。已改寫該條驗收條件。
  </li>
  <li>
    **兩個 predicate 收斂為一個標準（Ingest）。** 原本 `isRetryableStatus`（能不能再送）之外另有 `isWorthAttemptingAgain`，兩者只在 401 上分歧，理由是「登入是整頁 redirect，重啟往往正是修好 session 的那件事」。開發者判定系統只需要一種標準，實作照辦：401 不再於重啟後自動重送。代價很小——在 F1 之下本來就要等使用者走回那場比賽，而那時 SyncIndicator 會顯示未同步、重試手勢已經在那裡。D2 的 decision 與 alternatives、S03 與 S04 的驗收條件一併更新。
  </li>
  <li>
    **storage key 的名字變了。** D2 與 Design 圖寫的是 `pending-writes:v1`，實作用 `pending-writes`。理由見上一節，這不只是改名。已於 Ingest 更新 D2 與圖。
  </li>
  <li>
    **寫入的排序機制與 Design 描述的不同（Ingest）。** Design 原本寫「寫入串成一條 promise chain」。鏈會把每一次寫入都推遲一個 microtask，破壞「記一顆球到落地之間沒有窗口」這個前提。實作改為：閒置時直接寫入（同步 store 因此在函式返回前完成），進行中則只保留最新一份待寫快照——因為快照是完整的，中間那幾份本來就不值得寫。結果比計畫**更嚴格**，不是放寬。Design 的 Contracts、時序圖與 S02 的驗收條件已更新。
  </li>
</ol>

### 那項無法自動化的檢查

**「真實 app 被 OS 回收後重啟」沒有任何自動化層能證明**，特別是 iOS 的主畫面 PWA。它驗的是一個平台假設：iOS 回收 standalone web app 之後，localStorage 是否仍然存在。

**驗收時這項尚未執行**，於合併後在 `dev` 的 preview 部署上進行——不在 production，因為這個 Change 的主題就是資料完整性，讓它第一次被真正執行的場合不該是面對真實使用者資料的環境。

之所以可以在這項完成前合併：**它失敗不會造成回歸**。若 iOS 沒有保住 localStorage，這個 Change 只是在該平台上沒有帶來好處——記憶體中的佇列行為與合併前完全相同，沒有需要回退的東西。其餘部分由測試涵蓋，包含接線本身：`makeStore()` 是否真的接上 localStorage、provider 掛載時是否真的讀回。

#### 結果：通過

在 `dev` preview（合併 commit `ff6c0a47`）上，以加到主畫面的 iOS PWA 執行：開飛航模式、記數球、由 app switcher 強制關閉、重開後走回該場比賽。

裝置端：**那些球都還在畫面上**，SyncIndicator 維持未同步；關閉飛航後**未經手動介入即自行送出**。

| 檢查                                  | 結果                |
| ------------------------------------- | ------------------- |

| 同一 `id` 是否配到不同 `seq`          | 否                  |
| `seq` 是否單調遞增                    | 是                  |

## Follow-ups

- 上表第 1、2 項在本輪已一併寫入 D2 與 S02，Archive 時只需複核而非補寫。
- 佇列的重試狀態實際上是 `(gameId, setIndex)` 群組層級的事實卻複製到每一筆 entry 上，已獨立登記。本 Change 不持久化那些欄位，因此兩者互不影響。
- 使用者仍無法在比賽畫面之外看到有未送出的球，也無法主動捨棄一筆註定失敗的 entry；兩者都屬 `offline-recording`。
- ~~在 `dev` preview 上完成 iOS PWA 的回收後重啟檢查~~ **已完成並通過**，結果見上節。
- 該次驗證發現的新缺陷：**離線期間 SyncIndicator 全程顯示轉圈的「同步中」**。`deriveSyncStatus` 以 `nextAttemptAt !== null` 判定 syncing，而每次 `enqueued` 都會重設它，所以持續記球時狀態永遠不會走到 unsynced；加上 syncing 的圖示是 Spinner，讀起來像系統卡住。本 Change 讓資料變安全了，UI 卻沒有任何狀態把這個保證說出口。已獨立登記，與本 Change 的佇列行為無關，只在顯示層。

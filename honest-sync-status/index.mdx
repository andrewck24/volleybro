<TLDR>
  離線記球時指示器全程轉圈，看起來像卡住了。追下去發現轉圈只是症狀：指示器會說三種不同的假話——spinner
  承諾了它兌現不了的進度，警告色掛在會自己好的情況上，而「已保存」在
  localStorage 不可寫時根本是謊話。本 Change
  讓它說的每一句話都是真的：狀態改由實測失敗判定，navigator.onLine
  退為純文案訊號，警告語氣改掛不可重試，並新增一個本機儲存不可用的第一級狀態。
</TLDR>


## Context

`retryable-queue-persistence` 交付後的 iOS PWA 人工驗證，結論是持久化本身通過：飛航模式下記球、強制關閉、重開後球都在，恢復連線後未經手動介入即自行送出，資料庫比對顯示每筆一份、無重複。

但驗證過程中，整段離線期間指示器都顯示轉圈的「同步中」。**`retryable-queue-persistence` 讓資料變安全了，UI 卻沒有任何狀態把這個保證說出口。**

這張 Change 從「離線時別轉圈」開始，收斂後變成一個更大的命題：**指示器說的每一句話都必須是真的。** 目前有三句不是。

第一句是 spinner。`deriveSyncStatus` 以 `pending.some((p) => p.nextAttemptAt !== null)` 判定 syncing，而 `enqueued` 每次入列都設 `nextAttemptAt: Date.now()`——離線時每記一球就把整組重置回 syncing。值得說清楚的是：**「等待下一次重試」確實屬於重試生命週期，這個判斷本身不算錯。** 錯的是 spinner 隱含的「稍等即可」——線上時那是真的，兩百毫秒後就成功了；離線時它在重新連上網之前永遠不會兌現。

第二句是警告色。`unsynced` 配 warning 色與驚嘆號，觸發條件是「退避表用盡」。但那類 entry 會自己好——下一顆球的 flush 或 `online` 事件都會帶它送出。真正會遺失的是不可重試的那一類（4xx），而它們今天跟前者共用同一個狀態。

第三句還沒被說出口，是這張 Change 自己造出來的。今天 UI 說「N 筆未同步」，即使 `localStorage` 壞掉那句話仍為真；本 Change 要把它升級成「已保存」，**而那句話在 store 不可寫時是假的**。`retryable-queue-persistence` 的 D4 已經把這條記為 residual risk，並寫下「誠實的做法最終是告訴他們，只是要說出來，得先有一個地方可以說」。這張 Change 造出了那個地方，也造出了非說不可的理由。

還有一件事值得記下來：`retryable-entry-writes` 的 D2 在否決「只靠 piggyback、不做背景退避」時，已經預言過這個失效模式——「一個宣稱同步仍在進行中的指示器會是不真實的」。它用退避表把時間上界壓到約二十二秒。**沒被預見的是連續記球會不斷把那個上界重設，所以它在真實節奏下從未生效。** 這不是沒人想過的疏漏，是一個被想過、被設了上界、而上界在真實使用節奏下失效的案例。

## Goals

- 指示器在每一種狀態下所呈現的圖示、顏色與文字，都與系統當下的真實處境一致。
- 使用者在離線時知道自己的紀錄是安全的，而不只是知道它「還沒同步」。
- 警告語氣只出現在使用者真的需要做點什麼的時候。
- 「網路顯示已連線但到不了伺服器」與飛航模式獲得同等對待——前者在球場上更常發生。
- 本機儲存不可用這個既有的 residual risk 第一次對使用者可見，且在他還有選擇的時候可見。

## Non-goals

- **不做 outbox、跨場比賽可見性、衝突重放。** 那是 `offline-recording`。
- **不改重試政策。** `isRetryableStatus`（`status >= 500`）維持為唯一標準，不開第二套判斷。
- **不新增慢速輪詢。** 讓「會自動送出」在連線異常時也成真需要一個不終止的重試機制，那是 outbox 的定義。理由與代價見 D4。
- **不做不可重試 entry 的導航與刪除。** 已獨立登記為後續工作「不可重試 entry 的導向與刪除」，並以本 Change 為前置。
- **不改重試狀態的形狀。** 群組化屬後續工作「重試狀態改以 (game, set) 群組為單位」，本 Change 先於它——理由見下方排序。
- **不改儲存選型。** `localStorage` 對 IndexedDB 的取捨由 `retryable-queue-persistence` 的 D1 決定，本 Change 不重開；理由見 D3。
- **不偵測私密瀏覽。** 那是隱私功能，瀏覽器會主動封鎖偵測手法。代價是私密瀏覽下不會有警告——見 D3 與 Design 的 residual risk。

## Change boundaries

- **一定在內**：`deriveSyncStatus` 的五條有序條件、`hasFailedWrite` 的判準、`SyncIndicator` 的圖示／文案／版面／重試按鈕、一個讀取 `navigator.onLine` 的 hook。
- **在內**：`pendingWrites` slice 新增一個表示本機儲存不可用的布林欄位，以及開機時設定它的探測。這是本 Change 唯一新增的狀態，且它有兩個寫入者——開機探測與既有的 listener catch。
- **在內**：移除 `flushingGameIds`。它今天活著的唯一理由是舊的 `deriveSyncStatus` 要讀它；新模型不讀，它就成了本 Change 自己造成的孤兒。**這個移除是狀態模型改變的證據**：舊模型需要知道「有沒有 request 在飛」，新模型不需要。
- **在內（討論中浮現）**：`retryable-entry-writes` 的 S08 所建立的 per-rally 失敗標記收窄。它與指示器必須讀同一個判準，否則兩個表面會對同一批 entry 給出矛盾的語氣。
- **不在內**：佇列的送出、重試、退避、過期行為。`enqueued`、`flushSucceeded`、`flushFailed`、`retryRequested`、`rehydrated`、`hasExpired`、`nextAttemptDelayMs` 的語意全部不動。
- **不在內**：rally 端點、repository、SWR 設定、Entry List 的互動（只有標記的觸發條件改變，控制項本身不動）。

## Impact

Affected capabilities：`game-recording/rally-recording`、`game-recording/persistence`。兩者都不新增 sub-capability——本 Change 改變的是既有能力對自己處境的陳述，不是能力本身。

`game-recording/rally-recording` 的行為契約不變——記球的手勢、樂觀推進、送出的時機全部照舊。改變的是**系統對自己處境的陳述**：同一組佇列事實，被投影成一組不再說謊的狀態。

`game-recording/persistence` 第一次獲得一個對使用者可見的可用性契約。在此之前，「本機儲存是否可用」只存在於 console warning 裡；此後它是一個會出現在畫面上的狀態，而且在第一顆球被記錄之前就會出現。

## Alternatives considered

Design 頁完整記錄各組替代方案與否決理由。Overview 層級只記結論方向：

- **新增一個由 `navigator.onLine` 驅動的 offline 狀態**（原始票的方向）——只修好飛航模式。裝置連上網路卻到不了伺服器時它回報 `true`，指示器落回 syncing 繼續轉圈。它挑了比較好偵測的情境，不是比較常發生的。
- **把 syncing 收窄為「真的有 request 在飛」**——離線期間會在退避空檔與嘗試瞬間之間反覆切換，反而製造抖動；退避用盡後仍落到警告語氣，語氣依舊不對。
- **以計時器實作抖動門檻**（Notion 用三十秒）——需要一個 `setTimeout` 在門檻到期時強制 re-render。次數門檻用既有的 dispatch 推動狀態，效果相同而無新機制。而三十秒對在球與球之間抬頭掃一眼的記錄員過長。
- **偵測並封鎖私密瀏覽**——瀏覽器廠商持續封鎖偵測手法，且 app 在私密瀏覽下完全可用，失去的只是一個降級的保證。直接測「寫得進去嗎」涵蓋所有當下就失敗的成因；「現在可用、之後消失」的那幾種偵測不到。
- **改用 IndexedDB**——五個成因只解掉配額一項；且它的非同步 transaction 在「app 被回收」時可能尚未 commit，那正是持久化要存活的情境。
- **加一道慢速輪詢讓兩種情境的承諾都成真**——動到重試機制，並帶進「輪詢什麼時候停」這個新的生命週期問題。那是 outbox 要回答的。
- **兩種情境都顯示或都不顯示重試按鈕**——都顯示會給出一顆必定失敗的按鈕；都不顯示則讓連線異常的使用者完全沒有出路。Google Docs 與 Notion 不提供這顆按鈕，是因為它們的背景重試永不終止，那是我們沒有的前提。

## Decisions

| --- | -------------------------------- | ------------------------------------------------------------- |
| D1  | 狀態由什麼訊號判定               | 實測失敗（`attempts`）；`navigator.onLine` 只選文案           |
| D2  | 警告語氣掛在什麼條件上           | 不可重試，per-rally 標記一併收窄                              |
| D3  | 本機儲存不可用時誰說、什麼時候說 | 升為第一級狀態，開機就探測                                    |
| D4  | 誰負責偵測「伺服器恢復」         | 暫時交給使用者的手指，期限記在 `offline-recording` 的驗收條件 |

## 排序

**先於「重試狀態群組化」。** 該後續工作將重試狀態改以 `(game, set)` 群組為單位，會改變 `attempts` 與 `lastError` 的持有位置，而本 Change 的狀態模型全部讀這兩個欄位。先做本 Change，「重試狀態群組化」 面對的是一個已移除死欄位、狀態語意已釐清的 slice；反過來則須先在一個已知錯誤的狀態模型上建群組化，再重做指示器。

## Revisit triggers

- **重試狀態群組化落地**：`attempts >= 2` 的門檻語意由「單一 entry」變為「群組」，`deriveSyncStatus` 的條件式須重新檢視。
- **「不可重試 entry 的導向與刪除」交付**：警告狀態自此有可執行的動作，其語氣與文案應一併重估。
- **`offline-recording` 的持久重播上線**：終局狀態消失，手動重試按鈕失去存在理由，應移除而非留著成為第二條路徑。同時 D3 的儲存不可用會從降級模式升級為功能無法運作的理由。
- **rally 端點補上 request schema**：400 大量增加，「不可重試」從罕見變成常態，呈現密度與七天過期規則都要重估。
- **`navigator.storage.persist()` 在 iOS PWA 的授予條件被實地確認**：確認可靠則可關閉兩條 residual risk；確認不可靠則該移除它，而不是留著假裝有用。
- **現場出現三秒門檻過短或過長的證據**：過短表現為打嗝仍造成圖示閃動，過長表現為使用者在門檻成立前就已經開始擔心。

## Design

<TLDR>
  一道由上而下的關卡，第一個命中者勝出。風險最高的排最前面，最樂觀的排最後面——所以任何一種不確定都不可能被說成「同步中」。`navigator.onLine`
  站在關卡之外，只在其中一關決定要用哪一種措辭。
</TLDR>

## Adopted shape

指示器不儲存任何狀態，它是佇列事實加上一個儲存可用性旗標的投影。判斷是一道有序關卡：**由最壞的可能性往最好的可能性走**，因為每一關代表的風險都比下一關高，而一個被誤判為樂觀的狀態正是本 Change 要消除的東西。

順序不是任意的。關卡 1 排在關卡 2 之前，是因為「隱藏」的原意是**沒有任何風險**，而不是佇列為空——store 不可寫時即使一球未記，風險已經存在。關卡 1 排在關卡 3 之前，是因為前者危及整個佇列而後者只危及特定幾筆；被壓下去的資訊不會消失，Entry List 上的 per-rally 標記獨立於這道優先序呈現。而 spinner 被放到最後一關，正是因為它是最樂觀的陳述，任何一種已知的不確定都應該在抵達它之前被攔下來。

## Contracts

判斷式與文案都畫在上圖裡，因為那是規格本身而不是規格的插圖。這一節只講圖上看不出來的三件事。

**`navigator.onLine` 不在判斷裡。** 它在關卡 4 命中之後才被讀取，而那時「送不出去」已經是既定事實。兩種措辭因此都是真話：`false` 是它唯一可靠的方向；`true` 時「送不出去」的依據是失敗紀錄，不是它。

**`attempts` 是實測，不是推測。** 它記錄的是真的發出過請求、真的收到失敗。這使得「飛航模式」與「連上網路卻到不了伺服器」走同一條路——後者在球場上更常發生。門檻用次數而非時間：`attempts` 遞增本身就是一次 dispatch，狀態會自己翻，不需要任何 `setTimeout` 與其清理責任。

**同一個判準供兩個表面使用。** `hasFailedWrite` 改讀關卡 3 的判斷式，使指示器與 Entry List 的 per-row 標記不可能對同一筆 entry 給出矛盾的語氣。這**收窄了 `retryable-entry-writes` 的 S08 已驗收行為**——該切片的判準是「嘗試用盡」，此後只有不可重試者被標記。被收窄掉的那一類會自己好，不需要使用者做任何事。

`flushingGameIds` 在此模型下失去唯一的消費者，連同 `flushStarted` 一併移除。它是本 Change 改變狀態模型的證據：舊模型需要知道「有沒有 request 在飛」，新模型不需要。

## Testing strategy

判斷式是純函式，五道關卡與其邊界（尤其是門檻的 1 與 2、以及「不可重試」與「退避用盡」的區隔）在 `deriveSyncStatus` 的單元測試中窮舉，不需要渲染。

呈現層的測試針對可觀察的結果而非實作：狀態 4 不得渲染 `Spinner`、狀態 1 在佇列為空時仍須渲染、重試按鈕只在單一分支出現、`aria-label` 帶完整句子。`useIsOnline` 以派送 `online` / `offline` 事件驅動。

移除 `flushingGameIds` 是行為中性的，其現有測試連同被移除的 action 一併刪除——保留它們會是在測一個不再存在的概念。

`navigator.storage.persist()` 只驗證「被呼叫一次」。它的實際效果無法在測試中觀察，宣稱能觀察就是本 Change 正在消除的那種假話。

真實裝置上的觀感屬 developer acceptance，不由自動化測試承擔。

| 恢復連線後回到隱藏                     | **失敗**，見發現四               |
| 私密瀏覽顯示無法保存                   | **失敗**，見發現五               |
| 封鎖 Cookie 顯示無法保存（第二輪改用） | **無法執行**，見發現七           |

「連線有問題」是本 Change 為之擴大範圍的那個情境——D1 的整個論證建立在它比飛航模式更常見之上。經過兩輪嘗試仍無法穩定重現，**永久記為未驗證的路徑**，不算通過。

它由單元測試覆蓋：`deriveSyncStatus` 對「`navigator.onLine` 為 `true` 但仍達失敗門檻」有明確案例，指示器測試也涵蓋兩種文案與重試按鈕的顯示條件。缺的是真機上「訊號滿格卻送不出去」這個組合的實地確認。這是本 Change 最主要的主張唯一沒有現場證據的地方，下一個碰到相關程式碼的人應該知道。

### 發現四：恢復連線時整頁重載（既有缺陷，不屬本 Change）

`SerwistProvider` 的 `reloadOnOnline` 預設為 `true`，`layout.tsx` 未傳該 prop，於是每一次 `online` 事件都呼叫 `location.reload()`。記錄途中復網會清掉當前局與正在編輯的球，實測通常需要重開 app 才能繼續。

未送出的球不受影響——佇列在磁碟上。這個缺陷比本 Change 更早存在，只是「恢復連線」這一刻在此之前沒有人盯著看。已獨立成票並修正（`reloadOnOnline={false}`），不併入本 Change。

### 發現五：探測看不到私密瀏覽——**已核准的設計判斷錯誤**

D3 在 Propose 階段寫著「Safari 私密模式發放的是關掉分頁就消失的配額而不拋錯，所以讀回那一半能抓到」。**那句話是錯的。**

私密／無痕模式下 `localStorage` 在同一個 session 內完全正常：寫得進去、讀得回來、刪得掉。探測三步全部成功，於是回報健康。它能抓到的只有**當下就失敗**的 store——配額用盡、站台資料被封鎖。「現在可用、關掉才消失」在原理上無法被同步探測看見。

而偵測私密瀏覽本身，正是 D3 明確否決的事。

處置為 Ingest：D3 的 context、decision、consequences 與 revisit trigger 全數更正，`unwritable` 的涵蓋範圍由五個成因收窄為兩個，其餘三個移入 residual risk；Design 的 Scenario 增列「私密瀏覽不會有警告」為預期行為；驗收腳本第五項改為封鎖所有 Cookie。**沒有任何程式碼或文案被刪除**——狀態與它說的話都仍然成立，改變的是文件對它涵蓋範圍的宣稱。

一句話：這張以「不要宣稱超過你所知道的」為主題的 Change，自己在 D3 裡宣稱了做不到的事。

### 發現六：popover 字級低於排版級距（a11y）

popover 的說明文字用 `text-[11px]`，重試按鈕也是。設計系統的排版級距**最小只到 `text-xs`（0.75rem / 12px）**，沒有更小的定義——所以那是跑到級距外面，而不只是偏小。

更實際的問題是 px 字面值**不隨使用者的瀏覽器字級偏好縮放**，rem 會。使用者把預設字級調大，那兩處不會跟著變。

已改為級距內的值：標題 `text-sm`、說明 `text-xs`、重試按鈕依設計系統的按鈕規則採 `h-9` / `rounded-md` / `text-sm`。兩份設計系統文件都沒有寫下級距下限，所以也沒有東西能擋住這個錯誤——該規則已補入 `docs/design-system.md`，於文件分支交付。

### 發現七：狀態 1 沒有可觸及的觸發條件——只剩配額

第二輪把驗收條件由私密瀏覽改為「封鎖所有 Cookie」，結果**登入本身就失敗**：Cookie 被封鎖時 Better Auth 建不起 session，使用者停在登入頁，永遠到不了記錄畫面。這個成因探測抓得到，但沒有人看得到。

| 成因                  | 探測抓得到 | 使用者到得了記錄畫面 |
| --------------------- | ---------- | -------------------- |
| 封鎖站台資料 / Cookie | 是         | **否**——登入先失敗   |
| 配額用盡              | 是         | 是                   |

所以**開機探測唯一還會觸發的情境是「開 app 時配額就已經滿了」**。而 listener 的 catch 會在第一顆球入列時抓到同一件事——探測買到的是「第一顆球之前」而非「第一顆球當下」，一顆球的差距。保留它是開發者的決定：那顆球記下去之後才被告知，感受完全不同。D3 對它價值的設想比實際大得多，已第三度更正。

**文案同時改為指名配額。** 本 app 的 `localStorage` 只有佇列一個寫入者（表單草稿在 `sessionStorage`），塞滿它的幾乎必然是自己累積的未送出 entry——而佇列跨比賽、送出卻是 game-scoped，這正是 `retryable-queue-persistence` 的 D3 記下的「送達依賴使用者回到該場比賽」的長期後果。兩張 Change 在這裡接上了。文案依「是否有其他比賽的未送出 entry」分岔，才不會叫人去找不存在的比賽。

### 第二輪審查：Ingest 改了文件卻沒改程式碼

Spec 軸抓到最嚴重的一項：`pending-writes-storage.ts` 的 `probe` 註解**仍寫著發現五判定為錯的那句話**——「Safari 私密模式發放的是關掉分頁就消失的配額而不拋錯」。Ingest 更正了 D3 與三份 MDX，卻漏掉了原始碼裡同一個宣稱，而那是最會被相信的一份。同一句話也殘留在本頁的 FileTour 裡，與四節之外的發現五直接矛盾。

其餘同源的殘留一併更正：D3 的 context 與 consequences 對「哪兩個成因當下就失敗」說法不一致；`design.mdx` 的 risk 仍把站台資料被封鎖算進涵蓋範圍；D3 與 Overview 都還留著「配額在此規模下最不可能發生」，而配額如今是唯一可觸及的成因；D3 宣稱真機驗證涵蓋 Chrome，實際只在 iOS PWA 上執行。S02 的驗收條件是唯一沒隨 Ingest 更新的切片，仍描述舊的固定兩行文案。Changeset 的最後一條也仍在講「切換瀏覽器模式」這個探測看不到的成因。

Standards 軸的發現集中在新的註解規則第一次被實際套用：兩處 decision reference 在註解已把理由講完之後仍附上，四處測試註解在重新論證 Blueprint 擁有的決策（其中一處與原始碼註解實質重複），`failTwice` 與 Storybook story 各自硬編門檻 `2` 而非引用 `PENDING_WRITE_UNSENT_ATTEMPTS`。`copyFor` 的 `unwritable` 分支則收斂為共用 title 加三元 detail——兩支原本只有 detail 不同。

**未採納一項**：Feature Envy 的判斷，指 `pendingCount` 與 `othersPending` 應移入 `deriveSyncStatus`。兩者是呈現用的衍生值——一個印在角標、一個決定講哪句話；`deriveSyncStatus` 回答的是佇列語意。移進去等於讓佇列模組知道 UI 要顯示什麼。

**延後兩項**：五處未以 Change slug 限定的 decision id，以及三處長於程式碼的常數註解，全部來自更早的兩張 Change。註解規則是本輪才寫下的，回頭套用整個檔案庫是獨立工作。移除本 Change 自己那兩處之後，每個檔案只剩它自己那張 Change 的 id，歧義風險回到原本的水準。

## Follow-ups

- **不可重試 entry 的導向與刪除**：以本 Change 為前置，補上從指示器到 Entry List 的路，以及丟棄動作。本 Change 交付後，警告狀態第一次成為一個獨立可辨識的狀態，那張票的前提因此成立。
- **重試狀態群組化**：`attempts` 與 `lastError` 的持有位置將由 entry 移至 (game, set) 群組，`PENDING_WRITE_UNSENT_ATTEMPTS` 的門檻語意屆時由「單一 entry」變為「群組」，`deriveSyncStatus` 須重新檢視。
- **`navigator.storage.persist()` 在 iOS PWA 的授予條件**：待實地確認。確認可靠則可關閉兩條 residual risk；確認不可靠則應移除那三行，而不是留著假裝有用。

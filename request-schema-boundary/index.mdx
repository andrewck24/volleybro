## Context

`await req.json()` 直接往下送，game 的五條寫入路由對 request body 零驗證：

```
POST /api/games
POST /api/games/:id/sets
PUT  /api/games/:id/sets
PUT  /api/games/:id/sets/rallies
POST /api/games/:id/sets/substitutions
```

team 與 player 的九個 handler 全部都有 zod schema。**game 是唯一的例外，而且是五條全缺。**

### 三個具體後果

**body 不是陣列時直接 500。** `record-rallies.usecase.ts` 的 `rallies.forEach(...)` 收到 `{}` 會丟 `TypeError`，被 `withErrorHandler` 包成 `UnexpectedError`。客戶端拿到的是「發生未預期的錯誤」，而它其實只是送錯了形狀。

**rally 的 `player` 子物件完全沒人驗。** `rally-entry-validation` 建立的 `validateRallyEntry` 只看 `type` / `num` / `score` / `win`，沒碰 `player = { id, zone }`——`zone` 可以是任何數字，`id` 可以是任何字串。

關於 `id` 有一件事需要講清楚，因為它容易被誤讀成「空字串該被擋下」。空字串是**記錄員沒有指派球員給該側時的現行編碼**：對手得分時我方沒有球員可指，Redux 的 draft 仍帶著這個欄位與它的未設定佔位值。**拒絕它會讓對手得分的球記不了，所以邊界必須接受它——但接受不等於原樣放行。**

這個 repo 已經在三個地方說「沒有球員」就是 `null`：lineup 用 `nullableObjectId`、repository 的 `toPlayerRef` 回傳 `null`、`deriveSetStats` 讀到的型別本來就是 `{ id?: string | null }`。只有 `RallyDetail.player.id` 宣告成 `string`，跟其他三處不一致——那是與 `Team` 同一類的型別謊言。所以邊界接受 `""` 之後把它映射成 `null`，`RallyDetail.player.id` 改為 `string | null`。wire format 的佔位值由邊界吸收，內層只看得到一種「沒有球員」。

lineup 的 `player.id` 則相反：那裡的空字串沒有任何合法意義，既有的 `objectId` refine 擋得住它，本 Change 讓 `POST/PUT /sets` 也用上同一份定義。

**慣例分裂成三套。** schema 住在三個地方，而且驗證發生在兩個層：

| 位置                   | 數量 | 驗證發生在                            |
| ---------------------- | ---- | ------------------------------------- |
| `src/lib/validations/` | 6    | route                                 |
| route 檔內 inline      | 2    | route                                 |
| controller 內          | 1    | controller，且用 `safeParse` 手動包裝 |
| 沒有                   | 5    | —                                     |

第三列值得說清楚：`profile.controller.ts` 的 15 行 `safeParse` 加手寫 `ValidationError`，產生的結果與 `withErrorHandler` 對 `ZodError` 的既有處理**完全相同**。它不是一個做法，是一段沒人回頭刪的重複實作。

### 型別在說謊

替 `POST /api/games` 寫 schema 時撞上一件事：**app 自己送出的 payload 不滿足 `Game["teams"]` 的型別。**

`Team` 宣告 `id` / `players` / `staffs` 皆必填，但表單只送 `home: { id, name, players, lineup }` 與 `away: { name }`。而 `teamSchema` 沒有 `{ _id: false }`，所以 mongoose 替 away 自動生成一個宣告為 `ref: "Team"`、卻不指向任何 Team 的 `_id`。

同一條 payload 上還有兩個多餘欄位（`players[].list`、`info.teams`）與一個真正的型別錯誤（`weather.temperature` 送字串而型別是數字），三者都在 strip 之下安靜存在了很久。

**在邊界 parse 的全部價值來自「parse 完之後的型別是可信的」。如果那個型別本身在說謊，加 schema 只是把謊言正式化。** 所以本 Change 必須先把型別改成與現實一致。

## Goals

- game 的五條寫入路由在邊界拒絕形狀錯誤的 body，回 400 並指出欄位，而不是讓非法值一路穿到儲存層。
- repo 有一套可指認的 request 驗證慣例，第四種做法不會憑空出現。
- 「什麼構成一筆合法的請求」只有一份定義。
- `Game["teams"]` 的型別與 app 實際送出的內容一致，不需要任何 cast。

## Non-goals

- **不處理 server 對自己 response 的 `.parse()`。** 8 處 `PlayerSchema.parse()` 驗的是我們自己產生的資料，失敗代表資料層壞了卻被回報成 400。方向相反、失敗語意相反，另開一票。
- **不把 controller 變成 interface adapter。** 那會動全部 14 個 handler 與 15 個 controller，並牴觸一份已封存的 spec。本 Change 的 route 層驗證是過渡；終局已承諾，由 `api-route-restructure` 承接，且 schema 檔案不需要再搬。
- **不加 import 邊界的 lint 規則。** 每個候選工具都以路徑判層，而 `src/lib/` 仍裝著三個層的程式碼。本 Change 只消掉其中一層。
- **不把 `scoringMoves` 下沉到 entities。** 它混著 domain 欄位與 zh-TW 顯示字串，拆分需要一個獨立的設計決定。
- **不加跨欄位自洽檢查，也不移除 rally 的跨欄位冗餘。** `num` 決定 `type` 與 `win`，三者可能矛盾。那條檢查是排球規則，屬 entity，而 entity 要查 `scoringMoves` 仍會成環——它**仍然以那張表下沉為前置**，本 Change 不改變該順序。
- **不修 `docs/specs/api-objectid-validation/spec.md`。** 它是不可變的歷史快照，即使其 `@trace` 會因本 Change 搬檔案而指向舊路徑。現行知識改由 Blueprint 承載。

## Change boundaries

- **一定在內**：五條 game route、`src/interface/validations/`（新增 `game.ts`，遷入 `team.ts` 與 `player.ts`）、11 個 importer、`src/entities/game.ts` 的 `Team` / `Match` / `RallyDetail` 型別與 `validateRallyEntry` / `validateLineupPlayers`、`record-rallies.usecase.ts` 的呼叫點、`create-player.usecase.ts` 的 input 型別、`src/components/game/new/index.tsx` 的三處 payload 修正。
- **後來納入**：`game.repository.mongo.ts` 的 `toLineupRead` 與 `team.repository.mongo.ts` 的 `toTeam`。兩條讀取路徑原本都展開 `...lineup`，把 lineup subdocument 的 Mongoose `_id` 一起交給前端（`lineupSchema` 是唯一沒有 `{ _id: false }` 的 sub-schema）；前端把該值原封不動送回時，新的 `.strict()` 會擋下它。這個耦合在 S04 之前不存在，是 `.strict()` 本身製造出來的，所以留在本 Change 而非另開一票。
- **後來納入**：`jest.setup.backend.ts` 與 `src/test-utils/route-request.ts`。十三個 route test 各自帶著逐字元相同的 `next/server` / `next/headers` stub 與 request literal；本 Change 是製造出這批測試的那張票，所以收斂它們屬本 Change。
- **後來納入**：`src/lib/features/game/new-game-form.ts` 與 `src/lib/features/game/types.ts` 的 `SetOptionsFormSchema`。新增比賽的 payload 原本在 component 裡當場拼出來，沒有任何東西能問「表單的產出滿足伺服器嗎」——那正是 `away.name` 缺陷藏身之處。抽成模組讓那個問題可測；測試接著抓出 `SetOptionsFormSchema` 與 `Set.options.time` 的不一致，依 D2 由 client 收緊。
- **不在內**：`withErrorHandler` 的錯誤映射邏輯、`assertObjectId` 的實作與位置、repository 的任何**寫入**路徑、mongoose 的 `teamSchema._id` 設定、response 端的 `.parse()`。

## Impact

- `platform/clean-architecture`——request 驗證取得單一慣例；application 層對外的相依歸零；`src/lib/` 少掉一層混雜。
- `game-recording/rally-recording`——rally 的形狀規則從 entity 移到邊界，並涵蓋先前無人驗的 `player` 子物件；「沒有球員」在內層只剩 `null` 一種表示。
- `game-recording/persistence`——`Team` 與 `Match` 的型別改為與實際寫入一致；`Match.weather` 移除。

## Revisit triggers

- controller 成為 interface adapter：`.parse()` 的呼叫點移入 controller，schema 位置不變。
- 出現繞過 route 的第二個寫入者：D3 的「邊界是唯一入口」前提失效。
- `src/lib/` 的層歸屬清理完成：import 邊界規則變得可表達，慣例從 review 把關轉為工具強制。
- 前後端變成獨立發布：D4 的 `.strict()` 對向後相容的影響需要重新評估。
- 對手可連結為真實隊伍：D5 的選填欄位開始被填滿。

## Adopted shape

每一層只回答一個問題，而且只有一層回答它。

| 層                        | 回答什麼                      | 例子                                                       |
| ------------------------- | ----------------------------- | ---------------------------------------------------------- |
| route（`assertObjectId`） | 路徑參數是它宣稱的型別嗎      | `gameId` 是 24 位十六進位                                  |
| route（`Schema.parse`）   | request body 是它宣稱的型別嗎 | `type` 是 `MoveType`、`num` 是表的合法索引、沒有未宣告欄位 |
| use case                  | 這個人可以做這件事嗎          | `verifyTeamRole`                                           |
| entity                    | 這符合排球與 Game 的規則嗎    | `validateLineupPlayers` 的 roster 比對                     |
| repository                | 儲存機制自己的坑              | `anonymous` 檢查（arrayFilters 對 `null` 的匹配風險）      |

前兩列合起來是「這個請求的每個值都是它宣稱的型別」，所以它們同層、同機制——`assertObjectId` 拋 `ValidationError`、`Schema.parse` 拋 `ZodError`，都由 `withErrorHandler` 轉成 400。這不是新發明：path param 那一半在 `api-objectid-guards` 就已經這樣定案，本 Change 只是把 body 那一半補上。

### 一個被撤回的判準

本 Change 一度用「這個檢查需不需要資料庫狀態」來分層。它很好用，也給出了正確的結論，但**它不是 Clean Architecture 的判準**——CA 問的是規則的射程，而狀態相依性只是與之相關的一個表徵。兩個方向都會誤判：

- **stateless 卻是領域規則**：`away.num` 必須在 `scoringMoves[home.num].outcome` 內。這是排球規則（主隊扣球得分時，客隊那一側只可能是特定幾種動作），卻只需要查表。
- **stateful 卻不是領域規則**：「這個 `gameId` 存在嗎」。需要資料庫，但那是 404，不是業務規則。

它在 `validateRallyEntry` 上恰好答對，是因為那四條本來就不是領域規則——**正確結論配錯誤理由，會在下一個案例上失效**。所以判準改為上方 TLDR 的兩問。

### 為什麼 `validateRallyEntry` 整個移走，而 `validateLineupPlayers` 只移走一半

`validateRallyEntry` 檢查 `type` 在 enum 內、`num` 是 0 至 14 的整數、`win` 是 boolean、`score` 是數字。**四條都在回答「這個值真的是它宣稱的型別嗎」**，之所以需要在執行期問，只因為 TypeScript 的型別被抹除而 JSON 沒有型別。真正的排球規則長這樣：「後排球員不得記錄前排攻擊」——`validateRallyEntry` 裡一條都沒有。所以它整個落在第一問，屬邊界。

`validateLineupPlayers` 是兩件事黏在一起：

```ts
// (a) 型別重建：lineup 是物件、三個陣列都在
if (lineup == null || !Array.isArray(lineup.starting) ...) throw
// (b) 領域規則：被指名的球員必須在這支隊伍的名單上
for (const id of referencedIds) if (!rosterIds.has(id)) throw
```

(a) 的註解自承它存在的理由是「lineup 未經驗證就從 request body 進來」——**本 Change 之後那句話就是假的**，所以它跟著走。(b) 換掉 HTTP、換掉 MongoDB 都仍然成立，是第二問的典型例子；它需要的名單由 use case 傳入，entity 自己不查詢。

### 這是執行既有決策，不是推翻它

`rally-entry-validation` 的 D2 記了一條 revisit trigger：

> route 層的 request schema 上線之後，重新確認兩層驗證的分工：邊界回答「形狀對不對」，entity 回答「意義對不對」，**兩者不應互相複製**。

本 Change 就是那個觸發點。兩份已晉升的 D26 記錄（`game-recording/rally-recording` 與 `game-recording/persistence`）與 `platform/clean-architecture` 的一條 Known gap 需要在 Archive 時標記 superseded 或改寫。

### 一個看起來被解開、其實沒有的結

跨欄位自洽檢查（`scoringMoves[num]` 的 `type` / `win` 與存的一致、`away.num` 在 `outcome` 內）卡在一個前置條件：entities 不能 import `src/lib/scoring-moves.ts`，因為該檔 `import { MoveType } from "@/entities/game"`，反向會成環。所以它必須等整張表下沉到 entities。

schema 住在 `src/interface/validations/`，相依方向 `interface → lib → entities` 是一條直線，所以把那個檢查放進 `.refine()` **技術上做得到**。本 Change 一度打算這麼做，理由是它同樣只需查表。

**但那是撤回的判準在說話。** 依第二問，「主隊扣球得分時，客隊那一側只可能是這幾種動作」是排球規則，換掉傳輸與儲存都成立——它屬 entity。技術上放得進 schema，不代表它該放在那裡。**所以那個結沒有被解開，`scoringMoves` 的下沉仍然是它的前置。**

被真正解開的只有一件小事：`num` 的上界。它不是規則，是「合法索引的範圍」——型別重建的一部分——所以改用 `scoringMoves.length - 1` 由 schema 取得，手抄的 `LAST_SCORING_MOVE = 14` 與釘住它的測試一併消失。

## Contracts

- **錯誤形狀不變。** `withErrorHandler` 既有的 `ZodError → ValidationError` 映射照舊，客戶端拿到 `code: "VALIDATION"`、`reason: "INVALID_INPUT"` 與帶欄位路徑的 `details`。本 Change 不新增錯誤碼。
- **body parse 在 `teamId` 查詢參數檢查之後。** `POST /api/games` 缺 `teamId` 時仍回 `detail: "teamId is required"`，既有斷言不變。
- **schema 是 usecase input 的下游。** `satisfies z.ZodType<IXInput["data"]>` 由 schema 端宣告，方向 `interface → application`。usecase 不得反向 import schema 的型別。
- **`UpdatePlayerRoleSchema` 的 wire 欄位維持 `role`**，由 route 映射到 usecase 的 `newRole`。對外契約不遷就內部參數名。
- **`LineupSchema` 是唯一的 lineup 定義（server 端）。** 由 `src/interface/validations/team.ts` 匯出，同時供 `PATCH /teams/:id/lineups` 與 `POST/PUT /games/:id/sets` 使用。它是三份 lineup 定義裡唯一拒絕空字串的那一份。

## Testing strategy

三層，各證明不同的事。

**schema 單元測試——證明規則本身正確。** 欄位規則、範圍、`.strict()` 拒絕未宣告欄位。

**route 接線測試（backend-unit，無資料庫）——證明 schema 真的被掛上。** 每條路由送畸形 body，斷言 400 **且 controller 未被呼叫**。這一層不可省：`rally-entry-validation` 記下的教訓是「單元測試證明它會拒絕，證明不了有人在該拒絕時呼叫它」，而 `validatePlayerStatus` 有 11 個全綠測試卻零生產呼叫端。跑在 `pnpm test`，CI 每次都跑。

**integration 測試——證明拒絕時什麼都沒寫進去。** 只涵蓋 game 的五條寫入路徑，那裡的風險不只是拒絕，還有部分寫入。

**真實 payload 測試——證明沒打壞既有流程。** 6 條 retrofit `.strict()` 的路由，每條都要餵 client 實際建構的 payload。手寫的最小物件永遠會通過，`players[].list` 與 `info.teams` 就是這樣活下來的。`test/integration/game-rally-from-created-game.itest.ts` 已經是 game 這條的釘子，更新它而不是另建。

`test/integration/rally-validation.itest.ts` 的三個案例在 D3 之後**原封不動仍會通過**——zod 對缺欄位、超出 enum、缺 `win` 產生同樣的 400 與 `CommonReason.INVALID_INPUT`。它斷言的是可觀察行為，不是實作。

## 交付前的最後一項：`""` 映射為 `null`

開發者在 Blueprint Review 之前追問了一件 Overview 原本打算延後的事：邊界既然接受 `player.id: ""`，把它轉成 `null` 是不是更正確？

是，而且這個 repo 已經自己說了三次——lineup 用 `nullableObjectId`、`toPlayerRef` 回傳 `null`、`deriveSetStats` 讀到的型別本來就是 `{ id?: string | null }`。只有 `RallyDetail.player.id: string` 跟其他三處不一致，是與 `Team` 同一類的型別謊言，而消滅型別謊言正是本 Change 的前提（「如果那個型別本身在說謊，加 schema 只是把謊言正式化」）。

實測成本：把該欄位改成 `string | null` 之後 `tsc` 零錯誤——所有消費端都是 `Boolean(...)` 或 `if (scorerId && ...)` 這類真值判斷，`""` 與 `null` 走同一條路。實際改動三處：entity 型別、`rallyPlayerId` 加 `.transform`、schema 測試改為斷言轉換結果而非僅斷言接受。

**這不是 D4 禁止的 coercion。** 它與 `z.iso.datetime().transform(...)` 同類：先拒絕既不是 `""` 也不是 ObjectId 的值，再把通過的合法輸入映射到 domain 表示；`z.coerce.*` 則會靜默吞下垃圾。Redux draft 繼續送 `""`，由邊界吸收這個 wire format 的怪癖。

Overview 原本寫著「把這個佔位值換成 `null` 是另一張票的事」，該句已刪除。

## 三輪 review 沒抓到的東西

兩個生產缺陷，都是開發者手動操作發現的。

### 回歸一：陣容編輯頁存不了

調整替補名單後儲存回 400。

`lineupSchema` 是 team mongoose schema 裡**唯一沒有 `{ _id: false }`** 的 sub-schema，所以每份 lineup 都帶著自己的 `_id`。`team.repository.mongo.ts` 的 `toTeam` 用 `...lineup` 展開，那個 `_id` 於是進入 API 回應、進入 Redux，再被 `PATCH /api/teams/:id/lineups` 原樣送回——撞上新的 `.strict()`，400。

這與 #7 是**同一個缺陷的兩個實例**。S04 期間在 `game.repository.mongo.ts` 修掉了 `toLineupRead`，卻沒有去看 team 那一份，因為當時是從 game 的 `.strict()` 失敗反推回去的，不是從「哪些讀取路徑會被原樣送回」正面盤點。

修法相同：列出具名欄位。真正的問題是先前沒有任何東西表達這條不變式，所以補上 `test/integration/lineup-read-is-a-legal-request.itest.ts`——它把讀到的 lineup 直接餵回它自己的 request schema，team 與 game 兩條路徑各一個案例。**已做突變檢驗**：把任一條改回 `...lineup`，對應的案例就轉紅。

這件事也修正了 Testing strategy 的一個盲點：「餵 client 實際建構的 payload」擋不住這類缺陷，因為 payload 本身是**伺服器發給 client 的**。read 與 write 的往返才是那條不變式。

### 回歸二：新增比賽建不了

對手名稱留白時送出，回 400 `操作失敗：資料格式不正確`。

`AwayTeamSchema` 繼承的 `name: z.string().min(1)` 是本 Change 憑空加上的約束——`entities/game.ts` 的 `Team.name` 只是 `string`，沒有下限；表單的對手名稱欄位沒有預設值也沒有必填標記。移除該 `.min(1)`。

而本該擋下它的測試，`game-rally-from-created-game.itest.ts` 的 `newGameBody()` 註解寫著「這是 `NewGameForm.createGame` 實際送出的 body」，卻在表單唯一會留白的那個欄位上手填了 `"Away"`。

### 兩者共同的教訓

S02 的驗收條件要求「餵入該路由的 client **實際建構的** payload（取自對應的表單或 hook，不是手寫的最小物件）」。實際交付的是**人工抄寫**的物件加上一句「這是實際 payload」的註解——抄寫者在抄的時候，抄的是自己以為的樣子。

`draft-passes-validation.test.ts` 是唯一做對的那個：它驅動**真的 Redux store**，讓真正的 producer 產生 payload，再拿伺服器的 schema 當斷言。rally 那條路徑從頭到尾沒出過事。

所以補上同形式的測試，每一條有 client producer 的寫入路徑各一個：

| 路徑                                            | producer                             | 測試                                               |
| ----------------------------------------------- | ------------------------------------ | -------------------------------------------------- |
| `PUT /sets/rallies`                             | Redux entry draft                    | `draft-passes-validation`（既有）                  |
| `POST /api/games`                               | 新增比賽表單                         | `new-game-form.ts` + `form-passes-validation`      |
| `POST`/`PUT /sets`                              | set-options 表單                     | 同上                                               |
| `PATCH /teams/:id/lineups`                      | Redux lineup slice                   | `lineup-passes-validation`                         |
| `POST`/`PATCH /api/teams`                       | team 表單                            | `components/team/__tests__/form-passes-validation` |
| `POST /teams/:id/players`、`PATCH /players/:id` | 表單 resolver **就是** server schema | 不需要——不一致在型別上不可能                       |

`POST /api/games` 那條在補測試時立刻抓到第二個還沒爆的不一致：`SetOptionsFormSchema` 的 `time.start`/`time.end` 是選填，而 `Set.options.time` 兩者必填。想放寬伺服器時 `satisfies` 直接編譯失敗——**entity 是仲裁者**，所以收緊 client。

### 為什麼「餵真實 payload」這條驗收條件擋不住它自己

它把「真實」交給撰寫者的自覺。人工抄寫必然抄成自己理解的樣子，而理解錯誤正是缺陷的來源。唯一可靠的形式是**讓產生 payload 的那段程式碼自己去產生**——它做不到的地方（component 內的 inline 物件字面值），這條驗收條件本來就不該宣稱它做得到。

| `role` → `newRole` 重新命名       | `membership-section.tsx` 送的是 `role`；改名會弄壞它，也會把對外欄位彎成內部名稱                                         | 撤回，改由 route 映射 |

**D3 的判準在 Propose 之後、Apply 之前被替換過。**原本的「它需要資料庫裡的狀態嗎」不是乾淨架構的分界——`away.num ∈ outcome` 是無狀態卻是排球規則，「這個 gameId 存在嗎」是有狀態卻只是 404。改成兩個有序問題：**這是在重建型別，還是在判斷領域規則？** design.mdx 保留「一個被撤回的判準」一節記錄這件事。

## Residual risks

- **route 層驗證是過渡狀態。** D1 承諾終局是 controller 成為 interface adapter，由 `api-route-restructure` 承接。在那之前，「邊界是唯一入口」這個前提靠 review 把關，沒有工具強制——`src/lib/` 仍混著三個層的程式碼，任何以路徑判層的 lint 規則都還無法表達。
- **`.strict()` 對向後相容的假設。** 目前前後端同時發布，所以拒絕未宣告欄位是安全的。兩者一旦拆開發布，舊 client 多送一個欄位就會拿到 400。已列為 revisit trigger。
- **舊 game 文件缺 `teams.home.players` 時的錯誤語意不精確。** usecase 以 `?? []` 承接，所以缺席的名單會表現成一份空名單，錯誤在 lineup 比對時才以「球員不在名單上」的 400 現身。本 Change 之後建立的比賽不會有這個狀態（`HomeTeamSchema` 要求 `players`），舊資料則沒有偵測手段。
- **`.strict()` 的往返不變式只有兩條路徑被證明。** 新的整合測試涵蓋 team 與 game 的 lineup。任何其他「讀取值會被 client 原樣送回」的欄位若也帶著 Mongoose 的 `_id`，會以同樣的方式失敗。`lineupSchema` 是目前唯一缺 `{ _id: false }` 的 sub-schema，但那是巡過一次的結論，不是工具保證的。
- **收斂只做到 server 端。** `src/interface/validations/` 現在是一個領域一個檔、命名一致的請求契約家。client 端沒有同等待遇：`lib/features/{game,team}/types.ts` 一個檔同時裝著 20 個 `XxxResponseSchema` 與 2 個 `XxxFormSchema`，而三個字尾（`Schema` / `ResponseSchema` / `FormSchema`）代表三種不同的概念，卻沒有任何地方寫下這個慣例。本 Change 只動了那個檔 14 行，拆它不在範圍內——但「請求驗證有一套可指認的做法」這條 Goal，在 client 端並不成立。
- **`away` 的選填欄位是暫時的。** 隊伍查詢與資料分享功能上線後，away 會承載與 home 幾乎相同的結構，D5 的選填欄位會被填滿。
